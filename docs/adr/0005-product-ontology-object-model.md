# ADR 0005: 产品本体对象模型

- 状态: proposed
- 日期: 2026-09-05
- 角色: Alex Lee（评审/裁决），AI agent（起草）

## Context

ADR 0001 §2 裁定"产品本体是统一的 agent 协作契约"：agent 对文件的读写、待裁决的变更、对话与选区的锚定关系，都是一等 UI 对象。但该裁定只声明了契约的存在，没有定义契约的对象模型——哪些对象是一等的、各自的语义边界是什么、谁拥有谁。没有这层定义，后续所有功能 spec（编辑点、变更审批、Thread 导航、Session 管理）都会各自发明术语，契约无从统一。

本 ADR 的素材来自 PRODUCT-CONCEPT.md（仓库根目录，v0.1，头脑风暴产物，其自身声明"不作为结论"）。tower 已对 concept 文档做独立分析并与 Alex 对齐采纳边界；本 ADR 记录对齐后的裁决对象模型，不是 concept 文档的复述。concept 文档保持原位，其归档方式由 Alex 另行决定；本 ADR 引用其路径与节号（PRODUCT-CONCEPT.md §N）作为溯源。

与既有 ADR 的关系：本 ADR 是 ADR 0001 §2 的具体化，**不 supersede 0001**；对"极致快"的阐释（见 Decision §4）是对 0001 §5 / 0002 §6 既有合同的适用说明，**不修订**任何性能数字或门禁口径。

## Decision

### 1. 四个一等对象

产品本体由四个一等对象构成，外加一个既有概念（Workspace/文件）作为事实空间基底：

```text
文件 / Workspace   事实空间（source of truth，不是本 ADR 定义的对象）
Thread             意图空间
Session            运行时实例（Agent 的上下文空间）
编辑点             一次性认知事务
变更批次           协作执行记录
```

**与 ADR 0001 §2 的映射**：0001 §2 列举的三项一等 UI 对象在本模型中的归属——「待裁决的变更」即变更批次；「对话与选区的锚定关系」即编辑点（语义锚点是编辑点的固有属性）；「agent 对文件的读写」拆为两条路径——写路径落到变更批次，读路径**不是**一等对象：读是 Workspace/文件层的底层能力（Agent 在 Workspace 边界内查找、读取文件），不产生需要裁决或回滚的状态，故不设独立对象。权限/审批/回滚语义只挂在变更批次上是足够的：本模型中所有写路径都经委派产生批次（Agent 不得绕开批次写文件，见 §5），编辑点是意图对象而非变更、不产生文件写，人自己的手动编辑无需审批；因此批次是写路径的唯一闸门，无遗漏面。

### 2. Thread（意图空间）

**定义**：Thread 是显式的一等导航对象，代表"我正在用这些材料，与 Agent 一起完成什么"。它承载工作目标、阅读集合（关联文件及其在当前 Thread 内的角色）、Thread brief、编辑点集合、变更批次集合，以及一个或多个 Session。

**不是什么**：

- Thread **不是文件夹**：它对文件只做引用，不做包含；文件角色（主文档/参考材料/草稿等）只属于当前 Thread，不改变文件本身。
- Thread **不拥有文件**：同一文件可被多个 Thread 以不同角色同时引用；删除 Thread 不触碰任何文件。
- Thread **不是项目管理器**：Thread 首页的用途是恢复协作上下文（目标、状态、开放编辑点、最近判断），不是任务看板。
- Thread **不强制有主文档**：纯阅读/研究 Thread 成立，不强制产出正文。

**生命周期**：`进行中 / 暂停 / 完成 / 归档`，不因长期无活动自动删除。目标改变时创建新 Thread（分叉），新 Thread 可选带入文件、术语和已确认结论，默认不带入旧 Thread 的聊天历史、未解决编辑点和临时目标。

### 3. Session（运行时实例）

**定义**：Session 是 Agent 的运行实例，拥有独立 context window、Agent/模型绑定、工具权限、对话历史和当前运行状态。

**与 Thread 的关系**：Thread 是产品层的持续工作容器，Session 是运行时实例，两者**不等同**。每个 Thread 默认拥有独立 Session；Session 失效、上下文过长或更换 Agent 时，依据 Thread brief 重建新 Session（重建语义见 Consequences §代价与风险）。

**不是什么**：Session **不是协作历史的载体**——协作的连续性是 Thread 的属性，Session 可弃可重建；Session 也不跨 Thread 共享。

### 4. 编辑点（一次性认知事务）

**定义**：编辑点是一次性的认知事务——开始于阅读中的认知摩擦，结束于人认为摩擦消解并归档。它记录原始引用、文件与位置、用户意图（自然语言）、语义锚点、所属 Thread 和 Session。创建方式是选中原文后直接用自然语言描述意图，用户不必先选意图类型。编辑点默认不插入正文，不污染 Markdown 文件。

**生命周期**：

```text
开放 → 处理中 → 待回看 → 已解决 → 归档
```

**关键语义**：

- **完成条件是人认为这次阅读摩擦已经消解，不是 Agent 返回，也不是文件已改变。** 一个编辑点可以经历多轮对话和多次修改；也可以只得到解释、不修改正文即告解决。
- 归档后编辑点默认从正文界面消失，不再进入待处理列表，也不自动作为未来上下文注入；其对话、解释和修改历史保留可查。

**不是什么**：编辑点**不是批注/评论**（批注以正文为家，编辑点以事务为家，事务关闭即从正文消失）；编辑点**不是聊天消息**（聊天是 Session 的过程记录，编辑点是有明确完成条件的事务对象）。

### 5. 变更批次（协作执行记录）

**定义**：一次委派对应一个变更批次。批次记录目标、授权范围、Thread、Session、修改的文件与位置、关联编辑点、修改原因、原文与新文、时间、冲突状态。跨文件修改作为一个完整批次呈现。

**关键语义**：

- 授权边界由委派声明决定，不由修改大小决定；Agent 不得因局部授权扩大到整篇文章或整个 Workspace。
- 变更展示不止 Diff，必须回答三个问题：改了什么、为什么改、有什么影响或代价。
- 回看默认按编辑点进行（解释优先：你的问题 → Agent 的解释 → 做了什么修改 → 影响或代价 → 跳到真实正文），也支持按文件回看。
- **协作底线**：委派基于明确文件版本，版本未变化时应用、变化时暂停；不安全合并时不静默覆盖，提供重新处理、独立候选、差异查看和手动协调。**未接入 Lumir 协作协议的外部 Agent 直接改盘时，不产生变更批次、不伪造协作状态**——此类修改按外部文件修改检测呈现为冲突状态，由人裁决，不得倒填为某个批次的执行记录。

**不是什么**：变更批次**不是 git commit 的替代品**——它是协作层的审计记录，不接管版本管理职责；批次**不可被 Agent 静默追加**——不静默覆盖人的同期编辑，版本变化时暂停而非合并。

### 6. 分层：M2 最小循环 vs v1 MVP

本对象模型是 v1 的完整目标，不是 M2 的范围扩张：

- **M2 出口不变**：ADR 0004 锁定的 M2 出口仍是"完成一次完整的选中→对话→agent 改文件→裁决"循环。该循环只要求编辑点、单次委派、变更审批/回滚的最小可用形态，不要求 Thread 导航、变更批次完整呈现、Session 重建。
- **v1 MVP 锚定**：PRODUCT-CONCEPT.md §17 的 19 项是 v1 的目标清单，其中 Thread 持久化、多文件阅读集合、解释优先逐点回看、变更批次记录、编辑点归档等条目是本对象模型的功能化。MVP 锚定为 v1 目标，**不回灌为 M2 出口标准**。
- **记忆分层（个人偏好 / Workspace / Thread / Session，PRODUCT-CONCEPT.md §9）显式标注为 v1+**：v1 及之前不承诺任何跨 Session 记忆能力，agent 可用的上下文以当次委派的显式注入为限。

### 7. "极致快"口径澄清

PRODUCT-CONCEPT.md §4/§16 将"极致快"列为"第一版可以暂时弱一些"的项，容易被误读为性能合同松动。澄清口径：

- **本地编辑循环不被 Agent 阻塞是合同义务，不是可弱化项**：输入、选择、导航、撤销、阅读的响应性由 ADR 0002 §6 的四个数字锁定（冷启动 <300ms、keypress-to-paint <16ms、打开 1MB 文件 <100ms、常驻内存 <200MB），Agent 任务的执行不得侵蚀这些指标。
- **Agent 执行、索引构建、跨文件分析异步运行，可以慢**：这些路径不在性能合同内，其耗时是产品体验问题而非合同违约。

这是对 ADR 0001 §5「极致快由 ADR 0002 的性能合同量化」的适用阐释，不是修订：concept 文档中"极致快可以暂时弱一些"的表述，按上述拆分理解——可弱的只是合同之外的异步路径，合同之内的本地编辑循环没有"暂时弱"的余地。

## Consequences

### 正面

- ADR 0001 §2 的"协作契约"从此有可引用的对象清单与语义边界，后续功能 spec（编辑点、变更审批、Thread 导航）有统一的术语基础，不再各自发明。
- 每个对象的"不是什么"预先排除了一类设计漂移（Thread 滑向文件夹/项目管理器、编辑点滑向批注、Session 滑向历史载体）。
- M2 与 v1 MVP 显式分层后，concept 文档的 19 项清单不再构成对 13 周时间盒（ADR 0004）的范围压力。
- "极致快"口径澄清后，性能合同的保护范围与 concept 文档的措辞差异被消除，ADR 0002 的四个数字无任何松动。

### 代价与风险（三个技术判断）

1. **锚点漂移是本模型成立的技术先验。** 编辑点锚定在"文件+位置"上，而文件会被人和 Agent 持续修改，锚点必然漂移。模型成立的前提是漂移可管理，这不是设计偏好而是生存条件。因此 **M2 的第一个原型任务不是 UI，而是锚点机制**：offset + 上下文指纹 + 漂移降级策略（指纹匹配失败时如何降级呈现、如何请求人重新定位）。该原型若证明锚点无法稳定，触发 revisit（见下）。
2. **Session 重建是 brief 注入的 prompt 工程，不是真恢复。** Thread brief 注入新 Session 后，新 Agent 读到的是一份摘要，不是旧 Session 的认知状态；重建质量完全取决于 brief 的写作质量。**brief 质量是隐性成本中心**：它不出现在任何功能清单里，却直接决定"Session 可弃可重建"这一架构承诺是否兑现。v1 需要为 brief 的生成/维护投入不成比例的关注，且应预期早期用户体验在此处打折。
3. **PRODUCT-CONCEPT.md §18 的 11 条假设落成 M3 dogfood checklist。** 这 11 条（Thread 是否优于文件列表、用户是否长期维护工作目标、原地编辑点是否更自然、是否积累多个编辑点、解释优先直接改正文是否可信、变更批次是否可回顾可撤销、brief 能否恢复上下文、新旧 Thread 边界是否清楚、多文件阅读集合是否更有价值、跨文件结论能否回到原文、用户是否视 Agent 为熟悉自己的编辑）逐条进入 M3 dogfood checklist，dogfood 期间逐条打分（成立/不成立/证据不足）。该 checklist 作为 M3 出口标准（ADR 0004：连续两周替代 Obsidian）的细化判据——两周替代是必要条件，11 条打分是诊断依据；多条"不成立"即使两周出口达成，也应触发本 ADR 相应对象的 revisit。

### 其他代价

- 四个一等对象意味着四套状态持久化与生命周期管理，实现面显著大于"聊天侧边栏"形态——这是 ADR 0001 §2 已接受的代价，本 ADR 使其具体化。
- v1+ 的记忆分层当前无任何实现承诺，相关体验（"编辑认识你"）在 v1 内不兑现，对外表述需克制。

## Revisit 条件

- **锚点机制原型（M2 第一个原型）证明锚点无法稳定**（指纹匹配失败率过高、降级体验不可接受）→ 重估编辑点对象模型本身，包括"编辑点锚定原文位置"这一核心语义。
- **M3 dogfood 证明 Thread 容器多余**（checklist 第 1、2 条均不成立：用户不维护 Thread 目标，文件列表已够用）→ 模型退化为无 Thread 的编辑点模型，Thread 相关语义整体移除。
- PRODUCT-CONCEPT.md §18 checklist 中其他条目大面积不成立 → 按条目对应到具体对象，定向 revisit 该对象的语义，不整体推翻本 ADR。
