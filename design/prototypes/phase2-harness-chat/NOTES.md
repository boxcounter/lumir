## 第四轮需求原文（Alex 2026-10-06，verbatim）

> 「有没有办法让摘录胶囊之间可以输入内容？比如我摘录了一段，然后输入我的问题『这段内容是什么意思？』，然后我摘录另一段，然后输入我的问题『这里的 XXX 是指什么？』。这样的目的是让每个问题的目标（针对哪条摘录胶囊）更明确。如果无法实现这样的效果，就需要别的方案来实现针对性，比如每个胶囊有一个可见的编号，我的问题里需要明确说『摘录#1是什么意思？』。这个编号不仅对人可见，还需要在 agent 对话里对 AI 明确可见。」

tower 判断（Alex 已读）：混排可实现（成熟模式：atomic chip，如 Slack/飞书引用块、Notion mention），采纳混排 + 保留小号 #N 编号用于后续轮次引用与 AI 序列化——主路径与备选编号两个方案合并交付。

## 关键设计决策（第四轮）

1. **composer 改混排编辑区，胶囊是原子 chip。** 屏 5 的 composer 从「胶囊条 + 纯文本框」改为单个 contenteditable 编辑区：胶囊是 `contenteditable=false` 的不可拆分内联节点（删除/选择都按整体作用），光标可在任意胶囊前后继续输入。演示序列为完整交错：chip#1 → 「这段内容是什么意思？」 → chip#2 → 「这里的「可执行动作」指什么？」。其余屏（4/6-10）的 composer 沿用原 textarea，本屏隐藏。
2. **chip 形态从块级胶囊改为内联胶囊。** 一颗 chip = 引号 glyph + 小号编号 **#N** + 文档名（等宽）+（composer 内）× 移除钮。标题锚点与摘录原文不再内联展示，由 title 悬停提示与开发者预览（决策 4）承载——内联节点必须控制宽度，否则无法嵌在文字流里。旧块级 `.cap` 与胶囊条 `.h-caps` 全量移除并进 verify 残留断言。
3. **#N 编号对人、对 AI 一致可见。** 编号按**文档顺序**（消息内 chip 的阅读顺序）生成，线性操作流程中与插入顺序一致；中途插入新胶囊时其后胶囊自动重编号，保证「编号 = 阅读顺序 = 序列化顺序」三者永远一致。编号四处呈现：composer chip、transcript 用户消息 chip、agent 作答（「摘录#1 的…／摘录#2 里的…」）、序列化预览（`[摘录 #1]`）。
4. **开发者预览证明编号与交错对 AI 可见。** composer 上方常驻一块「开发者预览 · 发给模型的序列化消息」，JS 实时把草稿序列化为纯文本：每颗 chip 展开为 `[摘录 #N] 文档名 · 标题锚点` + `「摘录原文」` 两行，问题文字按原交错顺序排布。编辑文字、插入/移除胶囊都即时反映——这是「AI 看到的就是这个」的直接证据。原型里常驻是为了评审；实现期应为 debug 开关而非默认 UI（见观感裁决点）。
5. **摘录手势不变，插入点改为当前光标。** 仍是正文选中 → 浮动「摘录到对话」钮；差别在新胶囊插入**光标处**而非追加到末尾（点击按钮会夺走焦点，实现上平时用 `selectionchange` 记下编辑器内最后选区，点击时恢复并在该处 `insertNode`）。本原型这条链路是真交互，可直接在页面试：在编辑区点出光标 → 点「摘录到对话」→ 新 chip 落在光标处并重编号，预览同步更新。
6. **第三轮决策 6 的 composer 部分被本轮取代**（「胶囊条 + 预填文本」→ 混排编辑区）；其 transcript 部分由「块级胶囊附件 + 合并问题」改为「chip 交错消息 + agent 按编号分条作答」。编辑器侧两个瞬态摆拍（q1 跳回高亮、q2 选区 + 浮动钮）不变。

## 实现期选型提示（混排编辑器，非裁决）

- **本原型用原生 contenteditable + `contenteditable=false` 原子 span。** 成本最低、语义直接，但 contenteditable 的已知坑实现期必须正面处理：粘贴净化（拖进富文本会污染结构）、IME 组合态与原子节点的交互、撤销栈（浏览器自带 undo 对 DOM 干预不可靠）、跨浏览器序列化差异（换行产生 `<div>`/`<br>` 不一）。
- **候选替代：复用 CodeMirror 6。** 仓库编辑器已是 CM6（ADR 0002），composer 可用一个轻量 CM6 实例 + atomic ranges / widget decoration 实现 chip——避开 contenteditable 全部 quirks，与主编辑器同一套键位/扩展心智；代价是 composer 变重，且「看起来像输入框的 CM6」需要重做样式与无障碍属性。
- **不建议**：textarea + 覆盖层渲染（编辑态与显示态分离，光标/选中/IME 全要自己追，复杂度被低估的重灾区）。
- 倾向性建议：MVP 若只有 chip 这一种原子节点，contenteditable 可接受并把粘贴/IME 两条写进验收；若 composer 预期长出更多富交互（斜杠命令、@引用、建议列表），直接上 CM6，一次到位。

## 遗留观感裁决点（给 Alex）

1. **chip 宽度与信息密度**：当前只显示 #N + 文档名（约 180px），锚点进 title。若觉得「哪一段」不够一眼可辨，备选是 #N + 锚点（舍文档名）或两行高 chip（破坏行高节奏）。
2. **transcript 混排观感**：已发送消息里 chip 与文字交错（不再是块级附件），长问题 + 多 chip 时换行较碎（346px 窄 pane 实证一屏两行半）——是否接受，还是 transcript 沉淀时改回块级附件 + 文中 `摘录#N` 引用。
3. **开发者预览的归属**：原型常驻仅为评审证据；实现期建议收进 debug 开关（或 ⌥ 点击发送预览），不进默认 UI——请裁决。
4. **编号作用域**：本原型按「消息内序号」（每条消息从 #1 起）。若希望跨消息延续（会话内单调递增，便于「摘录#3 那段再展开」这类后续轮次引用），实现期改编号策略即可，交互不变——请裁决。
5. **中途插入触发重编号**：在 chip#1 前插入新胶囊会把旧 #1 变成 #2。已发送消息不受影响（历史消息编号冻结），仅草稿内重排——若观感困扰可改「按插入顺序、允许乱序编号」，但会破坏编号=阅读顺序的一致性。

## 关键设计决策（第三轮）

1. **pin 机制全量移除（Alex 裁决：「我认为 pin 是一个糟糕的设计，我不需要」）。** 编辑器侧装饰（左边线 + tint 底 + 行尾图钉 + hover 图钉钮）、composer 上方排队 pin 卡片、transcript 的 att-pin 附件、全部 pin 文案，零残留；`verify.mjs` 对全部 60 个组合加了 pin 残留结构断言防回潮。第二轮决策 4 与「沿用的第一轮决策」中的 pin 条目同步废止。
2. **摘录胶囊是替代机制（Alex 第三个方案，采纳胶囊形态）。** 选中正文片段 → 浮动「摘录到对话」钮 → 胶囊进入 composer 编辑框内（输入框上方）：一颗胶囊 = 引号 glyph + 文档名 + 标题锚点 + 短摘录 + 移除 ×。**点击胶囊在正文跳转到原位置并瞬态高亮**（Alex 点名的核心收益；本原型做了真交互：composer 与 transcript 里的胶囊都可点，jump + 1.4s flash 消退）。多胶囊在一条 composer 里累积、随一条消息一次发出——原需求 4「一次发多个」由「一条消息挂多颗胶囊」承接。发送后沉淀：用户消息携其胶囊（可继续点击跳回），agent 分条作答（屏 5）。与 pin 的本质区别：编辑器侧**零常驻装饰**，只有两种瞬态——进行中的选区、点击胶囊后的跳回高亮。
3. **harness 顶栏并入窗口标题栏（Alex 点子 1）。** harness pane 本体不再有头部栏；会话身份（可点出会话列表）+ 新会话钮构成标题栏的 **harness 段**（`.h-seg`），与编辑器 pane 的标签段同构——harness 在场时才出现，与标签段按 2:1 分宽（镜像 pane 宽度比），段边界近似对齐 pane 分隔条。会话列表浮层（屏 7）改从标题栏的会话名下拉展开。
4. **产品名 + 版本移到标题栏最左（Alex 点子 2）。** 「Lumir 0.2.0」放进 traffic-light 空位内、紧跟三颗系统按钮；标题栏右端原位置只留 harness toggle。
5. **ctx% 移进 composer 控制行（Alex 点子 3）。** 读数放在模型 / 思考程度 chip 之后、发送钮之前；黄色高亮（高用量）与 ⓘ info 气泡行为不变，气泡改为向上展开、右缘对齐读数右缘（防 346px 窄 pane 横向溢出，本轮实证修过一轮）。屏 6 摆拍 86% + 气泡展开态。
6. **屏 5 重做为多胶囊流。** 同屏讲完整故事：transcript 里一条已发送的消息挂两枚胶囊 + agent 分条作答；composer 里两枚待发胶囊 + 预填问题文本；编辑器里 q1 摆拍跳回高亮（pending-tint 黄，find-in-page 语义）、q2 摆拍选区 + 浮动「摘录到对话」钮（创建手势）。三个摆拍态都是瞬态的非常驻元素。

## 六条原则对照

- **内容即界面**：屏 1 正文占比与现行产品持平；harness 在场时正文仍是主 pane（2/3 宽）；编辑器侧无任何常驻装饰（pin 留痕已随机制移除）。
- **chrome 退后但不粗糙**：harness 本体头部栏整条消失（并入标题栏），chrome 总量净减；新增控件（胶囊、浮动摘录钮、浮层、info 钮、控制面板）全部有 hover/focus/过渡。
- **质感来自工艺**：除 accent 族中性化外零新色值、零渐变；圆角/字号/间距走既有 token 阶梯。
- **色彩克制且语义化**：彩色只剩 pending（用量警示 + 跳回高亮的 find-in-page 黄）+ ok（完成勾、已复制）；eink 全转明度/线宽/字重。
- **agent 可开可关**：屏 1-3 零 agent 痕迹（只留标题栏一颗 toggle 钮；harness 段随之不出现）。
- **对话是输入不是档案**：工具过程完成即折叠；胶囊是待发上下文与消息附件，不是编辑器留痕；agent 产出仍归提案队列（本原型不重设计，对话里只留一句指引）。

## 已知妥协点（诚实清单）

1. **红绿灯 / 窗口 chrome 是画在页面里的**（真实产品由系统绘制，且真实产品刻意不自绘），原型为自包含截图保留。
2. **屏 3 的拖拽态、屏 4 的工作态、屏 6 的说明气泡是静态摆拍**；屏 5 的选区 + 浮动钮、跳回高亮也是摆拍（但胶囊的点击跳回 + flash、「摘录到对话」在光标处插入 chip、× 移除重编号、序列化预览实时更新都是真交互，可直接在页面里点）。分隔条 hit area（5px）与抓柄形态供评审，手感归实现期。
3. **浮动「摘录到对话」钮是胶囊创建手势的建议形态，未经裁决**（备选：右键菜单、快捷键、selection 内联工具条）；其位置（选区右下）与触发时机归实现期定。
4. **跳回高亮借用 pending-tint（find-in-page 黄语义）**——与用量警示同族不同境，若评审觉得语义混淆，实现期可单立 token；eink 转 10% 黑。
5. **标题栏 harness 段与 pane 分隔条是近似对齐**（段按 2:1 flex 分宽，但标题栏右端还有 toggle 钮与 padding 占位，像素级差 ~30px）；真实产品若要做到像素对齐，需要装配层按 pane 实际宽度现算段宽（与现建第二标签段同一套路）。
6. **ctx 读数进 composer 控制行后，info 气泡向上展开会遮 transcript 末条消息**——气泡是瞬态覆盖层，真机 hover/点击才出现，非常驻遮挡；行内空间紧（模型 chip + 思考 chip + ctx + 发送 ≈ 346px 刚好放下），更长的模型名将挤压，实现期需给 chip 加 ellipsis 策略。
7. **会话列表浮层从标题栏展开后 z-index 压在 pane 之上**，摆拍态遮了 transcript 顶部一条消息——同为瞬态。
