## 关键设计决策（第五轮）

1. **inline chip → block 级引用卡片。** 一张卡片 = 引号竖条（3px 灰条）+ 摘录原文截断（`-webkit-line-clamp: 2`，最多两行）+ 小字出处行（等宽 `文档名 · 标题`）+（composer 内）× 移除钮。点击卡片跳回原文并瞬态高亮（四轮真交互保留）；hover title 显示完整摘录 + 出处。卡片在 composer 混排编辑区里是 `contenteditable=false` 的原子 block 节点，独占一块；问题文字在卡片之间的段落（`.qpara`）里，上下交替——演示序列保持 摘录1 + 问题1 + 摘录2 + 问题2。transcript 用户消息同构（卡片无 ×，已发送不可移除）。
2. **UI 全面去编号。** 卡片、transcript 用户消息、agent 回复文案里的 #N 全移除；agent 回复改按内容/出处回指（「『倒序阅读』那段」「『可执行动作』那段」）。verify 对全部 60 个组合加 `/#\d/` 渲染文本零残留断言。编号只剩两个不可见去向：DOM 的 `data-cap`（测试钩子）与序列化的 `index` 属性（AI 侧回指，Alex 裁决保留）。
3. **序列化预览改 XML。** 每段摘录序列化为 `<quote index="N" file="…" heading="…" lines="A-B">摘录原文</quote>` 一行；`lines` 必选（原型 fixture：q1 = `9-10`、q2 = `16-17`，模拟从选区捕获的行范围）；问题文字按交错顺序排布在标签之间；属性与文本做 XML 转义。编辑文字、插入/移除卡片即时刷新。index 按文档顺序从 1 严格递增——「index = 阅读顺序 = 序列化顺序」三者一致。
4. **预览块常驻标注「仅原型调试用途，不进产品」。** 落在 dp-label 文案里，verify 断言其在场。
5. **失锚降级链（实现期行为合同，原型记录备查）。** 点击卡片跳回 / 恢复上下文定位时：① 先按 `lines` 行号定位，并校验该处文本与摘录原文匹配；② 失配（文档已编辑、行号漂移）则在文档内搜索摘录原文字符串，命中即定位到命中处；③ 仍找不到则告知用户该摘录已失锚（不静默猜位置、不跳到错误段落）。三层逐级降级，每一层都有明确的失败出口。
6. **第四轮决策 2/3/4 被本轮取代**：内联 chip 形态 → block 卡片（决策 1）；#N 对人可见 → UI 去编号（决策 2）；`[摘录 #N]` 文本序列化 → XML `<quote>`（决策 3）。混排编辑区（contenteditable + 原子节点）、光标处插入手势、跳回高亮保留。

## 实现期提示（block 卡片 × contenteditable，非裁决）

- **卡片仍是原子节点，但从 inline 变 block**：`contenteditable=false` 的 `<div>` 独占一块，删除/选择按整体作用；与第四轮 inline chip 的差别在**插入语义**——block 卡片落在段落中间时须把光标所在段落从光标处拆成两段、卡片插中间（本原型 `splitText` + 重包 `.qpara` 实现），插入后光标落到卡片之后。
- **段落骨架**：编辑区顶层只出现两种子节点——`.qcard` 与 `.qpara`（问题段落）。用户回车产生的新块实现期须同样归一化为 `.qpara`，否则序列化的交错顺序会被裸 `<div>`/`<br>` 打乱（本原型序列化对裸文本/未知块做了宽容归并，但产品实现不应依赖宽容）。
- **序列化是单一真源**：卡片数据全在 `data-*` 属性（src/anchor/lines/ex），卡片 DOM 只负责渲染；序列化 walker 只认 `.qcard` 与文本。新增卡片种类时遵循同一约定。
- **lines 捕获**：选区 → 行范围的映射在真实编辑器里是 CM6 的 `lineAt(from)/lineAt(to)`；裁决已定 lines 必选，无选区（理论上不存在）时宁可不出卡片也不发空 lines。
- **失锚降级链的匹配校验**：行号定位后必须比对摘录原文（前缀匹配即可），防止文档编辑后行号指向错误段落却静默命中——第三层「告知失锚」是用户可见行为，需要 UI 形态（toast 或卡片内联态），本原型未设计，实现提案时补。
- 第四轮的 contenteditable 通用坑（粘贴净化、IME 组合态、撤销栈、跨浏览器序列化差异）与 CM6 替代方案评估照旧适用，见下「实现期选型提示（混排编辑器）」。

## 关键设计决策（第四轮，未被第五轮取代的部分）

1. **composer 改混排编辑区，胶囊是原子节点。** 屏 5 的 composer 从「胶囊条 + 纯文本框」改为单个 contenteditable 编辑区：胶囊是 `contenteditable=false` 的不可拆分节点（删除/选择都按整体作用），光标可在任意胶囊前后继续输入。演示序列为完整交错：摘录1 → 「这段内容是什么意思？」 → 摘录2 → 「这里的「可执行动作」指什么？」。其余屏（4/6-10）的 composer 沿用原 textarea，本屏隐藏。（第五轮变更：节点形态 inline chip → block 卡片，见五轮决策 1。）
2. **摘录手势不变，插入点改为当前光标。** 仍是正文选中 → 浮动「摘录到对话」钮；差别在新胶囊插入**光标处**而非追加到末尾（点击按钮会夺走焦点，实现上平时用 `selectionchange` 记下编辑器内最后选区，点击时恢复并在该处插入）。本原型这条链路是真交互，可直接在页面试：在编辑区点出光标 → 点「摘录到对话」→ 新卡片拆段落在光标处，预览同步更新。
3. **第三轮决策 6 的 composer 部分被第四轮取代**（「胶囊条 + 预填文本」→ 混排编辑区）；其 transcript 部分由「块级胶囊附件 + 合并问题」改为「卡片/问题交错消息 + agent 分条作答」。编辑器侧两个瞬态摆拍（q1 跳回高亮、q2 选区 + 浮动钮）不变。

## 实现期选型提示（混排编辑器，非裁决）

- **本原型用原生 contenteditable + `contenteditable=false` 原子节点。** 成本最低、语义直接，但 contenteditable 的已知坑实现期必须正面处理：粘贴净化（拖进富文本会污染结构）、IME 组合态与原子节点的交互、撤销栈（浏览器自带 undo 对 DOM 干预不可靠）、跨浏览器序列化差异（换行产生 `<div>`/`<br>` 不一）。
- **候选替代：复用 CodeMirror 6。** 仓库编辑器已是 CM6（ADR 0002），composer 可用一个轻量 CM6 实例 + atomic ranges / block widget decoration 实现卡片——避开 contenteditable 全部 quirks，与主编辑器同一套键位/扩展心智；block widget 天然契合卡片形态（比 inline widget 更稳）；代价是 composer 变重，且「看起来像输入框的 CM6」需要重做样式与无障碍属性。
- **不建议**：textarea + 覆盖层渲染（编辑态与显示态分离，光标/选中/IME 全要自己追，复杂度被低估的重灾区）。
- 倾向性建议：MVP 若只有卡片这一种原子节点，contenteditable 可接受并把粘贴/IME 两条写进验收；若 composer 预期长出更多富交互（斜杠命令、@引用、建议列表），直接上 CM6，一次到位。

## 遗留观感裁决点（给 Alex）

1. **卡片信息密度**：当前卡片显示两行摘录 + 出处行（文档名 · 标题），行号不进 UI（只在序列化 `lines` 属性）。若觉得出处行不够定位，备选是加 `· 第 9-10 行` 或 hover 卡片时正文侧同步预览。
2. **transcript 卡片观感**：已发送消息里卡片与问题段落上下交替，两张卡片 + 两个问题在 346px 窄 pane 约占一屏——是否接受，还是 transcript 沉淀时卡片折叠为单行（竖条 + 首行摘录）。
3. **index 的语义边界**：UI 去编号后，`index` 只对 AI 可见。若后续轮次用户想引用「第一张卡片那段」，agent 侧如何映射回 index（按消息内顺序推断）归实现期的 prompt 设计，原型不演示。
4. **失锚的 UI 形态**：降级链第三层「告知用户失锚」本原型只有行为合同、无视觉形态——toast、卡片内联警示、还是跳回时对话框，实现提案时补设计。

## 关键设计决策（第三轮）

1. **pin 机制全量移除（Alex 裁决：「我认为 pin 是一个糟糕的设计，我不需要」）。** 编辑器侧装饰（左边线 + tint 底 + 行尾图钉 + hover 图钉钮）、composer 上方排队 pin 卡片、transcript 的 att-pin 附件、全部 pin 文案，零残留；`verify.mjs` 对全部 60 个组合加了 pin 残留结构断言防回潮。第二轮决策 4 与「沿用的第一轮决策」中的 pin 条目同步废止。
2. **摘录胶囊是替代机制（Alex 第三个方案，采纳胶囊形态）。** 选中正文片段 → 浮动「摘录到对话」钮 → 胶囊进入 composer 编辑框内（输入框上方）：一颗胶囊 = 引号 glyph + 文档名 + 标题锚点 + 短摘录 + 移除 ×。**点击胶囊在正文跳转到原位置并瞬态高亮**（Alex 点名的核心收益；本原型做了真交互：composer 与 transcript 里的胶囊都可点，jump + 1.4s flash 消退）。多胶囊在一条 composer 里累积、随一条消息一次发出——原需求 4「一次发多个」由「一条消息挂多颗胶囊」承接。发送后沉淀：用户消息携其胶囊（可继续点击跳回），agent 分条作答（屏 5）。与 pin 的本质区别：编辑器侧**零常驻装饰**，只有两种瞬态——进行中的选区、点击胶囊后的跳回高亮。（第四轮：胶囊形态从块级改 inline chip；第五轮：再改 block 引用卡片，跳回/高亮/多挂载/瞬态语义全程不变。）
3. **harness 顶栏并入窗口标题栏（Alex 点子 1）。** harness pane 本体不再有头部栏；会话身份（可点出会话列表）+ 新会话钮构成标题栏的 **harness 段**（`.h-seg`），与编辑器 pane 的标签段同构——harness 在场时才出现，与标签段按 2:1 分宽（镜像 pane 宽度比），段边界近似对齐 pane 分隔条。会话列表浮层（屏 7）改从标题栏的会话名下拉展开。

## 六条原则对照

- **内容即界面**：屏 1 正文占比与现行产品持平；harness 在场时正文仍是主 pane（2/3 宽）；编辑器侧无任何常驻装饰（pin 留痕已随机制移除）。
- **chrome 退后但不粗糙**：harness 本体头部栏整条消失（并入标题栏），chrome 总量净减；新增控件（引用卡片、浮动摘录钮、浮层、info 钮、控制面板）全部有 hover/focus/过渡。
- **质感来自工艺**：除 accent 族中性化外零新色值、零渐变；圆角/字号/间距走既有 token 阶梯。
- **色彩克制且语义化**：彩色只剩 pending（用量警示 + 跳回高亮的 find-in-page 黄）+ ok（完成勾、已复制）；eink 全转明度/线宽/字重。
- **agent 可开可关**：屏 1-3 零 agent 痕迹（只留标题栏一颗 toggle 钮；harness 段随之不出现）。
- **对话是输入不是档案**：工具过程完成即折叠；引用卡片是待发上下文与消息附件，不是编辑器留痕；agent 产出仍归提案队列（本原型不重设计，对话里只留一句指引）。

## 已知妥协点（诚实清单）

1. **红绿灯 / 窗口 chrome 是画在页面里的**（真实产品由系统绘制，且真实产品刻意不自绘），原型为自包含截图保留。
2. **屏 3 的拖拽态、屏 4 的工作态、屏 6 的说明气泡是静态摆拍**；屏 5 的选区 + 浮动钮、跳回高亮也是摆拍（但卡片的点击跳回 + flash、「摘录到对话」在光标处拆段插入卡片、× 移除、XML 序列化预览实时更新都是真交互，可直接在页面里点）。分隔条 hit area（5px）与抓柄形态供评审，手感归实现期。
3. **浮动「摘录到对话」钮是胶囊创建手势的建议形态，未经裁决**（备选：右键菜单、快捷键、selection 内联工具条）；其位置（选区右下）与触发时机归实现期定。
4. **跳回高亮借用 pending-tint（find-in-page 黄语义）**——与用量警示同族不同境，若评审觉得语义混淆，实现期可单立 token；eink 转 10% 黑。
5. **标题栏 harness 段与 pane 分隔条是近似对齐**（段按 2:1 flex 分宽，但标题栏右端还有 toggle 钮与 padding 占位，像素级差 ~30px）；真实产品若要做到像素对齐，需要装配层按 pane 实际宽度现算段宽（与现建第二标签段同一套路）。
6. **ctx 读数进 composer 控制行后，info 气泡向上展开会遮 transcript 末条消息**——气泡是瞬态覆盖层，真机 hover/点击才出现，非常驻遮挡；行内空间紧（模型 chip + 思考 chip + ctx + 发送 ≈ 346px 刚好放下），更长的模型名将挤压，实现期需给 chip 加 ellipsis 策略。
7. **会话列表浮层从标题栏展开后 z-index 压在 pane 之上**，摆拍态遮了 transcript 顶部一条消息——同为瞬态。
8. **会话列表条目、摘录内容、文档正文是合成 fixture**（lines 行号 9-10 / 16-17 亦为合成值，仅演示行范围语义）；「⌘⇧N」「⌘⇧A」键位是本原型建议，未经裁决。
9. **accent 族中性灰阶是本原型建议值**，与现行 `src/style.css` 的蓝色 token 有出入——实现期改 token 是全局视觉变更，需走对应 change 流程；dark 下 accent-fill 反转为浅底深字，发送钮观感变化最大，Alex 过目时重点看屏 4/8 深色。
10. **dark / eink 全屏验证过不破版、对比达标，像素级细节没有逐一推敲**。
11. **提案队列不在本原型范围**；对话里「请在提案队列裁决」只是文案占位，队列形态沿用现状。
12. **「活跃编辑器 pane」暂无可见对应物**（第一版的 2px accent 线随去蓝取消，未另造中性形态）——ADR 0008 D3 的 selected window 语义在实现期需要一个可见表达，留作开放问题。三轮的胶囊 hint 已随胶囊条移除，但「摘录来自哪个 pane」的归属语义仍依赖它。
13. **「文档哪些段落已被讨论」的编辑器侧留痕随 pin 一并移除**（Alex 明确不要）；若日后想念这个信息，卡片跳转历史是唯一线索，不落编辑器。
14. **卡片摘录截断为两行**，完整摘录只能靠 hover title 查看——block 形态比四轮 inline chip 信息量已大增，但长摘录仍不可全文读；若两行不够，备选是点击卡片展开/收起（与跳回手势冲突，需另选触发位）。
15. **屏 5 与其余屏的 composer 是两套实现**（contenteditable 混排 vs textarea）——原型按屏切形态仅为分屏演示；真实产品里混排编辑区应是 composer 的唯一形态，无卡片时退化为纯文本输入，不存在两种输入框并存。
16. **agent 回复的按内容回指（「『倒序阅读』那段」）依赖摘录原文够短够独特**；长摘录或同一文档多段相似摘录时回指会变笨拙（「『先读结论再读论证——倒序阅读把大部分筛选成本压到…』那段」）——实现期 prompt 层用 index 消歧，UI 文案层截断引用，原型只演示短摘录的理想情形。
