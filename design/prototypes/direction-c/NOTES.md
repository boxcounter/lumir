# Direction C「驾驶舱」— 设计笔记

高保真静态原型，单文件自包含（CSS/JS 全内联，系统字体栈，无外部资源）。
切换方式：`?screen=1|2|3|4|5|6` × `?theme=light|dark|eink` × `?body=sans|serif` × `?composer=middle|bottom`。目标视口 1280×900。

## 屏 6 · Callout 样式（2026-09-24 迭代，D2 裁决落实）

callout 语义收敛（design-tokens-v1 v1.2 增补，节点 1 裁决 D2）的可视化验收屏：
13 个类型按五族语义色分组同屏陈列——蓝系 4（note/abstract/info/todo）、
绿系 2（tip/success）、琥珀系 2（question/warning）、红系 3（failure/danger/bug）、
灰系 2（example/quote）。骨架复用屏 1（agent 栏隐藏、strategy tab 激活），
正文换成 `#docCallouts`。样式形态 = 2px 左色条 + 族 tint 底色 + 标题行
（中文类型标签 650 / 英文类型名 550），刻意不引入图标：**同族的可区分性
全部压在标题行文字上**——红系「失败 / 危险 / 缺陷」三块同色，验证一眼
可辨。eink 下五族合一：色条全黑、底色全白（`--danger-tint: transparent`），
与 tokens 文档 v1.2 的 eink 规则逐条对应。本屏同时新增 `--danger-tint`
token（light/dark/eink 三主题），红系从此与蓝/绿/琥珀一样「色条 + tint」
成对。密度节奏照屏 4 先例在 `body[data-screen="6"]` 作用域内收紧。

## 屏 5 · 浮层（2026-09-24 迭代）

浮层 elevation token（`--shadow-raise` / `--scrim`，design-tokens-v1 v1.1 增补）的可视化
验收屏：底层是屏 1 主界面，上面同时浮着四类浮出物——vault 切换弹层（锚在侧栏
vault 名之下）、Outline 弹层（当前文档标题树、当前位置高亮）、右下 toast、
以及「遮罩分区 + 居中键位速查大浮层」。遮罩只盖正文右半区（左缘 x=660），左侧
保持未压暗，同屏对照 scrim 的明度差；toast 浮于 scrim 之上，层级一眼可读。
light/dark 下浮层壳 = `--preview-bg` + 1px hairline + `--shadow-raise`；eink 下
阴影全退场，浮层 = 白底实心黑框（modal 1.4px 强调档）、选中行黑底反白、
遮罩以 .35 纯黑明度差保留——与 tokens 文档 v1.1 的规则逐条对应。

## 屏 4 · 内容类型（2026-09-24 迭代）

同屏展示 Markdown 内容类型：frontmatter 属性区、表格、语法高亮代码块、标题层级
（h1/h2/h3）、段落、wikilink、引用块、无序/有序/多级列表。骨架复用屏 1（agent
栏隐藏），文件树切到 dimension-design.md 当前项。**全部内容摘自真实 vault**
（`~/Downloads/Everything-copy`，只读）：frontmatter 取自
`2_Areas/Product-Slax/Analytics/decisions/事件仓与采集实施.md`（status/date-opened/
date-resolved，与 dimension-design 同属 decisions 叙事），表格取自 dimension-design
的 Mode 值列表，代码块取自 threads-demo-plan.md 的 `const state`（节选标注刻在
代码块头部），wikilink 与 blockquote 分别来自这两篇原文。

样式决策要点：

- **frontmatter 呈现 = Obsidian properties 的极简版**：置于文档最顶部、标题之前；
  agent-bg 浅底圆角区；字段名 mono 11px 灰、值 13px 正文色；`status` 不渲染裸
  字符串，用语义 chip（resolved = 绿，与队列「已批准」同一语义色）。叙事是
  「YAML 头不是源码，是结构化属性」——编辑器把它当 UI 渲染，不当文本行。
- **表格**：th 只有底 hairline（结构档），无竖线、无斑马纹；首列（值）加粗，
  数字 tabular-nums；密度对齐队列条目。eink 下 th 底线升级为实心黑。
- **代码块**：独立组件带头部条（左：来源文件标注 + 「节选」；右：语言标记
  `js`），mono 13px，浅底。高亮四色 token：keyword 蓝 / string 绿 / number 琥珀
  / comment 灰——全部复用界面既有语义色阶，不引入新色相。
- **eink 的代码高亮与 frontmatter**：色彩退场，信息改由字重与灰度承担——
  keyword 700 纯黑、string/number 纯黑、comment 降灰 `#6e6e6e`；代码块与 fm 区
  从「浅底」翻转为「白底黑框」（1px 实心黑，与 eink 的 hairline 体系一致），
  chip 一律描边化。验证结论：高亮在黑白下仍成立，因为「注释 vs 代码」的对比
  本质是明度对比不是色相对比。
- **屏 4 专属节奏收紧**：内容类型全展示装不进默认节奏（溢出 146px），全部
  `body[data-screen="4"]` 作用域内收紧——doc pad-top 26、h2 16/5、h3 14/4、
  p 7、ol/ul 8、bq 10、fm 14 等。屏 1 排版节奏零影响（回归用截图 cmp 验证：
  s1/s3 字节级一致）。

## 表皮轴：composer=middle|bottom（2026-09-24 迭代）

第二个表皮轴：chat 输入框位置。默认 `middle`（对话区底部、队列上方，初版原样，
已用截图 cmp 验证零回归）。`bottom` 变体把 composer 沉到 agent 栏最底、Inbox
队列之下：chat 与队列之间由 queue-wrap 既有的强 hairline 直接分隔，composer
顶部 hairline 升级为结构档。实现用 flex `order`，composer 是固定高度（99px），
因此 chat（306px）与队列（355px）的几何在两轴间**完全不变**——A/B 对比时变量
只有位置，没有尺寸干扰。bottom 的叙事：队列与对话连成一条完整的时间线，
输入动作沉到面板底边（Things 式快速添加的位置），屏 3 里队列与中间栏审阅
视图的视线不再被输入框打断。

## 表皮轴：body=sans|serif（2026-09-24 迭代）

骨架选定后的第一个表皮轴：只动阅读表面的排版——屏 1 正文文档、屏 3 审阅视图里的
备忘录预览；文件树 / 标签 / agent 栏 / 队列 / 按钮等 chrome 全部保持无衬线。
默认 `sans`，与初版像素级一致（已用截图 cmp 验证零回归）。

serif 变体移植 direction-b 的正文基因：`ui-serif / New York / Charter / Songti SC`
系统字体栈、衬线标题层级（title 27px / h2 17px / body 15px，weight 600）、列表标记
保持 sans 小字、悬挂缩进不变。适配 C 的三栏密度做的取舍见 NOTES 末尾「妥协点」。

## 方向定位

三个方向里信息密度最高的一个：三栏（文件树 / 正文 / 常驻 agent 栏）。核心命题是
**「对话是输入，队列是档案」**——agent 栏内部上下分区：上半 chat（平铺行、非气泡、
输入框在对话区底部），下半 Inbox 提案队列（编号、一等裁决对象、可勾选批量处理）。
裁决时刻，中间栏整体切换为提案审阅视图：「裁决是一等界面」。

## 关键设计决策

### 1. 队列是 agent 栏的视觉重心，chat 退到次要
chat 区压缩到面板 44%，且全部用平铺行（发言人 + 时间戳小字 + 正文），不用气泡、
不用头像。队列占 56%，每条提案三行结构：编号 + 类型 + 状态 chip / 标题 / 元信息。
编号用 #41–#44 连号，暗示它是持久档案而非一次性卡片。队列里保留「今天早些时候」
分组（已批准 #41、已驳回 #39），让「档案感」在第一屏就成立——提案不消失，可回看。

### 2. 状态色只做三个语义，其余全中性
运行中 = accent 蓝（与主按钮同色，"活跃"语义统一）；待裁决 = 琥珀（唯一需要
注意力的状态）；已批准 = 绿（弱饱和、只出现在档案区）；已驳回 = 中性灰（拒绝不是
错误，不惩罚用户）。eink 主题下颜色全部退场：状态靠 chip 描边 + 圆点/文字，
选中态靠黑底反白。

### 3. 文件树参与叙事
agent 工作中（screen 2），受影响的源文件 `2026-R&D-Strategy.md` 右侧出现蓝点徽标，
下方插入一行斜体幽灵条目 `2026-R&D-Strategy-备忘录.md` + 虚线「新建」chip——
磁盘上还没有这个文件，但树已经告诉你它将要存在。这是「agent 在场」在 chrome 上
唯一的痕迹，且是信息而非装饰。

### 4. 裁决视图 = 文档页，不是对话框
审阅视图按「一份待签的文件」组织：面包屑定位（Inbox · 提案队列 › #42）→ 大标题 +
待裁决 chip → 元信息行（新建 1 个文件 / Agent 运行 43 秒 / 基于哪段对话 / 提交时间）
→ 变更文件卡（可逐文件展开，渲染/源码 seg 切换）→ Agent 备注。操作条固定在底部：
驳回 / 要求修改 / 批准并写入，左侧刻键盘快捷键（⌘⏎ / ⌘R / ⌘⌫）——Linear 式速度感
落在这里：裁决是高频动作，必须可以纯键盘连击。「批准前不会写入磁盘」一句写在
变更文件区右上，回应「不改写源文件」的产品铁律。

### 5. 高密度但安静的编辑态（screen 1）
agent 栏完全隐藏（原则 5：不在场时零痕迹），唯一入口是标题栏右侧的面板开关
（属于 app chrome，不算 agent 痕迹）。正文列 664px 居中，三级嵌套有序列表用
多级编号（1 / 1.1 / 1.5.1）还原文档结构，wikilink 用药丸形浅底 accent 色——
证明高密度方向也能安静。

### 6. 三栏密度分配
1280px = 侧栏 236 + 正文弹性 + agent 栏 348。agent 栏 348 是「队列条目三行
不折行」的最小宽度；正文在 screen 2/3 被压到 ~696px 时排版指标不变（max-width
664 仍成立），阅读不受 agent 在场影响——这是「用户仍可在中间栏读文」的兑现。

## 六条原则的落点

1. **内容即界面** — 正文 15px/1.7 系统无衬线（方向 C 定位），标题字距收紧
   （-0.012em），列表自定义悬挂缩进，数字全部 tabular-nums；界面 80% 是文本，
   无一张装饰图。
2. **chrome 退后，但不粗糙** — 全部控件自绘 1.3–1.5px 描边 SVG；hover/过渡
   0.1–0.12s；选中态圆角 6–7px 内嵌；hairline 分隔（`--border-soft` 比结构
   边框浅一档，层次靠两档灰而非投影）。
3. **质感来自工艺** — 无渐变、无卡片阴影（唯一起伏是 active tab 的 1px 边
   + 极浅投影，用来表达「它连着正文」）、无插画；质感靠对齐纪律（队列三行
   的 20px 悬挂缩进与 checkbox 对齐）和字重阶梯（400/500/550/650/680）。
4. **色彩克制且每色有语义** — light 主题彩色只有 4 个：accent 蓝（活跃/主
   行动）、琥珀（待裁决）、绿（已批准）、红（仅「驳回」文字按钮，不用填充）。
   modus 纪律保留：颜色少、对比达标、语义化；色相走柔和现代。
5. **agent 可开可关** — screen 1 零痕迹；在场时是一个分区明确的 pane
   （Zed 式结构：header / chat / composer / queue），不是气泡聊天窗。
6. **对话是输入，不是档案** — 本方向的核心理念，见上「关键设计决策 1」。

## 三主题策略

- **light**：全量打磨的主主题。近白中性灰（`#f4f4f1` frame / `#fdfdfc` 正文），
  暖度极低，避免旧 editorial 米色。
- **dark**：同一套结构，对比降一档（`#1a1b1d` / `#222326`），accent 提亮到
  `#8ba3ef` 保证 chip 与链接可读。三屏都不破版（screen 1 打磨到位）。
- **eink**：纯黑白灰。边框全部实心黑 hairline；选中态黑底反白；chip 全部描边
  化；状态语义改由形状/文字承担（圆点、进度条、chip 文案）。验证了 brief 的
  假设：三主题共享结构与排版基因，只分档对比度。

## 妥协点（诚实清单）

- **文件树长名截断**：`Slax-Reader-AI-Reading-Reimagined`、`2026-08-22-threads-demo-*.md`
  在 236px 侧栏里必然省略号结尾，两个 spec 文件截断后不可区分。真实 app 需要
  tooltip 或横向滚动，静态原型只能接受。这是密度与真实文件名之间的硬冲突。
- **正文是节选**：`2026-R&D-Strategy.md` 64 行装不进 900px 视口，可见部分经
  过取舍（保留 AI Coding 全列表 + 研发部一节的 wikilink），「碎片」一节标题
  被跳过。截图读上去像完整文档，实际是裁剪过的——评审时若翻原文会发现。
- **dark / eink 的 screen 2、3 只做了「不破版」**：token 全覆盖、无白边无对比
  事故，但 hover 层次、chip 饱和度没有逐屏细调，工艺集中在 light × 3 屏。
- **幽灵条目与徽标是静态叙事**：真实产品中「agent 正在改哪个文件」的徽标需要
  实时状态通道，原型只演示了视觉约定，没有演示徽标消失的完成态。
- **键盘快捷键是刻上去的**：⌘⏎ 批准等 hint 展示了 keyboard-driven 意图，
  但原型无交互，手感（连击裁决的节奏）无法从截图评估，需要后续可点击原型验证。
- **chat 输入框位置已轴化**：middle（队列之上）与 bottom（面板最底）两变体
  并存，见上文「表皮轴：composer」。middle 的顾虑是「边读队列边追问」视线
  要越过队列；bottom 的顾虑是输入框远离对话流、且与系统底栏（modeline）
  相邻，两个「条」叠在角落可能显得重。留给评审按手感裁决。
- **serif 轴的密度适配**：B 的正文是 16px/1.78 配整页阅读栏；C 的三栏驾驶舱
  里同样的内容要装进同一外框，serif 变体把正文微调到 15px/1.7（Songti 字面
  大于 SF，视觉尺寸反而相当）、doc 顶部留白 32→28、h2 间距 20/6→18/5、列表
  项距 2→1.5。行高 1.7 对 CJK 衬线仍属慷慨（Songti 自带行腹比 SF 宽），但
  拉丁长行（PR 一条）的换行点与 sans 版不同，两轴逐行对比时会发现折行位置
  不一致——这是字体更换的固有代价，不是 bug。
- **屏 4 的内容密度是「演示密度」**：八种内容类型同屏在真实文档里几乎不会
  出现，节奏收紧（字号不动、间距压缩）是为了装下演示而做的让步；真实文档
  不需要这套紧凑节奏。若后续某类内容单独成屏，间距可回到屏 1 的呼吸感。
