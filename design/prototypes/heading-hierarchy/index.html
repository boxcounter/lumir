一、背景与问题

过去六个月，Inbox 积压从 300 篇涨到 1,200 篇；读完率（read-through rate）从 38% 跌到 11%。问题不在收藏端——收藏动作已经足够轻——而在消化端：收藏之后没有任何机制把文章重新带到用户面前。

  • 积压分布：62% 来自「稍后读」插件，28% 来自 RSS 导入，详见 埋点字典
  • 读完率口径：停留 ≥ 90s 且滚动深度 ≥ 80%，代码里对应 readThrough 事件
  • 对照组：newsletter 频道的读完率 41%，接近健康水平

1.1 数据口径

统计窗口为 4月1日–9月20日。所有比率以「进入阅读视图」为分母，不含列表页停留。清洗规则有两处需要说明。

1.1.1 细分维度

按平台、来源频道、文章长度三维交叉。文章长度以中文字符数分桶：<1k / 1–5k / >5k。

平台拆分

iOS 读完率 14%，Android 8%。差异主要来自推送打开场景：iOS 推送直达阅读视图，Android 先落列表页。

备注

Android 的统计不含 6月12日–6月18日，那段时间埋点 SDK 升级导致滚动深度字段缺失。

附录说明

原始 SQL 与清洗脚本在仓库 analytics/readthrough/ 目录，可复跑。

二、方案对比

三个候选方案都围绕「把文章重新带到用户面前」，区别在于触发时机与打断成本。

方案触发时机打断成本预期读完率
每日摘要早 8:00 推送低18–22%
空位填充读完一篇后推荐下一篇无15–19%
周报复盘周日晚邮件无9–12%

2.1 性能预算

推荐计算全部本地完成，预算来自 性能合同：交互内不许有网络往返。核心约束：

ranker/config.ts · 节选ts
const budget = {
  rankP95: 40,          // ms，全量重排上限
  candidateCap: 200,     // 候选池大小
  embedding: 'local-v2', // 本地向量，无网络
  cacheTtl: 86400,       // 秒
};

三、决策与下一步

裁决记录：先做「空位填充」——它不打断、不需要新权限，且能复用已有的相似度索引。每日摘要降级为第二期候选。
  1. 9月30日前：候选池生成与排序跑通离线评测
    1. 评测集：过去 90 天的已读文章回放
    2. 指标：NDCG@5 ≥ 0.35，P95 延迟 ≤ 40ms
  2. 10月15日前：阅读视图尾部接入推荐条，灰度 10%
  3. 11月1日：按读完率决定是否扩量，复盘会复审
