# Design: tab-strip-context-menu

## 一、菜单形态：web 自绘浮层，不进统一键位表

沿用 M244 文件树条目菜单的口径，理由与那边逐条相同（不重复展开，见 `src/tree-menu.ts` 的文件头与本文件的差异部分）：

- **web 自绘而非 macOS 原生菜单**：原生菜单的项要在 Rust 侧定义、经 IPC 回传点击事件（⌘W 那条链路就是这么走的）；菜单内容是纯前端状态（哪一条标签、右侧还有几条），过一趟 IPC 只会多一处真源。另有一条实测理由：真机会话里右键坐标注入有「取不到窗口截图」的前科（M244 / M249 / M251 同族），原生菜单一旦弹出就无法在套件里关闭，会把整场场景卡死；浮层可以用 Esc 关掉。
- **不进 `src/keys.ts` 的统一表**：那张表的不变量是「一个 token 一条绑定」，而 ↑↓ / ⌃N⌃P / Enter / Esc 已被 `editor.cursor-*` 与 `editor.widget-escape` 占用。浮层持焦点时 editor 作用域因「事件目标不在 contentDOM 内」不命中，就地消费 + `preventDefault` 让 window 上的分发器让路（与树菜单 / 大纲浮层 / vault 浮层 / 键位面板同一套口径）。
- **右键不改上下文**：与文件树菜单同一条口径。这里还多一条独立理由——Close Tabs to the Right 的锚点必须是**指针落在的那一条**，如果右键顺手切换了前台标签，锚点就有了两个候选（指针那一条 / 前台那一条），菜单语义随之含糊。

## 二、两处菜单为什么各写各的机制、共用一套皮肤

tower 提醒②要求先试抽取共用底层。结论与理由（三条，按权重排序）：

1. **文件范围**：本 mission 的改动面不含 `src/tree-menu.ts`。抽底层要动它的导出面与类内部，进而要复跑它的单测与两条元素基线——一次跨 mission 的重构不该夹在一个功能 change 里。
2. **项集模型不同**：树菜单的项集随条目类型分流（文件行 / 目录行两套，含分隔线与破坏性项档），且菜单要标记**作用行**（`is-menu-target`，M251）；标签菜单是三条固定项，没有分隔线、没有破坏性档，作用元素是整条标签（它自己已经有 hover / active 态）。能共用的只有「容器 + 指针定位与翻转 + 键盘游标 + 外点关闭」这一层（两处各约 60 行），而这一层的两份实现各自被自己的单测覆盖（`tests/unit/tree-menu.test.ts` / `tests/unit/tab-menu.test.ts`）。
3. **皮肤是共用的**：外观（浮层壳、项的内边距 / 圆角 / hover / 选中底色 / eink 反白与描边）在 `src/style.css` 里只有**一份声明**——`.ft-menu` 与 `.tab-menu` 成对写进同一批选择器（M254 起）。改一处同时影响两处，这才是「同一语义不要两处真源」在外观层的要求；机制层的重复面是「两段各 60 行的 DOM 操作」，比一份共享皮肤值钱得多。

留一条后续选项（不属本 change）：若将来出现第三处浮层菜单，那时抽取的收益才会大于现在（三处共用一层），抽取点是把这两段合并成 `createFloatingMenu` 并让两处菜单各自提供项集与作用元素策略。

## 三、批量关闭的顺序控制（本 change 唯一的难点）

Close Other Tabs 与 Close Tabs to the Right 是一次动作关多个标签，而**脏标签的关闭要用户逐个决定**（M149 的确认浮条：保存并关闭 / 放弃修改并关闭 / 取消）。三者之间的语义约束：

- 一次只弹一条确认：两条确认浮条同时在场时，用户不知道自己在答复哪一个；浮条区还会互相挤占。
- 确认就是「用户还没答复」的窗口期：**在这个窗口里 MUST NOT 关掉后面的标签**——否则用户点「取消」时已经晚了（那些标签的修改已经没了）。

落地方案：`closeEach(targets, closeOne)` 顺序执行，`closeOne`（`resolveClose`）返回的 Promise 在**这个标签真的被关掉**（干净标签立即关；脏标签等用户选定出口）之后 resolve；返回 `false`（取消 / 保存未闭环 / 点掉浮条）即整批停手。

这要求「脏标签的关闭」有一个可等待的落点，而 M149 的确认浮条原本是开到就返回的（用户的选择在浮条的按钮回调里）。为它加一条**浮条被点掉**的回调通道：

- `src/main.ts` 的 `toast` 增尾部参数 `onDismiss`（sticky 浮条被点掉即通知）；
- 动作钮的 click 加 `event.stopPropagation()`——钮已经给出答复，MUST NOT 再走「点掉浮条」这一路。少了这一行，「保存并关闭」这条出口会被紧随其后的 `onDismiss` 抢先作废：那条路径先 await 保存、再关闭，而 `onDismiss` 是同步的，批量动作会在保存落地之前就停手（**这是本 change 最容易写错的一处**，单测与视觉场景各有一条断言钉它）。

「点掉浮条」按「没答复」处理（`closed = false`，停手），不作「默认放弃」——浮条是模态之外的东西，点掉它不该等于选了一个出口。

单标签关闭的两条既有路径（⌘W / ×）不经过批量逻辑，用户可见行为与 M254 之前逐字相同（它们的确认仍是「弹了就返回」，由用户自己收尾）。

## 五、已知边界

1. **菜单项的可用性不计算**：右侧没有标签时 Close Tabs to the Right 仍可点，点了是空动作（proposal 的 non-goal）。
2. **批量关闭不合并成一条确认**：三个脏标签 = 三次确认（与浏览器逐个确认同形）。合成一条需要新文案（「N 个标签有未保存修改」）与新的出口语义（保存全部 / 放弃全部），M254 的裁决是复用既有确认流，因此不做。
3. **菜单不做横向翻转**：右端只做「不越出挂点」的夹取（与树菜单同算式）。标签栏在标题栏中部，指针在右端时菜单会被向左夹住——形态与树菜单一致，不额外做翻转。
4. **真机右键通道的不确定性**：验收场景 50 走真实右键坐标注入，与场景 47 同族风险（本机有「取不到窗口截图」的前科）。若撞上，如实登记为通道边界，判定由 chromium 层（`tests/visual/scenes/tab-menu.spec.ts`）承担。
