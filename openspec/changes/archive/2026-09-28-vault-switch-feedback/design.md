# Design: vault 切换的即时反馈与浮层定位修复

## 0. 结论先行

两条改动的落点都很小，但每一条都有一处「看起来更直接、其实不成立」的写法，这里把推导留档：

1. **浮层定位**：入口可以被左栏滚出视口，所以纵向位置**必须夹**在挂点矩形内；夹的下界是视口上沿而不是「入口下沿」——因为入口可能根本不在视口里。
2. **装载指示**：起止点决定它有没有用。起点必须在用户动作的那一帧（不是「打开完成时」），终点必须挂在**会话恢复的 Promise**上（不是「树重建完」）——Alex 感知到的「卡住几秒」正是终点之前的那一段。
3. **两处否决**：指示**不给文案也不给读屏名**（文案 deck 单一来源，见 §3.2 的取舍与记账）；浮层**不做向上翻转**（见 §1.3）。

## 1. 浮层定位：为什么是「夹」，夹的是什么

### 1.1 缺陷的机制（可复算）

浮层挂点是 `.app-shell`（`position: relative`），坐标为绝对定位坐标 = 挂点局部坐标。`place` 的输入是入口（`.ft-vault`，树头部）与挂点的 `getBoundingClientRect()`，两者都是**视口坐标**，相减得到局部坐标。

入口在 `.tree-pane`（`overflow: auto`）里、不是 sticky。设左栏滚动量为 `s`、树头部高度 `h_head`、挂点顶边为 `host.top`：

- 入口下沿的视口坐标 = `host.top + h_head − s`；
- 旧算式给出的局部 `top` = `h_head − s + 4`。

`s` 超过 `h_head` 之后这个值转负，并且随滚动继续线性变小（Alex 的左栏滚到中部时，`s` 是几百到几千像素）。浮层整块被推到窗口上沿之外——**窗口**（不是任何 DOM 容器）把它裁掉：`.app-shell` 没有 `overflow`，所以裁它的是视口本身。这与既有口径「浮层宽度允许溢出左栏」不矛盾：溢出的是横向，纵向被视口裁掉是另一件事。

### 1.2 修法：夹进 `[0, 挂点高 − 浮层高 − 边距]`

```ts
const top = Math.min(
  Math.max(anchor.bottom - host.top + gap, 0),          // 入口在视口内时与旧式同值
  Math.max(0, host.height - height - margin),            // 入口在下沿之外时贴底
);
```

- `gap` / `margin` 沿用 4px / 8px（与 `src/tree-menu.ts` 的菜单同一组值，同一类浮出物不做两套手感）。
- 上界同时解决「窗口很矮」：浮层不会越出窗口下沿。
- 纵向余量 `room = host.height − top − margin` 小于浮层实测高度时，把 `max-height` 压到 `room`（inline style）——列表本来就有 `overflow: auto`，它仍是唯一的滚动容器。写 inline `max-height` 前**先清空一次**再测高：否则上一次打开压进去的值会被当成本次的内容高度量进来，浮层会一直矮着。
- **常态零位移**：入口在视口内时 `Math.max(anchor.bottom …)` 给出的就是旧式的值，`min` 分支不生效，浮层的像素位置与修前逐像素一致（视觉门禁的既有基线因此不需要更新）。

### 1.3 否决的写法

- **向上翻转**（下方放不下就整块翻到锚点上方，`tree-menu` 就是这么做的）：本浮层的锚点是**树的第一个元素**，它只可能被滚到视口上方，不可能落到视口下方；翻转要解决的场景在这条链路上不存在，加了就是死代码。
- **以左栏视图矩形为夹取范围**（锚点滚出时贴左栏上沿而不是窗口上沿，视觉上更贴近「入口在哪」）：需要从入口向上找滚动祖先。`vault-switcher.ts` 与单测的假 DOM 之间有一条**只出现存 DOM 面**的约定（`tests/unit/vault-switcher.test.ts` 的替身只实现被碰到的那些 API，`closest` / `parentElement` 不在其中，而该文件不在本 mission scope 内），为一个纯观感差异去扩这条约定不值得。代价是入口滚出视口时浮层会盖住标题栏左段（含原生 traffic 灯区）——浮层是瞬时的、关掉即消失，记为已知取舍。
- **`position: fixed`**：会绕开挂点坐标系，与横向对齐（入口左端）用的同一套视口相减不再对称，两处口径分叉不值当。

### 1.4 测试面的现状（如实记录）

浮层几何在 chromium 侧只有「不占常驻布局」「宽度溢出左栏」两条（`tests/visual/scenes/mv-vault-switcher.spec.ts`），**没有**滚动左栏后的几何断言；真机套件目前**没有滚动动作**（`scripts/acceptance/README.md` 的动作表里没有 scroll），所以「左栏滚到中部」这个现场在自动化里造不出来（见 §5 的边界与随本 change 落的 finding）。

## 2. 装载指示：起止点是全部设计

### 2.1 覆盖哪一段

三段耗时（`vault_open_path` → 树整树重建 → 逐标签会话恢复），指示覆盖**从点击到第三段结束**。理由：用户对「卡住」的感知是整段时间，而第三段（逐个文件读入 + 建会话 + 渲染预览）在标签多的 vault 上往往最长——如果指示只盖前两段，用户会看到「转圈没了但界面还在变」，等于把一次等待拆成两次。终点信号因此取 `switcher.onVaultLoaded()` 的 Promise：它 resolve 的时刻就是「整窗上下文 + 会话都就绪」。

### 2.2 为什么起点不在 `applyVault`

把 `begin` 放进 `applyVault` 是最省事的位置（唯一装载实现），但启动恢复路径也走它——那条路径已经有一句「正在恢复上次打开的 vault……」，再叠一个转圈是重复表达，而且会让启动态多出一个视觉元素（可能影响既有整页基线）。因此起止点分两处装配：

| 场景 | 起点 | 终点 |
|---|---|---|
| 切换 / 重新定位 | `switchToVault` 入口（点行的同帧） | 会话恢复 Promise 结束 |
| 新增（目录选择器） | 选择器返回之后 | 同上 |
| remap 浮条的「作为新 vault 打开」 | 动作时点 | 同上 |
| 启动恢复 | 不指示 | `end()` 无配对 `begin()`，no-op |

`end()` 采用**引用计数**（配平后归零才隐藏）：一次恢复途中再切一次时两段窗口会叠，计数保证前一段结束不会把后一段的指示撤掉；同时让「启动路径的多余 `end()`」自然退化为 no-op，不需要在调用点判断。

### 2.3 被 dirty 门拦下时不指示

`begin` 在门之后（`switchToVault` 里），门拦下时那段代码根本不执行——用户此刻看着三条出口，界面若还在转圈会与「请选择怎么办」自相矛盾。出口执行（保存并切换 / 放弃修改并切换）后照常 `begin`。「保存并切换」的**保存阶段**不在指示窗口内（它有自己的冲突/失败提示通道），这是有意的最小化：本 change 只回答 Alex 提的那一条。

### 2.4 落点：标题栏右端（否决 modeline 与若干替代位）

**落地元素**：`main.ts` 在 `shell.titlebar` 末尾追加一个 `<span class="vault-loading" role="progressbar" hidden>`。

- **为什么在标题栏**：Alex 的原话是「我会愣住，以为刚才点击没点中」——需要的是**余光可见**的信号。标题栏右端紧邻产品标识块，是屏幕上位置最稳定的常驻区；modeline 在窗口底行，且它右段已有「语法 · 行数 · 编码 + 版本号 + 主题」四个写入者，再插入一个异类元素会让「谁在写这一行」更难读。
- **为什么是末尾（标识块右侧）而不是标识块左侧**：`.titlebar-identity` 靠 `margin-left: auto`（`src/style.css`）钉右端——标签栏隐藏（空 vault / 装载中标签被清空）时它是**唯一**把标识块推到右边的力量。若把指示插在标识块**左侧**且不给它 `margin-left: auto`，在标签栏隐藏的空档里它会掉到 traffic 灯区右边（标题栏最左侧）；给它 `margin-left: auto` 则两份 auto margin 平分空白、指示落在标题栏正中。末尾追加是唯一在两种标签栏状态下都稳定落在右端的写法。
- **代价**：指示出现/消失时标识块横移约 19px（自身的 12px + 间距 6px + 1px 余量）。装载期间标签栏本身就在整批换（清空→逐个恢复），19px 的横移在这个语境里不构成第二处视觉噪音；`hidden` 时 `display: none`，空闲态逐像素不变（视觉基线不需要更新）。
- **否决「常态占位、只切透明度」**（`visibility: hidden` 会保留占位 → 常驻布局改变 → 全部整页基线与标识块元素基线漂移，且基线更新是 Alex 的人肉裁决点，不该被本 change 顺手触发）。
- **否决放左栏树头部（`.ft-header` 内、vault 名旁）**：语义上最贴（切换目标就在那里），但入口按钮的 `aria-label` 是显式写死的、按钮内部的内容在 ARIA 里是 presentational——把指示放进去等于放弃它在 AX 层的可观测性（真机验收只能靠截图），并且入口在未装载 vault 时不存在（空态打开路径就没有落点）。
- **标题栏拖拽区纪律**（REVIEW.md 第 16 条）：该元素**不挂任何事件监听**（它没有交互面），因此不触碰那条「标题栏内元素的监听静默打断窗口拖拽」的坑；真机场景 39（标识块拖拽移动窗口）在本次验收里一并复跑。

### 2.5 eink 与动效

- 环的两色取既有 token：底 `--border`、顶边 `--accent`。light/dark 下可见一条冷色弧在浅灰环上转；eink 档 `--accent` 与 `--border` 同为 `#000`，环是纯黑——**旋转不可见**，此时指示靠「环的出现与消失」表达。eink 是系统性降级档（同一份 token 语义），本 change 不为它单独造一套配色。
- `prefers-reduced-motion: reduce` 下关掉旋转，环本身仍在（省动效不等于省指示）。该分支没有门禁覆盖（chromium 视觉门禁不带该偏好），属于「照惯例写、未验证」的部分，如实记在这里。
- 这是本仓第一处 `@keyframes`（`src/style.css` 此前没有任何动画），没有既有惯例可依；0.8s/圈取的是「余光能看出在动、又不至于闪」的档位，观感归 Alex。

## 3. 文案与可访问性

### 3.1 无文案是**硬约束**（tower 裁决 + 本 change 的口径）

指示只有图形，没有可见文字；同时**不给 `aria-label`、不加隐藏文本**——任何读屏名都是一条新文案，而文案 deck（`文案-Copy.md`）是单一来源、本 change 不该往里面塞一条。

### 3.2 记账（不掩盖）

- 因此这条指示对屏幕阅读器用户**不是**可感知的通知：`role="progressbar"` 不带名字，AT 至多读出「进度指示器」这样的空壳。真正的可访问出口是「装载完成后界面内容整体替换」，以及失败时的人话浮条（既有链路）。
- 该缺口的正解是给指示一条读屏名（等于新增一条文案，需要走文案 deck 与 Alex 裁决），本 change 不做、也不假装解决：把它记在这里与 review-request 里，作为下一轮的候选。
- `role="progressbar"` 的选择是为了让真机 AX 树里**有**一个可断言的节点（无 role 的裸 span 在 WKWebView 里通常只是一个无名 `AXGroup`，与标题栏里既有的无名分组不可区分——那样的「断言」等于没判据）。**真机已确认这个选择成立**：WKWebView 把它暴露成 `AXProgressIndicator`，场景 49 的「装载指示此刻在场」因此是真机上可断言的判据（2026-09-27 实测 PASS，证据 `test-results/acceptance/2026-09-27-m252/49-vault-switch-feedback/`）。

## 4. 阶段读数（诊断面）

- 三段各记一条 `slow_callback`：`vault_load_open`（`vault_open_path` 往返，Rust 侧：注册表对账 + 起 watch + 全量枚举 + 逐 md 读正文建链接索引）、`vault_load_tree`（`tree.setVault` 的同步整树重建，装载路径上唯一的主线程重活）、`vault_load_restore`（逐标签会话恢复，从发起恢复到结束）。
- 阈值 250ms：低于它的装载在真机上感知不到等待。事件名与字段沿用既有的 `slow_callback` + `name`/`ms`（白名单字段，见 `src-tauri/src/logging.rs` 与 `src/diagnostics.ts`）——**不新增事件、不动 Rust 侧**，与本仓既有的 `code_structure_parse` 采样同一条通道。
- 读法：`<config>/lumir/logs/<UTC 日期>.jsonl` 里 grep `vault_load`。
- **真机实测（2026-09-27，合成 vault + 本 change 的放大器）**：
  - `vault_load_restore`：46 个标签 ≈ 992–1359ms（**≈25–30ms/标签**，逐标签串行：IPC 读 + 建会话 +（激活项）渲染）；14 个标签 ≈ 390ms（同一口径，线性）。
  - `vault_load_open`：12 个 16MB 稀疏 md（192MB）→ **4615ms**；12 个 4MB（48MB）→ **2252ms** → **≈48ms/MB，与解析字节数线性**。小 vault（65 个文件、总量 30KB 级）时低于 250ms 阈值、不产生读数。
  - `vault_load_tree`：合成 vault 规模（65–78 行）下始终未触发阈值；Alex 真实 vault 有 **8189 个文件（1525 个 md）/ 1057 个目录**（`find` 计数，只读未取内容），这一段的真实代价要在他机器上按日志读。
- **边界（需 reviewer 判一眼）**：这把 `slow_callback` 的语义从「同步后台回调超预算」扩展到「异步装载阶段超阈值」。事件名与字段都在白名单内，但 `openspec/specs/diagnostics/spec.md` 对该事件的描述口径未随之修改（该文件不在本 change 的 scope 内）。若 reviewer 认为这会污染诊断口径，处理方式是：要么接受「`slow_callback` = 任何被采样的耗时点」的广义读法（并落一条 finding 让 diagnostics capability 补口径），要么由后续 mission 在 diagnostics scope 内收口。本 change 不自行扩 scope。

## 5. 已知边界（不读成「已覆盖」）

1. **浮层几何的真机覆盖缺口**：真机套件没有滚动动作，造不出「左栏滚到中部」的现场（§1.4）。本 change 在真机侧验的是「打开浮层后列表完整可读、目标行点得到、切换闭环」这条端到端链路 + 截图证据；**「滚出视口后浮层贴视口上沿」这一条只有 chromium 侧的算式（本 change 的代码）与人工复算，没有自动化判据**。已随本 change 落一条 finding（建议给套件加 `scroll` 动作），不在本 mission scope 内实现。
2. **指示的 AX 可观测性为真，但要落到快照里需要一个足够长的装载窗口**：套件单次 AX 快照（`mode=ax`、不带截图）的往返延迟实测在**秒级**——43 个标签（恢复 1180ms）那一轮，紧随点击的那次快照读到的已经是「装载完成」态（43 个标签全在、无指示节点）。因此场景 49 用 12 个 16MB 稀疏 md 把后端装载阶段撑到 4.6s 以上，指示的存在才成为可稳定断言的事实。**放大的是观察窗口，不是判据**：指示要么在场要么不在场，快照不撒谎；装载比那次快照还快的运行会判红，复跑即可（该现象已写进场景正文）。
3. **带截图的快照更慢，「指示长什么样」没有真机截图证据**：`shot` 走 `mode=full`（AX + 全窗截图），实测该轮两张截图都落在装载结束之后（同一张图逐字节相同）。指示的外观目前由 CSS 与真机 AX 节点两处佐证，**观感（转速、大小、出现时的横移）归 Alex 的 dogfood**——本 change 不把「截图里看得见」写成已验证。
4. **时序断言是「窗口内可见」而不是「≤100ms」**：验收套件没有耗时断言（`steps.md` / `results.json` 只记场景总秒数），因此「点击后 <100ms 出现」只能由结构保证——指示在点击的同一个任务里 `begin`（没有定时器、没有 await），结构上不可能晚于下一帧；场景侧验的是「装载还在跑时它已经在场」。
5. **主线程被占住时指示不转**：若某一段是同步长任务（大 vault 的树重建、重文档的预览渲染），那一段里浏览器没有帧，环会停在原地——「在等」仍然可读（环在场），但「在动」不可读。这是本 change 不解决的（真正要改的是把重活拆帧或移出主线程），结论落在 review-request 的根因报告里。
6. **未覆盖：会话恢复途中再次切换的指示连续性**（引用计数分支）没有自动化判据，真机上要抢很窄的窗口；逻辑上由 `pending` 计数保证，单测面因 `createVaultLoadingIndicator` 只在 DOM 层、而 `tests/unit/vault-switcher.test.ts` 不在本 mission scope 内，未加单测。
