## Why

Alex 裁决（2026-10-12）原话：「我理解了。这个逻辑不用改，但有什么方法能让减少后续的疑惑。比如这次我产生的疑惑？」

**现场**：Alex 把权限档从 Read 切到 Write（`vault_write`）之后，仍然收到 `cli_run`（`zsh -lc …`）的批准询问，
于是产生疑惑。tower 核查规格后确认**行为符合现行裁决**——`vault_write` 档的承诺是「库内写自动放行、库外命令先问」，
而 shell 包装器（`zsh -lc …`）属危险黑名单，**任何档都逐个问**（含 `full_access`）。Alex 认可逻辑不改。

**诊断：疑惑的来源不是档位，而是卡片没说理由。** 切档这件事本身是自洽的（档位语义与判定一致）；
让 Alex 停下的是**批准卡弹出那一刻**——卡上只有问句（「要运行这条命令吗？」）与闸语义副句
（「批准后才会在终端运行，输出回到对话里」），没有任何一句说明「这条命令为什么会进闸」。
读者要自己把「我刚切到 Write 档」+「这条命令是终端命令」+「包装器黑名单」三件事串起来才能解释，
串不起来就落成「档位没生效？」的疑惑。同类疑惑会在 deny 规则命中时重演——工具行只说「权限规则拒绝了…」，
不说**是哪条规则**拦的。

**现状锚点**（对着本 worktree 源码核实）：

- 判定层序完全藏在 `src-tauri/src/harness/permissions.rs:59-96` 的 `decide()` 返回语句先后里，
  返回值是四变体 `Decision`（`permissions.rs:40-50`），**不带任何「哪一层拦的」元数据**；
  `matches_rule`（`:846`）只返回布尔、丢弃命中的规则串。
- 批准请求的事件载荷由 `events::approval_request_with_purpose`（`src-tauri/src/harness/events.rs:127-145`）
  手工拼 `serde_json::Value`，字段只有 `id` / `tool` / `diff?` / `argv?` / `purpose?`；
  快照面 `PendingApprovalSnapshot`（`src-tauri/src/harness/session.rs:195-211`）镜像同一批字段。
- 面板只在 `approvalAskOf`（`src/harness-panel.ts:4870-4881`）按工具名取问句、按载荷形状取副句；
  权限 chip 的 `title` / `aria-label` 是 `D426`（「权限模式：{mode}（点击切换）」），
  档释义（`D430`–`D432`）只在浮层里出现一次（`applyPermChip` `:4098-4108`、`buildPermPop` `:4113`）。

## What Changes

逐条对应 `specs/harness/spec.md` 增量里的一个 requirement：

1. **批准卡的「判定依据」行**（harness，MODIFIED：批准闸呈现与决策后收敛）：批准卡 SHALL 在问句下方展示一行
   人话的判定依据，说明**是哪一层**让这次调用进闸；该行 SHALL 由 Rust 判定管线产出、随批准请求事件与快照
   两条通道同源到达前端，前端 MUST NOT 自行推导层级；该行与待决问句、决策按钮**同一生命周期**（决策后随卡退场，
   MUST NOT 残留在终态记录里）。覆盖两层：危险黑名单（区分 shell 包装器与其余危险成员）与模式默认分层（带当时档位）。
2. **权限 chip 悬停提示补档释义**（harness，MODIFIED：权限模式切换）：chip 的 `title` / 可访问名 SHALL 在
   「权限模式：{mode}（点击切换）」之后附上**当前档的一行释义**——与浮层释义同源（同一份 `D430`–`D432`），
   不新增信息；`{mode}` 仍取全名。
3. **deny 规则命中也说得出规则原文**（harness，MODIFIED：权限机制）：用户 deny 规则命中时，回送模型并显示在
   工具行上的错误 SHALL 带上**命中的规则原文**（如「命中 deny 规则 cli(npm run deploy*)」），拒绝对话语义
   （直接拒绝、不进批准闸）MUST NOT 改变。

三条合起来把「为什么问我 / 为什么拒我」从**读者自己串**变成**界面直接说**——这正是 Alex 要的「减少后续的疑惑」。

## Non-goals

- **不改判定逻辑**：五层短路口径、三档语义矩阵、黑名单清单、规则语法、重定向行为、会话内批准缓存
  一律逐字节不变（Alex 原话「这个逻辑不用改」）。本 change 只加**解释**，不改**结论**。
- **不给不产卡的层加行**：allow 规则命中与缓存命中是静默放行（无 UI 面可挂），vault 内写重定向回送的是
  结构化错误——都不加「判定依据」（REVIEW.md 第 9 条：声明必须有消费者）。
- **不做可展开的详情**：判定依据是**一行**人话，不加折叠区、不加 ⓘ 入口、不做「为什么」的二级解释。
- **不改终态记录**：决策后的单行终态（已采纳 / 已拒绝 + 相对时间戳）与拒绝原因行（D408）不变；
  判定依据行随卡退场，MUST NOT 以置灰形态残留（与待决副句同一纪律）。
- **不改 wire 请求体与留存结构**：`llm_request.messages` 逐字节不变；JSONL 的会话留存结构不动
  （判定依据只活在事件与快照两条 UI 通道）。
- **不改 purpose 的地位**：purpose 仍是模型自述的阅读辅助，不参与判定；判定依据与它并列显示、互不替代。
- **不动权限浮层**：浮层的三档全名 + 释义（`D427`–`D432`）不变；本 change 只把释义**顺带**也放进 chip 悬停提示。
- **不加通知 / 不加提示音 / 不做切档时的解释**：疑惑的落点是卡弹出那一刻（Alex 原话），切档路径不加东西。

## 观测闸三问（低成本口径）

- **怎么知道用户用了它**：判定依据行随卡出现，常驻在 Alex 眼前；dogfood 时他看一眼即可，无埋点
  （沿用产品零埋点口径）。
- **怎么知道它有效**：主判 Alex 下次在非 `full_access` 档遇到终端命令 / 写工具进闸时是否不再回头问
  「为什么还问我」——他不再提这类问题即算有效；辅判 deny 规则命中时工具行直接给出规则原文，
  不必再翻配置文件核对。
- **出问题怎么发现**：机器面兜底——Rust 单测（层级映射真值表：五层各返回哪个层 + deny 规则原文）、
  前端单测（判定依据文案取值与缺省不渲染）、验收场景（三类拦截各断言文案 / 规则原文）、
  视觉场景结构断言（行随卡在场、随决策退场）。
