# Proposal: cli_run 走用户登录 shell 的 PATH

- Change ID: harness-cli-login-shell-path
- 日期: 2026-10-12
- 角色: Alex Lee（评审/裁决），AI agent（起草）

> 评审记录：
> 节点 1（提案评审）：**Alex 2026-10-12 已裁决**（见下「Why」的裁决原文与选项 B），本 change 是实现该裁决。
> 节点 2（归档评审）：留白（实现完成后填写）。

## Why

Alex 原话（2026-10-12）：

> 「现在 harness 每次使用 shell 命令都需要用包裹方式，否则会找不到一些命令，导致每次使用都需要我 approve。」

agent 当时的说明：「`tvly` 装在 `~/.local/bin/`，在你的 zsh 交互环境 PATH 里，但 Lumir 的执行环境不加载
shell 配置，所以裸命令找不到，走 `zsh -lc` 已解决。」

**问题结构**：`cli_run`（`src-tauri/src/harness/tools.rs:894`）直接用 `std::process::Command` 起命令，
子进程的 `PATH` 是 Lumir 进程继承来的一份——它不含用户 shell 启动文件里追加的目录（如 `~/.local/bin`、
Homebrew、pnpm 等）。于是模型要么把每条命令写成 `zsh -lc 'tvly …'`（shell 包装器被归为**危险命令**、
任何权限档都弹批准闸），要么因找不到命令失败重试。Alex 的体验是「每条命令都要 approve」。

**Alex 裁决（2026-10-12）**：选「**登录 shell 取 PATH**」方案——即 Claude Code 的 shell 快照路线的轻量版：
只从用户登录 shell 里取一份完整 `PATH`，**不快照函数 / 别名 / 其它环境变量**。备选项（放弃）：
① 让模型继续用 `zsh -lc` 包裹（把逐条 approve 的成本推给用户，且每轮多一层 shell）；
② 让用户在配置里手写额外 PATH 目录（把「照抄用户 shell 环境」这件事变成手工维护）。

## What Changes

逐条对应 `specs/harness/spec.md` 增量的一个 requirement（ADDED ×1）：

1. **cli_run 执行环境（登录 shell PATH）**（harness，ADDED）：会话内**首次** `cli_run` 时，经用户登录
   shell 解析一份完整 `PATH`（shell 取 `$SHELL`，缺失或空白回落 `/bin/zsh`），把结果**注入此后每个
   `cli_run` 子进程的环境变量**；解析在独立子进程内进行、带超时（默认 5 秒）、结果在进程内
   **缓存复用（成功与失败都缓存）**。解析成功时注入值为「解析结果在前 + app 继承到的
   额外目录去重追加在后」；解析失败时**不改写子进程环境**，照常继承 app 自身 `PATH`（回退语义）。
   **权限模型不动**：本机制只影响「子进程能否找到命令」，MUST NOT 影响「命令是否被放行」——裸命令照旧
   走命令分类、危险黑名单、allow/deny 规则与模式默认分层。

一句话：**让裸命令找得到（不再需要 `zsh -lc` 包裹），但判定管线一个字不改。**

## Alex 裁决点

| 1 | 修法路线 | A. 模型继续用 `zsh -lc` 包裹；B. **登录 shell 取 PATH（Claude Code 快照的轻量版，只取 PATH）**；C. 用户在配置里手写额外目录 | **已裁决：B**（Alex 2026-10-12）。A 把 approve 成本留给用户、每轮多一层 shell；C 把「照抄 shell 环境」变成手工维护 |

无待裁裁决点——本 change 是实现上述两条已裁决定的落地；实现期若发现需改设定（如旗标语义与预期不符、
需引入新配置项），按影响面升级线报 tower。

## Non-goals

- **不改权限模型**：命令分类、危险黑名单、shell 包装器规则、`allow`/`deny` 规则、模式默认分层、
  批准缓存——**一个字不改**；`zsh -lc` 包裹仍照旧被判为危险、任何档都问（本 change 不豁免它，
  只是让模型**不再需要**用它）。
- **不快照 shell 的函数 / 别名 / 其它环境变量**：只注入 `PATH` 一个变量（裁决点 2 的 A）。
- **不持久化 PATH 快照**：解析结果只活在**当前进程内存**里（`OnceLock`），不落盘、不进配置、不进 vault；
  下次启动重新解析（用户改了 shell 配置无需任何迁移动作）。
- **不改请求装配 / 工具 schema / 面板**：`cli_run` 的参数 schema、批准卡、事件载荷逐字节不变。
- **不新增遥测 / 日志事件**：diagnostics 日志的事件名与字段在白名单内（`src-tauri/src/logging.rs`），
  本 change 不碰它；解析失败是**静默回退**（见「已知边界」）。
- **不引入 shell 包装器白名单**：不因为「我们现在自己会起 shell」而放宽 `sh` / `bash` / `zsh` 的危险归类。

## Impact

- **影响的 specs**：`harness`（ADDED ×1：cli_run 执行环境（登录 shell PATH））
- **影响的代码**：
  - `src-tauri/src/harness/tools.rs`：新增 PATH 解析 / 缓存 / 合并的纯函数与子进程解析器，
    `cli_run` 的 `Command` 构造处按解析结果注入 `PATH`（约 `tools.rs:774-935`）；模块头补一段说明。
  仅此一个源文件；前端、命令层、权限层、留存层均无改动。
- **关联约束**：ADR 0002 §6 性能合同——解析是**惰性**的（首次 `cli_run` 才触发，不拖慢冷启动）、
  带超时、结果缓存（失败也缓存，不每条命令重试），不落在 keypress-to-paint 路径上；
  ADR 0007 工具集边界——不新增工具，只改 `cli_run` 的执行环境；
  仓库信息卫生——实证结论只写「定义在哪个启动文件」，不落真实 home 路径 / 真实 shell 配置内容。
- **不影响的既有行为**：权限判定结果、批准闸交互、工具结果信封、`cli_run` 的 stdout/stderr 截断与
  超时（60s）口径、命令分类与危险黑名单——全部不变。

## 观测闸三问（低成本口径）

- **怎么知道用户用了它**：Alex dogfood 时不再需要写 `zsh -lc` 包裹、也不再因「command not found」
  被逐条 approve——行为差异肉眼可见，无埋点（沿用产品零埋点口径）。
- **怎么知道它有效**：判据是「装在 `~/.local/bin` 的裸命令（如 `tvly`）在不加包裹的情况下能直接跑起来」；
  机器面兜底 = Rust 单测（标记解析 / 合并回退 / 旗标 / 子进程链路 / 真 zsh 冒烟）。
- **出问题怎么发现**：解析失败是**静默回退**（不改环境、行为回到本次改动前）——这是刻意的「fail-safe
  而非 fail-loud」，代价是失败时没有直接信号。**已知边界**：若需「解析失败要可见」，需要一个新日志事件
  （`logging.rs` 白名单，本 change scope 外）——列为后续候选，不在本 change 内做（见 design §5）。

## 已知边界

- **解析失败静默回退**：首次 `cli_run` 时若解析超时 / 取不到标记，退化为「继承 app 的 PATH」——即回到
  本次改动前的行为，用户无感知。这是刻意的（宁可静默回退也不能因解析失败让 `cli_run` 整体不可用），
  但意味着「解析没生效」不会有直接信号。让失败可见需要新增日志事件，属 scope 外，记为后续候选。
- **只对 zsh / bash 猜旗标**：其余 shell（fish / nu / …）的启动文件与旗标语义不同，不猜——直接回退继承。
  当前目标用户（Alex）用 zsh，覆盖到位；将来若要支持别的 shell，按新需求再议。
- **`-i`（交互）会执行交互启动文件**：其中可能有慢插件（starship / pyenv / zoxide 的 init）或杂输出；
  用超时兜底（挂住即放弃），用标记夹取兜底（杂输出不进结果）。
