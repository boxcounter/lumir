# Design: code-outline

本文件分九节。**第 1 节与同批 [code-variable-highlight 的 design](../2026-09-24-code-variable-highlight/design.md) 的第 1 节逐字一致**（同一份语言栈盘点的两条消费者），其余各节是本 change 自己的。

## 1. 语言栈现状与分层（两份 change 共用的同一节）

### 1.1 现状：code 模式给不出结构

- 非 md 文件一律只读 code 模式（M130 方向 A，`src/editor.ts:999-1002`）。
- 它的语法来源是 `@codemirror/legacy-modes` 的 `StreamLanguage`（21 门语言同一机制，`src/preview/code.ts:84-104` 的 `LANGUAGES`）。
- StreamLanguage 产出的树是**扁平的 token 序列**：整篇文档一个 `Document` 节点，其下直接是 token 叶节点（`max depth: 1`，节点名只有 `keyword` / `variableName.definition` / `typeName` / `string` / `comment` …）。读数与命令见 [evidence/02](evidence/02-current-code-mode-readings.md)。
- 那些 token 名**不含符号名、不含符号范围、不含嵌套关系**——所以「函数在哪、类里有哪些方法、当前光标在哪个方法里」在现状管线上一个都答不出来。这不是配置问题，是机制缺口。
- 因此今天在代码文件里按 `⌘⇧O`：`extractHeadings`（`src/toc.ts:119-141`，只认 `^ATXHeading([1-6])$`）在扁平 token 树上命中 0 条 → 命中空态提示「这份文档还没有标题，大纲为空」（D84）。**这句话在代码文件上是错的**（实测见 evidence/02）。

### 1.2 分层的判据（两条，都可复核）

1. **有官方 `@lezer` 语法**：与既有依赖体系同源（本仓已依赖 `@lezer/highlight` / `@lezer/markdown`，`@codemirror/language` 又依赖 `@lezer/common` / `@lezer/lr`），由 CodeMirror 组织维护，与 `@lezer/lr` 的兼容性有版本保证。社区单维护者包一律不进本批（逐条理由见 [evidence/01](evidence/01-language-stack-survey.md) §2.2）。
2. **探针核验无阻断性缺陷**：语法必须能对目标语言的普通代码产出可用的结构树。这一条把官方语法 `@lezer/yaml` 也筛掉了（它有一个已在 `1.0.4` 复现的位置缺陷，见 [evidence/01](evidence/01-language-stack-survey.md) §6）。

判据 2 不是形式条款：它是「用别人的语法来产出结构」这件事的**验收门槛**，与「不用近似 parser 冒充」是同一条纪律（着色面上已有先例：change `codeblock-toml-yaml-highlight` 明确拒绝近似 parser）。

### 1.3 三层结论（21 门注册语言逐门落位）

**T1 —— 符号大纲 + 变量高亮（8 门）**：声明节点与引用节点都在探针里逐个列了名（[evidence/01](evidence/01-language-stack-survey.md) §3），是「条目类别」与「同一变量判据」的第一手依据。

| 语言 | 结构解析包 | 大纲条目覆盖（见 §2.1 的类别词表） |
|---|---|---|
| javascript | `@lezer/javascript` | 函数 / 类 / 方法 / 类字段 / 常量与顶级变量 |
| typescript | `@lezer/javascript`（`configure({dialect:"ts"})`） | 同上 + 接口 / 类型别名 / 枚举 |
| python | `@lezer/python` | 函数 / 类 / 方法 / 顶级赋值（常量） |
| rust | `@lezer/rust` | 函数 / 结构体 / 枚举 / trait / 常量与静态量 / impl 块 / 字段 |
| go | `@lezer/go` | 函数 / 方法 / 类型（struct、interface）/ 常量与变量声明 |
| c | `@lezer/cpp` | 函数 / 结构体 / 全局常量与变量 / 字段 |
| cpp | `@lezer/cpp` | 同上 + 类 / 类内方法 |
| java | `@lezer/java` | 类 / 接口 / 方法 / 构造器 / 字段 / 常量 |

**T2 —— 只做大纲、不做变量高亮（2 门）**：结构是「规则集」而非「符号」，但规则的选择器是天然的可跳转目标（IDE 的样式表层大纲同形）。

| 语言 | 结构解析包 | 条目 = |
|---|---|---|
| css | `@lezer/css` | 所有 `RuleSet`（条目文本 = 该规则的选择器原文，层级 = 嵌套） |
| scss | `@lezer/sass` | 所有 `RuleSet` + 所有 `SassVariableName`（`$变量`） |

**T3 —— 本次不支持（11 门）**：无大纲条目、无符号链；`⌘⇧O` 给一句说明真相的提示。逐门理由：

| 语言 | 落 T3 的理由 |
|---|---|
| ruby | 只有社区包（`codemirror-lang-ruby`，507 dl/wk）——判据 1 排除；另：其声明名与局部读同为 `Identifier`，判据要更细 |
| shell | 社区包停更 2 年+（`@fig/lezer-bash`，2023-02）且**在普通 bash 上出错**（`local x=1`、`$(( ))`、`function f {` → 11 个 error 节点）——判据 1+2 都不过 |
| toml | 社区包停更（`lezer-toml`，2022-08）；无官方语法 |
| swift | 只有单维护者新包（11 dl/wk）——判据 1 排除 |
| kotlin | 同上（5 dl/wk） |
| lua | 同上（8 dl/wk）；另一候选 `lezer-lua` 依赖**已废弃的 `lezer` 包**、周下载 0 |
| sql | 官方 `@codemirror/lang-sql` 的语法**不产出声明节点**（实测只有 `Statement`，`VALUE` 被词法成 `Keyword`）——判据 2 排除 |
| yaml | 官方 `@lezer/yaml@1.0.4` **有位置缺陷**（空行 + 注释行开头 + 区块映射 → `Document [65536, 11)`，`iterate` / `resolveInner` 全失效）——判据 2 排除 |
| json | 有官方语法，但「条目」只能是键路径（`Property` / `PropertyName`），需要先定一套「键条目的文本与层级怎么取」的产品口径（见 §6 的边界）——**本 change 不做**，留待另一个 change |
| html | 同上：条目只能是元素（`Element` / `TagName`），而元素名重复度极高（实测语料 6 个 `Element`、12 个 `TagName`），列表里不足以区分目标 |
| xml | 同 html |

**为什么 json / html / xml 不在 T2**：css 的规则集选择器天然唯一度较高、且是开发者真正会跳的目标；元素名与键名则大量重复，一个 `div` 条目标不出「哪一个」。给它们定一套条目文本口径（例如带 id 的元素、键的完整路径）是**产品决定**，不是语法决定——本 change 不替它做决定，也不做半套（记入 §6 的边界与 §2.1 的「不覆盖」清单）。

### 1.5 与 legacy-modes 着色管线的并存关系（本 change 的核心机制决定）

三条候选，本 change 推荐 **S2**：

| 机制 | 形态 | 代价与风险 |
|---|---|---|
| **S1 单管线（lezer 接管着色）** | 有官方语法的语言改挂 `LRLanguage`，着色由语法的 `styleTags` 驱动；legacy mode 退为无语法语言的兜底 | ① **会改变观感**：tag 词汇与既有 `TOKEN_GROUPS`（`src/preview/code.ts:158-169`）不同，取色随之变化；② 撞上 spec 的既有不变量「同一段代码在围栏与整文件打开时 SHALL 得到同一套 tag 与配色」（`editor-live-preview` 的「Markdown 渲染保真」第 2 款）——围栏侧的着色是 `src/preview/code.ts` 手工驱动 legacy mode 得到的，只改一侧就破 parity，两侧都改则是另一个大 change；③ 全量视觉基线要重拍，且用户没有要求改颜色 |
| **S3 lezer 当 language + 手工着色** | lezer 语法占住 `language` facet（结构 + 后台解析由 CM 管），着色改成装饰层（复用手工驱动 StreamLanguage 的既有机械） | ① `language` facet 只有一个生效位（`@codemirror/language/dist/index.js:654-660` 的 combine 取第一个），要保住 legacy 着色就得把着色从 facet 路径挪到装饰路径——**着色来源被改写**，parity 与基线同样要重验；② 为「拿结构」付了整套渲染管线的改动代价 |
| **S2 双管线（推荐）** | legacy mode **继续当 language facet**（着色一行不改）；结构解析用 `@lezer/*` 语法**自己驱动**（`parser.parse(text)`），只在需要时跑一次并缓存 | 代价：同一份文本被两套词法各读一遍（①②的对照与理由见下）；换来：**着色、parity、视觉基线、既有断言全部零改动** |

**推荐 S2 的理由（按分量排序）**：

1. **用户要的是结构，不是颜色**：S1/S3 都会动到「同一段代码长什么样」，而本 change 的被裁决面不含观感变化。零观感变化意味着零基线重拍、零既有断言改写——这是可交付性的最大变量。
2. **parity 不变量在 S2 下自动成立**：`editor-live-preview` spec 要求围栏与 code 模式同 tag 同配色。S2 不动着色管线，这条要求**逐字照旧**；S1/S3 都必须同时改围栏侧才不破。
3. **两套词法不是「同一语义两处真源」**（[REVIEW.md](../../../../REVIEW.md) 第 8 条的形态）：那条纪律针对的是「同一个语义被两处各自维护」（扩展名表、配色表）。这里两者的**语义不同且不互相校验**——着色只看 legacy mode（它今天就在做这件事），结构只看 lezer 树；语言**身份**仍只有一份来源（`LANGUAGES` 的 `CodeLanguage` 键，结构表按同一键类型做穷尽检查）。设计上明确一条纪律：**两棵树 MUST NOT 互相校验、MUST NOT 混用**（着色不参考 lezer 树，结构不参考 legacy token），免得日后长出「用 token 名冒充结构」的旁路。
4. **改动面收敛在一处**：新增一个模块（§4）+ 两个消费者（大纲、变量高亮），`src/preview/code.ts` 的着色部分零改动。

**如实记下 S2 的两个代价**：

- 同一份文档在内存里可能同时存在两棵树（legacy 树由 CM 按视口解析，很小；lezer 树是全文件的，1MB 级约 40 万节点——内存影响见 §1.6 的已知边界）。
- 「同一段代码的两种读法可能不一致」在理论上存在（例如 legacy mode 把某段当字符串、lezer 当标识符）。处置：**结构功能的口径只由 lezer 树定义**（spec 里写死），界面不同时呈现两种判定，所以不会出现「同一处两个答案都可见」的场面。

### 1.6 解析时机、缓存与性能

- **触发**：**首次需要结构时**才解析——用户在 code 模式按下 `⌘⇧O` 展开大纲（或第一次双击标识符，见同批另一 change）。MUST NOT 在打开文件时无条件解析（那会把 1MB 级的 80–290 ms 塞进打开路径）。
- **缓存**：缓存的身份是**文档内容**（键 = 语言 + 原文，与 `src/code-structure.ts` 的 `cacheKey` 同口径）——内容不同才重新解析，**切回内容相同的文件命中已有缓存、不重新解析**。理由：code 模式**只读**（M130 方向 A），文档在打开期间不会变——这是本设计成立的关键前提，若将来 code 模式可编辑，缓存策略必须重做（记入 §6 的边界）。（2026-09-24 归档时按 Alex 节点 2 裁决改准：原稿此处写「换文件、外部重载、切换标签使缓存失效」，与同一句前半的「按文档内容 + 语言缓存」自相矛盾；实现侧零改动。同批的 `code-variable-highlight/design.md` §1.6 与 §4.3 按同一口径改准。）
- **读数（量级，headless 下界，见 [evidence/01](evidence/01-language-stack-survey.md) §5）**：100KB 代码的结构解析 ≈ 8–30 ms（无感）；1MB ≈ 78–291 ms（**可感**）。树遍历（取条目）6–8 ms。
- **已知边界（如实写）**：1MB 级代码文件**首次** `⌘⇧O` 会有一次可感延迟（量级见上），此后同一文件不再付。这不是达标声明，是需要实现期在真机端点上复测并在必要时升级机制的项（升级路径见 §7）。
- **不在键入路径上**：只读模式没有键入；光标/滚动只驱动指示段的节流刷新（沿用 `src/toc.ts:94` 的 120 ms 口径），且指示段只在结构**已解析**时才可能显示（§3.1）。

### 1.7 本节涉及的裁决点

语言覆盖分层（T1 / T2 / T3 的取舍）与依赖许可（§1.4）是提案期的正式裁决面，落在两份 proposal 的
裁决点 1 / 2；**机制选择（§1.5 的 S2 与 S1/S3 的拒绝）同样单列为裁决点**——它牵动 parity 不变量与常驻
内存，写在 [code-outline proposal](../2026-09-24-code-outline/proposal.md) 的**裁决点 6**（本 change 按它的结论行事，
对应一句写在本 change proposal 的裁决点表之后）。三候选的代价与拒绝理由以 §1.5 为准。

## 2. 大纲的数据模型

### 2.1 条目类别词表与「不覆盖」清单

统一词表（供 spec 与断言使用；**界面不显示类别标签**——md 大纲也只显示文本与缩进，本 change 不引入新的视觉语言）：

`function` / `method` / `constructor` / `field`（类或结构体成员）/ `constant`（常量、静态量、顶层赋值）/ `class` / `interface` / `enum` / `struct` / `trait` / `type`（类型别名）/ `module`（命名空间）/ `impl`（rust 的 impl 块）/ `rule`（css/scss 的规则集）/ `variable`（scss 的 `$变量`）

**条目覆盖（逐语言的实际映射）**：见 §1.3 的表。实现落点是一张**逐语言声明节点 → 类别**的表（放 §4 的模块里，`Record<CodeLanguage, …>` 形式做编译期穷尽检查）。

**MUST NOT 覆盖**（写进 spec，防实现期顺手扩面）：

- 函数体内的**局部变量**与**参数**：它们不是文件的结构单元，一个大函数就能把列表淹掉；它们属于「同一变量高亮」的领域（同批另一 change），不是大纲的。
- 表达式里的**引用**（`CallExpression` 之类）：大纲列声明，不列引用。
- 导入语句（`import` / `use` / `#include`）：它们是依赖声明，不是本文件的符号；列进去会让大纲在文件顶部堆一大段。
- json 的键、html/xml 的元素：见 §1.3 的理由（缺条目文本口径）。

### 2.2 条目文本口径

- **有条目名字子节点的**：取名字子节点的原文（逐语言规则由探针实测确定，见 [evidence/01](evidence/01-language-stack-survey.md) §3）。几个必须写死的细节（都是实测差异，猜必错）：
  - javascript/typescript：函数名与类名是 `VariableDefinition`；方法名是 `PropertyDefinition`。
  - java：方法名是**第一个** `Definition` 子节点（返回类型的 `TypeName` 排在前面，取错会得到类型名）。
  - c/cpp：`InitDeclarator` 的第一个 `Identifier` 是声明名（第二个是初始化表达式里的引用）；cpp 的**类内**函数名是 `FieldIdentifier`（顶层函数是 `Identifier`）。
  - python：`FunctionDefinition` / `ClassDefinition` 的第二个子节点是名字（`VariableName`），与引用同名，必须靠位置判。
  - rust：函数与常量名是 `BoundIdentifier`，类型名是 `TypeIdentifier`。
  - go：`ConstSpec` / `FunctionDecl` / `MethodDecl` 的名字是 `DefName`。
- **没有名字子节点的结构节点**（如 rust 的 `ImplItem`，css/scss 的 `RuleSet`）：取该条目**起始行的原文**——去行首缩进、去行尾 `{` 与尾随空白；超长按既有浮层的省略号口径收尾。css/scss 的选择器另按「选择器部分」取（`RuleSet` 的选择器节点原文），不取整行（避免把 `{` 与同行声明带进来）。
- **一个声明节点带多个名字时逐个成条目**（M197 实现期补的口径，本设计原文没写）：go 的分组声明
  （`var (A = 1; B = 2)`）与多名字声明（`var a, b = 1, 2`）、java 的多声明符字段（`int a, b;`）各自
  成条；只取第一个名字会**静默丢掉**其余符号（实现期实测踩到过 `B` 消失）。这一类的条目落点是**各自
  名字的起点**（不是 `var` / 类型修饰符处）——多条条目若共享同一个起点，「当前位置归属」会永远选中
  最后一条，指示段因此会说错符号。
- **MUST NOT** 做二次渲染、MUST NOT 猜测修复（与 md 大纲「显示作者写下的那一行」同族纪律）。

### 2.3 层级与缩进

- 层级 = **语法嵌套深度**：条目的父链上有多少「条目级容器」（类体内的字段/方法比类深一级；impl 块内的函数比 impl 深一级；css 嵌套规则深一级）。MUST NOT 按类别排序或按类别赋层级。
- 缩进 = 沿用 `src/toc.ts` 既有的归一规则：以「本条链里最浅的条目」为基准，避免只出现深层条目时浪费一层空缩进。
- 顺序 = 文档顺序（与 md 一致）。

### 2.4 空态与不支持

| 情形 | 行为 |
|---|---|
| 语言在 T1/T2 且文件里有条目 | 正常展开浮层 |
| 语言在 T1/T2 但文件里没有条目（空文件、只有导入/注释） | toast：**这份文件没有可提取的符号，大纲为空**（新文案 **D115**，M199 补登 deck） |
| 语言在 T3（含 yaml、shell、sql、json、html、xml…） | toast：**这份文件类型暂不支持大纲**（新文案 **D116**，M199 补登 deck；措辞以 delta spec 为准——本节原文写的「这份文件的语言暂不支持大纲」与之不一致，M197 实现期改准；是否点名扩展名/语言名见 §3.2 的取舍） |
| 非 code 模式（md） | 一切照旧（D84 原文不动） |

## 3. UI 通道复用与代码分支差异

### 3.1 指示段（masthead 的当前位置指示段）

- 复用同一个元素（`shell.ts` 的 `.masthead-section`，`src/main.ts:172-180` 装配）与同一套节流刷新（`src/toc.ts` 的 `schedule` / `SYNC_THROTTLE_MS = 120`）。
- 代码分支显示的内容 = **当前符号链**：光标（滚出视口时取视口顶部，口径与 `anchorPos` 逐字相同）所在位置的最内层条目链，用同一个分隔符拼接（如 `Util › greet`）。
- 可见性：**仅当**当前文件是 code 模式、语言在 T1/T2、结构已解析、且当前位置落在某个条目内时显示；其余情形隐藏（含：位置在首个条目之前、结构尚未解析、T3 语言）。
- **「结构尚未解析」这条是推荐项，代价写实**：打开代码文件后若用户从未按过 `⌘⇧O`（或双击过标识符），解析未触发 → 指示段不出现。理由是**不在打开路径上加解析**、且让指示段的出现时机**可预测**（没有异步竞态，截图类门禁不会拍到「有/无指示段」的中间态——`toc.ts:74-84` 的 `refresh()` 正是为 md 侧的同类问题长出来的）。若 Alex 要求「打开即出现」，处置是加一次空闲时段预解析：代价是打开路径上多一段可感的后台工作 + 指示段出现时机变成异步（须同步改截图类门禁的口径）。**这是裁决点**（见 proposal 的裁决点 7）。
- md 分支：逐字不动（含「光标落在首个标题之前时隐藏」这条）。

### 3.2 浮层

- 复用 `⌘⇧O` / `toc.toggle` 与既有浮层（`.lumir-toc*` 的 DOM、样式、`aria` 形态、80% 总高上限、就地键 `↑↓` / `⌃N` / `⌃P` / `Enter` / `Esc`），**不新增键位、不新增命令、不新增面板**。
- 代码分支的差异（逐条都是「不做 md 那样」的地方）：
  1. **跳转落点**：光标落在条目的**声明起点**（声明节点的 `from`——通常是 `class` / `function` / `const` 等关键字，前导缩进不在节点范围内），该位置滚到视口居中。MUST NOT 用 md 的「行尾」口径：代码的声明行常常很长（函数签名、参数表），行尾落在函数体开头，看不到符号名。MUST NOT 修改文档（ADR 0003 §3）。
  2. **条目文本**：见 §2.2（名字子节点 / 起始行原文）。
  3. **空态提示**：见 §2.4 的两条新文案；md 的 D84 在代码文件上 MUST NOT 再出现（那正是本次要修掉的错话）。
  4. **浮层底部的键位提示**：逐字沿用（就地键集合没变），MUST NOT 因为语言不同而改提示文本。
- 浮层打开**不做** 25 ms 预算截断（md 侧 `FULL_PARSE_BUDGET_MS = 25` 的回落语义在这里不适用）：半截大纲是**错的信息**（用户看不出少了一半）。改为「首次解析一次做完，之后走缓存」；代价即 §1.6 的已知边界。

### 3.3 视觉

不引入新的视觉语言：符号链用既有 `.masthead-section` 规则（含 `›` 分隔与省略号收尾），条目用既有 `.lumir-toc-item`（含 `--toc-depth` 缩进、`is-current` 当前段、`is-active` 键盘游标）。样式若需微调（例如条目文本超长的省略），改 `src/style.css` 里既有规则，不新增类名前缀。

## 6. 已知边界与未验证项

**已核实的边界（写进 spec 或 proposal）**：

- T3 的 11 门语言没有大纲，`⌘⇧O` 只给提示（含 json / html / xml 的「缺条目文本口径」与 yaml / sql 的语法缺陷，逐门理由见 §1.3）。
- 1MB 级代码文件**首次**打开大纲有一次可感延迟（headless 下界 78–291 ms）。
- 结构解析的缓存前提是 **code 模式只读**；若将来 code 模式可编辑，缓存与失效策略必须重做。
- 解析结果驻留内存（1MB 级约 38–51 万个节点，[evidence/01](evidence/01-language-stack-survey.md) §5 的节点数列）。这是**新增长期占用**，实现期须在常驻内存端点上复测（口径见 `perf-measurement` spec），本提案不宣称达标。
- **md 围栏代码块内的符号大纲不做**：围栏是正文的一部分，且今天没有嵌套解析树（着色是手工驱动 legacy mode 得到的，见 `src/preview/code.ts:344` 的 `highlightCode`），要做得先引入围栏嵌套解析（`markdown({codeLanguages})` 或自己进 overlay mount）——那是另一条管线，另立 change。本 change 的条目只来自「打开的文件本身」。
- **php 不接**：注册表里 php 当前是 `null`（无语言包 → 纯文本，M130 的裁决），而 `@lezer/php` 是官方语法。把它接上属于「扩语言覆盖」，会同时改动 php 文件的观感（纯文本 → 有色语法视图）与一类新基线，与本需求的「拿结构」是两件事（proposal 裁决点 5）。

**未验证项（不许当成已验）**——**M197 实现期逐条处置**（读数落 `test-results/m197/`，详见
`real-corpus-and-unverified.md`、`perf-first-outline.json`、`perf-memory.json`）：

- 真机（WKWebView）下的浮层条目手感、符号链的观感、1MB 文件首次展开的可感延迟——**延迟已测**：1MB
  级 `.js` 首次解析 **177.0ms**（app 自己的 `slow_callback` 诊断事件，debug 构建、产品端点），落在
  §1.6 的 headless 下界区间（78–291ms）内、§1.6「1MB 首次有一次可感延迟」的已知边界**成立**；关掉
  再开不产生第二条日志（缓存生效）。**手感与观感仍归 Alex**（截图证据在
  `test-results/acceptance/2026-09-24/30-code-outline/shots/`）。
- 语法包对**真实 vault 语料**的健壮性——**已复核**：本仓自己的源码 172 文件 / 1.58MB → 21 个错误节点；
  用户真实 vault 里的代码文件 112 个 / 14.4MB（以 Obsidian 插件的压缩 `main.js` 与 css 片段为主）→
  2486 个错误节点，最差文件是压缩 bundle；**条目质量抽查显示错误节点不产生假条目**（778KB 的
  `obsidian-tasks-plugin/main.js` 上 2357 个错误节点仍只产出 834 条真实顶层声明，无空文本 / 超长垃圾
  文本）⇒ **没有任何语言需要降层**（§7 备选② 未触发）。顺带记一条现实边界（非缺陷）：压缩 CSS 的
  选择器可以很长（实测最长 721 字符），按 §2.2 的省略号口径在浮层里截断显示。
- 本 change 的 `--toc-depth` 缩进在深嵌套（如 4 层以上的类/方法/嵌套结构）下的可读性——**仍未验**
  （归 Alex 的手感项）：现有断言覆盖到 3 层（css `.nested > .inner > .deep`、java / python 的
  `class > class > method`），4 层以上没有实测读数与截图，不得当成已验。
- 三个社区包（ruby / swift / kotlin / lua）的实际质量：探针只做了「能解析小样本、无 error 节点」，
  未做边界与增量复核——这也是本批不纳入它们的一部分理由（**本条维持原状**：判据 1 就不过，
  不需要为了「更完整」去复核不纳入的包）。
- **常驻内存（§1.6 的已知边界，proposal Impact 要求复测）**：**已测，且如实记下不利读数**——
  1MB 级 .js（33000 条条目）上，RSS 合计从「打开未解析」293.7MB 升到「首次展开」626.9MB（+333MB），
  反复开关可到 897.7MB 峰值（其中 WebKit 渲染进程 746.9MB）；app 自己的 native 进程只有 101.7MB。
  **不宣称达标**：本次是 debug 构建 + 单点采样（非 §4 的 release + idle 10s + 5 样本口径），与 CI
  门禁阈值（250MB）不可比。可确认的是 **S2 的常驻内存代价在极端形态下真实且可观**，普通文件（几十到
  几百条条目）下增量落在噪声里。升级路径：§7 备选 6（缓存派生数据而非树）+ 浮层条目表虚拟化
  （后者是 M148 起既有的渲染路径，已作为 finding 上报，不在本 change 范围内）。

## 7. 备选机制（备记，防止实现期绕回）

1. **把结构解析交给 CM（占 language facet）+ 换着色管线**（S1/S3）：见 §1.5 的三条代价。若将来要做，它应当是一个**独立 change**（含围栏侧 parity 与全量基线重拍），不是本 change 的实现分歧。
2. **无解析器的语言用启发式近似**：被 [proposal](proposal.md) 的 Non-goals 与用户原话排除（「不是字符匹配」）。记录在此仅为堵住「先上个能用的近似」这条回头路。
3. **按语言动态 `import()` 语法包**：可能减少首包体积与启动开销，代价是多一层异步与「第一次打开该语言文件时的等待」。作为实现期可选项记录（不是本次要求）；若采用，`⌘⇧O` 的首次延迟会把动态加载时间也算进去。
4. **空闲时段预解析**（打开文件后自动跑一次）：能让指示段「自动出现」，代价是打开路径上的后台工作 + 指示段出现时机变成异步（截图门禁口径要跟着改）。作为 §3.1 的裁决点备选列出（即 proposal 的裁决点 7）。
5. **Worker 解析**：彻底消除主线程卡顿，代价是新基础设施（worker 打包、Tauri 的 CSP 面、结构化数据与树的双份内存）。记录为实现期若实测卡顿不可接受时的升级路径；本次不采用。
6. **缓存派生数据而非树**（只留「条目表 + 标识符索引」，解析完丢弃树）：可能显著降低常驻内存（1MB 的树 vs 一张扁平索引表），代价是后续若需要更多查询（如变量高亮的遮蔽判定需要祖先链）就要求索引阶段把所需信息一次算全。本批两 change 的建议：**先留树**（实现简单、两个消费者都能直接用），内存复测不达标时再转向「派生数据」形态。
