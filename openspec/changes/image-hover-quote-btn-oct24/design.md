# Design: 图片悬停引用钮的真机判据修复

- Change ID: `image-hover-quote-btn-oct24`
- 依据：`.local/probes/m670-hover-probe.md`（真机 DOM 级探针，读数取自 AX 快照）
- 基线：[openspec/specs/editor-live-preview/spec.md](../../specs/editor-live-preview/spec.md)
  的「块级复制触发钮」hover 浮现条款；[场景 222](../../../scripts/acceptance/scenarios/222-image-quote-to-chat.md)

## D1 根因：判据的前提写错了——「窗口 key」应为「webview 有焦点」

探针在真机 WKWebView 里读到三组事实（同一台机器、同一批跑批）：

| 状态 | `AXWebArea` 标记 | 注入的 `mousemove` | `:hover`（`.cm-lp-image-box`） | 钮 |
|---|---|---|---|---|
| 有焦点 | `(focused)` | 到（计数增长） | 命中 | `visibility: visible`、进读屏树 |
| 无焦点 | 无标记 | **不到**（计数冻结） | 停在旧目标 | 停在 `visibility: hidden` |

两条路都会掉进「无焦点」：

1. **启动态不确定**：`pnpm tauri dev` 拉起的实例有时带焦点、有时不带（同一脚本连跑四轮的
   读数：一次 `focus=true`、三次 `focus=false`）。
2. **标题栏单击把它打掉**：M669 给 222 / 163b 加的 `focusWindow click: true` 落在标题栏的
   拖拽区（`data-tauri-drag-region="deep"`），单击之后 `(focused)` 标记消失——它想买「窗口
   key」，实际买到的是「webview 失焦」。

因此判据层需要一个**确定的**（determinstic）聚焦手段：在正文里真实单击一次
（`clickEditor real: true`，swift + CGEvent mode 1）。它同时满足 hover 要用到的三件事：app 在前台、
窗口成为 key、webview 拿到焦点。这条手法不是新发明的——场景 163b 的注释里已经写着同一句话
（「真实鼠标点击：同时建立 DOM 焦点与 key window」），只是 222 当年选了标题栏那一下。

**被否决的替代方案**：

- **保留标题栏单击、再加一次正文单击**：多一步真点击，且用户的真实手势不会「先点标题栏再点正文」，
  场景要的是可判读数而不是模拟冗长动作。一步够用（正文单击本身就激活 app）。
- **改用 AXPress / KimiCU 坐标点击**：实测不建立 webview 焦点（`clickEditor` 非 real 档跑完
  `AXWebArea` 仍无 `(focused)`），hover 依旧死。
- **产品侧改成 JS 驱动的浮现（监听 `mouseenter` 加 class）**：不解决任何问题——事件本身就没投递到
  页面（`move` 计数冻结），JS 监听器同样收不到；而 `:hover` 在有焦点时工作正常，改它就是无依据的
  重构（REVIEW.md「诊断先于处方」）。

## D2 判据的区分度：陈旧 hover 状态会让正观测恒真

探针抓到一条真实假绿：先悬停出钮，再做标题栏单击（移动通道死掉），随后的悬停注入一次事件都没到，
但页面上的 `:hover` 仍停在旧目标，`AXButton (摘录到对话)` 仍在读屏树——「hover 后钮在场」照样绿。
这与 REVIEW.md「假绿：断言看着有覆盖，实际不判任何东西」同族，修法是给每条正观测配一条**紧邻的**
负观测：

- ① 悬停前：`ax: { not: "/AXButton \\(摘录到对话\\)/" }`（静止态不可见）；
- ④ 悬停 svg 前：先把指针移到非图片目标（标题栏的 vault 切换钮）并断言钮**退回**静止态——
  这一条同时是「可见性双向」的产品判据（离开必须收回），不是只为了让 ① 有区分度。

两条负观测都必须紧邻正观测（同一段、中间不夹会移动指针的动作），否则它们自己会变成新的空断言。

## D3 ② 段的第二个红：选区配方差一行，不是产品缺陷

`⌃⇧N` 是 `editor.extend-line-down`（`extendVertically`，按可视行）。舱面分栏后第 3 行那段文字
折成两个可视行，从行首连按两次只把选区头停在折行续行的行首——图片行（第 5 行）根本没进选区；
从**续行行首**继续往下推也推不动（M670 实测：连按五次，`sel=` 读数停在同一个折行首，`keys=7`
说明按键全部到达 DOM；同一份命令在 chromium 里正常推进，所以这是 WKWebView 下 `moveVertically`
的坐标测量差异，不是键位逻辑）。

定型配方（实测，别再改回连按）：`⌃⇧E`（扩选到第 3 行行尾，锚点留在行首）→ `⌃⇧N` ×3。三次把
「正文 + 空行 + 图片行」括进选区；两次停在图片行行首（严格重叠判据不命中）；四次起会把第 7 行
（QOMEGA）与第 9 行的缺图引用带进来，卡片角标读成「含 2 张图片 · 1 张图片未能引用」。
`⌃⇧E` 必须用**扩选**版：`⌃E` 会把锚点带到行尾，摘录原文没有正文，退化成「选区只有图片」的
单图片块路径（实测）。

判据侧补一条「含 1 张图片」正观测：卡片角标由 `countExcerptImageRefs` 从摘录原文派生，是
「图片真的进了选区」的唯一机器可读面——只看「卡片数 = 2」分不出「图片进了选区」与
「图片被跳过但残留了块」。

## D4 视觉层为什么不变量是「三态」

视觉场景（chromium）此前对位图写了两态（静止 `toBeHidden` → 悬停 `toBeVisible`），对 svg 只有
「悬停后可见」。补成三态（静止不可见 → 悬停可见 → 指针移开重新不可见）之后，产品侧的不变量
「可见性双向跟随指针」在 chromium 层可证伪：把 `.cm-lp-image-box:hover` 那条选择器去掉即红。

注意这一层**抓不到**本 change 的真机根因（chromium 里 hover 一直正常）——所以它是产品不变量的
守门人，不是本缺陷的复现测试。复现只存在于真机层（222），那一层靠 D2 的负观测夹层保区分度。
