# Design: preview-tab-removal

## 一、为什么是「移除机制」而不是「改掉斜体」

斜体本身是 M149 预览标签设计的唯一可见线索（`openspec/specs/multi-tabs/spec.md:65` 的「预览（临时）标签的标题 SHALL 为斜体」）。它表达的是一台**隐藏状态机**：单击树文件开出来的是「临时」标签，下一次单击会就地顶掉它；双击 / 首次输入 / ⌘-点击把它「固定」住。

Alex 的反馈是「第一个 TAB 名是斜体，其他 TAB 不是」——他把它读成样式坏了，没有读成「这一篇是临时的」。这说明该信号在真实使用里没有传递出去。可选的三条路：

1. 换一个更显眼的线索（点、色、轮廓）——仍然要求用户学会一台两态的状态机；
2. 保留状态机但让视觉线索不显眼（去掉斜体）——状态机的行为照旧发生（单击顶掉上一篇），而用户失去了唯一的提示，**比现状更糟**；
3. 移除状态机（tower 裁决选的这条）：单击一律开正式标签，行为与提示一致，标签栏回到单一形态。

选 3 的代价如实记：单击浏览多个文件时标签会累积（旧语义下它们互相顶掉）。这是**有意的取舍**——被顶掉的标签是一种静默损失（用户上一眼看的文档凭空消失），而累积是可见的、用户自己能用右键菜单的三条关闭路径收拾（见同批 change `tab-strip-context-menu`）。两条合起来才是完整的交互：**打开不再有隐藏语义，关闭有显式入口。**

## 二、落点意图为什么会塌成两个值
旧口径有三个意图（`src/tree.ts` 的 `"preview"` / `"pinned"`，加装配层的 `"current"`）。预览机制移除后：

- `"preview"`（复用可复用标签）与 `"pinned"`（新开固定标签）的**唯一差别**是「会不会被下一次单击顶掉」——差别的前提没了，两者是同一个落点；
- `"current"`（就地替换前台标签）仍然独立：链接跟随 / 另存为新文件 / 恢复备份三条链路都是「当前这份文档换个落点」，与标签数量无关。

因此收敛成 `"new"` / `"current"` 两个值，判定点收到装配层一处（树不再持有意图参数）。这不是为了少写几行——**树上那条 `event.metaKey` 分支在旧口径之外没有任何意义**，留着它就是留一条永不生效的意图判定（未来的读者会以为它还在起作用）。

### 空文档会话的复用

`editor.sessions()` 里可以存在一个**没有文件路径**的会话（冷启动的示例文档；`closeSession` 关掉最后一个标签时新建的空文档）。它不是标签（标签栏按「有路径」过滤），承载的是「还没有打开任何文件」这个状态。

旧口径把它算作「可复用的标签」之一。移除预览机制后它仍然该被复用——否则每次单击都会在会话列表里多留一份不可见的空会话（一次单击看不见，但这是白占内存且让「空态」出现第二份）。复用条件收紧成「干净」：脏的空文档有真实内容且没有落盘基准，复用等于丢草稿（`openFile` 的守卫在它是前台时会拦下，非前台时这里是第二道）。

## 三、spec 的写法：为什么「打开与固定语义」是移除 + 新增，而「标签栏的显示与形态」是修改

OpenSpec 1.12 的校验器对 MODIFIED 块有一条硬约束：**MODIFIED 要求的 scenario 名必须逐个来自现有 spec**（`findMissingCurrentScenarios`：名字按出现次数配对，少一个就 ERROR「omits scenario(s) the current spec still has」）。scenario 改名 / 删除的唯一合法通道是整条 requirement 走 REMOVED + 新增承接条（先例：归档 change `editable-non-md-files` 把「单内核双模式落地」整条移除、由「单内核双模式与可编辑性落地」承接）。

据此：

- **「打开与固定语义」→ REMOVED + ADDED「打开语义」**：这条 requirement 的名字与内容都建立在「预览 / 固定」二元性上，移除那半边之后名字已不正（它的 6 个 scenario 里有 3 个直接讲预览），重述比缝补诚实。
- **「标签栏的显示与形态」→ MODIFIED**：名字仍然成立（讲的就是标签栏的形态），只有一句（斜体）要删。它的第三个 scenario 名 `dirty 与预览态在标签上可见` 里的「预览态」已不存在——**这个名字按上面的约束保留**（改名只能靠整条移除 + 新增），代价是该 scenario 的断言变成一条否定式（标签栏 MUST NOT 出现第二种标题字形）。这条口径写进 delta 正文里，避免未来读者以为它漏改。
- **`vault-workspace` 的两条 → MODIFIED**（「按 vault 持久化标签列表」与「装载后恢复标签列表」）：不带上它们，归档后 living spec 会与实现**直接矛盾**——那两条分别写着「预览（临时）标签 SHALL NOT 被持久化」与「以固定标签语义逐个打开（MUST NOT 用点击文件树的预览语义）」，而入盘过滤已经删除、恢复走的就是单击那条落点的 `"new"`。同样按上面的约束保留两个历史 scenario 名（`预览标签不入盘` / `固定标签语义`），断言改成与当前实现一致的表述。

## 四、已知边界与遗留（如实登记）

1. **`src/save-controller.ts` 的 `OpenIntent` union 未收窄**：仍写着 `"current" | "preview" | "pinned"`。装配层加了一层显式适配（非 `"current"` 一律按 `"new"`），并注明它可随 union 收窄一起删。不静默把 union 当已收窄用。该文件不在本 change 的 scope 内，落点记在 `docs/backlog.md`。
2. **生成的 bindings 里有一条过时注释**：`src/bindings/VaultSession.ts` 的文档注释仍是「有序的 vault 相对路径（固定标签；预览标签不入盘，design §4.2）」——它由 Rust 侧的 doc comment 经 ts-rs 导出（源在 `src-tauri/`，本 change 的改动面之外）。改它要动 Rust 侧注释并重导出 bindings，归入 docs/backlog.md 的那条收尾 finding。
3. **「用别的方式提示临时态」不再考虑**：移除是本 change 的裁决内容，不保留「以后可能换回来」的钩子（没有开关、没有配置项）。
4. **实现期因 scope 扩张而多做的两件事**（tower 2026-09-27 批准，逐条记明，防「静默扩 scope」）：
   - `EditorSession.preview` 字段与 `src/vault-switcher.ts` 的入盘过滤**一起删掉**（原计划留成死代码，见提议阶段的裁决记录）——理由是一个写「移除」的 change 里留一个恒 false 的同名字段不自洽；
   - `scripts/acceptance/scenarios/14-tabs.md` 与 `31-code-variable-highlight.md` 的预览断言**同批改齐**（套件是行为判定的下沉通道，留一个明知必红的场景等于让 `--check`/全量跑失去意义）。
