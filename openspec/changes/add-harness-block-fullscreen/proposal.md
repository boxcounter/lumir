## Why

Alex 2026-10-23 的需求原话（逐字）：

> 「harness pane 中的 code 和 table 也支持全屏查看（类似 content pane 里的做法）」

**现状**（起草时逐处读过源码）：

- **harness 面板自己渲染 Markdown**：围栏 / 缩进代码块走 `buildCodeBlock`
  （`src/harness-panel.ts:2801`，`<pre class="lumir-hp-codeblock">` + 同一份 `highlightCode` 的 token
  span）；表格走 `renderBlock` 的 `Table` 分支（`:2947`）产出真 `<table>`。两者都**没有**任何块级
  动作钮——面板上只有消息级「复制」与工具行、图片卡片的交互。
- **content pane 已有两条成熟的全屏能力**，形态与关闭路径都稳定：表格全屏
  （`src/table-fullscreen.ts`，深克隆渲染态子树、自然尺寸 + 双向滚动）与代码块全屏
  （`src/code-block-fullscreen.ts` + `src/preview/code-block-content.ts` 的 `planCodeBlock`，按行 +
  头部条 + token，64 KiB 之上降级为单块纯文本）。两者共用同一台浮层状态机
  （`src/overlay-state.ts`：五条关闭路径回同一个 close、Esc 就地消费、blur 兜底、焦点归还由装配层
  注入），并共用 `src/overlay-scope.ts` 的主题镜像。
- **面板的块触发钮家族也已经存在**（`.lumir-block-trigger`，`src/preview/block-trigger.ts` 定义
  共享形态、`src/style.css` 写一份壳 / 热态 / eink 规则）——只是今天只在编辑器里用。

**为什么值得做**：agent 动辄在回复里贴长命令、长 diff、宽表格；harness pane 的宽度是为对话留的，
宽表格被压成一列一列折、长代码块要横向拖。全屏是这类内容唯一能读的形态，而 content pane 已经有
现成的做法——两条能力的**使用体验应当一致**，用户不需要记两套。

## What Changes

逐条对应 `specs/harness/spec.md` 增量里的 requirement：

1. **代码块与表格的全屏入口**（harness，ADDED：对话里的代码块与表格全屏查看）。harness 面板里
   每一块**终态渲染出的**围栏 / 缩进代码块与表格，悬停其可视盒 SHALL 浮现全屏钮（与 content pane
   的块级动作钮同一形态家族、同一钳制口径）；点击打开应用内全屏遮罩。加载中的流式尾块里，块一旦
   成为终态即可用（见第 3 条的口径）。
2. **遮罩复用既有两条能力**（同上）。表格走既有表格全屏（深克隆渲染态子树、自然尺寸 + 双向滚动）；
   代码块走既有代码块全屏（按行 + 头部条 + token 的呈现口径，超上限降级为单块纯文本）。关闭路径
   SHALL 与既有完全一致：Esc、点击遮罩、再次触发（toggle 语义）、焦点离开兜底；关闭后焦点 SHALL
   回到发起它的面板（不是编辑器）。
3. **流式渲染的口径**（同上）。消息还在生长时打开的遮罩 SHALL 是**打开那一刻的快照**：后续增量
   不再灌进遮罩（内容 MUST NOT 一部分新一部分旧、也 MUST NOT 静默变成空）；用户关闭后再打开即看到
   最新内容（D4）。这条与 content pane 两条全屏的「快照」语义同源（表格全屏的文件头明写「打开那
   一刻渲染态 grid 的只读快照副本」）。
4. **只读与不改文档**（同上）。遮罩内容是只读副本（克隆 / 重建都不带事件监听、不在编辑子树内），
   打开与关闭 MUST NOT 改动文档、MUST NOT 改动会话留存、MUST NOT 触发任何发送。

## 起草期取值（已裁决之外，请评审时一并裁）

| # | 取值 | 倾向与理由 | 若你选另一侧 |
|---|---|---|---|
| D1 | 入口 = **hover 触发钮**（右上角内侧），**不加**默认快捷键 | 与 content pane 同族（那里也是钮 + 无默认键：`table.toggle-fullscreen` / `code-block.toggle-fullscreen` 都在「默认不绑键」清单里）；面板里的命中对象不是编辑器 caret，键位命令要另定命中判据 | 若你要快捷键，需要先定「当前块」的判定（焦点在面板内时按消息里的第几块？），是另一条设计 |
| D2 | **复用**既有两个单实例遮罩，不为 harness 另建 | 关闭路径、主题镜像、读屏语义、焦点归还全在同源实现里；单实例也符合「同一时刻只有一个应用模态」 | 另建遮罩 = 复制一套关闭路径与主题规则（REVIEW.md『同一语义两处真源』条），且两套形态必然漂移 |
| D3 | 代码块内容口径 = **复用 `planCodeBlock` 重建**（与 content pane 逐项同形） | 与「类似 content pane 的做法」逐字对齐：行 + 头部条 + token、64 KiB 降级同源 | 克隆 `<pre>`：实现更小，但呈现口径与 content pane 分叉（行号槽 / 头部条 / 超限降级三处会不一样） |
| D4 | 流式中打开 = **打开即快照**（不跟随生长） | content pane 两条全屏都是快照语义；跟随生长要处理「重解析后该块不存在」「用户已滚动时不许抢滚动」两件麻烦事，且会让遮罩一边跳一边读 | 跟随生长：体验更「活」，但要定块身份、增量边界与滚动锚点，属另一条设计 |
| D5 | 读屏名 = 面板内**按消息内序号**（如「Markdown 表格 2」「Markdown 代码块 1」） | 与图片编号同一口径（每条消息内 1-based、只数该类块）；content pane 的编号是按文档的，面板按消息是最近的等价物 | 不带序号：读屏时同一条消息里两个表格无法区分 |

## Non-goals

- **不做块级复制钮**：面板已有消息级复制（复制整条消息）；块级复制是另一条能力，不在本提案。
- **不做图片 / 工具卡片 / 引用卡片的全屏**：只覆盖代码块与表格（Alex 原话的范围）。
- **不加默认快捷键**（D1）。
- **不改 content pane 的两条全屏**：按钮位置、呈现口径、关闭路径逐条不变——本提案只增加**调用方**。
- **不做流式跟随**（D4）。
- **不做编辑 / 导出**：遮罩是只读查看，不回写消息、不改会话留存。
- **不改消息的复制 / 摘录 / 路径链接语义**：钮的加入不改变块内文本的既有交互。

## Impact

- **影响的 specs**：`harness`（ADDED：对话里的代码块与表格全屏查看）。`editor-live-preview` 的两条
  全屏条款被**引用**（同一实现），不改字面。
- **影响的代码 / 系统**：
  - 前端：`src/harness-panel.ts`（块的定位容器与悬停钮、内容计划的构造、读屏名）、
    `src/harness-panel.css`（slot 与钮的位置 class；壳 / 热态 / eink 仍取共享类）、
    `src/main.ts`（两个遮罩端口的注入：打开时记住来源是面板、`restoreFocus` 回面板、
    `themeScopeSource` 取面板根）。
  - 遮罩模块：**零行为改动**（除非主题镜像来源需要多一个注入点，见 design §4.3）。
  - 后端：零改动。
- **关联约束**：
  - ADR 0003 §3：只读查看，不写源文件、不改留存。
  - ADR 0002 §6：遮罩打开是一次 DOM 克隆 / 一次着色计划，量级与既有两条全屏相同（代码块 64 KiB
    上限同源）。
  - 视觉：全套取既有 token 与 `.lumir-block-trigger` 共享类；MUST NOT 引入新色值 / 字号。

## 观测闸三问

- **怎么知道用户用了它**：悬停 + 点击是显式动作；dogfood 可感知；无埋点。
- **怎么知道它有效**：长代码块 / 宽表格悬停出现钮、点开能整块读完；Esc 回到原处；消息还在流式时
  打开看到的是点开那一刻的内容，关闭再开是最新内容。
- **出问题怎么发现**：视觉场景（钮在场与点击后遮罩内容、Esc 关闭后的焦点）、单元测试（内容计划复用
  `planCodeBlock` 的既有断言 + 只读快照语义）、真机验收（流式中打开的快照口径 + 关闭归还焦点）。
