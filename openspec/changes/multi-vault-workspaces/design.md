## 2. 会话数据存哪：与注册项**分开**存放

**方案**：`~/.config/lumir/vault-sessions/<id>.json`（新目录，与注册表目录同级），`id` 是注册项的稳定 id。

**形态**：

```json
{ "version": 1, "tabs": ["docs/a.md", "README.md"], "active": "docs/a.md", "updated_at": 1758096000000 }
```

**为什么不做成注册项的一个字段**（mock 的数据缺口表与 backlog 第 10 条都用了「registry 旁 `last_session`」这个措辞，本 change 把它落在**旁**而不是**内**）：

- 注册项文件是**身份**：id ↔ path 的映射，是 remap 锚点。它的读取路径对解析失败一律容错跳过（`workspaces.rs:95-99` / `:143` / `:168-171`），一旦被跳过，`reconcile_vault`（`:200-216`）会按路径找不到而 `vault_register` **发一个新 id**——身份漂移，且新旧两个文件同时存在后 `find_by_path` 的结果不再确定。
- 会话是**易变的界面状态**：每次标签变化都可能重写。把高频、易变的字段放进身份文件，等于把「会话写坏」升级成「vault 从列表与 remap 候选中消失」。分开存放后，会话损坏的最大后果是「没有标签历史」，符合「只恢复标签列表」这一决策的风险等级。
- 反方向的理由（同一个文件 = 一次原子替换就同时保证身份与会话一致）在本场景里不成立：两者没有必须同时提交的不变式——会话缺失等价于空列表，注册项缺失才是真损失。

**生命周期**：`id` 在重映射后保留（既有口径：注册项只归档不删除、路径恢复即复位，`src-tauri/src/workspaces.rs:44-46`），因此重定位后会话仍然跟随。会话文件不参与注册表治理（`sweep_registry` 不碰它），也不做删除：注册项从不删除，孤儿文件只可能来自手工操作，属无害残留。

**校验与降级**（ADR 0002 §5 的纪律适用于本存储）：`version` 不匹配 / JSON 解析失败 / 字段类型非法 → 当作「没有标签历史」，记一条 warning，不阻断打开；`tabs` 里的条目 SHALL 是合法 vault 相对路径（非绝对路径、不含 `..`、不越出 vault），越界条目丢弃——会话文件在配置目录里，是可手改、也可被其它进程写的面，不该成为「打开 vault 之外的文件」的入口（ADR 0003 的边界）。

## 3. 何时写

| 时点 | 动作 |
|---|---|
| 标签集合 / 顺序 / 激活项变化后 | 防抖落盘（一次写只有几百字节，tmp + rename） |
| 切换 vault 之前 | flush 待写内容（**不得**只依赖防抖定时器：切走之后再没有「当前 vault」这个上下文，写不成了） |
| 退出之前 | flush（与既有退出链路同点；正常退出与「放弃修改并退出」都走） |
| 写失败 | 降级 warning，不拦动作、不影响打开的成功语义（与 `last_vault` 写失败同口径） |

**为什么三个时点都要**：只靠防抖 → 强退 / 崩溃丢掉最后一次改动；只靠切换与退出 → 崩溃丢掉整个会话（用户在 A 里开了 8 个标签、应用崩了、重开发现一个标签都没恢复）。

**写入的串行性**：注册项今天由主线程上的 command 串行写（`workspaces.rs:1-3` 的文件头注释已经写明「应用进程内 command 调用串行，跨进程并发不在本阶段范围」）。会话文件是**独立文件、单一写者**（本 change 新增的写入路径），不参与注册项的读-改-写，因此不需要与 `sweep_registry` 之类的治理写共享串行纪律——这也是分开存放顺带买到的性质：同文件方案必须回答「会话写与治理写互相覆盖怎么办」，分开后这个问题不存在。

## 4. 恢复的执行口径

### 4.1 为什么必须用「固定标签」意图

M149 的打开语义：单击文件树 = 复用可复用的预览标签（**就地替换**，不新开、不改位置）；双击 / ⌘-点击 = 新建固定标签（`openspec/specs/multi-tabs/spec.md` 的「打开与固定语义」）。如果恢复时按默认意图逐个打开，第一个文件开成预览标签，第二个就把它顶掉——**N 个标签的会话只会恢复出 1 个标签**。因此恢复 SHALL 用固定意图逐个打开。这条推导必须写进 spec（`multi-vault-workspaces` 的「装载后恢复标签列表」），否则实现期很容易写成默认意图、并在只有 1–2 个标签时看不出来。

顺序：按存储顺序逐个打开 → 最后激活存储的激活项（`tabs.ts.activateTab`，会触发装配层的 `syncActiveDocument` 一次对齐）。激活项不可用（不在恢复出来的集合里、文件缺失）时退化为第一个可打开的标签。

### 4.2 预览标签不入盘

持久化过滤掉预览标签（`session.preview === true`）。理由：预览标签是「随时会被顶掉的槽位」，而恢复出来的标签一律是固定标签——把预览标签也入盘会得到两种坏结果之一：恢复成固定标签（数量与上次的语义不符），或恢复成预览标签（用户点一下文件树它就消失，恢复结果自己塌掉）。代价是「上次唯一打开的那个文件是预览标签时不会被恢复」，可以接受（最多丢一个文件的便利，不丢内容）。

列表行摘要里的数字与入盘的数字**同源**（都是固定标签数）：摘要的作用是「切之前就知道会恢复什么」，数字如果算上预览标签就是在承诺一件不会发生的事。

### 4.3 跳过与提示

逐个打开时，文件已不在 vault 内 / 打不开 → 跳过并在末尾给**一次**计数提示（文案 V16「{n} 个文件已不在这个 vault 里，已跳过」）。MUST NOT 逐个报错（8 个标签里 3 个缺失会刷出 3 条浮条，把「整窗换上下文」这件事淹掉）。全部不可用 → 空 vault 首入态（标签栏隐藏 + 一句引导），与「这个 vault 还没有打开的文件」同形。

### 4.4 不阻塞

恢复是逐标签的异步装载，树与窗口在恢复开始前就已可用（`loadVault` 完成即出树）。恢复 N 个标签 = N 次读文件；慢卷或大文件会让后面的标签晚出现，但不在键入路径上、也不挡住首帧。**观察点**：dogfood 期若出现「标签一多打开就慢」，先量 `session_restored{count}` 与逐标签耗时，再决定要不要做惰性装载（本 change 不做：M149 的模型是「每个标签一份 `EditorState`」，惰性装载要引入「尚未装载的标签」这个新状态，属独立设计）。

### 4.5 与「无标题缓冲」的关系

M156 的 design §4.5 已把「恢复完成触发 `loadVault` 时，无标题缓冲（`path === undefined`）继承手动打开语义：守卫放行、缓冲丢弃」显式化。本 change 不改变它：标签恢复发生在 `loadVault` 之后，那一份未命名缓冲照旧被 `editor.reset()` 作废，随后由恢复出来的标签占据编辑器。若节点 1 把该语义收紧（M156 登记的那个边缘），本 change 的标签恢复顺序不受影响——收紧的是「什么时候应用恢复结果」，不是「恢复什么」。

## 5. 与 M156 的衔接

### 5.1 时序

```
后端：setup ──► 起 lumir-vault-restore 线程 ──► 恢复完成 ──► vault:restore_finished（唤醒信号）
前端：                                  vault_current（权威）──► loadVault(A, restored=true) ──► 标签恢复(A 的会话)
用户抢先：列表/新增入口 ──► vault_open_path(B) ──► loadVault(B) ──► 标签恢复(B 的会话)；A 的恢复整体丢弃
```

### 5.2 三条边界

1. **MUST NOT 把标签恢复挂进恢复线程或 `open_vault`**：标签是前端状态（每个标签一份 `EditorState`，`src/tabs.ts` + `src/editor.ts`），后端只提供「这个 vault 的会话是什么」这一份数据。放到后端只会多一条「后端读到的东西前端未必能用」的耦合面。
2. **受 M156 的让位规则约束**：用户已在恢复期间成功装载了别的 vault 时，本次恢复整体被丢弃（后端世代号 + 前端 `vaultLoaded`），标签列表一并丢弃——它属于被丢弃的那次恢复。恢复进行中（`restore_pending` 为 `true`）不恢复任何标签（那时还没有 vault 装载，界面是空态 + 恢复中提示）。
3. **完成点是既有信号，不新造时点**：M156 的 `vault:restore_finished` 是权威的「启动恢复已结束」时点（它的 design §8 已经写明「多标签会话恢复若要接启动流程，应复用这条信号」）。本 change 正是这条信号的第一个消费者，MUST NOT 另起一个「启动完成」时点。

### 5.3 为什么本 change 对 `vault-workspace` 只有 ADDED、没有 MODIFIED

- M156 已经对「last_vault 记忆与启动恢复」这条 requirement 提交了 MODIFIED 增量（未归档）。本 change 若再 MODIFY 同一条，两个未归档 change 的增量会在归档时互相覆盖（后归档的那个基于旧文本）。
- 本 change 需要的行为变化全部是**增加值**：列表、切换、会话持久化与恢复，既有 requirement（打开即替换、单激活、注册表治理、`last_vault` 口径、dirty 守卫判据）逐条仍然成立。因此本 change 不动任何既有 requirement，只 ADD 新的，并在新 requirement 里**引用**既有口径（如「按 `multi-tabs` 既有判据拦下」）而不是重述——避免 REVIEW.md 第 8 条那类「同一语义两处真源」。

## 6. 切换流程与并发

```
点列表行 B
  ├─ dirty？（任一有路径的标签脏）
  │    ├─ 是 → 在拦下处给三动作（保存并切换 / 放弃修改并切换 / 取消），不发起打开
  │    └─ 否 → 继续
  ├─ 落盘 A 的会话（flush）→ 调 vault_open_path(B)
  │    ├─ 成功 → loadVault(B)：masthead / 标签栏 / 文件树 / 正文一次性换 → 恢复 B 的会话（若 B 命中 remap 门，走既有两出口浮条）
  │    └─ 失败 → 保留当前上下文，只给一条失败提示（沿用 `src/main.ts:466-470` 的既有口径）
  └─ 切换期间再来的切换请求 → 忽略
```

**必须点明的两条并发纪律**：

1. **一次只处理一个切换**：两个 in-flight 切换（用户在等待期间点了别的行）会互相覆盖——先完成的那个装载上下文，后完成的又覆盖一次，还可能与「落盘 A 的会话」交错。忽略第二次请求是最省且可解释的口径（现状的同步路径下这个窗口很窄，但标签恢复是异步的，窗口会变宽）。
2. **dirty 的检查发生在发起打开之前，且不得被绕开**：M158 r1 评审的 P2-2 就是这个问题——mock 里「点列表行」这条路径绕过了守卫直接切换，与「任一标签 dirty 即拦下」自相矛盾。spec 里为此写了一条 scenario（再次点击仍被拦下）。`loadVault` 里的既有守卫保留为最后防线，不撤。

**判据不变、只加出口**：本 change MUST NOT 新造一套 dirty 判据。判据就是 `save-controller.ts:237-251` 的 `guardVaultSwitch()`（任一**有路径**的标签 dirty 即拦下），也是 `multi-tabs` spec 里已经写死的口径；无标题缓冲（`path === undefined`）的处置沿用 M156 design §4.5 显式化的既有语义（守卫放行）。实现期该函数需要从「返回 boolean + 自己弹文案」扩展为「把被拦下的信息（脏标签数）交给调用方，由切换流程给出三动作」——这是调用形态的调整，判据与文案口径不动。

## 7. 裁决点 A / B 的对照与翻转落点

形态、代价、推荐理由见 proposal 的裁决点一节（表格随 mock 的 §2 同源）。这里只写实现期与 spec 的翻转落点：

| 落点 | 方案 A | 方案 B |
|---|---|---|
| 左栏头部元素 | `button.ft-vault`（名称 + `▾` caret，`aria-haspopup="listbox"` / `aria-expanded`） | 现状 `span.ft-vault-name` + `button.ft-switch-btn`「切换」（点击改为开列表）+ `button.ft-add-btn`「＋」 |
| 新增入口位置 | 浮层底部（分隔线之下），浮层里的**唯一**入口 | 左栏头部常驻；浮层里**不再重复**一个「新增 vault…」 |
| 文案 deck | D4「切换」退场（deck 里标注停用、不复用，与 D30 / D2–D3 的既有处置同形） | D4 保留原样 |
| 视觉基线 | 树头部区域变化（「切换」按钮消失、名称可点） | 树头部多一个 ＋ |
| spec | requirement 的形态句改一处 | 同 |

两种形态都**共用**同一条命令（打开切换器）与同一次浮层渲染，`Cmd-o`、↑↓ / Enter / Esc、列表内容、切换流程全部不变——这是把 A / B 的翻转成本压到「一个元素 + 一句 requirement」的原因。

## 8. 备选方案与拒绝理由

| # | 方案 | 拒绝理由 |
|---|---|---|
| A1 | 会话作为注册项的字段（`last_session` 写进 `workspaces/<id>.json`） | §2：注册项解析失败会被既有读取路径跳过 → 身份漂移；把易变状态混进身份文件扩大了损失面 |
| A2 | 会话存 `config.json` | 配置是用户可编辑面（ADR 0002 §5 的逐字段校验含义就是「非法值只丢弃该字段」），会话与用户配置共享一次写 / 一次校验失败会连带丢会话；且 config 体量无界 |
| A3 | 在恢复线程里读会话、把标签一并建好再回传前端 | 标签是前端状态（M149 的每标签 `EditorState`）；M156 的恢复中态是空态布局，后端也没有建标签的能力，回传只会多一层跨语言的数据搬运 |
| A4 | 恢复时用默认（预览）意图逐个打开 | §4.1：只剩最后一个标签 |
| A5 | 只恢复「最近文件」而不是标签列表 | 决策 3 逐字是「只恢复标签列表」；最近文件是另一个功能 |
| A6 | 列表命令在主线程上顺便探测每个 vault 路径 | 慢挂载卷上 `exists()` 可能长时间不返回——与 M156 对启动路径的同一条论证；列表在用户点开时同步返回体验最好，因此探测要么不做、要么放到主线程之外 |
| A7 | 顺手把用户主动打开 / 切换也异步化（换 mock 的两拍过渡） | M156 的 Non-goal 显式把它留作独立项；本 change 只登记代价（§9），不夹带。异步化会改 `vault_open*` 的时序与前端等待模型，属另一个 change 的量级 |
| A8 | 失效与归档项从列表里过滤掉 | 归档标记的用途是抑制**自动**浮条；列表是用户主动打开的面，过滤掉会让「我一共有几个 vault」这个列表存在的理由落空（§proposal 口径 10） |
| A9 | 列表行显示绝对路径 | 行宽不够且信息量低（mock 的尾部三段口径）；本机绝对路径也不是需要常显的信息 |
| A10 | 切换时清空编辑器再装载（先给空态再填） | 会出现空窗闪烁，且用户可能把空窗当成「vault 被清空了」；保留旧上下文到新 vault 就绪是更稳的口径（mock 的 note_switch 同口径） |

## 9. 风险与未决点

- **慢挂载卷上的可用性探测**：列表命令的可用性状态若来自实时探测，慢卷上可能长时间不返回。口径是「不在主线程探测」；具体做法（`async` command，或干脆只读注册表记账、把权威判定留给点击时的打开失败）留给实现期，spec 只钉「不阻塞主线程」。**未在真机量过**（mock 的「已知未做」也留了这一条）。
- **大 vault 上切换的界面不响应**：同步打开路径（M156 的非目标）意味着 770ms 级 vault 的切换会有等量级的无响应。本 change 不修；登记为后续项（「用户主动打开 / 切换移出主线程」），并应在归档时落一条 backlog 条目或 finding，避免这条账只在 design 里。
- **恢复的启动 IO**：恢复 N 个标签 = N 次读文件，属既有打开链路的代价；观察点是诊断日志（`session_restored{count}`，`log_event` 通道已有），不是门禁。
- **视觉基线**：方案 A 会让「切换」按钮消失、名称变成可点元素——所有含该元素的整页基线都会变。按 AGENTS.md 的硬规则，`--update` 前截图须 Alex 过目；按 REVIEW.md 第 3 条，删除 UI 后要逐一核对该元素出现过的所有整页基线的时间戳是否随本次更新（含「删了却没被容差抓到」的假绿风险，0.001 的容差在 1200×800 下约 960px）。
- **验收套件的表达力**：本 change 的核心场景（两个合成 vault 之间切换、重启后恢复标签、dirty 三动作）需要合成 vault 里有两个可选目录与可预置的会话文件；`configWrite` 对 `last_vault` 的覆盖能力在 M156 的任务清单里（3.4）也是待补项——落地时若发现套件还缺某个动作，应作为套件缺口登记，不静默降级为「人工看过」。
- **未决（节点 1）**：裁决点 1 的 A / B。另有一处可翻转但未单列：**已归档的失效项是否也在列表里**（本 change 选「在」，理由见 proposal 口径 10）；若 Alex 倾向「列表也按归档过滤」，翻转成本是一句 requirement + 一个 scenario。
- **承接与收口**：`docs/backlog.md` 第 10 条（多标签会话恢复）由本 change 承接，归档时更新其状态；新增的「用户主动打开 / 切换异步化」在归档时落 backlog。
