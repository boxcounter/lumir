# Proposal: 多 vault 工作区（vault 列表、切换、按 vault 恢复标签列表）

- Change ID: multi-vault-workspaces
- 日期: 2026-09-17
- 角色: Alex Lee（评审/裁决），AI agent（起草）

## Why

今天 vault 是「只看得见当前那一个」的：没有列表、没有键位、切换带不走任何现场。

- **入口只有一个、语义是替换**：左栏树头部的「切换」文字按钮（`src/tree.ts:197-204`，M30）点击直接弹系统目录选择器，把当前 vault 换掉。界面上任何地方都看不到「我一共有几个 vault」。
- **盘上已有数据，但没有消费它的面**：注册表 `~/.config/lumir/workspaces/*.json`（字段 id / path，M126，`src-tauri/src/workspaces.rs:37-50`）已存在，但只被两类内部用途消费——remap 候选（`remap_candidates`，`src-tauri/src/workspaces.rs:131`，按失效路径过滤）与打开路径的注册判定（`is_registered`，`:181`）。没有「列出注册表」的命令，也没有列表 UI。失效与归档标记（`missing_since` / `archived_at`）带 `#[ts(skip)]`（`:41-49`），不进 webview 契约，前端画不出「路径不可用」。
- **零标签会话持久化**：只有 `last_vault` 一个配置项（`src-tauri/src/config.rs:48`）——重启恢复一个 vault 的路径，不恢复任何标签。`docs/backlog.md` 第 10 条已把「多标签会话恢复」列为待裁决，v1 明确不做。
- **零键位**：`src/keys.ts` 里没有任何 vault 相关绑定（`grep -i vault src/keys.ts` 无命中），打开与切换只能用鼠标——与「Emacs keybinding PKM」的阶段定位（ADR 0006）不一致。
- **切换会静默丢内容**：切换 vault 的守卫（`src/save-controller.ts:237-251`）拦下后只给一句无动作的 sticky 文案，出口是用户自己回编辑器存好再重试。

**四个决策已由 Alex 定**（逐字，本 change 的落地前提）：

> 「一个 space 只对应一个 vault」
> 「一次只激活一个 space、切换即整个窗口换上下文」
> 「只恢复标签列表」
> 「命名继续用 vault，不用 space」

**UX mock 已合并**：`demo/multi-vault.html`（M158，r2 评审 clean、已并入 master）。Alex 已看过形态并采纳进入提案阶段；页内说明面板有完整状态机与 13 条待裁决。**入口 A / B 两种形态他没有点名单选**，因此作为本 proposal 唯一保留的裁决点（见下）。

**与 M156（`startup-restore-off-main-thread`）的关系**：那个 change 已并入 master 的 change 列表（未归档），它给启动恢复立了契约面——`restore_pending` 三态、`vault:restore_finished` 完成信号、`vault_current` 为权威状态、世代号让位规则。本 change 的标签恢复挂在它的完成点之后，**不修改它的任何 requirement**（分工见 design §5）。

## What Changes

七条 requirement（全部落在 `vault-workspace` capability，见 `specs/vault-workspace/spec.md`）。人话版本：

1. **vault 列表可见**（requirement「vault 列表与可见性」）：新增列出注册表的命令，给出每个 vault 的显示名（= 目录名）、上次打开时间、路径可用性、可恢复的标签数。失效项不静默移除（列表是用户主动打开的面，与自动浮条的口径分开），列表按最近打开倒序。
2. **切换器入口与浮层**（requirement「vault 切换器入口与列表浮层」）：文件树头部给一个常驻入口（形态 = 裁决点 1），只有一个 vault 时也在；浮层与大纲浮层同一手法（绝对定位、不占常驻空间）；新增「打开 vault 切换器」命令 + 默认键位，浮层内 ↑↓ / Enter / Esc（与大纲浮层 D86 同口径）。未装载 vault 时（含启动恢复进行中）没有列表入口，空态沿用既有 D5 / D6。
3. **新增 vault**（requirement「新增 vault」）：列表里的「新增 vault…」走既有目录选择器；选中未注册目录 = 登记为新的 vault 并**自动切过去**；命中 remap 候选门时沿用既有两个出口浮条，不绕过；不要求命名。
4. **切换 = 整窗换上下文**（requirement「vault 切换与整窗上下文替换」）：单激活；复用既有打开链路，不新增第二条装载通道；切换器把守卫的出口放在拦下它的地方（保存并切换 / 放弃修改并切换 / 取消，与关标签确认 D93 同形）；目标打开失败保留当前 vault；一次只处理一个切换。
5. **失效 vault 的处置**（requirement「失效 vault 的处置」）：路径不可用的行不可切换，只给「重新定位…」（复用既有 `vault_remap`），重定位成功即打开；不提供「从列表移除」。
6. **按 vault 持久化标签列表**（requirement「按 vault 持久化标签列表」）：新增记录「有序的 vault 相对路径 + 激活项」，键控在注册项 id 上；只存这个列表——不存未保存内容、撤销史、光标与滚动位置；**预览标签不入盘**；变化后防抖写、切换前与退出前 flush；写失败只降级 warning。
7. **装载后恢复标签列表**（requirement「装载后恢复标签列表」）：每次 vault 装载成功后（切换 / 新增后 / 启动恢复完成）按列表重建标签，**一律按固定标签**（用预览语义会让第 2 个起互相顶掉，只剩最后一个）；激活项不可用时退化为第一个；文件已不在 vault 内时跳过并给一次计数提示；不恢复光标与滚动。启动恢复路径上，标签恢复发生在装载**之后**，并受 M156 的让位规则约束。

## 需要你裁决的一点：新增入口摆法 A / B

这是本 proposal 唯一保留给你翻转的裁决点（其余建议口径见下一节，你不点头即按建议实现）。

| 维度 | 方案 A · 列表内新增（推荐） | 方案 B · 左栏固定入口 |
|---|---|---|
| 新增入口 | 列表浮层底部「新增 vault…」 | 左栏头部常驻 ＋，与「切换」并列 |
| 切换入口 | vault 名称本身（＋ `▾` caret 作可点提示）；现状「切换」文字按钮退场 | 沿用「切换」文字按钮（点击改为开列表），＋ 是新增入口 |
| 左栏头部控件数 | 1（名称 + caret） | 3（名称 + 切换 + ＋） |
| 点到新增 | 两步（开列表 → 点底部） | 一步 |
| D4「切换」文案 | 退场（进 deck 处置） | 保留，不动已入库文案 |
| 代价 | 可点性靠 caret 提示，不如文字标签直白 | 244px 头部密度上升；名称与「切换」两个控件做近义的事 |

**推荐 A**，理由：切换是中频动作（一个用户通常 1–3 个 vault），新增是低频动作（装一次就完了）——把低频动作收进中频入口，左栏保持安静，与 M52 定稿的「低频动作弱化、朱红只在需要分流处出现」同一条线。反方向的理由（B 的价值）是新增一键可达，但这条价值在 1–3 个 vault 的真实用量下不足以换左栏头部的密度。

**翻转成本**：实现前翻到 B 只落在两处——左栏头部的那一个元素（名称 vs 切换按钮 + ＋），以及 `Cmd-o` 打开的那条命令仍然照开列表。spec 的形状随之改一句话（requirement 里已把两种形态并列写明），无实现返工。控制台里切到「并排对照」可以一眼比。

### 本 change 自己引入的实现面口径（mock 没画到的）

| 面 | 建议口径 | 理由 |
|---|---|---|
| 标签列表存哪 | 配置目录下的 `vault-sessions/<id>.json`（新目录，与注册表同级） | 存进注册项文件会把「易变的界面状态」混进「身份文件」：注册项的解析失败在既有读取路径里一律被当作无效项跳过（`workspaces.rs:95` / `:143` / `:168`），会话损坏会连带让 vault 从列表与 remap 候选中消失并触发新 id 注册。分开存放把失败面隔开：会话损坏只剩「没有标签历史」 |
| 存什么 | 有序 vault 相对路径 + 激活项（+ 版本号、更新时间） | 相对路径是既有标签模型的口径（`FsEntry.path` 就是 vault 相对路径，`src-tauri/src/fs_io.rs:54`；D91 也用相对路径），vault 重定位后仍然有效；绝对路径在重定位后整批失效 |
| 何时写 | 标签集合 / 顺序 / 激活项变化后防抖写；**切换前与退出前 flush** | 只靠防抖会被强退与崩溃吃掉最后一次；只靠切换/退出写则崩溃丢掉整个会话 |
| 恢复怎么开 | 逐个用既有 `openFile` 的**固定标签**意图，最后激活存储的激活项 | 用默认（预览）意图会让第二个起就地顶掉前一个，恢复结果只剩一个标签——一个必须写进 spec 的推导（M149 的预览语义） |
| 恢复的代价 | 逐标签装载、不阻塞树与窗口 | 恢复 N 个标签就是 N 次读文件；慢卷上不能让树等它 |
| 切换复用哪条链路 | 既有 `vault_open_path` / `vault_open` | 现状的 `pickVault`（`src/main.ts:436-471`）已经处理了 remap 门与「已有 vault 时打开失败不抹树」；新增第二条通道就会复制这两条语义 |
| 列表命令的线程 | 不在 Tauri 主线程上做 vault 路径探测（慢挂载卷上 `exists()` 可能长时间不返回） | 与 M156 对启动路径的同一条论证（`is_dir()` 在未挂载网络卷上可能长时间阻塞） |
| 新增 `last_opened_at` | 打开成功时写（与 `last_vault` 同一次成功路径） | 排序与「上次打开时间」都需要它；写在失败路径上会让失败的开也改动排序 |
| basename 派生 | 收敛为单一函数 | 今天 `src/tree.ts:240` 与 `src/main.ts:498` 各有一份同名派生（REVIEW.md 第 8 条同族），列表是第三个消费点，正好一起收 |

## 语义变化（Alex 需要知悉）

1. **打开 / 切到一个用过的 vault 会自动重开它上次的标签**（本 change 最显眼的行为变化，决策 3 的落地）。首次打开某 vault（无历史）仍是空态。
2. **「切换」按钮的语义变化**：现状点击直弹系统目录选择器；此后点击开列表（方案 A 下这个按钮退场，改为名称本身可点）。
3. **新增 vault 会自动切过去**（决策建议 3）：上下文被换到新 vault，用户要回原 vault 得再切一次。
4. **dirty 拦截从「无动作提示」变成三动作**（建议 9）：不影响判据（仍是「任一有路径的标签有未保存修改」），只增加出口。
5. **大 vault 上切换有几拍界面不响应**：用户主动打开与切换今天走同步 command（M156 的非目标里明确不动它），大 vault 下与启动卡顿同源，只是发生在主动动作上。本 change 不修、登记为后续项。
6. **配置目录多一个子目录**：`vault-sessions/`（只在配置目录，不碰 vault、不违反「不改写源文件」铁律）。

## Non-goals

- **不引入 space 概念**：界面与契约继续只用 vault（决策 4 逐字：「命名继续用 vault，不用 space」）。
- **不做独立显示名与重命名**：显示名 = 目录 basename；要命名就是另一件事（registry 加 `display_name` + 改名入口）。
- **不做多 vault 同时打开**：不做分屏、不做多窗口、不做「在一个窗口里同时看两个 vault」（决策 2 已定单激活）。
- **不恢复标签以外的东西**：光标位置、滚动位置、撤销史、未保存内容一律不恢复；不做崩溃前的编辑内容恢复（那是既有 recovery 链路的职责，不在本 change）。
- **不把用户主动打开 / 切换移出主线程**：M156 显式把它列为独立项（「不改用户主动打开 vault 那条路径的同步性」），本 change 只登记代价，不夹带异步化，也不做过渡态 UI。
- **不做「从列表移除 / 删除 vault」**：注册项只归档不删除（既有治理口径）。
- **不做标签排序的拖拽、不做标签分组**（M149 已排除拖拽排序）。
- **不改 `last_vault` 的口径与配置 schema**（ADR 0002 §5），也不修改 `startup-restore-off-main-thread` 的任何 requirement——本 change 的标签恢复挂在它的完成信号之后。
- **不新增 perf 端点、不改阈值与门禁口径**：切换走既有打开链路，冷启动读数不受本 change 影响。
- **不写 vault**（ADR 0003）：会话只落在配置目录。
- **不做列表的常驻 UI**：浮层不占常驻行高。

## Impact

- **影响的 specs**：`vault-workspace`（7 条 ADDED requirement；无 MODIFIED / REMOVED）、`multi-tabs`（1 条 MODIFIED requirement：「未命名文档的 dirty 守卫」——只改其第三个 scenario 的提示口径与第三段的提示内容，判据原文不动，见 `specs/multi-tabs/spec.md`）。其余 capability 不动：`file-tree` 的空态不变，`perf-measurement` 无 delta。
  - 为什么 `multi-tabs` 这次需要 MODIFIED 而 `vault-workspace` 不需要：对 `vault-workspace` 的零 MODIFIED 是为了规避与 M156 未归档 MODIFIED 增量的归档互覆；`multi-tabs` 上没有任何未归档 change 持有增量（M156 与 toc-popover 都不碰它），加 MODIFIED 无冲突风险。若不加，归档后 living spec 会留下一条与本 change 行为直接矛盾的 scenario（M161 r1 P2-1）。
