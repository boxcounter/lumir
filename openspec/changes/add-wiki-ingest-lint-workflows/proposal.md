## Why

1. **门槛在「机制的精通与纪律」，而产品目的正是消掉它**（Alex 原话）。现状的 LLM Wiki 实践要求人记得
   三件事：什么时候该 ingest、lint 该查哪几项、写完要更新 index 与 log。任何一件漏掉，错误都会以
   「后续 ingest 把错结论当事实引用」的形式复利。产品要做的不是把这三件事写得更清楚（文档已经很清楚），
   而是让漏掉它们变得困难：入口可发现、机械检查不花 token、纪律由后置校验兜底。
2. **确定性计算先于 LLM**（真源「调度策略」第 1 条）。孤儿页（入链为零）、断链、index 漂移是纯图遍历，
   本仓已有现成的解析与图结构（`src-tauri/src/link_graph.rs` 的 `LinkGraph`：路径解析、锚点解析、
   名称→路径的多态解析结果）。把它们交给 LLM 逐页读，是在用最贵的方式做最便宜的判断；做成机制阶段
   则每次运行零 token 开销、结果可复现。
3. **累积产物的错误方向不对称**（真源「错误方向不对称」）。漏记可补、错记污染。所以 wiki 的写入必须
   比普通对话更保守：写范围可声明、写入可逐个批准、来源必须可追、写完必须过机械校验。这三条都是
   机制能兜住的，不依赖模型当次的心情。
4. **流程知识必须可编辑、可评审、随 vault 走**（真源「机制进代码、策略进文档」）。个人 vault 的
   wiki 与公司治理 vault 的 wiki 在页面类型、合并规则、lint 清单上必然不同；把这些写进代码，等于
   把某一个人的 schema 变成产品语义。工作流定义与 vault 配置放在 vault 里，改流程只改文件。
5. **入口是能力的一部分**。要求用户记住「说 ingest 加路径」是产品失败的一种：用户不知道能力存在，
   或者在需要它的那一刻想不起正确的说法。可发现性应由生产者负责（真源设计原则第 2 条的同一逻辑）：
   能力出现在文件树右键、命令与工作流列表里，每一项带一句人话说明。
6. **现在做的成本最低，用后删的成本也最低**（Alex 裁决）。本 change 零代码；工作流定义是文本，
   删掉一个能力 = 删一个文件或改一个开关，不牵动数据结构与留存格式。真源把「验证」搬到建成后的
   真实使用中，本提案的观测节就是那次验证的读数口径。

## What Changes

单一新 capability `wiki-workflows`（含「vault 级配置」这个首个住户）。设计取舍与实现细节见
[design.md](design.md)，逐条对应 [specs/wiki-workflows/spec.md](specs/wiki-workflows/spec.md) 的
requirement。

### A. Vault 级配置与启用（`<vault>/.lumir/config.json`）

1. **首个 vault 级配置文件**：`<vault>/.lumir/config.json`，`[wiki]` 为第一个住户。键：`enabled`、
   `dir`、`index`、`log`、`inbox`、`sources`。全部路径为 **vault 相对路径**，校验拒绝绝对路径、
   `..` 逃逸与指向 vault 之外的目标；未知键忽略（与既有配置口径一致），非法值回落默认 + 一条人话
   warning，不阻断 vault 打开（ADR 0002 第 5 条）。`sources` 缺省为空数组——机制不内置任何目录名，
   启用时由用户从 vault 的顶层目录里勾选声明。
2. **配置随 vault 走**：启用状态是 vault 的属性，不是某台机器的属性——daily vault 在 iCloud 中同步，
   换机后同一个 vault 的启用状态必须跟着来。这是选 vault 内配置文件而非全局 `config.json` 的理由。
3. **启用与骨架**：用户在 UI 里点「启用 wiki」→ 写 `[wiki] enabled = true`；若 `dir` / `index` / `log`
   在盘上缺失，同一动作按用户确认创建**空骨架**（目录 + 空文件），MUST NOT 写入任何页面模板、字段
   清单或 schema 文案——schema 属于 vault 的 AGENTS.md，机制不生成它。已存在的文件 MUST NOT 被覆盖。
4. **未启用即隐身**：未启用（或配置文件不可读、iCloud 占位未下载）时，所有 wiki 入口不出现、工作流
   不可运行、诊断里每个被拒的入口调用都有明确原因。MUST NOT 用「默认开启」代替用户的选择。

### B. 工作流定义（`<vault>/.lumir/workflows/**/*.md`）

1. **格式**：Markdown + YAML frontmatter，身份只看 `name`。字段闭集合：`name`、`description`、
   `inputs`、`tools`、`write_scope`、`gate`、`checks`、`requires_log`、`unattended`、`model`。
   正文是该工作流的**流程契约**（人可读的步骤说明），与 vault AGENTS.md 的冲突以 vault 约定为准
   （正文里明确写出这条优先级）。
2. **内置两条默认定义**：`wiki-ingest` 与 `wiki-lint`，以数据形式编入二进制（先例：内建 `explore`
   子代理），可被 vault 级同名定义覆盖，生效版本可在界面上只读查看。内置只给**流程骨架**与安全约定，
   MUST NOT 含页面类型、页面模板、合并规则、lint 条目清单或任何路径样例。
3. **发现与生效**：打开工作流列表时扫描一次（不做 watcher）；定义非法时逐条丢弃 + 点名 warning，
   其余照常；同名定义 vault 级覆盖内置；来源（内置 / vault）在界面上标出。
4. **无魔法口令**：流程知识落在定义文件与 vault AGENTS.md，用户不需要记住任何命令词；需要记住的
   只有「在哪点」，而那是界面问题。

### C. 确定性检查（机制阶段，不是新工具）

1. **闭集合四个检查器**：`link_graph`（断链 + 入链为零的页，排除 index 内的链接）、
   `index_membership`（`dir` 内文件与 index 链接的双向差集）、`frontmatter_fields`（按声明校验
   必填字段在场与类型）、`date_expiry`（按声明的日期字段判过期）。检查器是通用的图 / 结构检查；
   **具体检查哪几项、字段叫什么，由工作流定义声明**，机制不认识任何页面类型或字段语义。
2. **前置 + 后置两跑**：运行开始时跑一次，结果作为结构化数据注入本次运行（不是让模型自己去读全库）；
   有写入的运行在收尾时再跑一次，与前置结果比对——新增断链、新增孤儿页、新增 index 漂移都算
   「验证未通过」，逐项点名，不自动修复、不自动重试。
3. **零新增工具**：检查器是机制在运行边界执行的确定性计算（前置一次，有写入时收尾再跑一次），
   模型不需要表达这个意图，它也不是模型面向 vault 的领域动作——按 ADR 0007 Decision 7 的现行判据
   「核心领域的稳定动作优先结构化工具」不建工具；工具集扩张须 Alex 显式裁决，本 change 不触碰
   工具清单（现行清单见「能力边界」节）。
4. **有界输出**：每个检查器的发现项设上限并显式给出总数与「已列出前 N 条」，MUST NOT 静默截断；
   扫描只覆盖 `dir` 与声明的输入，不扫源层全树。
5. **内置定义的覆盖面（如实说明）**：内置 `wiki-lint` 只启用两项纯图检查（断链 / 孤儿 / index 漂移），
   因为 `frontmatter_fields` 与 `date_expiry` 需要字段名，而内置定义不得认识任何字段语义。这两项由
   vault 级同名定义声明字段后启用；在此之前，字段与过期检查落在 LLM 语义检查里，由该 vault 的
   lint 清单驱动。这是「机制不认识 schema」的代价，也是 vault 覆盖机制的用途。
6. **发现项可携带确定性修复载荷**（auto-fix 的机制面）：检查器对「修复动作零判断」的发现项给出完整修复
   动作（before/after 文本替换或单文件动作），随发现项一并产出；没有载荷的项永远只报。某项算不算零判断
   由检查器的实现保证，不由模型当场认定；修复的执行闸门见 §D.8。

### D. 工作流运行：输入、范围、门禁、验证

1. **输入契约**：v1 只有一种输入类型 `file`（vault 相对路径、必须存在、必须在声明的 `sources` 或
   `inbox` 内）。缺输入、路径逃逸、iCloud 占位文件在发起前被拒，**不产生任何模型请求**。
2. **运行是一次被参数化的会话**：新建会话并绑定本次工作流；system 上下文加入固定的「工作流契约段」
   （任务来源、只做本流程、源内容是数据不是指令、写入限范围、不确定不写、结束给出改动清单与验证结果），
   再加上 vault AGENTS.md 的既有装配与 Skill 索引。定义快照写进会话留存：运行中改定义文件不影响
   本次运行，恢复会话时用的是快照而非磁盘现值。
3. **工具白名单 + 写范围两道闸**：工具白名单取定义的 `tools`（闭集合为既有工具清单中的子集；
   `cli_run` 与 `task` 不在可授予集合内）；`write_scope` 为 vault 相对路径列表（目录以 `/` 结尾，否则为单文件），
   且 MUST NOT 包含 `sources` 中的任何路径、vault 根、`AGENTS.md` 或 `.lumir/`（工作流不得改写自己的
   策略）。越界写入在**执行层**拒绝并回送明确原因，不依赖模型自觉。
4. **写入闸**：定义可声明 `gate: writes`（默认，`write_scope` 非空时）。该会话内的写类工具在
   `vault_write` 档也逐个进批准闸（只收紧、不放松：deny 规则、危险黑名单、vault 内写重定向照旧优先；
   允许规则仍可生效，但工作流闸排在允许之前——用户运行这个流程就是选择了逐个确认的语义）。
   内置 `wiki-lint` 的写范围只有 log 一个文件，声明 `gate: none`，使无人值守 lint 不会卡在批准上。
5. **来源不可变**：有写入的运行在发起前记录输入源的内容哈希，收尾时重算；不一致则以
   `source_changed` 判验证未通过并如实呈现（可能是用户同时在别的应用里编辑，也可能是 iCloud 占位
   物化），MUST NOT 静默忽略。
6. **log 兜底**：定义可声明 `requires_log: true`（内置两条都声明），收尾校验 log 文件在本次运行期间
   确有变化；没变即判验证未通过。格式是否正确由 lint 的 LLM 语义检查负责，机制只判「有没有记」。
7. **失败语义**：任何失败都落终态（不出现「永远转圈」）：输入被拒、定义非法、前置检查失败、模型
   失败、验证未通过各有明确状态与原因码；验证未通过不撤销已写入的内容（写入已经过人审），只在
   会话里给出逐项差异并提示下一步。
8. **auto-fix 的执行闸门**：修复动作走与模型写入完全相同的管线——`write_scope` 必须覆盖目标文件、批准
   语义按定义的 `gate`、执行层越界拒绝照旧，MUST NOT 出现第二条写入通道。内置 `wiki-lint`（写范围仅 log、
   `gate: none`）因此不修页；vault 级定义要启用修复须自行扩写范围并承担对应批准语义。无人值守运行不修页
   （见 §F 与 Non-goals）。

### E. 触发与入口（降低门槛的落法）

1. **文件树右键**：源层内的 Markdown 文件上出现「收进 wiki」（仅 wiki 已启用时）；这是 ingest 的
   默认入口，不需要用户先想起任何词。
2. **工作流选择器**：一个入口列出全部生效定义（名字 + 一句 description + 所需输入），选中后按
   `inputs` 收集输入；已打开的文件在符合条件时预填。选择器复用既有浮层控件，不新增视觉语言。
3. **命令与菜单**：`wiki.run` 命令与菜单项落到同一实现；**不新增默认键位**（避免与既有键位表、
   原生菜单 accelerator 的冲突核对成本），用户可经 `[keys]` 自行绑定。
4. **运行中的可见面**：会话开头一张「工作流」卡片（名字、输入、确定性检查摘要、可展开查看生效
   定义），收尾时卡片上追加验证结果行（通过 / 未通过 + 原因 + 逐项差异入口）。过程与结论仍在
   正常 transcript 里，不另建面板。
5. **建议模式仍只是约定**：会话里识别到值得沉淀的结论时，模型可以问一句并把结论落到 `_inbox`
   暂存文件（同一套写范围与批准闸），**不自动写 wiki**。会话内容不是 v1 的 ingest 输入——每个进入
   wiki 的结论都必须能追到一份文件来源，这是保守写入的前提。

### F. 与 cron 的依赖：调度归 cron，工作流定义独立

1. **本 capability 不含任何定时器**。ingest / lint 的定时触发由 change `add-cron-runtime-daemon`
   承载：cron 任务新增一个可选字段 `workflow`（与 `prompt` 二选一）+ `inputs`，运行交接时把
   「工作流名 + 输入」交给本 capability 的运行装配。
2. **只允许无人值守定义被调度**：`unattended: true` 的定义可被 cron 触发（内置 `wiki-lint` 为 true，
   `wiki-ingest` 为 false——没有对话与人审的 ingest 不成立）。cron 侧对 `unattended: false` 的
   工作流 MUST 拒绝并落诊断。
3. **审批语义沿用 cron**：无人值守运行遇到需批准的工具调用即中止（不挂起）；因此「`unattended: true`
   + `gate: writes` + 非空写范围」的组合在装载期给一条 warning（它永远不会在无人值守下跑完）。
4. **两个 change 可独立落地**：本 capability 的手动入口不依赖 cron；cron 侧未落地时，lint 仍可手动
   运行。依赖关系写清但不等它。

### G. 观测：怎么知道用了 / 有效 / 出问题怎么发现

诊断事件（本地 JSONL `~/.config/lumir/logs/YYYY-MM-DD.jsonl`，每行一个事件；字段键由 `logging.rs`
的 BTreeMap 按**字母序**输出，下面命令的匹配顺序据此写死）：

- `wiki_enabled`：`dir` / `index` / `log` 是否本次创建、`sources` 数量。
- `wiki_workflow_started`：工作流名、来源（内置 / vault）、入口（文件树 / 选择器 / 命令 / cron）、
  输入类型、工具白名单、写范围、`gate`、检查项、模型、定义快照哈希。
- `wiki_workflow_preflight`：每个检查器的发现数、扫描文件数、耗时、是否有界截断、总发现数。
- `wiki_workflow_finished`：终态（completed / failed / aborted / verification_failed）、原因码、
  轮次、tokens、写工具调用计数（按 `patch` / `create` / `move` / `delete` 拆分）、验证逐项结果、
  log 是否变化、源是否变化、耗时。
- `wiki_verify_failed`：检查项、新增发现项（路径 + 目标）的前若干条与总数。
- `wiki_workflow_rejected`：原因（disabled / definition_invalid / input_invalid / source_missing /
  source_placeholder / not_unattended / scope_invalid / workflow_not_found）。

**怎么知道用了**：

```bash
rg -c '"event":"wiki_workflow_started"' ~/.config/lumir/logs/
rg --no-filename -o -r '$1' '"entry":"([a-z_]+)".*"event":"wiki_workflow_started"' ~/.config/lumir/logs/ | sort | uniq -c
```

第二条按入口分桶：`--no-filename` 去掉文件名前缀，`-r '$1'` 只打印入口名（`entry` 在 `event` 之前是
键序决定的，模式必须同序，否则恒为空匹配）。无命中时 `rg` 退出码 1，属正常（日志里还没有 wiki 事件），
不是命令写错。

**怎么知道有效**：四个读数，各给可执行命令。`cat … 2>/dev/null | jq` 的写法同时覆盖「日志目录为空 /
文件不存在」：`jq` 读到空流，输出空（④ 会明确打印「数据不足」），退出码 0。

① 写入产出（每次 ingest 的新建 / 改写量）：

```bash
cat ~/.config/lumir/logs/*.jsonl 2>/dev/null | jq -r 'select(.event=="wiki_workflow_finished" and .workflow=="wiki-ingest") | "\(.ts)\tcreate=\(.write_calls.create // 0)\tpatch=\(.write_calls.patch // 0)"'
```

② 机械健康度走势（每次 preflight 的各项发现数）：

```bash
cat ~/.config/lumir/logs/*.jsonl 2>/dev/null | jq -r 'select(.event=="wiki_workflow_preflight") | .ts as $t | .results[] | "\($t)\t\(.kind)=\(.total)"' | sort
```

③ 验证失败比例（终态分桶）：

```bash
cat ~/.config/lumir/logs/*.jsonl 2>/dev/null | jq -r 'select(.event=="wiki_workflow_finished") | .status' | sort | uniq -c
```

④ 门槛是否真的降了（启用 → 首次成功 ingest 的间隔）：

```bash
cat ~/.config/lumir/logs/*.jsonl 2>/dev/null | jq -s -r '([.[]?|select(.event=="wiki_enabled")]|sort_by(.ts)|.[0].ts) as $a | ([.[]?|select(.event=="wiki_workflow_finished" and .workflow=="wiki-ingest" and .status=="completed")]|sort_by(.ts)|.[0].ts) as $b | if $a==null or $b==null then "数据不足（尚未启用或尚无成功 ingest）" else "启用到首次成功 ingest：\((($b|sub("\\.[0-9]+Z$";"Z")|fromdateiso8601)-($a|sub("\\.[0-9]+Z$";"Z")|fromdateiso8601))) 秒" end'
```

复发读数取 ② 的时间序列：同一检查器的 `total` 在连续两次 lint 的 preflight 里都不下降，说明上一次
的修复没落地或 schema 有缺口（后者应触发改 AGENTS.md 的提议）；逐项差异（哪条断链还在）在两次 lint
的报告里对，机制事件只带计数，不重复存明细。

**出问题怎么发现**：

```bash
rg --no-filename -o -r '$1' '"event":"wiki_workflow_rejected".*"reason":"([a-z_]+)"' ~/.config/lumir/logs/ | sort | uniq -c
cat ~/.config/lumir/logs/*.jsonl 2>/dev/null | jq -r 'select(.event=="wiki_workflow_finished") | "\(.status)\t\(.reason)"' | sort | uniq -c
cat ~/.config/lumir/logs/*.jsonl 2>/dev/null | jq -r 'select(.event=="wiki_verify_failed") | "\(.ts)\t\(.reason)\t\(.new_items_total)"'
```

入口被拒与运行失败各有终态与原因码，不出现静默跳过；定义非法、检查器声明非法、写范围非法各产一条
点名 warning；验证未通过逐项点名（新增断链 / 新增孤儿 / index 漂移 / log 未变化 / 源被改动）；
iCloud 占位文件与冲突副本只报告不自动处理；cron 触发的失败沿用 cron 的结果通知与诊断。真机验收覆盖
入口、禁用态、输入拒绝、检查器结果、写范围越界、写入闸、验证未通过与无人值守触发（见 tasks §7）。

以上命令用 macOS 自带的 `jq` 1.7 与 `rg` 在起草期实测跑过（合成日志：三问各有非空读数；真实日志
目录尚无 wiki 事件：`rg` 无命中退出码 1、`jq` 输出空或「数据不足」且退出码 0）。实现期按 tasks §6.4
在真机上复跑一遍并把读数写进完成报告。

## 能力边界（本 change 刻意不碰的东西）

- **不新增工具**：工具清单与 ADR 0007 Decision 7 的现行清单一致——vault 操作工具 9 件（含
  `vault_list`）、编排工具 1 件（`task`）、调度工具 3 件。确定性检查是机制阶段，不是模型可调用的
  工具；工作流也不能把 `cli_run` 或 `task` 授给自己（前者写范围管不住任意命令，后者委派绕开本
  流程的门禁与记账）。
- **不新增触发源**：用户输入与 cron 仍是仅有的两个触发源；工作流是被参数化的一次运行，不是新的
  运行原语。因此也不触碰「触发 → 装配 → 工具循环 → 留存」公共层（那是 change
  `add-harness-subagents` 的兑现面）。
- **不新增调度与并发**：没有定时器、没有并行、没有后台 run；无人值守由 cron 的槽位承载。
- **不改写源文件**（ADR 0003 铁律）：源层只读由三道叠加保证——`write_scope` 校验拒绝源路径、
  执行层越界拒绝、收尾哈希比对。
- **不把 schema 写进代码**：页面类型、字段清单、合并规则、lint 条目清单、日志格式全部只在 vault 的
  AGENTS.md 与工作流定义里；代码里 MUST NOT 出现任何具体页面类型名、字段名或日志前缀字面量。

## Non-goals

- **不做自动 ingest / 会话结束自动沉淀**：没有用户发起的运行就不读源、不写页；建议模式只是
  「问一句 + 落 `_inbox` 暂存」的约定，不是自动写入通道。
- **不做 Query 机制**：问答是普通对话，召回顺序与归档规则由 vault 的 AGENTS.md 定义，机制不介入。
- **不做 embedding / 向量检索**：与真源的召回五层谱系一致，本 capability 不建索引。
- **不做跨 vault 链接或跨 vault 聚合**：领域边界是真实的；一个工作流只服务一个 vault。
- **不做页面模板生成器 / schema 初始化文案**：启用只建空骨架，schema 由人（或 agent 在用户要求下）
  写进 vault 文档。
- **不做 lint 全自动修页**：无人值守、零人审地改页不在本 change；零判断（格式类）发现项的 auto-fix 经
  既有写入闸与人审执行（设计取舍 16、§D.8），需要判断的修复仍走新一次 ingest 或人工。
- **不做按页 / 局部范围的 lint**：v1 的检查范围是整个 wiki 目录，范围收窄等真实需求出现再加。
- **不做定时调度**：由 cron 承载（见 What Changes F）。
- **不做多源批量 ingest**：一次运行一个源文件；批量是多次运行或未来的子代理任务。
- **不做 PDF / 音视频源**：与 vault 草稿的源层口径一致，转换在外部完成后再作为普通文件源。
- **v1 不投递图片源给模型**：既有图片投递协议只服务 composer 附件，`vault_read` 是纯文本读取，
  没有「从 vault 路径读图给模型」的链路。工作流 MUST 检测源里引用的本地图片并在首次消息与会话
  卡片里明确标注「未被查看」，契约段禁止基于未查看的图片下结论；图片真正进入 ingest 由后续 change
  做（候选路径见 design §6.3）。这条是本提案唯一一处**低于真源图景**的能力，列出来避免被读成
  「已经支持图片源」。
- **不做 `_inbox` 专用界面**：它是目录与约定；列表与审阅由 lint 报告呈现（语义检查项）。
- **不做工作流定义的 UI 编辑器**：v1 定义是文本文件；界面只提供只读查看。
- **不做 watcher 热加载**：打开列表 / 发起运行时扫描，避免文件监听的生命周期与失效面。
- **不做 iCloud 冲突副本的自动合并**：只报告，由人决定（与 vault 草稿的处置口径同向）。
- **不做「一键清理 wiki」**：删除页面仍走既有 `vault_delete` 与批准闸，不属于任何内置工作流。

## 降级路径（反向扳机已撤回）

不设零使用删除判据。只有四种由人判断后的降级动作：

1. **某个工作流用不上** ⇒ 直接删定义文件；内置定义不可删，但可被同名定义覆盖成实际需要的形态
   （定义必须可运行，不能是空操作）。
2. **lint 的机械项没必要** ⇒ 从工作流定义的 `checks` 里删掉对应项，机制代码不动。
3. **写入闸太吵** ⇒ 把 `gate` 改为 `none`（只对显式选择的定义），或用允许规则细化；MUST NOT 通过
   放宽写范围来减少批准。
4. **整个 wiki 能力用不上** ⇒ `[wiki] enabled = false`：入口消失、工作流不可运行、盘上文件原样保留。
   真源「用后删」的删除动作是另一次裁决，不在本 change 预设。

## 设计取舍（节点 1 裁决点，逐条可否决）

1. **形态 = 前台会话 + 工作流定义，不是子代理**（推荐）。ingest 需要与用户来回讨论、逐页确认；
   子代理的隔离上下文只回摘要，恰好丢掉讨论。lint 可以是子代理，但报告需要就地讨论与后续修复，
   也留在会话里更好。备选：做成 `task` 委派——省主会话上下文，但两种不同形态的实现会让「工作流」
   变成两套语义，不推荐。
2. **确定性检查做成机制阶段，不做 LLM 工具**（推荐）。理由：ADR 0007 Decision 7 的现行判据是
   「核心领域的稳定动作优先结构化工具」——检查器是运行边界上由机制执行的确定性计算，不是模型
   面向 vault 发起的动作，不属于核心任务链上的稳定一步；且模型不需要「按需再扫」的能力，
   前置一次、后置一次已覆盖写前依据与写后校验。备选：新增只读工具 `wiki_lint`——需 Alex 裁决
   扩张工具清单（现行 9 + 1 + 3，其中 `vault_list` 属 vault 操作工具、`task` 属编排工具）。若真实
   使用中出现「运行中途想重扫」的需求，另立 change。
3. **内置两条默认工作流**（推荐）。没有内置，用户要先写一份定义文件才能用——门槛没降。内置只给
   流程骨架与安全约定，可被 vault 覆盖、可只读查看；schema 与检查清单仍在 vault 文档。备选：不带
   内置，改用文档里的样例定义——样例会漂移，且第一步仍是手写。
4. **流程正文里写明「与 vault 约定冲突时以 vault 为准」**（推荐）。这样 vault 的 AGENTS.md 仍是
   流程与 schema 的唯一权威，内置正文只是兜底骨架；避免「两处真源」漂移。备选：内置正文就是完整
   流程——更省心，但与 vault 文档必然分叉。
5. **【已裁决】vault 配置用 JSON（`.lumir/config.json`）**（Alex 2026-10-18：「JSON.」）。理由：与既有
   `config.json` 同一解析与校验口径，不引入第二个 parser（`src-tauri/src/config.rs` 的模块头已记录
   「JSON 而非 TOML」的选型与重评条件）；代价是手写时没有注释。TOML 备选已关闭，不再作为可选项。
6. **写范围精确到文件，而不只是目录**（推荐）。lint 的「只出报告」需要一个精确到 log 文件的写范围，
   而不是「允许写整个 wiki 目录」；否则「不改页」只能靠提示词。备选：引入 `log` 专用开关——多一个
   只为内置定义存在的机制面。
7. **工作流写入闸排在允许规则之前（只收紧）**（推荐）。用户发起一个「逐页人工确认」的流程，语义
   就是这个流程里的写入要逐次确认；允许规则可以放宽别的会话，不能替代这次选择的语义。deny 与危险
   黑名单仍优先。备选：完全继承权限档——默认档下写入自动放行，写入门禁形同虚设，与真源「累积产物
   用批准闸」冲突。
8. **验证不自动修复、不自动重试**（推荐）。新增断链 / 孤儿 / index 漂移已经发生在人审通过的写入
   之后，自动修等于绕开人审。机制只呈现差异，修复是下一次运行或人工编辑。备选：一轮自动修复
   ——省事，但把「错记」的纠正也交给了同一个模型。
9. **会话绑定定义快照**（推荐）。运行中改定义不影响在跑的运行，恢复会话按快照还原；否则同一会话
   两次请求的系统上下文可能不同，行为不可复现。代价：改定义后要新起一次运行才生效。
10. **写入由模型执行、log 由模型写、机制只校验「写了没有」**（推荐）。日志格式是该 vault 的 schema，
    机制不复制格式；机制只保证「没有静默漏记」。备选：机制代写日志——格式统一，但把某个 vault 的
    格式写进代码。
11. **一次运行一个新会话**（推荐）。不绑定专用会话：wiki 的记忆在 vault 里，不在会话里；专用会话会
    制造第二份「上下文记忆」，且与 cron 的 `dedicated` 语义重复。备选：每个工作流一个专用会话。
12. **入口：文件树右键 + 选择器 + 命令，不新增默认键位**（推荐）。降低门槛靠可发现，不靠再加一个
    要记的快捷键；默认键位还会引出与既有键位表 / 原生菜单 accelerator 的三源核对。备选：给
    `wiki.run` 一个默认绑定——多一个记忆负担与冲突面。
13. **【已裁决】不做原型**（Alex 2026-10-18：「不需要。」）。本 change 不新增视觉语言：入口复用文件树
    菜单与既有浮层控件，运行卡片复用 transcript 的既有块形态。若将来要在实现前看形态，另立 change
    （不在本 change 的制品范围内）。
14. **未启用即隐身**（推荐）。未启用 vault 不出现任何入口，第一个入口是「启用 wiki」本身；不用
    「默认开启、可关」——wiki 会写入用户的知识库，默认开不是中立选择。
15. **【已裁决】v1 只检测图片、不投递图片**（Alex 2026-10-18：「采纳v1 标注 。」）。理由与候选路径见
    design §6.3：投递需要把 vault 图片纳入会话的附件引用与恢复口径，混两套引用形态会让「这次运行
    读了什么」不可对账；先做检测并禁止模型装看过，是保守且可交付的一步。v1 就把源内图片导入附件
    存储的备选（更完整，但把一次输入的可重建性绑到附件目录与内容寻址上）留待单独 change。
16. **【已裁决】零判断检查发现项纳入 auto-fix，无人值守不修**（Alex 2026-10-19：「采纳，请你修改。」）。
    社区实操信号（llm-wiki 的 `--fix`、Obsidian 生态的格式类自动修）显示格式类修复风险极低、收益实在，
    而「只报不修」会让格式类项在 lint 报告里持续堆积变吵。边界三条：只有检查器能产出完整确定性修复动作
    （before/after）的项可修——可修性由机制保证，不由模型当场认定；修复走既有写入闸与人审，不开第二条
    写入通道；无人值守 lint 仍只报不修（它的写范围只有 log，扩写范围即转为前台语义）。备选：维持只报不修、
    未来另立 change——已被 Alex 的采纳裁决关闭。
