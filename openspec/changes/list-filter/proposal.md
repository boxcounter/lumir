# Proposal: 两处列表浮层支持输入筛选（大纲浮层与 vault 切换器）

- Change ID: list-filter
- 日期: 2026-09-24
- 角色: Alex Lee（评审/裁决），AI agent（起草）
- 状态：**提案阶段（未获节点 1 裁决）**。本 change 只产制品，零产品代码；实现待裁决后另立 mission。

## Why

用户需求原话（2026-09-24）：**「需求：Outline 和 vault 列表里支持输入筛选，比如 vault 列表显示时当我输入"s"时就会筛选出 s 开头的 vaults」**。

两个落点：① Outline（`⌘⇧O` 的大纲浮层，capability `toc-outline`）；② vault 列表（`⌘O` 的 vault 切换器浮层，capability `vault-workspace`）。原话里的「s 开头」用「比如」引出，是**举例不是定义**，匹配语义因此列为裁决点（见「须提请 Alex 节点 1 裁决」第 ①）。

### 二、量级（决定要不要防抖）

- **大纲**：条目数 = 文档标题数。既有长文 fixture 是 60 条标题（`scripts/acceptance/fixtures/toc-long.md`）；筛选跑在**已提取的快照数组**上，**不重跑** lezer 解析——打开路径上那次「25ms 预算的全量解析」仍然是唯一一次（`src/toc.ts:96`、`:119-122`）。
- **vault**：条目数 = 注册表里的 vault 数（用户本机数据，量级未知；验收套件用合成 registry）。列表只在打开时拉一次（事实 3），筛选纯内存。
- 结论：每次击键的成本是「一次子串过滤 + 一次列表 DOM 重建」，量级几十到几百条，**不引入防抖**（防抖会把「打字即筛」变成「打完才筛」，与诉求相反）。这条 MUST 实测，且**不能引用既有性能门禁**：`scripts/perf/keypress-to-paint.mjs` 注入的是**编辑器**里的按键（`docs/specs/perf-measurement.md:111-115`），不覆盖浮层击键（见 design §5）。

## What Changes

1. **两处浮层支持输入筛选，匹配语义是「大小写折叠的子串匹配」**：查询为空 = 全量；匹配对象是条目**显示文本**本身（标题 = 行原文去掉 `#` 标记串与结尾标记后的全文，行内标记不剥离；vault = 显示名即目录名）；结果**保持原有顺序**，不排序、不打分、不高亮。（delta：ADDED `toc-outline / 浮层输入筛选的匹配语义`）
2. **筛选的交互与退出口径**：浮层里有一个真输入框，焦点随打开落到它上面，打字即筛；`↑↓` / `⌃N` / `⌃P` 在**结果集**里移动（沿用同一份 `move()`，不产生第二套下标逻辑）、`Enter` 对当前条目执行既有动作、`Esc` 一步关闭浮层并丢弃查询；无命中时**不关浮层**，给一行提示，底部键位提示仍常驻；关闭再打开从空白查询开始。（delta：ADDED `toc-outline / 浮层输入筛选的交互（输入框、焦点与退出）`）
3. **vault 侧只加自己的作用面**：匹配字段是显示名；失效行**同样参与筛选**（它是重定位的唯一入口）；「新增 vault…」不受筛选影响（它不在列表里，无命中时仍可用）；匹配语义与键盘/退出口径**引用** `toc-outline` 那两条，不另立一份。（delta：ADDED `vault-workspace / vault 列表浮层的输入筛选`）
4. **既有条款两处收口**（否则 living spec 会与实现直接矛盾）：`大纲浮层` 的「SHALL 列出全部标题」限定为「无查询时」，以及「高亮**当前段**」限定为「当前段仍在结果集里时」。（delta：MODIFIED `toc-outline / 大纲浮层`）
5. **零新增键位、零新增命令、零新增配置项**：筛选**禁止**走统一键位表——单字符 token 在表里合法（事实 5），绑进去等于吞掉编辑器里键入的每一个字母。（写进 ADDED requirement 的 MUST NOT）

### 语义变化（如实登记，给 Alex 一个拒绝面）

| 路径 | 今天 | 本 change 之后 |
|---|---|---|
| 浮层打开时按可打印字符（`a`–`z`、数字、中文） | 什么都不发生（表里无单字符绑定） | 成为查询串，列表即时收窄 |
| 用户在 `[keys]` 里把某**单字符**绑成了命令（如 `s = "document.save"`） | 浮层打开时按 `s` 会真的执行那条命令（`global` 作用域与焦点无关，`openspec/specs/keymap-commands/spec.md:31-35`） | 浮层打开期间 `s` 被浮层消费为筛选字符，那条命令不触发。**这是有意变化，写进 spec 的 MUST** |
| `Esc`（筛选态下） | 关闭浮层 | **不变**（一步关闭并丢弃查询）——推荐项 |
| 浮层底部键位提示 | 五个就地键 | **不变**（推荐项下不需要改写，因而 15 处验收断言 + 1 处视觉断言不动） |
| 两处浮层的 AX 结构 | 列表持焦点，键盘游标所在条目带 `(focused)` | 输入框持焦点、`aria-activedescendant` 上移到输入框；游标条目的 AX 形态**待实测**（这条直接影响验收场景「游标落在哪一条」的判据通道，见 design §5） |
| 浮层的可见元素 | `⌘O` / `⌘⇧O` 打开后只有列表（+ 大纲的提示行） | 多一行输入框（两张元素级基线要重拍，见 Impact） |

## capability 归属：宿主 `toc-outline`（两条共用规则），作用面各落各的

**结论**：**匹配语义与筛选交互两条共用规则落 `toc-outline`**（大纲侧那两条 ADDED requirement 就是规则的唯一真源）；**`vault-workspace` 的 ADDED 只写自己的作用面**（匹配哪个字段、失效行、新增入口、当前项标记），并用一句必备引用指回大纲侧那两条，**MUST NOT 在本 capability 里重述规则文字、也 MUST NOT 另写一份匹配实现**。不新建 capability。

| 本 change 的条款 | 为什么落在这里 |
|---|---|
| 匹配语义（子串 / 大小写折叠 / 顺序不重排 / 多字节安全） | 规则的**难点**全在大纲侧：中文长标题决定了前缀不可用（裁决点 ①）、顺序口径是「文档顺序」、深度归一问题只在大纲侧存在（裁决点 ⑤）。规则的**必要性论证**在这里，条文也就在这里 |
| 筛选交互（输入框、ARIA、焦点、键盘与退出） | 大纲浮层是两处里更完整的那个（列表 + 底部提示 + 当前段高亮 + 就地键家族），交互口径写在它这里，`vault-workspace` 引用一句即可；反过来写会让 `toc-outline` 引用 vault 侧的条文 |
| vault 的匹配字段、失效行、新增入口、当前项标记 | 这些只有 vault 侧有（`src/vault-switcher.ts` 的三支 `Enter` 与「新增 vault…」都是它独有的），落 `vault-workspace` 最省解释成本；**vault 浮层行为本来就归 `vault-workspace`**（它的「vault 切换器入口与列表浮层」requirement 就是这份 spec 里描述浮层的条款，`openspec/specs/vault-workspace/spec.md:151-179`，本 change 是在这条之上追加筛选，不是换宿主） |

**反方（如实记录）**：也可以把宿主定成 `vault-workspace`——理由是**用户原话举的例子就是 vault 列表**，「s 开头的 vaults」这句在 vault 侧最好落地；把规则写在大纲 capability 里，读者要先进大纲才读到「vault 列表怎么匹配」。若 Alex 取这一侧，翻转的落点只是两条 requirement 的归属与两处 `specs/` 文件的内容对调，条文文字不动。

**为什么不是新建 `list-filter` capability**：本 change 的共用规则只有两条，且都挂在既有浮层的交互上；新建 living spec 要手写 Purpose、要维护一份只为两条规则存在的 capability，成本与目的不匹配（同 `document-end-marker` proposal 对新建 capability 的处置口径）。**触发重评的信号**：第三处列表（文件树）出现同类筛选诉求时，把规则提到新的 `list-filter` capability，两处 delta 改为引用它。

## 观测：怎么知道它被用了、有效、出了问题能发现

- **怎么知道被用了**：新增真机场景 `scripts/acceptance/scenarios/29-list-filter.md`（编号按现有最大 28 续）+ 两处浮层各一组步骤；每批合并后由 agent 先跑，Alex 只看 FAIL 项与手感项。
- **怎么知道有效**：判据落在**结果集**上，不落在「输入框里有字」上——`↑↓` 的游标落点必须落在**命中条目**上（沿用既有 `(focused)` 通道，形态若因焦点迁移而变则按实测改写）、无命中态出现、清空查询后全量条目回来。反向验证：把筛选整段关掉重跑同一场景，必须 FAIL。
- **出问题怎么发现**：视觉门禁守「新输入行在位、浮层总高仍在既有上限内、列表仍是唯一滚动容器、提示仍常驻」；无命中态与新文案有独立场景；`13-toc` / `17` / `18` 三个既有场景全量重跑一遍，防的是「筛选把既有的浮层行为挤坏」。
- **不新增埋点**：本 change 不新增诊断事件（要新增须同时扩 Rust 事件白名单，属另一件事）。
- **手感归 Alex**：输入即筛的跟手感、命中变少时的观感、输入行在浮层里的分量，不下沉到门禁。

## Non-goals

- **不做模糊匹配**（子序列 + 打分）、**不做拼音检索**、**不做简繁 / 全角半角 / 大小写之外的任何归一**：拼音要词典与索引，属另一件事（原话没有它）。
- **不做命中片段高亮**：`openspec/specs/toc-outline/spec.md:73` 明令浮层 MUST NOT 引入新的视觉语言。
- **不做结果重排 / 频次排序 / 最近使用优先**：vault 侧「排序由后端给出、前端不重排」是既有口径（`src/vault-switcher.ts:14-16`），大纲侧顺序即文档顺序。
- **不做多词 AND / 排除语法 / 正则 / 分词**：v1 是单一子串。
- **不给文件树加筛选**：原话只点两处；文件树是第三处，触发时按上面的信号把规则提到新 capability。
- **不做跨浮层的「快速打开」/ 全局搜索**：本 change 不加新浮层、不加新命令。
- **不做查询的持久化**：关闭浮层即丢弃，重开从空查询开始。
- **不新增键位、命令、配置项**；**禁止**把单字符放进统一键位表（事实 5）。
- **不改大纲指示段**（masthead 的当前标题路径）：它读的是光标位置，与筛选无关。
- **不改 vault 浮层的排序、摘要、失效行语义与「新增 vault…」的既有动作**（只让它们参与 / 不参与筛选）。
- **不做输入法候选与组合期的产品化处理**（如拼音候选面板）：只在实现上不打断 IME 的既有行为。
