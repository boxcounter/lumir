## Why

Alex 2026-10-23 的需求原话（逐字）：

> 「增加 App 启动屏。」

原话没有说用途。本文先把启动链路拆开、把「今天用户在每个阶段看到什么」摆出来，再给用途定位的
倾向——因为**同一句「启动屏」，服务于感知性能与服务于品牌，会产出两个形状完全不同的东西**。

**启动链路现状**（起草时逐处读过源码；时间读数为仓内既有证据）：

| 阶段 | 谁在做 | 用户看到 | 证据 |
|---|---|---|---|
| S0 spawn → setup 完成 | macOS + Tauri | 什么都没有（窗口 `visible: false`），只有 Dock 图标 | `src-tauri/tauri.conf.json` 的 `app.windows[0].visible`；冷启动本机读数 median 174.0ms（n=20，[evidence/cold-start.json](../../../docs/design-parity-contract/evidence/cold-start.json)） |
| S1 `LUMIR_READY` + 施加尺寸 + `show()` | Rust setup | 窗口出现，**内容是空的**，只有原生底色 | `src-tauri/src/lib.rs`：`emit_ready`（:195）→ `window_state::init`（:200）→ `apply_startup_size`（:201，`show()` 在 :348） |
| S2 页面装载 + 主模块执行 + 壳挂载 | webview | 仍是空窗，直到前端把 `.app-shell` 建出来 | `index.html` 只有一个空的 `#app`；`src/main.ts` 在模块顶层 `createShell`（:187），CSS 也由它 `import`（:142） |
| S3 主题施加 | webview（异步 `configGet`） | 结构上，首个内容帧用的是 CSS 默认块（light），`[ui] theme` 要等 `configGet` 返回才施加——dark / eink 用户是否会看到一帧 light 属未实测（见 design §9 已知边界） | `src/style.css` 的 `:root, :root[data-theme="light"]`（:14）；`src/main.ts` 的 `configGet().then(...)`（:3731）里 `applyTheme`（:3808） |
| S4 vault 状态落地 | Rust 恢复线程 + webview 拉 `vault_current` | 恢复中：未打开空态 + 一行「正在恢复上次打开的 vault……」（文案 D95）；无 vault：空态 | `src/main.ts` 的 `refreshVaultStatus`（:3682）；[vault-workspace 的「启动恢复的时序与可见性」](../../specs/vault-workspace/spec.md) |
| S5 树装载 | webview 主线程（同步整树重建） | 树出现 | `src/main.ts` 的 `applyVault`：「大 vault 上可能数百 ms」（:3586-3590） |
| S6 标签恢复 | webview（异步） | 标签逐个建壳、激活项内容装载 | `src/main.ts` 的 `switcher.onVaultLoaded`（:3612-3615）；启动路径**不开** M252 的装载指示器（只有用户发起的装载才 `begin`，:1684） |

**两个结构事实**（本提案的立论基础）：

1. **用户真正等待的那几段既没有呈现，也没有读数。** 冷启动合同的端点是 spawn → `LUMIR_READY`，
   只覆盖 S0–S1；S2–S6 全在端点之外（[docs/specs/perf-measurement.md](../../../docs/specs/perf-measurement.md)
   §1 明写「前端首屏挂载暂不入端点」；归档件 `multi-vault-workspaces/tasks.md` 也登记了「标签恢复发生在
   `LUMIR_READY` 之后、不在任何被测量的端点里」）。
2. **大 vault 的慢落在 S4–S6，而 S2 的空窗与 vault 规模无关。** 所以「只盖住空窗」的启动屏解决不了
   Alex 关心的大 vault 冷启动；要服务感知性能，启动态必须至少活到 S5（树可用）。

**为什么值得做**：启动期是唯一「用户已经决定要用这个 app、界面却什么都还说不出来」的时段。今天它被
切成三段互不相干的表达——先是一块空窗（S1–S2，无任何信息），中间一次主题翻转（S3），再是一行恢复
提示（S4 的 D95）。这三件事合起来就是「启动慢」的主观来源，而它们都不是计算量问题。

## What Changes

逐条对应 spec 增量里的一个 requirement：

1. **启动态的上屏与撤下**（`app-startup`，ADDED）：启动层在主模块装载**之前**画出首个内容帧，即启动态
   ——覆盖整窗的结构化启动面。它活到三种情形之一先到：当前 vault 的树装载完成 / vault 状态落到未打开
   终态 / 安全阀超时（实现值 ≤10s）；撤下在单帧内完成、无动画。启动态不挡已有入口：标题栏拖拽区保留
   （窗口可拖动），「打开 vault」入口在场且在启动态里打开的 vault 优先于进行中的恢复（既有让位规则不变）。
2. **启动态的内容与视觉口径**（`app-startup`，ADDED）：骨架几何与色值只取既有 token、MUST NOT 伪造条目 /
   计数 / 百分比 / 预计时间；产品名取元信息真源、读不到就整体隐藏；阶段行只在恢复中显示（复用 D95 文案，
   不新增文案条目）；三主题同构、首帧前先施加主题。
3. **启动态与启动链路的边界**（`app-startup`，ADDED）：不改 `LUMIR_READY` 的位置与语义、setup 零新增同步
   工作、不新增后端读取或命令、不推迟窗口首次上屏；启动层读到的配置交给主模块复用（同一份读数不在两处
   各读一次）；冷启动主口径 median 增量 ≤10ms（同机前后对比）。
4. **启动态的可观测性**（`app-startup`，ADDED）：启动层首帧与撤下（含撤下原因）各落一条既有诊断日志
   读数，用于观察与归因，MUST NOT 进 CI 门禁。
5. **恢复中呈现的归属改判**（`vault-workspace`，MODIFIED「启动恢复的时序与可见性」）：恢复进行中的可见面
   从「未打开空态的布局 + 恢复中提示」改为「启动态 + 阶段行（同一句文案）」；「打开 vault」入口在启动态内
   承担。其余条款——`restore_pending` 语义、`vault:restore_finished`、让位规则、`LUMIR_READY`——**逐字不变**。

## Non-goals

- **不做品牌开场动画 / 入场动效**：`ui-design-system`「chrome 表面与动效纪律」明确「MUST NOT 新增入场动画」，
  全仓过渡只有 0.1s / 0.12s 两档。启动态是静态面，撤下是瞬时切换。
- **不显示进度百分比 / 剩余时间**：没有可信的分母（树条目数与装载耗时都不预估），假进度比没有进度更糟。
- **不新增 perf 端点、不改冷启动合同、不动 CI 门禁口径**：只补诊断读数，端点定义仍归 `perf-measurement`。
- **不做「上次会话摘要」**：启动态不显示最近打开的文件、vault 名或标签数——那会变成第二份会话真源。
- **不新增文案条目**：阶段行复用既有恢复中提示（D95）；D1 若选品牌侧再另立条目。
- **不改窗口首次上屏时机**：`apply_startup_size` 的尺寸施加 / `show()` / 激活时序不变。
- **不处理相邻缺陷**：M525 的启动窗口底色在 `show()` **之后**才由恢复线程施加（`lib.rs`：`apply_startup_size`
  :201 → `start_restore` :204 → `restore_last_vault` 里 `apply_startup_window_background` :772），dark / eink
  用户在窗口出现的一瞬可能看到 light 底色。它属窗口层、与启动态正交，已单独登记（见 Impact「相邻缺陷」）。

## Impact

- **影响的 specs**：`app-startup`（新建 capability，ADDED ×4）、`vault-workspace`（MODIFIED「启动恢复的时序
  与可见性」，一条 requirement 整块替换）。`ui-design-system` / `perf-measurement` 只被**引用**，字面条款不动。
- **影响的代码 / 系统**：
  - 前端：新增启动层（boot 入口 + 启动面模块 + 样式），`index.html` 的脚本入口改到启动层；`src/main.ts`
    改为被动态装载；撤下信号挂在既有收口（`applyVault` 的树装载段、`refreshVaultStatus` 的未打开终态分支），
    **不新造状态机**。
  - 后端：**零新增命令**；仅在诊断日志白名单补一个事件名（两条读数用）。
  - 测试：视觉场景（三主题首帧、骨架几何、零动画 / 零过渡）+ 真机验收场景（启动态出现与撤下、恢复期间
    打开另一个 vault、安全阀）。
- **关联约束**：ADR 0002 §6（冷启动 <300ms，端点不变）、ADR 0004（人不 review 代码，制品即判据）、
  `ui-design-system` 的布局与动效纪律、`vault-workspace` 的恢复让位规则、仓库信息卫生（启动面不含任何
  真实 vault 内容）。
- **相邻缺陷**（另行登记，不在本 change 内修）：M525 的启动窗口底色晚于 `show()` 施加；前端首个内容帧先按
  light 默认 token 出图（D5 选倾向侧时由本 change 顺带修掉后者）。

## 观测闸三问

- **怎么知道用户用了它**：每次启动都会看到——没有开关，只有「在不在」。
- **怎么知道它有效**：大 vault 冷启时，窗口出现后的首个内容帧就是骨架（恢复中出现阶段行），随后树出现；中间
  不再有半成品壳、也不再有主题翻转（窗口上屏到首帧之间那一小段仍由窗口底色承担，见 design §9）。
  诊断日志里「上屏 → 启动层首帧」的读数可按机器复核。
- **出问题怎么发现**：启动层异常时降级为撤下启动态、既有启动路径照走（不白屏、不阻断）；视觉场景守三主题与
  几何；真机验收守出现 / 撤下 / 安全阀 / 让位；`gate.sh quick` 与冷启动 CI 读数守「没拖慢」。
