## Why

Alex 原话（2026-10-11）：「要做，而且卡片上要显示编号，允许我点击。另外，我平常使用 Kimi Code Web
它的一个做法我用着也顺手，可以供你参考：hover 图片时，会出现两个按钮 @ 和 删除，当我点击 @ 时，
就会在光标处插入 image X。」（附 Kimi Code Web 截图：hover 图片卡片浮出 `@` 与删除两钮，点 `@` 在
光标处插入「Image 1」字样的引用。）

**Alex 要的是三条硬保证**：① 图片卡片上显示编号；② 编号可交互（hover 出 `@` / 删除两钮，点 `@`
在光标处插入「Image N」引用）；③ 投递时**模型侧看到同源编号**——人看到的 N 与模型看到的 N 一致，
投影层一处改动。

**现状锚点**（本提案全部事实性断言都对着 worktree wt-446 @ e4abfbf 的源码核实；M440 的贴图实现已在
master）：

- **图片块已是 composer 的第三类原子块**：`{kind:"image"}`（`src/quote-card.ts:73`）；卡片 DOM 复用
  `.lumir-hp-qcard` 整族、composer 态已有 `×` 移除钮（`src/harness-panel.ts:2320` 的
  `createImageCardEl`，移除钮在 `:2338`）。**卡片上没有任何编号**。
- **投递投影今天不带标签**：`projectDelivery`（`src/quote-card.ts:202`）把块序压成
  `[text…, image…, text…]` 的 parts；图片 part 只带 `name`（内容寻址文件名，`:217-222`）。
- **wire 上模型没有任何文本把手能指代「第几张图」**：Rust 侧 `content_of_parts`
  （`src-tauri/src/harness/attachments.rs:348`）把图片 part 装配成 `{"type":"input_image",
  "image_url":"lumir-attachment://<name>"}`；发送前 `expand_image_refs` 把 `image_url` 换成 base64
  data URL——**模型既看不到编号，也看不到文件名**，只有一串按序交错的图片字节。
- **留存与恢复都是「有位置、无编号」**：`record_llm_request` 记的就是发送前那份 input（引用形态），
  恢复路径 `panel_text_of_content`（`attachments.rs:314`）把 `input_image` part 还原成
  `<image ref="…" type="…"/>` 占位行，面板/transcript 的图片卡片因此只有顺序、没有编号。
- **既有 living spec 明文禁止编号**：「引用消息序列化协议」（`openspec/specs/harness/spec.md:334`）
  写着「序列化结构 SHALL NOT 包含任何编号……**UI SHALL NOT 显示卡片编号**」（Alex 2026-10-06 的
  一致性原则）。Alex 这次的诉求**正面修订**这条原话——本 change 必须把「为什么图片是例外」讲清楚
  （见 What Changes 第 2 条与裁决点 3）。
- **@ 引用的落点机制已经存在**：`insertPlainTextAtCaret`（`src/harness-panel.ts:323`）就是「光标处插入
  文本、段落中间拆段」的纯函数；卡片插入的光标口径（`caretFromDom()`，不可得时落 composer 末尾）
  见 `insertMessageQuoteCard`（`:2474`）与 `insertQuoteCard`（`:5466`）。

**要解决的问题**（Alex 的现场）：多图先贴后描述时，模型收到的是一串**无标签的图**——人嘴里说的
「第 2 张」在 wire 上不存在对应物，模型只能靠自觉按顺序数。指代错图是必然的失败模式，而这正是
Alex 要的硬保证要堵掉的。

## What Changes

逐条对应 `specs/harness/spec.md` 增量里的一个 requirement：

1. **图片编号与引用**（harness，ADDED）：图片有了**编号**，且编号是**一处真源、三处消费**——
   - **编号规则**：在**单条消息内**按图片块出现次序 1-based 编号（`Image 1` / `Image 2`…），只数图片块
     （不数引用卡片 / 消息摘录卡片 / 段落），从 1 起、无空号；删除图片块后其余图片即时重编。
   - **卡片显示**：composer 与 transcript 的图片卡片都显示自己的编号；编号**不进卡片数据模型**，是块
     序列的**派生读数**（一个纯函数算出「块下标 → 编号」，卡片渲染与投递投影共用同一份计算）。
   - **@ 引用**：composer 内图片卡片提供「插入引用」钮（`@` 形态），点击在**当前光标处**插入该图的引用
     文本 `Image N`（N = 该卡片当前编号），插入后光标落在插入文本之后、可继续输入；插入走既有光标
     模型（段落中间拆段），零新机制。
   - **投递同源编号**：发送时**每个图片块**在投递序列里携带标签行 `Image N`，紧邻该图片内容之前；N 与
     卡片徽标同源。标签**进 wire 请求**，但**不进会话留存的文本面**（留存以结构化标签字段记在图片 part
     上，标签文本在发送前由该字段生成）——否则恢复路径会把标签当正文复现。
   - **恢复与 transcript**：恢复路径按同一编号规则重建卡片；transcript / wire / composer 三处的 N 一致。
2. **引用消息序列化协议**（harness，MODIFIED）：把 2026-10-06 的「零编号」条**从「一切卡片」收窄为
   「有文本身份的引用卡片」**——`<quote>` / `<msg-quote>` 依然零编号（它们的 `file` / `heading` /
   `lines` / `role` / `at` 属性本身就是身份，agent 可按出处回指，「编号对人无区分价值」这句对它们仍然
   成立）；**图片块是例外**：图片在 wire 上没有任何文本身份（`input_image` part 只有字节），编号是
   模型指代单张图的**唯一把手**，故图片块携带编号。UI 的「显示卡片编号」禁令同步收窄为「引用卡片与
   消息摘录卡片不显示编号；图片卡片显示其编号」。

## Alex 裁决点

| # | 裁决点 | 选项 | 起草倾向 |
|---|---|---|---|
| 1 | 编号**分配规则** | A. **位序编号**：按图片块当前次序 1..n，删除后重编（Kimi Web 口径，无空号）；B. **稳定编号**：插入时递增分配、删除不复用（已插入的引用文本恒不悬空，代价是删除留空号，且编号要随卡片数据走）；C. **原子引用联动**：引用是原子块（记住它指的那张图），卡片徽标与引用一起重编（无空号、无悬空，代价是新块类型 + 编辑/快照语义） | **倾向 A**——派生读数、零新状态、跨 composer/transcript/wire/恢复自动一致（编号不进任何持久化面），也正合 Alex 参考的 Kimi Web 口径。代价如实登记：删除图片后，**已经插进正文的引用文本可能悬空**（正文是用户自己的字，系统不静默改写）——这是**可见**的不一致（徽标与文字同屏），不是静默错投。若 dogfood 证明这个窗口真被踩到，再走 C |
| 2 | 编号**作用域** | A. **每条消息**内从 1 起（composer 发完清空，下一条重新从 1）；B. **会话内连续**（跨消息累加） | **倾向 A**——引用是在**当前这条消息**里插的、模型也是按**单条消息**理解图序的，作用域与「引用」这件事的作用域同宽；B 的跨消息编号会在**删除一条历史消息**时把其后的编号全部重编（M406 的删会话是既有能力），得不偿失 |
| 3 | 引用在 **composer 数据层**的形态 | A. **纯文本**（`Image N` 就是段落里的普通文字，可编辑可删，系统不改写）；B. **原子 mention 块**（新块类型，整块选择/删除、可点跳回对应图片、随编号联动） | **倾向 A**——Kimi Web 就是纯文本，Alex 的原话也是「在光标处插入 image X」；纯文本零新块类型、零快照/投影/编辑语义面，且引用插进句子中间是用户的正常写作动作（原子块会让句中断句、选区、删除都变得别扭）。B 留作「A 的悬空问题真被踩到」时的升级路径（与裁决点 1 的 C 同族） |
| 4 | **投递标签注入**范围 | A. **恒注入**——每个图片块前都注入 `Image N` 标签（无论用户是否已用 `@` 引用过）；B. 仅当用户没有引用该图时才注入 | **倾向 A**——硬保证不能建立在「启发式去重」上（按文本搜 `Image N` 判「是否已引用」既脆又会误判用户的正常文字）；代价是用户用 `@` 插入引用时，同一编号在一次投递里可能出现两次（用户正文里一次、系统标签一次）——不算噪音：系统的标签是**权威配对**，用户的话是正文 |
| 5 | 两钮（`@` + 删除）**可见性** | A. **恒显**（与既有 `×` 的现有口径一致，`@` 恰在其左）；B. **hover 出两钮**（Kimi Web 形态，含既有 `×` 一并改为 hover 显示） | **倾向 A**——既有 `×` 今天就是恒显（`src/harness-panel.css:1591`，无隐藏规则），改动它等于动已发版的行为；hover-only 会藏起可发现性（键盘 / 触屏更差）。Alex 引 Kimi Web 主要是为了「`@` 一键插引用」这条交互，可见性属**视觉/手感面**：若 Alex 要 B，实现时按 hover 形态做（两钮同在 DOM、hover 与 focus-within 均可显示），代价与收益都很小。**最终形态以 Alex 过目截图为准** |

编号**显示位置**（缩略图角标 vs 元信息行前缀）不在上表：它是纯视觉选取，implementation 期给截图由 Alex
手感裁决（design §8 给出默认口径）。

## Non-goals

- **引用卡片 / 消息摘录卡片的「零编号」口径不变**：本 change 只给**图片块**编号；`<quote>` /
  `<msg-quote>` 的序列化元素与 UI 呈现 MUST 保持无编号。
- **跨消息 / 全局编号**：不做会话级累加编号（见裁决点 2）。
- **引用悬空检测与自动改写**：系统 MUST NOT 扫描或改写用户正文里的 `Image N` 文字（裁决点 1 的已知代价）。
- **原子 mention 块**：v1 不做（裁决点 3 的 A 之外，留作升级路径）。
- **图片卡片其余形态**：缩略图、元信息行「从文件名开始、无 `image ·` 前缀」（M440 的裁决）、错误态、
  读回失败占位**逐字节不变**；本 change 只加编号徽标与 `@` 钮。
- **投递口径**：M440 的「引用进留存、data URL 进 wire、JSONL 无 base64、按 vault 稳定 id 分置」逐条不变；
  本 change 只在图片 part 上多一个**标签字段**。
- **编辑器侧贴图链路**（落 vault、`![[…]]`）：不碰。
- **一次粘贴多图**：M440 的口径不变（只取第一张）。

## 观测闸三问（低成本口径）

- **怎么知道用户用了它**：产品零埋点，天然痕迹在 wire 留存——`llm_request` 的 messages 里 user 项的图片
  part 带标签字段、wire 里带 `Image N` 文本行，可直接 grep；用户经 `@` 插入的引用会在正文里留下
  `Image N` 字样（与系统标签同形，两者都在留存里可见）。
- **怎么知道它有效**：主判 Alex dogfood 手感——先贴两张图、再写「Image 2 的配色不对」，模型是否答对了
  那张图；负信号是模型答错图或反问「你指的是哪一张」（与今天「靠自觉数顺序」的表现对照，是这个功能的
  主判据）。
- **出问题怎么发现**：机器面兜底——新增验收场景断言**三处编号一致**（卡片徽标 = wire 标签 = 恢复后徽标）、
  留存文本面无标签行、删除后重编为位序；编号与投影不变量单测；图片卡片徽标与两钮的视觉基线。失败路径
  （引用插入时拿不到光标）按既有口径落 composer 末尾，无静默失败。
