## Why

1. **定期笔记靠人记住就会死**。daily log 的价值不取决于功能多强，取决于「每天那一篇到底建没建」。
   现在的 Lumir 没有任何时间触发源：建这篇笔记完全依赖使用者自己想起来，而想起来这件事恰好是
   daily log 要解决的那部分问题。这就是 Alex 说的「降低这个门槛」。
2. **运行时守护足够，系统守护不值当**。触发精度是「一天一次、分钟级」，Lumir 开着就能覆盖绝大多数
   使用时段；系统级守护（launchd）的复杂度不在触发本体，在生命周期管理（plist 安装 / 卸载 /
   升级迁移 / 配置同步）与故障域扩张（跨进程调试、通知权限、macOS 后台项管理）。所以本 change
   只做进程内定时器 + 拉取兜底，系统守护明确留档不做（量级判断来自设计真源，属经验推测）。
3. **纯拉取也不行**。只在「启动 / 切前台」时检查，等于把提醒推迟到下一次你碰电脑——21:00 的提醒
   在 23:00 才出现，那家咖啡馆已经关门了。定时器负责「到点主动触达」，拉取负责「错过之后补上」，
   两源共享同一个判定函数才不会出现「定时器说没建、兜底说建了」的分裂。
4. **「进入创建好的环境」是第二个原语**。光发通知不解决问题：点开之后还要有一个日期正确、小节齐全
   的笔记等着你。模板机制（预建文件 + 打开 + 可选预载会话）不是 cron 的附属，它是所有「定期笔记」
   （daily log、周复盘，将来的定期 lint 入口页）共用的创建原语；cron 只是它的一个调用方。
5. **手工验证与产品目的错位（Alex 2026-10-18 推翻原方案）**。原计划「先手工验证一两周再开发」，
   但手工验证测的是「精通 LLM Wiki 机制且有纪律的人用不用得起来」，而产品目的正是让不靠那份纪律
   的人也用得起来。验证因此搬到建成后的真实使用里，用反向扳机（见下）兜底删除成本——单用户、
   AI-only、无兼容包袱，删起来很便宜。

## What Changes

两个新 capability，逐条对应 `specs/` 增量里的 requirement。

### A. `cron`（运行时守护）

1. **运行时定时守护**：进程内评估循环，按本机本地时间判断「本地日期内已到任务 `at` 时刻且条件
   未满足」；同一任务同日至多一次通知。应用没运行 = 没有任何触达（这是运行时守护的定义，不是缺陷）。
2. **拉取式兜底 + 判定函数共享**：app 启动就绪后、主窗口获得焦点时，调用**同一个**判定函数；
   已过点但当日尚未通知的，补发一次。两个触发源只在「何时调用」上不同，判定输入输出与投递决策
   完全一致。
3. **通知与点击唤起**（独立功能点，不是「发通知」的附属）：权限检查与申请；到点未满足时投递
   macOS 系统通知（app 在后台也投）；点击通知本体 → 唤起并聚焦主窗口 → 确保环境存在（缺失则建、
   已存在则不动）→ 打开该文件（可选把模板声明的 prompt 预载进 harness 草稿）。目标 vault 未打开
   时先走既有 vault 打开链路。
4. **cron 任务定义（配置即数据）**：`[cron].tasks` 数组，任务 = `{id, vault, at, template, days?}`；
   逐项 schema 校验、非法项丢弃 + 人话 warning（ADR 0002 第 5 条）；不支持 cron 表达式、不支持
   任意条件表达式或脚本执行。
5. **通知去重状态**：`<config>/cron-state.json` 记录每任务「最近通知的本地日期」；独立小文件
   （与 `window-state.json` 同惯例），不进 `config.json`、不进 vault；损坏按无状态处理。

### B. `note-templates`（笔记模板原语）

1. **模板定义（配置即数据）**：`[note_templates].<id>` = `{path, body, prompt?}`；`path` 是 vault
   相对路径模板（只识别 `{{date}}` = 本地日期 `YYYY-MM-DD`），`body` 是正文行数组，`prompt` 可选。
2. **模板实例化**：原子创建（`O_EXCL`）——目标已存在即 no-op、绝不覆盖或改写（ADR 0003 铁律）；
   缺失父目录时创建；日期占位符按当天替换；失败不留半截文件。
3. **当日实例的打开入口**：独立于 cron 的入口（命令），不存在则实例化、存在则直接打开；打开复用
   既有文档打开链路；声明了 `prompt` 时写进 harness composer 草稿（复用既有草稿通道），**不自动
   发送**。cron 点击链路与这个入口共用同一个前端事件，不写第二套打开实现。

### C. 首场景：daily log 每日 21:00 提醒（端到端验收样例，不是特化代码路径）

`[cron].tasks` 一条任务，`at = "21:00"`，`vault` = daily vault，`template` = daily-log 模板
（`daily/{{date}}.md`，日期 frontmatter + 固定小节）。21:00 时若今日文件不存在 → 通知；点击 →
建文件、打开、把模板里的 prompt 预载进草稿。代码里 MUST NOT 有 `daily-log` 字面量。

## Non-goals

- **系统级守护明确不做**：不装 launchd / LaunchAgent / 登录项 / 系统 cron，不做「Lumir 没运行也能
  触达」。留档的升级触发条件 = 出现「Lumir 没运行也要触达」的真需求（如定时抓取推送）；届时另立
  ADR/change，不在本 change 里预留钩子。
- **不做 cron 表达式 / 通用调度器**：不支持 `* * * * *`、秒级触发、一天多次、任意条件表达式、
  脚本或 shell 命令执行。任务定义只声明「哪天 + 几点 + 用哪个模板」。
- **不做通知动作按钮**：v1 只有「点击通知本体」一条交互，不做「已完成 / 稍后提醒」按钮，也不做
  通知内联回复。
- **不做应用内任务管理 UI**：v1 配置即数据，没有增删任务的面板；新任务靠手写 `config.json`。
- **不做自动发送**：模板的 `prompt` 只预载进草稿，MUST NOT 自动发起对话（不产生无人点头的
  token 花费）。
- **不做后台常驻形态**：不新增菜单栏常驻 / 关窗不退出之类的形态；窗口关闭即应用退出（既有行为），
  关闭后无触达。
- **不做多机去重**：iCloud 同步的 vault 在多台 Mac 上会各自判定、各自通知；这是单机运行时的
  如实边界，不在本 change 里解决。
- **不做模板变量 DSL / 模板编辑器**：只有 `{{date}}` 一个占位符；模板正文是配置里的行数组。
- **不做跨 vault 链接 / wiki 工作流**：本 change 只交付「时间触发 + 创建环境」两块地基，ingest /
  lint 等 wiki 流程随之后排。

## 反向扳机：连续 4 周零使用即从产品删除

**条款（Alex 2026-10-18 裁决原文）**：「连续 4 周零使用即删除」。

**判据**：从本 change 合并之日起连续 4 周，「由本 change 引入的链路被真正使用」的次数为 0。
「使用」只认**点击通知后真正进入环境**这一件事——诊断日志事件 `cron_open` 的累计条数为 0
（定义见 design §11）。仅仅「通知每天照常弹」不算使用：通知弹了四周没人点，说明它是噪音而不是
提醒，同样触发删除。

**动作**：扳机触发即删除 `cron` capability 的运行时守护、通知链路与任务配置面；`note-templates`
一并摘除，除非届时能指名独立调用方（非 cron 路径的真实使用者）——写不出调用方就等于没有消费者
（AGENTS.md「变更默认直接切断」的举证口径），一并删除。删除走一个新 change，把本 reverse trigger
的判定结果写进其 proposal。

**观测手段**：`cron_notified` / `cron_open` 两个白名单诊断事件（本地 JSONL，`~/.config/lumir/logs/`，
不联网、不外发）。周检查一次即可，不需要指标系统：

```bash
rg -c '"event":"cron_open"' ~/.config/lumir/logs/    # 4 周内累计为 0 ⇒ 扳机触发
```

## 观测：怎么知道用了 / 有效 / 出问题怎么发现

- **怎么知道用了**：`cron_open` 事件（点击 → 创建/打开是否成功、是否新建）。零条就是没用，见上。
- **怎么知道有效**：同一任务下 `cron_notified` 的时刻与当日实例文件的落盘/打开时刻是否在同一晚；
  若通知后从未出现 `cron_open`、而文件仍靠手动创建，说明提醒链路没帮上忙。
- **出问题怎么发现**：配置校验的逐项 warning（非法任务被丢弃时会说清是哪一项）；通知权限被拒时
  一条人话 warning；`cron-state.json` 损坏时一条 warning；点击链路失败落诊断事件（含错误码），
  不静默。真机验收场景覆盖通知到达与点击唤起（见 tasks/design §9）。

## 节点 1 需裁决的设计取舍（逐条可否决）

1. **模板定义放全局 `config.json`**（推荐），而不是 vault 内的模板文件、也不等未来的
   `<vault>/.lumir/config.toml`（该原语在设计真源里仍属「留档不展开」）。理由：运行时守护在没有
   打开任何 vault 时也要判定，模板描述必须随手可得；正文短（daily log 十行内），行数组够用。
2. **prompt 预载为草稿、不自动发送**（推荐）。理由：无人点头的 token 花费与「策展权在人」冲突；
   一次点击 = 一次明确的意图，但「打开面板」不等于「允许立即调用模型」。
3. **只做「点击通知本体」**，不做动作按钮与稍后提醒（推荐 v1 最小）。理由：macOS 上多动作会被折进
   「选项」菜单，交互收益低；真正的需求先由四周真实使用暴露。
4. **条件由模板目标路径推出**（推荐），不引入独立条件表达式。理由：首场景与「定期笔记」族共享同一
   形态——「今天的实例建了吗」；表达式 DSL 会把一个声明式配置变成小型编程语言，违反 ADR 0002
   第 5 条「配置即数据、拒绝配置即代码」。
5. **任务粒度 = 每天一次 + 可选 weekday 过滤**（推荐），不支持一天多次 / 任意间隔。理由：多次触发
   可由多条任务表达；任意间隔是 cron 表达式那一档，明确不做。

## 裁决点

以上 5 条均为设计取舍，Alex 有拒绝面；本 proposal 不自带未裁决的阻塞项。节点 1 通过前不进入实现。
