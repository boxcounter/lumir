## Why

两个现场（2026-10-23，Alex 两张反馈截图）：

1. **纯读命令也要批准**。保险库写入档下 `cli_run tvly search "…"` 弹批准卡。`tvly` 不在 28 条只读
   白名单里（`src-tauri/src/harness/permissions.rs:250-254`），分类器按「未知 ⇒ 写」保守处理
   （同文件 `:389-390`），模式层于是逐个问。config 里的 `cli(tvly search *)` 本来就能放行
   （同文件 `:147-150` 的 allow 层），但**界面上没有任何入口把这条规则写进去**——用户唯一的逃生口
   是手改配置文件。
2. **`bash -lc` 任何档都问**。`bash -lc "ls …; echo …; ls … | tail"` 被 shell 包装器规则判危险
   （`:294-308`），任何权限档都逐个问。卡上的「采纳且本会话不再问」是**死按钮**：会话缓存在
   判定管线**第 5 层**才被读（`:152-155`），危险黑名单在**第 3 层**就返回了（`:139-145`），
   点了等于没点——缓存写进去了，但永远读不到。

根因不是这两条命令的个案，是三个结构性缺口：

- **有规则表、没有入口**：`[harness].permissions.allow/deny` 与匹配器（`permissions.rs:955-1030`）
  都已存在，但没有任何界面动作能从一次批准里沉淀规则。
- **会话记忆粒度是整条命令**：键是 `(工具, 规范化 argv)` 精确匹配（`permission_cache.rs:55-72`），
  `tvly search` 换个关键词就是一条新命令。
- **shell 包装器是绝对层**：包装器内容一律「不可知」（`permissions.rs:294-308`）；而 `cli_run`
  是 argv 直传、无 shell（`tools.rs:1213-1222`），复合命令只能包一层 `bash -lc`，模型落进黑名单
  是结构性的，不是模型任性。

同日六家一手调研（Claude Code / OpenAI Codex CLI / Cursor / Gemini CLI / Aider / Kimi Code）的
横向对比见底稿 §2.7：除 Aider 外每家都有「用户可持久化的命令前缀规则」，且五家能做「从批准动作
直接沉淀规则」；包装 / 复合命令的拆分里，Claude Code 与 Codex CLI 明确逐子命令判定，Cursor 用
沙箱兜底，没有一家把「shell 包装器」做成无条件 opaque。Lumir 是唯一「规则表存在但没有入口」的
一家。

### A1 · 从批准卡沉淀命令前缀规则

- 批准卡在「采纳 / 拒绝 / 采纳且本会话不再问」之外增加第三枚次级动作：**「以后都允许 `<规则>`」**。
  规则文本由**后端**从待决调用的 argv / 路径现算（单一真源），按钮上逐字显示将要写入的规则——
  授权面在按下之前就可见。
- `cli_run` 的规则形如 `cli(tvly search *)`：命令 + 首个非 flag 子命令；第二词是 flag 时退化为
  单词前缀 `cli(tvly *)`。
- vault 写工具取路径前缀：`vault_patch(notes/*)`；根目录文件给精确规则 `vault_patch(a.md)`。
- 不做裸工具级持久授权（`vault_patch` 不带模式 = 把整个 vault 的写都免掉，比任何一家的
  don't-ask-again 都宽）。
- 规则写回 `[harness].permissions.allow`，去重；写入是全局作用域（Alex 单用户，先全局；
  vault 级作用域列为后续候选，不在本期）。
- 权限浮层底部新增「已记住的规则」段：逐条显示规则原文 + 删除钮；列表为空时不渲染该段。
  列表取自后端当前配置（浮层打开时现读），MUST NOT 以前端缓存的旧值呈现。

### A2 · `bash -lc` 受限解包

只处理 `sh` / `bash` / `zsh` / `dash` 的 `-c` / `-lc` 精确形态（恰好一个脚本参数）。脚本必须是
**线性脚本**：只用 `;` `&&` `||` `|` 分隔、参数是字面量（允许单 / 双引号）、只允许
`2>/dev/null` / `>/dev/null` / `1>/dev/null` / `2>&1` 四种无害重定向。**每一个**子命令都经既有
`classify_cli` 判为只读，整条才按只读放行；任何一个子命令不是只读（含未知命令、`cd`）、或脚本
出现变量（`$` / 反引号 / `$( )` / `${ }`）、`<` / `>`（非白名单重定向）、`&`（后台）、括弧、
here-doc、换行、反斜杠转义——一律 **fail-closed**：维持现状「危险，任何档都问」。

三条不可妥协的边界（design §2 逐条钉）：

1. 解包**只降不升**：只有「全部子命令只读」这一种情形改变分类；其余情形维持**危险**，MUST NOT
   降为「写」——否则 `bash -lc "mkdir x"` 会在完全访问档被静默放行（现状是问）。
2. 子命令分类 MUST 复用既有 `classify_cli`，MUST NOT 引入第二套分类语义（REVIEW.md
   「同一语义两处真源」条）。
3. deny 规则与 allow 规则仍按**整条** argv 的主体串匹配，黑的还是黑的：`cli(bash *)` 的 deny
   照旧命中；allow 规则照旧绕不过危险层。

### A3 · 会话记忆前缀化

- `cli_run` 的会话记忆从「精确 argv」改为「命令前缀」，与 A1 共用同一个前缀生成器（一处真源）。
- 记住的粒度在按钮文案里显式写出（「记住 `tvly search` 开头的命令」），不让授权面静默放大。
- vault 工具与会话记忆保持精确路径 / 精确主体串（路径前缀留给 A1 的持久规则，会话内不放宽）。
- 缓存的作用域与生命周期不变：内存态、`(vault, session)` 命名空间、切会话即清空、不落盘。

### 死按钮隐藏（D3 的落地）

危险黑名单卡不再渲染两枚次级动作。后端把「本卡支持哪些次级动作」作为显式字段随批准事件与
`harness_state` 快照两条通道下发（与判定依据同源同路），前端只按字段渲染，MUST NOT 自行推断。

### A4 · 模型侧引导（identity.md）

在系统提示词的工具使用纪律里补三句：`cli_run` 直传 argv、不经过 shell；登录 shell 的 PATH 已
解析，裸命令可直接调用；需要组合查询时优先拆成多次 `cli_run`，确需 shell 时才用 `bash -lc`。
提示不是安全边界，只降低包装器的自然使用频率——真正的放宽由 A2 的保守判据承担。

## Non-goals

- **不引入 `ask` 规则层**（Alex 2026-10-23 裁决 D4）。`[harness].permissions` 仍只有 `allow` /
  `deny` 两张表；「某命令必须永远问」的诉求留给后续最小切片（届时先改 living spec 的口径）。
- 不做完整策略引擎（规则作用域 session / vault / user、规则管理器 UI、优先级数值），不做 OS
  沙箱（`sandbox-exec` 方案缓）。
- 不做通用 shell 解析：不解包 `cmd` / `powershell` / `pwsh` / `osascript` / `eval` / `exec`，
  不解包 `bash script.sh` 与多重 flag 形态，不解析 here-doc / 变量 / 控制流。
- 不改规则匹配语义为 glob / 正则：仍是「主体串前缀 + 结尾 `*`」，只补一处等值容差（Q2）。
- 不展示 / 编辑 deny 规则（仍手编 config）；不提供规则的作用域分级。
- `vault_delete` 与 `cron_task_*` 不提供持久规则入口（删除与「每天自己跑」的授权不宜一次点到永久；
  它们保留会话内的既有记忆能力）。理由与备选见 design §3.2。
- 不修既有只读白名单成员的自带写能力（`sed` 的 `w` 脚本命令、`base64 -o`、`rg --pre`、
  `git -c diff.external`）——那是**改动前就存在**的面，本 change 既不扩大也不收窄，已登记 finding
  另行处理。

## 裁决点（本提案新增）

每项给倾向；Alex 只否掉不同意的项即可。编号 Q 与 design.md §10 一一对应。

- **Q1 前缀生成的粒度**：两词前缀（命令 + 首个非 flag 子命令）还是单词前缀（只到命令名）？
  **倾向两词**：`cli(tvly search *)` 与 `cli(tvly *)` 的风险差一个量级——`tvly` 将来若有
  `tvly save` 之类的写子命令，两词前缀不会把它一并放行。第二词是 flag 时（如 `npm --version`）
  退化为单词前缀，按钮上照样显示实际文本。
- **Q2 规则匹配的等值容差**：`cli(git push *)` 是否也匹配无参数的 `git push`？
  **倾向是**：现有实现里 `*` 前的空格是词边界，精确等于前缀的命令反而匹配不上（`subject` 没有
  尾随空格），这会让「点了一次以后都允许、下次同一条命令又问」的怪提示出现。容差只在「前缀以
  空格结尾」时生效，不引入 glob。
- **Q3 解包的安全集取值**：分隔符 `;` `&&` `||` `|`；无害重定向 `2>/dev/null` `>/dev/null`
  `1>/dev/null` `2>&1`；其余一律 fail-closed。**倾向就取这一集**：`2>&1` 只合并输出流、不碰
  文件系统，留在集内能少问一大类命令（它不属 D1 原文的「仅 `/dev/null`」，故在此单列求裁）；
  `>>` 与 `<` 留在集外（前者写文件、后者可读任意文件喂给只读命令再经管道外泄）。
- **Q4 非全只读脚本的分类归属**：维持「危险」还是降为「写」？**倾向维持危险**：降为写会让
  `full_access` 档静默放行所有包装脚本（现状全问），等于用 A2 夹带了一次权限放宽。
- **Q5 规则写回通道**：前端用既有 `config_set_value` 整表覆盖，还是后端新增命令做单写者？
  **倾向后端**：规则文本必须由后端从 argv 现算（不采信前端传入的文本）；前端做数组读改写会与
  权限档写回（同一个 `[harness]` 表）并发交错，丢更新。
- **Q6 规则列表的入口位置**：权限浮层底部（分段 + 逐条删除），还是独立设置页？**倾向浮层**：
  权限 chip 已经是「权限」的唯一入口，加一个设置页等于新开一处要维护的浮层 / 页面；列表为空时
  整段不渲染，浮层形态在常见情况下零变化。
- **Q7 `vault_delete` / `cron_task_*` 是否给持久规则入口**：**倾向不给**。删除进废纸篓虽可恢复，
  但「一次点击 = 以后永久免问删除」的授权台阶过高；cron 的批准时刻是用户唯一能看见「它以后每天
  会自己跑」的时机，一次点到永久等于把这个时机取消。两者保留会话内的既有记忆能力。

## 顺带项（不另立 change）

- **living spec 口径改准**：`openspec/specs/harness/spec.md` 的「权限机制」requirement 与 Purpose
  都写着「三层权限规则（allow / ask / deny）」，实现只有 allow / deny。本 change 在 delta 里把
  requirement 改准为两层；**Purpose 句不是 requirement，不进 delta**，在归档时同步改（tasks 明列，
  与「归档后核对新建 capability 的 Purpose」同一处置通道）。
- **验收场景回扫**：改权限 / 闸语义的 change 必须回扫既有场景的闸期望，见 tasks 第 4 节。
