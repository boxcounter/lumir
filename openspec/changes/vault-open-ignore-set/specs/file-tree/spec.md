# file-tree 增量规格

> 起草注记（非规格正文）：本 delta 两条 MODIFIED，基线是 living spec
> [openspec/specs/file-tree/spec.md](../../../../specs/file-tree/spec.md) 的「全类型文件树展示」与
> 「watch 驱动的增量刷新」。变更来源是 Alex 节点 1 裁决（2026-09-28）的硬性约束：
> **被 vault 的 VCS 忽略规则挡住的目录与文件 MUST 仍然可见**——树因此从「枚举快照」变成
> 「枚举快照 + 按需层」，两条 requirement 相应改写（机制见 change 的 design §4）。

## MODIFIED Requirements

### Requirement: 全类型文件树展示

系统 SHALL 在 app-shell 的侧栏（宽 236px，见 ui-design-system「应用骨架布局」）挂载文件树，展示当前 vault 的全类型条目（目录可折叠，默认排序：目录在前、同缀按名称）。条目 SHALL 显示文件名与类型区分（至少区分目录 / Markdown / 图片等可预览附件 / 其他）。树的行形态 SHALL 取 design tokens：行高 25px、层级缩进 `8px + 14px × 层深`、选中态底色 `--sel`、hover 底色 `--hover`；eink 主题下选中态 SHALL 为黑底反白，行内次级元素（徽标 / ghost 项）SHALL 同步反白（eink 降级规则 ④）。树的数据来源 SHALL 为 fs-io 的枚举结果、按需枚举结果（`fs_scan_dir`，见 fs-io「按需枚举目录」）与 watch 增量事件，webview MUST NOT 直接访问文件系统（ADR 0002 §3）。

**可见集 SHALL 包含惰性条目**：被 vault 自己的 VCS 忽略声明（用户规则）命中的目录与文件（fs-io「全类型递归枚举」）SHALL 与普通条目一样出现在树里（同一行形态、可折叠 / 可点开、可右键），MUST NOT 因为「不在装载时的枚举结果里的深层」而被隐藏或渲染成不可用。惰性目录的子孙不在装载结果里，SHALL 在**用户展开时**经 `fs_scan_dir` 取回一层并合并进树模型；树 MUST NOT 把一个尚未取回子孙的惰性目录渲染成**空目录**（两种状态在模型里必须可区分——fs-io 的惰性标记即此用途），MUST NOT 因为取数在途而阻塞界面（ADR 0002 §6）。被**内置规则**挡住的名字（`node_modules` / `target` / `.git` 等）不出现在树里（口径见 fs-io「全类型递归枚举」），且这必须靠**单一真源**保证：这些名字的增量事件在 fs-io 侧就被挡下（fs-io「watch 增量事件流」的组件判定），树侧 MUST NOT 依赖自己的一份名单做二次过滤（前端没有、也不该有第二份忽略名单）。

惰性条目的可见性 MUST NOT 被读成「它已进索引」：链接解析与附件索引只覆盖主动枚举的条目（见 fs-io 的确定性条款）。

#### Scenario: 全类型混合展示

- **WHEN** vault 含 md、代码、图片、嵌套目录
- **THEN** 文件树全部展示并正确区分类型，不只展示 Markdown

#### Scenario: 行形态与层级缩进

- **WHEN** 展开三层嵌套目录并选中其中一个文件
- **THEN** 各行高 25px，缩进按 `8px + 14px × 层深` 逐级递增；选中行取选中态底色（eink 下黑底反白）

#### Scenario: 被忽略规则挡住的目录与文件仍然可见

- **WHEN** vault 根的 `.gitignore` 声明 `.local/`（磁盘上有 `.local/tutorial.md`），用户打开该 vault
- **THEN** 树里出现 `.local` 行（与普通目录同一行形态），展开后出现 `tutorial.md`，点开可读到正文

#### Scenario: 惰性目录不被渲染成空目录

- **WHEN** 用户展开一个惰性目录而取数尚在途中
- **THEN** 该目录 MUST NOT 呈现为「没有子条目的空目录」（展开态与空态在树模型里由惰性标记区分），界面不被阻塞；取回后子条目按排序规则并入

#### Scenario: 内置规则名字不出现在树里

- **WHEN** vault 根含 `node_modules/` 与 `target/` 目录（即使 `.gitignore` 里写了 `!target/` 把它取反）
- **THEN** 树里没有它们的行（与今日行为一致；内置规则不可被用户规则的取反推翻）

### Requirement: watch 驱动的增量刷新

文件树 SHALL 消费 `fs:entry_changed` 增量事件对树做局部更新（新增节点、删除节点、更新条目），MUST NOT 在每次事件后全量重扫重绘。刷新 SHALL 保持用户的折叠/展开状态不丢失。

惰性子树的实时性 SHALL 与 fs-io「watch 增量事件流」的判定一致：**未被按需展开过**的惰性目录，其内部的变更不进事件流——树里那些行是「展开那一刻的快照」，这是有意的取舍（把用户没在看的东西的变更挡在事件流之外，包括 `.tower/**` 这类高频 churn 的工作区）。用户展开过（物化登记）的目录，其下的增删改 SHALL 照常反映到树里。条目**自身**的增删改（行的出现与消失）SHALL 总是实时——包括惰性条目本身（外部删掉 `.local` 之后树里 MUST NOT 留一个死行）。

目录经**树内重命名**（含改回原名）后，该目录 SHALL 仍可展开并列出其全部子条目——这是「刷新保持折叠/展开状态」在改名这一形态上的落点：重命名前处于展开状态的目录 SHALL 保持展开（展开态随目录迁移到新路径，含其子孙前缀），未展开的保持折叠；树内 MUST NOT 残留旧路径的行。**外部进程**发起的改名（树没有对应的提交登记）只保证「可展开且子树齐全」，展开态不迁移——判据只认 app 自己发起的那一次改名，避免把「同一 debounce 窗口里删了 A 又新建 B」误判成改名（M258）。惰性目录的「子树齐全」按 fs-io 的同策略口径：它是惰性条目时，改名后仍是惰性行，子孙在展开时取回。

#### Scenario: 增量刷新保持展开状态

- **WHEN** 用户已展开若干目录，外部在 vault 内新建一个文件
- **THEN** 新文件出现在对应位置，既有目录的展开状态不变

#### Scenario: 树内重命名目录后保持展开且子树齐全

- **WHEN** 用户在树里展开目录 `a`（含 `a/x.md`），再经条目菜单把它改名为 `b`
- **THEN** 树中出现 `b` 行且仍为展开态（`b/x.md` 行在场）；旧路径的行不残留；改回 `a` 亦然

#### Scenario: 外部改名后目录仍可展开

- **WHEN** 外部进程把目录 `a` 改名为 `b`（树内没有对应的提交登记）
- **THEN** 树中出现 `b` 行，`b` 可展开并列出其全部子条目（展开态不迁移：判据只认 app 自己发起的改名）

#### Scenario: 未展开的惰性子树不产生刷新

- **WHEN** 外部程序在一个未被用户展开过的惰性目录里持续写入文件（如 agent 工作区）
- **THEN** 树不因这些变更发生任何更新（事件在 fs-io 的判定处被挡下），该目录行的存在与否仍随磁盘实时变化

#### Scenario: 惰性目录展开后的变更照常反映

- **WHEN** 用户展开过 `.local`（其中已有 `tutorial.md`），随后外部删除该文件
- **THEN** 树里 `tutorial.md` 行消失（物化过的目录，其下的增删改照常进事件流）
