## Why

Alex 2026-10-23 原话（逐字）：

> 「改进 harness pane 流式输出时的可操作交互性，现在的情况是只要正在输出，我就无法阅读
> AI 的输出，因为在快速滚屏，用鼠标往上滚动也不行，立刻会被流式输出拽到底部。」

同一需求的参考方向（Alex 给的，供参考、不锁死）：「只有用户本就在底部时才跟随滚屏，上滚即
脱离跟随，给『回到底部』浮钮与未读提示。」本提案按这个方向展开，逐项取舍见 D1–D8。

**现状机理（起草时对 `src/harness-panel.ts` 实读，行号以本分支 HEAD 为准）**：

- transcript 的滚动只有一个动作：`scrollToBottom()`，实现是
  `transcript.scrollTop = transcript.scrollHeight`（`src/harness-panel.ts:5936`）。
- 全文件 **16 处**调用它；其中流式增量走的就是这条：rAF 合帧回调（`:7201`）调用 `flushChunks()`
  （`:7211`），后者在正文缓冲非空时于 `:7236` 写一次滚动位。也就是说，用户上滚之后，**下一
  个有正文增量的帧（≤16ms）就会被写回底部**——Alex 说的「立刻被拽到底部」就是这条赋值。
- 面板**没有任何 `scroll` 监听**，也没有「用户是否在底部」这个概念；因此今天的面板在结构上
  不可能尊重用户的阅读位置。

**为什么值得做**：这不是一个锦上添花的交互优化，而是「流式输出期间面板不可读」。当前模型的
回答越长、工具循环越多（工具行也在写滚动位），用户越没法在中途核对已产出的内容——而
「边看边判断要不要停止」正是流式输出的核心价值。缺陷在结构层（无条件贴底），补丁式修复
（比如延迟滚动、动效缓冲）只会把「拽到底部」变成「稍后拽到底部」，必须引入「跟随 / 脱离」
两态。

## What Changes

逐条对应 `specs/harness/spec.md` 增量里的 requirement：

1. **跟随态由几何位置定义**（ADDED：transcript 的跟随滚动与回到底部）。视口距内容底部
   不超过回底容差 = 跟随态；用户以任何方式把视口带离底部超过脱离阈值 = 脱离态。两态之间是
   滞回区间，底部附近不抖动。**判据只有一份**：滚轮、触控板、拖动滚动条、消息摘录卡跳回旧
   消息的滚动定位，同一套几何判据，不按输入通道分叉。
2. **上滚即脱离、回底即恢复**（同上）。脱离态下任何内容增长（流式正文、思考块、工具行、
   通知、错误、批准卡）**MUST NOT 写滚动位**（`scrollTop` 变化 ≤ 1px）——这是本 change 的
   核心可机器验收判据：修前每次增量都把视口拽到底，修后视口纹丝不动。视口回到距底容差内
   （手动滚回或点钮）自动恢复跟随，无需显式开关。
3. **回到底部浮钮 + 未读圆点**（同上）。脱离态下在 transcript 视口右下角浮现「回到底部」钮，
   不随内容滚动；点击回到底并恢复跟随。脱离期间有新内容到达时钮上呈现未读圆点（D3：无数字
   计数——流式增量不构成「消息」的计数单位，数字会是伪造读数）。
4. **强制回底白名单**（同上）。只有用户自己发起的动作强制回底：发送消息、切换 / 恢复会话
   （含快照重建与重新打开面板）。自动回合、通知、错误、批准卡都不拽视口（D5）——其中错误
   行的既有「滚到可见」按同一判据收口，见第 5 条。
5. **错误行的「滚到可见」按同一判据收口**（MODIFIED：错误呈现）。既有条款要求错误行就地
   替换并「滚到可见」；脱离态下这条会重新制造「拽到底部」。增量把它改为：跟随态下滚到
   可见，用户已离开底部时不改滚动位，改由回底钮的未读提示承担。去重行为本身不动。

## 起草期取值（请评审时一并裁）

| # | 取值 | 倾向与理由 | 若你选另一侧 |
|---|---|---|---|
| D1 | **跟随判据 = 几何位置**（距底容差内即跟随），不设显式「跟随 / 暂停」开关 | 用户的心智模型是「我滚上去了 = 我要看这里」，不需要先学会一个开关；没有开关就没有「开关开着但我滚上去了」的冲突态。参考方向本身也是按位置描述 | 显式开关：需要一个常驻控件或快捷键，并定义「开关开着、用户上滚」时谁赢——这是本 change 想消除的歧义，不推荐 |
| D2 | **脱离即显示回底钮**（无论有没有新内容） | 钮首先是「回到底部」的导航件，其次才是提示件；脱离态下用户随时可能需要回去。若只在新内容时显示，用户上滚后想主动回底反而找不到入口 | 只在有新内容时显示：更安静，但「上滚看一眼再回去」要多一次手动滚动 |
| D3 | **未读提示 = 圆点，不计数** | 流式增量的「条」不可定义（chunk 不是消息，思考块 / 工具行也不是消息）；任何数字都要先发明计数单位，属于伪造读数。圆点只回答「下面有没有新东西」 | 数字计数：需要定义计数单位（完整消息？轮次？工具行？）与清零时机，且流式期间数字会持续跳动，信息价值低于噪音 |
| D4 | **不新增任何键位**：Space / PgDn 在 composer 聚焦时保持既有归属（Space 键入空格；PgDn 由引擎 / 既有键位表决定，本 change 不干预）；不把 transcript 改成可聚焦的键盘滚动区 | 键盘滚动 transcript 今天就不存在（容器不可聚焦），没有回归面；新增全局键位会与 composer 的编辑键冲突，加一个「回底」快捷键又要在键位表里占用稀缺组合。键盘用户可通过 Tab 聚焦回底钮后 Enter 回底 | 新增快捷键 / 让 transcript 可聚焦：需要定义焦点环、与 composer 的焦点切换、Space 的归属（输入还是翻页），属独立的可访问性 change |
| D5 | **强制回底白名单只含用户动作**：发送消息、切换 / 恢复会话、切 vault、重新打开面板；批准卡与错误**不**强制回底 | 批准卡到达时强制回底 = 用户正在读的那一屏被抢走，正是本次要解决的问题；批准是阻塞项，但用户滚回底部后会看到（未读圆点也提示「下面有新东西」）。错误同理 | 批准卡 / 错误强制回底：需要更强的「必须被看到」论证；若确需，正确形态是 transcript 之外的提示（如阶段行加「等待你批准」），那是另一个 change，不在本提案内静默扩张 |
| D6 | **脱离态跨轮次保持**：一轮结束后不自动回底；新回合 / 自动回合开始也不自动回底，直到用户回底或发送消息 | 用户上滚就是为了读，轮次结束不是「可以拽走」的信号；自动回合更不是用户动作 | 每轮开始自动回底：流式一停就跳，阅读会被反复打断；自动回合（cron / 子代理唤醒）下尤其突兀 |
| D7 | **浮钮形态与落点 = transcript 视口右下角的圆形浮钮**，不随内容滚动 | 右下角不压正文主体、与系统 overlay 滚动条的常用滑道错开，且与面板内既有浮动件（消息摘录钮）同一落点语言；浮在视口层（不占内容流）才能「随时可点」。放内容流里会随内容滚出视口，失去意义 | 顶部横幅 / 底部行内条：横幅占一条常驻高度（内容位移），行内条会滚动；两者都要额外的布局账 |
| D8 | **回底容差 6px、脱离阈值 16px**（滞回；两值都小于一行正文渲染高度，默认 13px × 1.5 ≈ 19.5px） | 容差吸收亚像素与舍入；滞回避免底部附近因回弹 / 小抖动反复切换。取值按「一次有意的滚动至少移动一行」倒推：16px < 一行 19.5px，滚一行就脱离；6px 只吸收舍入 | 单一阈值：在底部附近会闪烁（本 change 的视觉断言会把它钉红）；更大阈值：用户只滚一行也会被继续拽底 |

数值型取值（按钮尺寸 / 间距 / 圆点大小）不在裁决点里，按既有 token 与面板配方在 design §4 定。

## Non-goals

- **不改流式渲染本身**：Markdown 增量渲染、rAF 合帧、思考块 / 工具行 / 批准卡的形态一律不动。
  本 change 只改「内容增长后是否写滚动位」这一个决策点。
- **不做「暂停跟随」开关 / 常驻状态条**（D1）。
- **不做数字未读计数**（D3）。
- **不新增键位，不改 composer 键位归属**（D4）。
- **不改编辑器 / 预览 / 左栏 / 任务区的滚动行为**：本 change 的判据只作用于 transcript。
- **不做 transcript 之外的新提示面**（如阶段行里的「等待你批准」计数）：若 D5 裁「批准卡必须
  被看到」，那是独立 change。
- **不解决内容重排导致的阅读位置漂移**：`finalizeStreamingMessage` 会对当前消息的所有文本段
  做一次全量重渲，高度可能有微小变化；本 change 保证「脱离态下不写 `scrollTop`」，不承诺
  「任何内容重排都不改变可见行」。跨引擎的原生滚动锚定行为记为已知边界（design §6）。
- **不改错误行去重**：同文案只留一条的行为逐字不变（只改「滚到可见」在脱离态下的适用）。
