## ADDED Requirements

### Requirement: 保存应答的归属与迟到响应

保存结果 SHALL 只对**发起这次保存时的那份文档**生效。每次保存发起时 MUST 随路径捕获两项
归属凭据：该路径的**装载世代**与本次保存的**在途 token**。应答（成功或失败）落地时 MUST
先核对这两项凭据，任一不符即整体丢弃——写入结果、CAS 基准、dirty 状态与用户可见提示都必须
停留在当前文档自己的状态上。

下列事件 MUST 使该路径上的旧保存凭据整体失效（装载世代推进、该路径的在途标记撤下）：

- **vault 复位**：切换 / 重新打开 / 重新定位 vault（`vault-workspace` 的切换语义）会把全部
  路径上的文档一起换掉，旧 vault 的保存应答 MUST NOT 落到新 vault 的同名相对路径上。
- **同一路径的文档重新打开**：读快照成功并登记 CAS 基准（`noteOpened`）之后，此前发出的
  保存应答 MUST NOT 覆盖刚登记的基准。
- **app 内改名**：旧路径与改名后的新键上的旧保存应答都 MUST 失效；改名不改字节，CAS 基准
  仍按既有口径迁移。

旧应答失效后 MUST NOT 产生任何状态变化：MUST NOT 写 revision（CAS 基准）、MUST NOT 清
dirty 或清除崩溃备份、MUST NOT 弹「已保存 / 保存冲突 / 已被外部删除 / 保存失败」提示、
MUST NOT 改动缓冲区或选区。

在途保存标记 MUST 按 token 绑定，MUST NOT 只按路径整键归属：旧保存在任何时刻收尾（成功 /
失败 / `finally`）MUST NOT 撤下同一路径上**新保存**的在途标记。失效事件之后，同一路径的新
文档 SHALL 可以立即发起自己的保存，不被仍未收尾的旧保存挡住。

失效判据 MUST 是**路径级**的：打开新标签或打开别的文档 MUST NOT 让其他标签在途的保存作废
（MUST NOT 用全局装载世代号做保存应答的失效判据）。没有失效事件的正常保存，其成功推进与
失败处置（冲突的两个恢复动作、`fs_not_found` 的另存入口）MUST NOT 因本要求改变。

强制覆盖保存（拉取磁盘当前 revision → 写入两段）MUST 在每一段 await 之后用同一套凭据复查；
归属已失效时 MUST NOT 继续发起写入，MUST NOT 把返回的 revision 应用到新文档上。

#### Scenario: 切 vault 后同名文档收到迟到的成功应答

- **WHEN** vault A 的 `README.md` 保存已发出、应答仍在途；用户放弃修改并切换到 vault B，
  打开同名 `README.md` 并登记了 B 的 CAS 基准；随后旧应答成功返回 A 的 revision
- **THEN** 该应答被整体丢弃：B 文档的 CAS 基准仍是打开时登记的那一个，dirty 标记与缓冲区
  不变、不出现「已保存」提示；B 文档随后的 ⌘S 携带 B 的基准发出，不产生假 CAS 冲突

#### Scenario: 切 vault 后同名文档收到迟到的冲突应答

- **WHEN** 与上一场景相同的交错，旧保存的应答以 `document_conflict`（或 `fs_not_found`）失败
- **THEN** 新 vault 的同名文档上 MUST NOT 出现任何冲突 / 另存提示，dirty 与缓冲区不变；
  新文档自己之后的冲突仍按既有处置给出 sticky 提示与两个恢复动作

#### Scenario: 同一路径重新打开后旧应答到达

- **WHEN** `a.md` 的保存在途，同一路径被重新打开（读快照成功并登记新基准），旧应答随后返回
- **THEN** 旧应答被丢弃，重新登记的基准不被覆盖；下一次保存使用重新登记的基准

#### Scenario: app 内改名后旧应答到达

- **WHEN** `a.md` 的保存在途，用户在 app 内把 `a.md` 改名为 `b.md`（CAS 基准迁到新键），
  旧应答随后返回成功或失败
- **THEN** 旧应答 MUST NOT 写入新键的基准、MUST NOT 清 `b.md` 的 dirty、MUST NOT 在 `b.md`
  上弹出任何提示；`b.md` 的下一次保存使用迁移过来的基准

#### Scenario: 旧保存收尾与新保存交错

- **WHEN** 旧保存的在途标记已因失效事件撤下，同一路径的新文档已发起自己的保存；旧保存随后
  收尾（成功、失败或 `finally`）
- **THEN** 新保存的在途标记仍在：再按 ⌘S 不会发起并行的第二次写入；新保存自己的应答照常
  推进基准并清 dirty

#### Scenario: 打开新标签不影响其他标签的在途保存

- **WHEN** 标签 A 的保存在途，用户打开标签 B（装载事务开始、B 读快照并登记基准），随后 A
  的保存成功返回
- **THEN** A 的保存照常闭环（基准推进、dirty 清除、提示只说 A）；B 的基准与状态不受影响

#### Scenario: 强制覆盖保存的失效窗口

- **WHEN** 用户选择「强制覆盖保存」后，在读磁盘基准或写入的 await 期间发生 vault 复位 /
  同路径重开 / 改名
- **THEN** 覆盖链不再继续发起写入或丢弃已返回的结果；新文档的 CAS 基准不被旧覆盖应答覆盖，
  也不出现成功的覆盖提示
