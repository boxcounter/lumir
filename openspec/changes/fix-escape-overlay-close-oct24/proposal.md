## Why

### 现象

真机验收场景「只读白名单收紧：写形态进闸」（`scripts/acceptance/scenarios/231-harness-readonly-write-forms.md`）
的第二段，用户路径是：

1. 打开 harness 面板，点权限 chip 展开权限浮层；
2. 点「完全访问」，chip 读数翻成完全访问档、配置落盘（这些断言当时全部 PASS）；
3. 按 **Escape**，原意是收起权限浮层。

第 3 步之后 **Lumir 进程消失**：辅助功能树在同一秒退化成只剩一个节点，系统进程表里查不到该
进程，系统日志同一秒出现「窗口请求关闭 → 网页进程关闭 → 应用终止」的链条；没有崩溃报告（不是
段错误）。两次独立跑批都在同一步复现。对照现场：Escape 在输入框（composer）持焦时注入，只收起
面板，不退出——所以这不是「Escape 键坏了」，是焦点位置决定命运。

对真实用户同样可达：只要在权限浮层里点过一档，再按 Esc 想收起浮层，就可能直接丢掉整个窗口。

### 为什么这是产品缺陷，不是测试写法问题

- 现有规格没有任何一条把 Escape 定义为「关窗 / 退出」。相反：
  - `keymap-commands` 的「⌘W 归标签——原生菜单关闭项让出该加速键」条写死：`⌘W` 只关标签、
    **不关窗**；退出仍走 `⌘Q`（有未保存守卫）与窗口红灯按钮——窗口关闭只有这两个用户入口；
  - `harness` 的「浮层可访问性」条写死：浮层打开时 Escape **先收浮层**，无浮层时才收面板。
- 因此「Escape 关窗」不是设计，是缺陷。把验收场景从 Escape 改成「再点一次权限 chip」只能让
  套件不再看这条路径，用户仍然会撞上。

### 机制（结论）

已坐实到代码层的因果链有三段，最后一段由系统日志支撑：

1. **浮层选定后不关**，并重建自身内容（权限档位列表、provider 列表都是同一形态）；重建把原先
   持焦的按钮从页面里摘掉，浏览器把焦点送回 `body`。
2. **面板的 Escape 处理器挂在面板容器上**——焦点在 `body` 时，按键事件不经过面板，处理器根本没
   运行，也没有任何代码阻止这个按键的默认行为。
3. **没人消费的 Escape 落到原生窗口关闭链**：窗口框架无条件把关闭请求交给应用层，应用层只在
   文档有未保存修改时才拦；这次文档是干净的，于是窗口被销毁；单窗口应用销毁最后一扇窗即退出。

第 3 段里有一个归因要更正：缺陷报告把日志里的「prevented close」读成「未保存守卫拦住了」，代码
对照显示那句话来自窗口框架对系统 AppKit 的无条件拒绝——真正的销毁发生在更下一层的运行时，而产品
自己的未保存守卫这次**根本没被触发**（文档不脏）。所以「未保存文档在 Escape 路径上是否保得住」
目前**没有证据**；按代码推断应当保得住（dirty 时守卫会拦下关闭），但形态会变成「按 Esc 弹出一
次退出确认」——用户按的是 Esc，那同样不是意图。本 change 的判据因此比「不丢数据」更严：Escape
根本不应产生关闭请求，提示也不应出现。

### 为什么是现在

- 影响面是所有「浮层 / 面板持焦或失焦时按 Escape」的路径，不止权限浮层：任何浮层在自身重建后
  都可能把焦点丢到 `body`，此后一次 Escape 就能带走整个应用。
- 未保存文档在这条路径上的实际形态（是否弹退出提示、数据是否完好）现有证据未覆盖；按代码推断
  数据应能保住，但应以真机证据为准。这是潜在的数据丢失面，优先级高于普通交互缺陷。

## What Changes

1. **Escape 的顶层关闭语义（`keymap-commands` 新增一条 requirement）**
   一次 Escape 只关闭最上层的那一层（浮层 → 面板），关闭后焦点回到该层的触发元素（面板这类容器
   层回到它关闭前承接键盘的区域）；没有可关闭层时保持该焦点的既有归属（编辑器 widget 容器交还
   编辑器、输入条取消、面板收起），在 `body` 这类没有归属的焦点上为无操作。**Escape 在任何焦点
   位置都不得关闭窗口或退出应用**；窗口关闭的用户入口仍只有红灯按钮与 `⌘Q`。

2. **窗口级兜底 + 统一准入（同一条 requirement 的结构要求）**
   未被下游处理器消费的 Escape 必须在到达原生窗口之前被消费，不能依赖「焦点恰好落在某一层的
   容器内」。兜底挂在窗口冒泡阶段、排在统一键位分发器之后；不进 `KEY_BINDINGS`（「一个 token
   一条绑定」不变），不处理已被消费的事件。「什么算关闭意图」只有一份判断（组合期不关层、
   带修饰键只消费默认行为不关层），**层的就地键处理器与兜底共用它**——就地处理器先运行，不共用
   就会在兜底看到之前把 ⇧/⌘/⌃/⌥+Escape 或组合期 Escape 当成关闭。

3. **层栈是「谁最上层」的唯一判据（同一条 requirement）**
   各层自己的就地键处理器与兜底共用同一条关闭实现，层在打开 / 关闭时同步登记 / 注销；全部
   可关闭层都登记（含不持焦的 Context hover 泡与 effort 提示——它们的关闭不移动焦点）。这样
   才挡得住今天已经存在的隐性问题：面板与会话浮层同时打开时的关闭顺序、以及「层内持焦件被
   重建摘除」之后的失焦状态。

4. **harness 浮层重建后的焦点保持（`harness` 修改「浮层可访问性」条）**
   点选权限档位 / 切换 provider / model / effort 时浮层保持打开并重建列表，焦点必须留在浮层
   内的同一语义项上——语义键是「段 + 该项 id」，按重建时的当前状态取（成功落回新项、写回失败
   回滚后落回旧项），不得落到 `body`；没有可回落的对应项时交给触发钮。同时写明 Escape 收浮层
   （含 effort 提示）不得关窗或退出应用（通用口径指向 `keymap-commands`，不复制）。

5. **判据（详见 design §5）**
   纯逻辑层：准入矩阵（键 × 修饰键 × 组合期 × 已消费）× 层栈决策 × 重建保焦（三段 + 回滚）的
   单测，含反向验证；真实监听链：`escape-admission` 结构场景（真实 DOM 下就地处理器与兜底同一
   准入）；真机层：**先红后绿**的新验收场景（权限浮层持焦按 Escape 不关应用、浮层关闭、composer
   仍在、文档逐字节不变，外加 `shift+escape` 反例段），其他浮层逐类回归，以及应用退出路径的
   反例（带未保存修改时 `⌘Q` 仍被拦下、干净文档 `⌘Q` 仍正常退出）。

## Non-goals

- **不改窗口关闭与退出本身的语义**：红灯按钮、`⌘Q`、`⌘W` 关标签、未保存守卫的判定与提示全部
  不动。本 change 只保证 Escape 不再混进这些路径。
- **不在原生层加 Escape 拦截**：原生关闭请求分不出「用户点红灯」与「按键漏下来」；在原生层
  一律拦截会改变用户关窗语义。本轮把保证放在按键进入原生层之前的消费点，并用真机反例守住
  退出路径（D4）。
- **不重做各浮层的开合与可访问性形态**：不改 `role` / `aria-*`、不把浮层改成 dialog、不动宽度
  与落点（宽度在途 change `overlay-width-contract-oct24` 负责）。
- **不改输入法行为**：组合期的 Escape 仍归输入法，兜底不介入。
- **不修与本缺陷无关的浮层重建焦点问题**：发现即登记 finding，不在本 change 里顺手扩面。
- **不用「改验收场景」规避**：如果实现前已有把 Escape 步骤改成「点 chip」的临时处置，一并回退；
  场景必须保留 Escape 作为关闭路径，且先红后绿。

## 裁决点（D1 已由节点 1 裁决，其余未回按倾向落地）

- **D1 没有浮层时 Escape 的语义**（节点 1 已裁决）：**不额外消费**——不新增任何关闭 / 焦点 /
  状态动作，焦点在编辑器 widget 容器里仍执行既有的交还编辑器、输入条仍就地取消、面板仍收起。
  为满足同一句裁决里的「任何时候不能因此退出应用」，窗口兜底只做一件事：当这个按键**在所有
  下游处理器都没被消费**时，阻止它的默认行为落到原生关窗——它不关层、不移动焦点、不改既有归属，
  因此不构成新的 Esc 行为。现状里「焦点落在 `body` 上按 Escape 会退出应用」不是行为约定，是
  缺陷本身，不按「保持既有行为」保护。
- **D2 兜底的作用面**：倾向「全应用一条窗口级兜底」，不是只修权限浮层或只修 harness 面板。
  理由：缺陷的成因是「焦点不在层内容器内」，任何组件级处理器都挡不住下一条同类路径。
- **D3 浮层重建后的焦点落点**：倾向「留在同一语义项上」，语义键为「段 + 该项 id」——权限档位、
  合并选择器的 provider / model / effort 三段都覆盖，且按重建时的当前状态取键（写回失败回滚后
  落回旧项）。没有对应项再回落触发钮。比「一律回触发钮」多保一步——键盘用户连按方向键换档时
  不会被送回起点。
- **D4 是否加原生层拦截**：倾向「本轮不加」。原生关闭请求不带成因，无法区分 Escape 与用户点
  红灯；要加只能改变用户关窗语义。若真机探针证明存在「DOM 收不到 Escape」的焦点位置，再单独立
  项，不在本 change 里猜。
- **D5 顺带修「两个浮层同时开」的层序问题**：倾向「一并修」。层栈天然覆盖：今天面板与标题栏
  会话浮层可以同时打开，面板的 Escape 分支只看权限 / 合并 / hover 三泡，第二下 Escape 会把面板
  收起而会话浮层还在。这是同一语义的第二份实现，不修就会让新合同从第一天起不成立。
