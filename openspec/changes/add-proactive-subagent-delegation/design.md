# Design: 主动委派（工具描述承载时机）、`explore` 补 `vault_list`、`llm_request.tool_names`

- Change ID: `add-proactive-subagent-delegation`
- 日期: 2026-10-29
- 角色: Alex Lee（评审 / 裁决），AI agent（起草）

本文的读者是裁决者：不看代码即可判断「为什么改、改成什么、不做什么、怎么验」。

## 1. 问题与结论

子代理机制（change `add-harness-subagents`，2026-10-24 归档）已经把「定义 → 清单注入 → `task` 委派
→ 子运行 → 摘要回传」整条链落地。留下的缺口是**模型会不会用**与**用了以后能不能在留存里查明**：

1. **`task` 的工具描述只讲能力，不讲时机**，且通用提示词里没有委派指引。模型看到「有个工具能派活」，
   没有任何判据告诉它「什么样的任务该派、什么样的不该派」。Mock 驱动的验收场景把「派活」写死在
   fixture 里，执行链绿了，但「模型自己会不会选」从未被测过——这是覆盖面声明超出真实验证的典型形态。
2. **内建 `explore` 的描述与工具集不一致**：描述说「按路径枚举」，`tools` 里却没有列目录工具
   （`vault_list` 已入册，但 `explore` 没有声明它）。模型照描述去做会撞上「工具不存在」。
3. **留存里没有「这次请求暴露了哪些工具」的读数**：`llm_request` 记了 system / messages / 参数 /
   字节数，唯独不记工具名。于是「工具没暴露（开关关了 / 闸拦了）」与「暴露了但模型没选」在事后
   完全无法区分——真发现「正式会话没有 `task` 调用」时，排查只能靠猜。
4. **没有通用执行者**：用户不写定义时，任何要改文件 / 跑命令的任务都没有子代理可派——内建只有只读的
   `explore`，写类与 `cli_run` 只能由主会话自己做。这也是「为什么不让模型给动态指令」的另一半：
   `task.prompt` **已经是**每次调用自带的动态、自包含说明（F12），缺的不是指令的动态性，而是**能力
   够宽的执行者**与「何时用它」的判据。

对应三个变更（外加一个待裁候选）：**策略进工具描述**（新 requirement）、**内建定义调整——`explore`
补 `vault_list` + 新增 `general` 候选**（MODIFIED 定义 requirement）、**`llm_request.tool_names`**
（MODIFIED 留存 requirement）。`general` 是否落地由节点 1 单独裁决（§9.2），不默认已批准。

### 1.1 能力验收的四层判据（通用，本 change 只应用）

同一类问题已经发生两次（Alex 观察，经 tower 转述，本轮未复跑）：cron 落地后模型用 `cli_run` 手搓
系统调度而不是用 cron 工具；子代理落地后模型不主动 `task`。共同形态是**能力在场 ≠ 能力被用上**，
而当时的验收只覆盖了「能力能跑」。据此，本 change 的验收与报告一律按四层判据组织；这一节只在本
change 内应用，不改 `docs/process/**` 的任何流程文档（是否固化进流程属独立裁决）。

| 层 | 判据 | 本 change 的证据形态 |
|---|---|---|
| ① 能看见 | 启用时工具**实际**暴露给模型，暴露面可复核 | `llm_request.tool_names` 含 `task`（单测 + 场景 255）；`enabled=false` 时不含（场景 194，负向对照） |
| ② 会选择 | **用户不点名工具**时，真实模型按「专用优先 → general 次选 → 都不合适自己做」选择，并按总成本决定简单任务是否委派（不设硬门槛）；合理的只读子任务可单独派 | 真实 provider 六格观测（§7：explore 正向 / general 观测 / 简单只读观测 / 简单写观测 / 整件事无匹配不硬派 / 关闭开关负向） |
| ③ 能执行 | 选中之后的执行链正确 | 既有 mock 场景（180 等）与 Rust 单测：委派、并行、后台、闸、resume、批准透传 |
| ④ 可复核 | 事后能从留存区分「未暴露 / 未选择 / 执行失败」 | `tool_names` × `llm_response.tool_calls` × `subagent_rejected` / `subagent_finished.status` 三处读数（§5.2） |

三条硬口径，写进节点 1 供裁决：

1. **同类能力只补执行测试（③）不算验收完成**——③全绿而②从未观测，正是前两次的失效形态。
2. **本 change 的真实 provider 验收是②的硬证据**，不是「补充观察」；②不达标即本 change 不达标，
   不得以 mock / 单测替代（§7.4 的失败处置）。
3. ①③④可机器判；②只能由真实模型观测，因此样本、模型、时间与限制必须随证据一起记录（§7.3），
   结论只作存在性判据，不外推成通过率。

## 3. 变更点一：把「何时委派」写进 `task` 工具描述

### 3.1 文案草案（逐字待 Alex 裁决；本 change 的唯一文案基准）

`task` 描述的结构固定为三段，顺序不变：**能力说明 → 委派策略段 → 定义清单**。下表的三段文案是
唯一基准：实现、spec 增量、单测与文档抄录都以本节为准；**四条判据的固定标签**（「匹配就委派」
「无匹配就自己做」「按总成本权衡」「独立才并行」）是跨制品的锚点，改文案若动到标签，须同批改
spec 增量、单测断言（tasks 1.2）与文档抄录（tasks 1.5）。

**段一 · 能力说明**（沿用现文，不改语义）：

> 把任务委派给一个子代理：子代理有独立上下文，只把摘要返回；不能再次委派；需要批准的调用会弹给用户。

**段二 · 委派策略段**（新增，代码内单一常量）：

> 委派时机（按这四条判断要不要调用本工具）：
> - 匹配就委派：任务要跨多份文件反复搜索、比对，或过程材料多、你只需要一份压缩后的结论。清单里有
>   description 与能力都对得上的**专用**子代理时，直接派给它，不必等用户点名；没有专用、但有通用的
>   general 且任务在它的能力范围内时，派 general——**专用优先，general 是次选，不是默认选择**。
> - 无匹配就自己做：专用子代理与 general 都对不上时（整件事、以及能从它拆出来的子任务都算），自己做，
>   不要调用本工具——不要拿能力不够的子代理硬扛整件事，系统也不会替你改派。反过来，如果能拆出一个
>   description 与能力都对得上、本身有独立价值的子任务，就只把那段交给它、剩下的自己做：例如多份
>   笔记的只读对照交给只读子代理，拿回差异清单后自己写最终文件——这是分工，不是兜底。
> - 按总成本权衡：委派有固定开销（另起上下文、多一轮摘要），也可能有收益——省下主会话的上下文、
>   可并行、可以用专用模型、把大量过程材料关在子运行里。简单任务同样可以派：只要这些收益加起来
>   超过开销就值得。没有「简单任务一律不派」的硬规矩，你自己按总成本判断。
> - 独立才并行：互不依赖的多份调研可以在同一条消息里发多个 task 并行；后一步依赖前一步结果的，
>   不要并行。这条是许可不是义务——不要为了并行而并行。

**机制层只有四类硬约束**（§3.4 展开）：权限（批准 / 拒绝）、预算（轮次 / token / 时间三闸）、深度
（恰好 1 层）、能力（工具白名单）。**委派与否不在机制硬约束之内**——它是策略启发式，机制既不能
强制委派，也不能禁止委派。

**段三 · 定义清单**（沿用现行格式，每行一个定义）：

> 可用子代理：
> - explore：只读探索：…

### 3.2 为什么放在工具描述，而不是 identity

- **决策点就近**：工具描述是模型决定「要不要调用它」时读到的文本；identity 是全局纪律，写在里面的
  委派指引会推广到所有回合、所有任务，包括不需要委派的回合。
- **避免无条件指令**：Alex 的方向是「优先工具描述而非无条件 identity」。identity 里写「多调研就派
  活」会变成跨任务的全局指令；工具描述里的四条判据是可判断的启发式，不是一律委派或一律不委派。
- **不硬性规定委派时机**（Alex 2026-10-29 裁决）：是否委派由主会话按总成本决定。策略段给的是判断
  材料（开销与四类收益），不是禁令；「简单任务也可以派」写在同一段里。
- **定义可变、策略不变**：清单每回合随定义变化，策略段是常量；两者同一处组装，顺序天然可断言。
- **可机器判**：描述是纯文本常量，单测能逐条断言三段顺序、四个固定标签在场、策略段只出现一次（§6）。若写
  进 identity，断言对象变成整段装配后的 system prompt，判据反而更脆。

已知代价：工具描述在 wire 上位于 `tools` 数组，注意力位置不如 system。这是一条**可测的假设**
（H2），不是已知结论；§7 的真实验收就是它的检验，失败处置见 §7.4。

### 3.3 与「机制不内置任务类型」的界线

「委托运行（`task` 工具）」条要求「机制 MUST NOT 解析 prompt、MUST NOT 内置任何任务类型、场景名或
路径知识」。策略段是**给模型的判断指引**，不是机制的路由表：系统不解析它、不据它分支、不按它校验
调用。本 change 在新 requirement 里把这条界线写成明文（「策略段 SHALL 被表述为给模型的判断指引，
系统 MUST NOT 解析它」），避免下一次有人把它读成「内置了任务类型」。

策略段不含任何具体场景名（不写「评审 proposal」「整理日志」这类词），只描述任务形状（多文件、
材料多、可压成摘要、彼此独立）。

### 3.4 「适合委派」只是形状条件：无匹配就自己做，不兜底、不改派

节点 1 追问：「如果有任务适合委派，但不适合 `explore`，会怎么样？」——原稿的「匹配就委派」容易被
读成「形状适合就派」，本节把这层合同补齐。

**两个独立条件**。委派成立需要同时满足：

1. **形状条件**：任务跨多份文件调研 / 比对，或过程材料多、只需要一份压缩结论；
2. **匹配条件**：清单里存在 `description` 与**所需能力**都对得上的定义——针对**整件事**，或针对
   能从它**独立拆出的子任务**。

整件事与拆出的子任务都不匹配时，正确行为是**主会话自己做**。这不是降级，而是策略判据的第二条
（固定标签「无匹配就自己做」）：

- **匹配到自定义定义就派给它**：「匹配就委派」的宾语是**对得上的那一个**（例如自定义的 `research` /
  `reviewer`），不是「随便一个子代理」，更不是「默认 explore」。清单里哪个描述与能力对得上就派哪个。
- **整件事不匹配就自己做**：只有只读的 `explore`、而整件事要写文件 / 跑命令 / 改删时，整件事由
  主会话完成——MUST NOT 把它硬塞给 `explore`。主会话持有完整工具注册表（含写类与 `cli_run`），
  不存在「只有靠子代理才能完成」的事。
- **能拆出匹配的子任务就只派那段（合理分工，不是兜底）**：把整件事里**能力与描述都对得上、且自己
  有独立价值**的一段交给子代理，剩下的自己做。例：多份笔记的**只读对照**交给 `explore`（它只读、
  只回摘要），拿回差异清单后主会话写 `summary.md`。判定「独立价值」的三条：①子任务自身就是一个
  可交付单元（有明确产出，而不是把同一件事切一半）；②只用子代理已声明的工具就能完成（不要求它
  越权）；③体量够大、拆出去确实省上下文。三条都成立才是分工；拿能力不匹配的子代理硬扛原任务、
  或者把任务切成「你读前半我读后半」这种为绕过能力限制而切的做法，都不算。
- **机制不改派**：`task` 的 `agent` 不存在时只回 `agent_not_found` 与可用名字清单，不启动子运行；
  系统 MUST NOT 按任务内容替模型挑定义、MUST NOT 在能力不匹配时降级执行。理由与 §3.3 同源：一旦
  机制按任务内容选定义，就是内置路由，等于在代码里解析 prompt。
- **为什么不做自动兜底**：自动兜底会把「没有合适的人」变成「悄悄用了不合适的人」——错误从「明说
  做不到」变成「做了但质量差」；而能力匹配是语义判断，机制没有可靠判据，只能靠模型的判断与如实
  的描述。合理分工不在此列：它派出去的那一段本来就是匹配的，只是没把不匹配的部分也塞进去。

**代价与边界**：这条合同把描述准确性变成前提——清单里的 `description` 与 `tools` 必须如实反映能力，
描述虚高会让模型误判「有匹配」。`explore` 补 `vault_list`（§4）正是同一方向：先让内建的描述与能力
一致，再要求模型按描述判断。

**机制只硬约束四类，委派时机不在其中**（Alex 2026-10-29 裁决）：机制层能拒绝一次委派的只有
**权限**（ask 未批准 / deny 规则）、**预算**（三重闸与 `max_subruns_per_turn` / `max_concurrent`）、
**深度**（子运行无 `task`）、**能力**（工具白名单）。「任务太简单不值得派」「这类任务必须派」都是
**策略启发式**，MUST NOT 被实现成机制闸；机制 MUST NOT 以任务大小 / 形状 / 内容为由拒绝或强制委派。
这条界线让模型保留按总成本判断的空间，也让验收不必把「简单任务是否派」当硬判据（§7.2 B / F）。

**与「主动委派」不冲突**：策略仍然鼓励在匹配时主动派，只是不把「形状适合」当成充分条件；「不做
无谓委派」与「该派就派」是同一个判据的两面，具体由模型按总成本权衡（§3.1 第三条判据）。

## 4. 变更点二：内建定义的调整（`explore` 补 `vault_list`；新增 `general` 候选）

### 4.1 `explore` 补 `vault_list`

- `explore.tools` 由三件变四件：`vault_read` / `vault_search` / `vault_list` / `skill_load`。
- 描述同步改准：「在 vault 里**列目录**、按路径枚举、搜索与读取文件、加载 skill，产出结论与依据；
  不改文件、不跑命令。」——「按路径枚举」从空话变成有对应工具的能力。
- **`DEFAULT_TOOLS` 不动**（仍只读三件）。理由：缺省集是「未写 `tools` 的自定义定义」拿到的闭集合，
  扩它等于给所有既有自定义定义**悄悄加一个读能力**（行为变了、定义文件没变）；而 `explore` 是内建
  定义，显式声明第四件就能解决名不副实，不必动缺省。这条列为裁决点（§9.3）——`docs/backlog.md:6`
  的 M772 条目问的正是「缺省集要不要一起扩」，若 Alex 要一并扩，本 change 内加一行改动即可，不必
  另立 change。
- 不改其它工具、不改闭集合（9 件 vault 操作工具）、不改深度（子运行仍无 `task`）、不改权限模型
  （`vault_list` 是只读工具，已在读类放行面内）。

与主动委派的关系：`explore` 是「多文件调研」这个首场景的默认承载者。描述承诺能列目录而工具做不到，
模型委派出去的 explore 会在第一步撞墙（「工具不存在」），主动委派的收益被这条不一致吃掉。补
`vault_list` 是让「匹配就委派」这条策略真的可执行的前提。

### 4.2 新增内建 `general`（候选，待节点 1 裁决，不默认批准）

**先回答追问的前半句：为什么不是「允许模型给动态指令」**——这条已经成立，不需要新机制：
`task.prompt` 就是每次调用自带的动态、自包含任务说明（F12），子代理定义正文只是**身份段**，不承载
任务内容；而 `tools` 与三项预算来自定义 frontmatter，**不能由 prompt 动态提权**——这是安全边界：
模型不能靠一句话给自己或子代理加权限。真正的缺口是「没有能力够宽的执行者」：内建只有只读
`explore`，用户不写定义时，写文件 / 跑命令的任务无子代理可派（Gap 4）。

**候选定义（不默认生效）**：

| 项 | 值 |
|---|---|
| `name` | `general` |
| `description` | 「通用执行：按任务说明读写 vault、改文件、跑命令；不预设任务类型，一切由 prompt 决定。」 |
| `tools` | 9 件 vault 操作工具全量：`vault_read` / `vault_search` / `vault_list` / `vault_patch` / `vault_create` / `vault_move` / `vault_delete` / `skill_load` / `cli_run` |
| `model` | `inherit` |
| 三闸 | 取 `[harness.subagents]` 缺省（定义不写值） |
| 正文 | 通用执行身份段：按 prompt 完成任务；先读后改；写与命令受父会话批准闸；不能再次委派；结束给结论、依据与改动清单 |

**边界（写进 spec）**：`task` 与三件 cron 工具**仍不可得**（闭集合外 + 深度 1 层，F13）；ask 级调用
**照常透传**父会话批准卡并点名 `general`；`general` 与其他定义走同一条装载 / 校验 / 清单 / 覆盖
路径（同名自定义定义可覆盖，覆盖产 warning）；`[harness.subagents].enabled=false` 时一起退场。

**为什么推荐 9 件全量而不是更窄**：`general` 的存在理由就是「没有专用定义时的通用执行者」。若只给
只读工具，它与 `explore` 高度重复（多一个名字、少一个明确用途），除增加清单噪声外没有收益，故
**只读 general 不采纳**。写类与 `cli_run` 的风险由三道既有闸约束：权限档位、批准透传、三重失控闸。

**成本与滥用风险（正面写）**：

- **能力面最大**：`vault_delete` + `cli_run` 意味着 `general` 能删能跑；所有 ask 级调用仍要用户批准，
  但 `vault_write` 档下 `vault_patch` / `vault_create` / `vault_move` 属自动放行——一次委派可以在
  无人值守期间改多个文件。
- **过度委派**：有了 general，「把活派出去」的门槛降低，简单任务也可能被派走（多一层上下文、
  多一轮摘要，反而更慢更贵）。对策不是禁令：策略段给出「按总成本权衡」的判据（省上下文 / 并行 /
  专用模型 / 过程材料 vs 多一轮开销），并用真实 provider 的观测格（B / F）记录「无收益委派」的
  读数——记录与评估，不按数量判红（Alex 规则：机制不硬约束委派时机）。
- **配额**：子运行计入同一 provider 配额；后台 general 叠加自动唤醒会放大消耗（既有 `AUTO_WAKE_CHAIN_MAX`
  与并发上限不变，本 change 不加新闸）。
- **可观测**：`subagent_started` 的 `agent` 字段区分 general 与专用，`tool_names` 与 `subagent_finished`
  照旧；滥用可从这两处读数发现。

**覆盖规则**：与 `explore` 相同——用户级 / vault 级同名定义覆盖内建，覆盖产一条人话 warning。

**与 `explore` 的分工**：`explore` 仍是只读调研的首选；`general` 是「需要写 / 命令且没有专用定义」时
的次选。策略段按「专用 > general > 自己做」的顺序表达。

## 5. 变更点三：`llm_request.tool_names`

### 5.1 形状与写入点

```jsonc
{"kind":"llm_request","request":{"provider":"…","model":"…","system":"…","messages":[…],
 "params":{…}},"request_bytes":12345,"tool_names":["vault_read","vault_search","vault_list",
 "vault_patch","vault_create","vault_move","vault_delete","skill_load","cli_run","cron_task_create",
 "cron_task_list","cron_task_remove","task"]}
```

- **位置**：与 `request_bytes` 同级（`llm_request` 顶层附加字段），不塞进 `request`。
- **口径**：按请求里 `tools` 数组的顺序取 `name`，只取名字；MUST NOT 记录 schema / description /
  参数。去重不做（请求里的定义本就不重名，重复即是缺陷，应暴露而不是被静默抹平）。
- **恒在场**：无工具的请求（压缩调用）记 `[]`。`[]` = 「这一请求不带工具」；键缺失 = 「没有记录」
  （本 change 之前的旧文件）。两者 MUST NOT 混同——把缺失读成空数组会让「没记」变成「没有」，正是
  REVIEW.md「读不到当成空」条拦的形态。
- **写入点唯一**：`record_llm_request`（`turn.rs:966`）是唯一产出点，与发送同点。子运行的请求走
  同一函数（审计流水），因此子运行的白名单也自动可核——**深度 1 层因此从「靠代码保证」变成
  「留存上可查」**：子运行的任一 `llm_request.tool_names` 都不含 `task`。

### 5.2 为什么能区分「未暴露」与「未选择」

| 观测 | 结论 |
|---|---|
| `tool_names` 不含 `task` | 未暴露：开关关闭 / 定义清单为空 / 闸剔除。此时「没有 `task` 调用」不是模型的决定 |
| `tool_names` 含 `task`，同轮 `llm_response.tool_calls` 无 `task` | 已暴露、模型没选：策略 / 模型行为问题 |
| `tool_names` 含 `task`，`llm_response.tool_calls` 有 `task` | 已暴露且已选：主动委派发生 |
| 已选但结果不成功 | 执行失败：看工具回执的 `ok` / `code`（如 `agent_not_found`、`model_not_configured`）、`subagent_rejected` 的 `reason`、`subagent_finished` 的 `status` / `stopped_by` |

前三行正是本次交接争议点的机器判据：把「正式会话没有 task 调用」拆成「未暴露 / 未选择」两种结论，
一眼可分；第四行保证「派了但没成」不会被误读成「没派」——四层判据里 ④ 的完整形态（§1.1）。

### 5.3 兼容与隐私边界

- **兼容**：纯追加键。读取侧的每一处（恢复、标题素材、时间读数归属走查、读数重算、通知陈旧判定）
  都按已知字段取值——`system` / `messages` / 只按 `kind` 配对——没有任何一处遍历未知键。因此**不需要
  兼容层、不需要迁移、不改写旧文件**（AGENTS.md「变更默认直接切断」：这里根本没有要切断的消费者）。
- **隐私**：只记工具名（产品常量），不记 schema / 描述。这一点有实际意义——`task` 的描述里含**用户
  写的子代理定义描述**（vault 文件内容），若把整段描述落进每条 `llm_request`，等于把用户内容复制到
  留存的高频记录里。名字集合本身会暴露「subagents 是否启用」，这是本地诊断文件、不外发，且正是要
  观测的东西。
- **体量**：约 13 个短名字，百字节量级；相对 `request_bytes` 可忽略，不进性能合同（ADR 0002 第 6 条
  的路径是打开 / 按键 / 渲染，不在请求序列化里）。
- **不放进 `llm_response`**：暴露面是请求的属性，响应侧没有对应的真源；放两处就是两份真源。

| C 关停（负向） | 同 A 的提问，**经设置面**关闭「子代理」总开关（`[harness.subagents].enabled=false`） | 是否仍委派 | 属缺陷判红：`tool_names` 不含 `task`、无 `subagent_started` |

各格的分工：A 与 E 证明「能派得出去（专用 / 通用），且合规的分工不被误判」；B 与 F 收集「委派
选择 + 成本」的读数（不设硬门槛）；D 证明「整件事没人能干时不硬派、合理拆分仍允许」；C 证明
「关停确实生效」。顺序上 C 放最后——它是唯一改开关的格，紧接 §7.5 的恢复。

D 的**证据边界**：它只覆盖「整件事需要写文件、清单里只有只读子代理」这一种形态，验证两件事——
整件事没有被硬派、自动改派不存在；**不能证明所有不匹配情形**（不同描述措辞、多个定义都接近时的
取舍、能力边界更细的情形都未被覆盖），也不度量「零 `task`」与「只派只读子任务」哪一种更多。报告里
MUST 照写这句，不得把它写成「无匹配一定自己做」或「一定会拆」的普遍结论。

E 的**证据边界**：只证明「批量变更任务可被 general 承接，或按分工把只读子段交出去」这一形态；不证明
「所有写类任务都该派」，也不对「委派 vs 自己做」的优劣下普遍结论——是否委派由模型按总成本判断，
本格只核对「没有把能力不匹配的整件事硬派」与「结果正确」。

### 7.3 记录内容

模型 id（取 `llm_request.model`，不读配置）、提问原文、开始时间、六格的抽取结果、每格的 `tool_names`
数组与 `tool_calls` 名字表、**每格的委派与否 + 结果质量 + tokens + 耗时**（B / F 的成本观测就靠这四项）、
格 D 的清单构造与恢复读数、格 E 的子运行 `agent` 与 `tools` 读数及用量。落
`.local/reviews/proactive-subagent-delegation-oct29/real-provider.md`。

### 7.4 样本限制与失败处置

- **限制**：单模型、每格 N=1。因此结论是**存在性判据**（「机制可达、策略生效」），不是通过率，也
  不外推到其它模型 / 其它任务形态。报告必须照写这句，不得表述为「模型会主动委派」。
- **D 的额外限制**：只覆盖「整件事需要写文件 + 只有只读子代理」一种形态；不能证明所有不匹配
  情形（见 §7.2 末段）。**D 的清单构造不成立**（覆盖文件未生效、仍有可写子代理）时记「未验证」，
  不得改写成 PASS。
- **A 未委派**（已暴露、未选）：判 FAIL，先按 §3.1 改一处措辞（一次只改一处），复跑 A；最多两轮。
  两轮仍不达标 ⇒ 停手上报 Alex，附两轮的措辞差异与读数——这正好是「是否把指引搬进 identity」的
  裁决依据（§9.5），不在实现期自行加。
- **E 判红只有两种**：①把含写 / 移动的整件事交给只读代理；②结果不正确。**E 出现「只派只读枚举
  子任务、写由主会话做」不判红**——这是策略允许的分工（§7.2）；同样，**E 完全不委派也不判红**
  （按总成本判断），但要在报告里记「未委派」并附主会话 tokens / 耗时。
- **B / F 不判红**（Alex 2026-10-29 裁决：委派与否由总成本决定）：只记录「是否委派 / 质量 / tokens /
  耗时」。若委派且质量不差，记为成本读数；若委派后**多花 token 而质量与上下文收益都无改善**，
  记一条「无收益委派」观察项并在报告里单列，供后续决定是否调措辞——不进 PASS / FAIL 判定，也不
  触发复跑。
- **D 把整件事派给只读代理**（`task` 的 prompt 要求写文件 / 执行命令）：判 FAIL——「无匹配就自己
  做」没有生效，先按 §3.1 改一处措辞，复跑 D；两轮仍不达标则停手上报。**D 出现「只派只读子任务」
  不判红**：这属策略允许的合理分工，按 §7.2 的判据核对（prompt 只含只读诉求、子运行工具集为只读
  白名单、写由主会话完成）后记为合格。
- **成本观测**：A / E 的委派记录 `subagent_finished` 的 tokens / `duration_ms` 与主会话摘要字符数，
  B / F 记录两侧的 tokens 与耗时；报告给出「委派 vs 主会话自己做」的量级对比（不做统计推断）。
- **不得**：重跑到绿而不记录失败轮次；改 fixture 冒充真实选择；只跑 mock 就宣称验收通过；把
  `.local` 证据写成「模型行为已达标」而不给六格读数。
- **C 异常**（`enabled=false` 仍有 `task`）：属缺陷，按 bug 处理，不是验收失败。
- **任何一步失败、超时或中止**：收尾恢复照跑（§7.5）——**先恢复再上报**，不把用户环境留在关闭态
  或残留覆盖文件。

### 7.5 强制收尾：恢复开关与覆盖文件并核实（无论成功失败）

格 C 与格 D 之后，无论后续步骤成功、失败、超时还是中止（含 app 崩溃后的重启），下面两件恢复都是
验收的必做步骤；**任一未恢复即视为验收未完成**，不得写 PASS。

**A. 子代理总开关**（格 C 改过）

1. **动作**：经设置面把「子代理」总开关恢复为 §7.1 记录的进入时值（本次预期为**开启**）。
2. **核实**：取一处**恢复之后**的独立读数——设置面显示的开关状态为开启，**或**新发一条请求后
   `llm_request.tool_names` 含 `task`；两者至少一项成立。MUST NOT 复用格 A 的旧读数充当核实。
3. **留痕**：把「进入时值 / 格 C 关闭后的读数 / 恢复动作 / 恢复后的核实读数」四行写进
   `.local/reviews/proactive-subagent-delegation-oct29/real-provider.md`；失败的轮次同样留痕。
4. **禁止**：不得读取、备份或改写凭据文件（`config.json` 等）来实现或核实恢复；不得用改配置文件
   代替设置面；不得因「反正只是本地开关」跳过恢复。
5. **恢复失败**：设置面不可用、或核实读数仍为关闭 ⇒ 立即停手，把现场（界面状态、时间、已完成的格）
   上报 tower / Alex，不得继续其它验收，也不得自行改文件「修好」。

**B. 格 D 的同名覆盖文件**（`general` 获准时写过 `.lumir/agents/general.md`）

6. **动作**：删除该文件——**无论 D 成功、失败、超时还是中止都删**。该文件属合成 vault，不得留在
   盘上，也不得以「下次再说」跳过。
7. **核实**：删除后取**独立读数**证明内建 `general` 已恢复——下一回合的生效清单（例如一次委派
   `general` 时 `subagent_started.tools` 为 9 件），**或** 覆盖文件已不存在且一次新委派的
   `subagent_started` 显示 `general` 的工具集为 9 件。MUST NOT 只凭「文件已删除」推定生效。
   若 `general` 未获准（无覆盖文件），本步改为核实清单仍是只有 `explore`。
8. **留痕**：把「覆盖文件路径 / 删除动作 / 恢复核实读数」三行写进同一份 real-provider.md。
9. **恢复失败**：文件删不掉、或核实读数仍显示只读覆盖 ⇒ 立即停手上报，**不得继续其它验收、不得
   写 PASS**，也不得自行「再覆盖一次」或改其它文件绕过。

## 8. 非目标、依赖与残余风险

**归档顺序（语义依赖）**：`vault_list` 进入「工具集声明与默认收紧」条的闭集合，由 change
`add-harness-vault-workspace-list` 的 delta 承担（该 change 已实现、待归档）。本 change 若先归档，
并入后的 living spec 会出现「`explore` 声明了闭集合外的工具」的自相矛盾——因为两个 delta 改的是
**不同** requirement（一个改「子代理定义文件」，一个改「工具集声明与默认收紧」），归档对账门禁只比
同一 requirement，看不见这个矛盾。故**本 change MUST 在该 change 之后归档**；实现与评审不受影响
（代码侧 `vault_list` 早已入册，装载不依赖 living spec 文字）。

- 不改 identity / 工作区段 / AGENTS.md 装配的任何措辞（§9.5 是独立裁决）。
- 不改子代理深度（子运行仍无 `task`）、不改权限模型、不改闭集合；新增工具只有 `general` 声明已含的
  9 件（即不再引入新工具，`general` 只是把它们显式声明给一个内建定义）。
- 不记录完整工具 schema 或描述（隐私与体量，§5.3）。
- 不引入按任务类型的路由 / 分类器：策略是文本指引，机制不解析。
- **机制不硬约束委派时机**（Alex 2026-10-29 裁决）：硬约束只有权限 / 预算 / 深度 / 能力四类；不得把
  「简单任务不派」「只读任务必须派」写成机制闸。
- 残余风险：策略段在 `tools` 数组里，注意力位置弱于 system；若真实模型仍不选，需要提示词层兜底
  （独立 change）。
- 残余风险：真实 provider 的单次观测受模型随机性影响；六格设计用 B / F / C / D 四个对照提高解释力，
  但仍不能替代多轮统计——本 change 不声称统计显著性。
- 残余风险：D 只覆盖一种「能力不匹配」形态（需写文件、清单里只有只读子代理），其它不匹配形态
  （描述相似但能力边界更细、多个定义都接近）未被验证（§7.2 末段）。
- 残余风险：`general` 若获准，是内建定义里能力面最大的一项（写类 + `cli_run`）；批准闸与三重闸照旧
  约束，「委派惯性」可能上升——用 B / F 格的选择与成本读数观测（§7.4），不设硬门槛。

## 9. 裁决点（逐条可否决）

1. **策略段文案**（§3.1 逐字）：四条判据的措辞是否可用？特别是「按总成本权衡」这条——它把委派
   决定交给模型判断，是否读得懂、是否会被读成「尽量别用」或「尽量都派」；「专用优先、general 次选」
   的顺序是否表达清楚。
2. **是否新增内建 `general`，以及它的工具集**（§4.2；**不默认已批准**）：
   - 推荐：**新增**，`tools` 取 9 件 vault 操作工具全量（含写类与 `cli_run`）。理由：没有它，用户不写
     定义时写类 / 命令类任务无子代理可派，而只读 general 与 `explore` 高度重复，等于加一个没用的名字。
   - 边界（不论选哪个工具集都成立）：`task` / cron 工具仍不可得（闭集合 + 深度 1 层）；ask 级调用
     透传父会话批准卡并点名 `general`；同名定义可覆盖；关停时随内建一起退场。
   - 备选 A：**只读 general**（`tools` = 只读四件）——不推荐，与 `explore` 重复，只增加清单噪声。
   - 备选 B：**写类但去掉 `cli_run`**——降低执行面，但 `general` 的用途从「通用执行」退化成「能改
     文件」，跨工具的组合任务仍要主会话做；若担心 `cli_run` 的爆炸半径可选它。
   - 备选 C：**不新增 general**——按 §9.2.1 的缩减清单同步全部制品。
