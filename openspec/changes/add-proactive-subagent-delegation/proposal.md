# Proposal: 主动委派（策略进工具描述）、`explore` 补 `vault_list`、`llm_request.tool_names`

- Change ID: `add-proactive-subagent-delegation`
- 日期: 2026-10-29
- 角色: Alex Lee（评审 / 裁决），AI agent（起草）

> **来源**：用户交接材料（tower 转述的要点，非逐字）——正式版 0.11.1 上
> `harness.subagents.enabled=true`、task 暴露链未见断点，但正式会话没有 `task` 调用；identity 无主动
> 委派指引，`task` 描述只讲能力不讲何时用；mock fixture 写死第一次 `task`，不能验证真实模型主动
> 选择；`llm_request` 不记录工具清单。用户明确要求：按 OpenSpec 流程先出节点 1 提案，不直接改代码；
> 真实 provider 必须验证「主动选择」而不是只补 mock；并已采纳「给 `explore` 补只读 `vault_list`」。
>
> **节点 1 追问（2026-10-29，经 tower 转述）**：「如果有任务适合委派，但不适合 explore，会怎么样？」
> ——原稿只写了「匹配就委派」，容易被读成「形状适合就派」。答复落成 design §3.4 的合同：**必要条件
> 只有一个**——清单里有 `description` 与能力都匹配的定义（整件事或能独立拆出的子任务）；「多文件 /
> 材料多」不是门槛，只是判据三里的收益信号。匹配到哪个自定义定义就派给哪个。整件事和拆出来的子任务
> 都没有匹配时，主会话自己做；**禁止把能力不匹配的完整任务硬塞给 `explore`，也不允许机制自动改派**。
> 但**能拆出匹配且有独立价值的子任务时可以只派那段**（例如多份笔记的只读对照交给 `explore`，主会话
> 随后写 summary）——这是合理分工，不是 fallback（初稿曾写成「拆分一律禁止」，节点 1 前按 Alex 纠正
> 改回此边界）。策略段因此由三条判据变**四条**，新增固定标签「无匹配就自己做」；真实验收补格 D，
> 区分「整任务硬派（禁止）」与「只读子任务委派（允许）」两种结局，并写明它只覆盖这一种情形。
>
> **节点 1 追问二（2026-10-29，经 tower 转述）**：「为什么不是允许模型委派 subagent 并给动态指令，
> 或者增加 general subagent？」——**动态指令已经存在**：`task.prompt` 就是每次调用自带的动态、
> 自包含任务说明（F12）；定义正文只是身份段，`tools` / 预算来自 frontmatter，**不能**由 prompt
> 动态提权（这是安全边界）。缺的是**能力够宽的执行者**：内建只有只读 `explore`，用户不写定义时
> 写类 / 命令类任务无子代理可派。答复落成 design §4.2 的**候选**：新增内建 `general`（9 件 vault
> 工具全量、`task` / cron 仍不可得、批准照常透传），策略改为「专用优先 → general 次选 → 都不合适
> 自己做」，真实矩阵补 general 观测格与简单任务观测格。**`general` 是否新增及其工具集是节点 1 的
> 显式裁决项（design §9.2），本提案不默认已批准**；它与本提案的其他条款一起裁决：若节点 1 否决
> `general`，**本提案不进入实现**，由 tower 修订后重新走节点 1，实现者 MUST NOT 自行删减合同。
>
> **节点 1 裁决留痕（2026-10-29，经 tower 转述）——委派时机改为按总成本判断**：「是否委派由主会话按
> 总成本决定，『简单任务不派』不得硬性要求。」据此本稿的三处改动：① 策略第三条由原硬性禁令改为固定
> 标签「**按总成本权衡**」（旧标签已退役）——委派有固定开销，也有省上下文 / 并行 / 专用模型 /
> 过程材料四类收益，简单任务也可以派；② **机制硬约束只保留四类**（权限 / 预算 / 深度 / 能力），
> 委派时机不再是机制闸；③ 真实验收里 B（简单只读）与 F（简单写）从「不派才算过」改为**观测格**：
> 记录选择、质量、tokens 与耗时，评估有无「无收益委派」，不按委派与否判红。
>
> **本 change 只做提案**：不改产品代码、不改 living spec、不改既有 prompts。节点 1 通过后才进入实现。

## Why

子代理机制的链已经通了：定义文件 → 清单注入 `task` 描述 → 委派 → 子运行 → 摘要回传（`task` 描述
的现文与清单格式见 `src-tauri/src/harness/tools.rs:333`）。通的是**执行链**；没有通的是**模型自己
会不会用**，以及**事后能不能查明它为什么没用**。三个缺口各自独立，但指向同一件事：能力在场 ≠ 能力
被用上。

1. **`task` 的描述只回答「我能派活」，不回答「什么时候该派」。** 描述里是一句能力说明加一串定义
   清单；identity 与工作区段也没有委派指引。模型看到的是一个可用工具，缺少把它和「这类任务该交给
   别人做」连起来的判据。结果就是：任务再适合委派，模型也只是自己做。
2. **「自动委派」的验收其实是 mock 驱动的。** 委派场景的 fixture 第一条响应就写死了 `task` 调用
   （`scripts/acceptance/fixtures/harness-subagent-delegate.json`），场景与覆盖表却把它称作「自动
   委派」（`scripts/acceptance/scenarios/180-subagent-delegate-discovery.md`、`COVERAGE.md:27`）。
   它证明的是「派出去之后链条走得通」，不是「模型会主动派」。这条覆盖声明超出了真实验证范围，是
   REVIEW.md 收录过的假绿形态。
3. **留存分不清「没暴露」与「没选」。** `llm_request` 记了 system / messages / 参数 / 字节数，唯独
   不记这次请求给了模型哪些工具（`src-tauri/src/harness/turn.rs:966`）。于是「正式会话里没有 `task`
   调用」在事后无法拆开：可能是开关 / 闸 / 清单让它根本没出现，也可能是它出现了而模型没用。排查
   只能靠复现，不能靠读数。
4. **内建 `explore` 的描述与能力不一致。** 描述写「按路径枚举」，`tools` 里却没有列目录工具
   （`src-tauri/src/harness/agents.rs:43`）；`vault_list` 早已入册（`tools.rs:176`），只是
   `explore` 没声明。模型照描述委派出去，第一步就撞「工具不存在」。这条已作为待裁条目记在
   `docs/backlog.md:6`（M772），本 change 承接并收口。
5. **没有通用执行者（追问二的落点）。** 内建只有只读 `explore`：用户不写定义时，写文件 / 跑命令的
   任务没有子代理可派，`task` 对它们等于不可用。**动态指令并不缺**——`task.prompt` 已是每次调用的
   动态自包含说明（`tools.rs:345`），定义正文只是身份段，`tools` / 预算不能由 prompt 提权；缺的是
   「能力够宽的执行者」与「何时用它」的判据。

## What Changes

三个变更（外加一个待裁候选 `general`），各自对应一条 spec 增量；机制、权限模型与深度都不动。

1. **`task` 工具描述承载委派策略**（`harness-subagents` ADDED「委派的触发时机」）。描述结构固定为
   「能力说明 → 委派策略段 → 定义清单」（能力说明沿用现文）。策略段是代码内单一常量，逐字草案见
   design §3.1（该节是唯一文案基准），表达四条判据，标签固定为：
   - **匹配就委派**：清单里有 `description` 与能力都对得上的**专用**定义就派它，不等用户点名；
     没有专用、但有 `general` 且任务在它能力范围内时派 `general`——**专用优先，general 次选，
     不是默认**。注意：跨多份文件 / 材料多不是委派的门槛，只是判据三里的收益信号；
   - **无匹配就自己做**：整件事、以及能从它拆出来的子任务，清单里既没有对得上的专用定义、也不适合
     `general` 时，自己做，不调用 `task`——**不把能力不匹配的整件事硬塞给子代理**，系统也不替你
     改派；**能拆出匹配且独立可交付的子任务时可以只派那段**（如只读对照交 `explore`、自己写结论），
     这是分工不是兜底；
   - **按总成本权衡**：委派有固定开销（另起上下文、多一轮摘要），也有收益（省主会话上下文、可并行、
     可用专用模型、过程材料关在子运行里）；简单任务也可以派，只要收益超过开销。是否值得由模型按
     总成本判断——不写「简单任务一律不派」这类硬禁令（Alex 2026-10-29 裁决）；
   - **独立才并行**：互不依赖的多份调研**可以**在同一条消息里并行派；依赖前一步结果的不并行。
     这是许可不是义务——不得表述为「必须并行」，也不得为了并行而并行。

   策略是**给模型的判断指引**，机制不解析它、不建任务类型枚举或路由表（界线写成明文）。机制侧同时
   写明：**不提供任何自动改派 / 自动兜底路径**——`agent_not_found` 只回错误与可用清单、不启动子运行，
   系统不按任务内容替模型挑定义、不在能力不匹配时降级执行。**机制硬约束只有四类**（权限 / 预算 /
   深度 / 能力）；委派时机不在其中，机制 MUST NOT 以任务大小或形状拒绝或强制委派。通用提示词
   （identity / 工作区段 / AGENTS.md 装配）**不**加入委派指引——策略只有一个居所，是否搬进提示词
   属独立裁决（见 design 裁决点 5）。
2. **内建定义调整：`explore` 补只读 `vault_list`；新增 `general` 候选**（`harness-subagents` MODIFIED
   「子代理定义文件」）。
   - `explore.tools` 由三件变四件（`vault_read` / `vault_search` / `vault_list` / `skill_load`），
     描述同步改准为「列目录、按路径枚举、搜索与读取文件、加载 skill」。
   - `general`（**候选，待节点 1 裁决**）：通用身份段 + `tools` 取 9 件 vault 操作工具全量（含写类与
     `cli_run`）；`task` 与 cron 工具仍不可得，ask 级调用照常透传批准卡并点名 `general`；可被同名
     定义覆盖。只读 general 与 `explore` 高度重复；窄化工具集不是一个可实施选项——二者都属「本提案
     不进入实现、重新走节点 1」。成本与滥用风险见 design §4.2 / §9.2。
   - `DEFAULT_TOOLS` 不动（仍是只读三件）——扩缺省集会改变所有既有自定义定义的行为，是否一并扩
     单列为裁决点。不改闭集合、不改深度与权限模型。
3. **`llm_request` 增 `tool_names`**（`harness` MODIFIED「会话本地留存」）。每次会话请求的记录里
   增加「本次暴露给模型的工具名清单」：按请求中的顺序、只记名字、不记 schema 与描述；恒在场，无
   工具的请求记 `[]`；本 change 之前的文件缺该键，读取方 MUST NOT 把它当空数组。由此三类观测可
   区分——不含 `task` = 未暴露；含 `task` 但响应里没有 `task` 调用 = 暴露了没选；两者都在 = 派了。
   子运行走同一记录点，因此「子运行的工具集里没有 `task`」（深度 1 层）也从代码保证变成留存可查。

mock 与真实 provider 的分工也要改准：mock **不再冒充真实行为**——mock 与单测守「暴露面 + 执行链」
（含 `enabled=false` 时 `tool_names` 不含 `task` 的负向断言，与启用时形成区分度）；「模型主动选择」
由真实 provider 的六格观测判定（explore 正向 / general 观测 / 简单只读观测 / 简单写观测 / 整件事
无匹配不硬派 / 关闭开关负向），证据只抽字段、不读取或复制凭据。判据、样本限制与失败处置见 design §7。

## 验收判据：能力验收的四层（通用，本 change 只应用）

同类问题已发生两次（Alex 观察，经 tower 转述）：cron 落地后模型用 `cli_run` 手搓系统调度而不用
cron 工具；子代理落地后模型不主动 `task`。两次的共同形态是「能力能跑」被当成了「能力可用」，而
「模型会不会用」从未被观测。本 change 起，这类能力的验收按四层报告（口径见 design §1.1）：

| 层 | 判据 | 本 change 的证据 |
|---|---|---|
| ① 能看见 | 启用时工具实际暴露，暴露面可复核 | 单测 + 场景 255（`tool_names` 含 `task`）与 194（关闭时不含） |
| ② 会选择 | 用户不点名，真实模型按「专用优先 → general 次选 → 都不合适自己做」选择，并按总成本决定简单任务是否委派（不设硬门槛）；合理的只读子任务可单独派 | 真实 provider 六格（design §7.2）；这是②的硬证据 |
| ③ 能执行 | 选中之后的执行链正确 | 既有 mock 场景与 Rust 单测 |
| ④ 可复核 | 留存能区分「未暴露 / 未选择 / 执行失败」 | `tool_names` × `tool_calls` × `subagent_rejected` / `subagent_finished` |

三条对裁决的承诺：**同类能力只补执行测试（③）不算验收完成**；**②不达标即本 change 不达标**，不得
用 mock / 单测替代；②的模型、任务、时间、样本限制必须随证据记录，结论只作存在性判据。四层判据
只在本 change 内应用——是否固化进 `docs/process/**` 属独立裁决，本 change 不改任何流程文档。

## Non-goals

- **不改 identity / 工作区段 / AGENTS.md 装配的措辞**。委派指引只进 `task` 描述；真实验收不达标时
  是否搬进提示词，是独立裁决，不在实现期自行加。
- **不扩 `DEFAULT_TOOLS`**（推荐口径）：只让内建 `explore` 显式声明 `vault_list`。
- **不改子代理深度、权限模型、工具闭集合**；不新增 `explore` / `general` 声明之外的任何工具。
- **`general` 不获得编排与调度工具**：`task` 与三件 cron 工具仍在闭集合之外（深度 1 层不变）。
- **不接受「prompt 动态提权」**：`task.prompt` 只表达任务内容，不能改子代理的工具集 / 预算 / 模型；
  能力面只能由定义文件声明。
- **不记录完整工具 schema / 描述 / 参数**：只记名字（`task` 的描述含用户写的定义描述，属用户内容）。
- **不做自动改派 / 自动兜底 / 能力探测**：没有「没有匹配就找个能跑的」「能力不足就降级执行」这类
  路径；`agent_not_found` 只报错，机制不按任务内容替模型挑定义。
- **不把能力不匹配的整件事硬塞给子代理**：只读子代理不承接需要写文件 / 跑命令的整件事；但**允许
  只委派匹配且独立可交付的子任务**（如只读对照交 `explore`、主会话写结论）——这是分工不是兜底，
  不属于本 Non-goal 的禁止面。
- **不硬性规定委派时机**（Alex 2026-10-29 裁决）：机制只有权限 / 预算 / 深度 / 能力四类硬约束；不做
  「简单任务一律不派」这类机制闸或提示词禁令，是否委派由主会话按总成本判断。
- **不做按任务类型的路由 / 分类器**：策略是文本指引，机制不解析 prompt。
- **不用 mock 冒充「主动选择」**：不新增「fixture 写死 `task` 即算自动委派」的断言，也不把既有场景
  继续称作自动委派。
- **不调模型参数 / 不改 provider**：真实验收用既有配置，只观测。
- **不做可配置的委派策略**（不开放开关 / 阈值 / 按定义配置策略文案）。

  - REVIEW.md「覆盖声明超出真实验证」「值或开关声明了却没有消费者」「读不到当成空」「断言等价于
    子串」：分别对应 180 改准、`tool_names` 有真实消费者（验收与排查）、缺失 ≠ `[]`、启用 / 关闭
    两侧取值的区分度断言。

## 裁决点

细节与去向见 design §9，此处只列裁决面：

1. **策略段文案**（design §3.1 逐字）：四条判据的措辞可否使用；「按总成本权衡」这条是否读得懂、
   会不会被读成「尽量别用」或「尽量都派」；「专用优先、general 次选」的顺序是否表达清楚。
2. **内建 `general` 及其工具集**（design §9.2，**不默认已批准**；与提案其他条款一起裁决）：
   **唯一可按本稿实现的选项是新增 full-9 `general`**（9 件含写类与 `cli_run`；`task` / cron 仍不可得、
   批准照常透传）。**只读 `general`、去 `cli_run`、不新增**都属「本提案不进入实现」：由 tower 修订
   后重新走节点 1——窄化会改动定义、断言、E/F/D 合格路径与恢复合同，实现者 MUST NOT 自行删减。
3. **`DEFAULT_TOOLS` 是否一并扩到四件**：推荐只改 `explore`（缺省集不动）。
4. **真实 provider 验收的判据与样本量**：六格 × N=1、单模型的存在性判据是否够用，还是同格跑 3 次。
   B / F 是观测格（委派与否不判红），见 design §7.2。
5. **是否需要 identity 兜底**：推荐本 change 不做，真实验收不过再独立裁决。

> 拆分委派不是裁决点：禁止的是「把能力不匹配的整件事硬塞给子代理」与「机制自动改派」；允许把
> 匹配且独立可交付的子任务单独派出去（design §3.4）。
