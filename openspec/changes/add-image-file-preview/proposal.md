## Why

Alex 2026-10-23 的需求原话（逐字）：

> 「支持显示图片文件。现在能在 markdown 文件里显示 line image，但是在左栏里直接点击图片文件，不会在
> content pane 里显示，而是提示"Preview not supported yet:{path}"」

**现状**（起草时逐处读过源码）：

- **分类层已认识图片，打开层不认**：扩展名注册表把图片单列一类（`src/preview/attachments.ts` 的
  `IMAGE_MIME`，含 `svg` / `heic`），文件树据此显示图片条目；但 `openKind`（`src/tree.ts:222`）
  只返回 `md` / `code` / `text`，其余一律 `"binary"`——图片因此在打开链路里与 PDF 同档。
- **落点是「暂不支持预览」覆盖层**：`loadSessionContent`（`src/main.ts:2201`）对 `kind === "binary"`（分支在 `:2208`）
  直接 `showNotice(t("D25", { path }))` 并返回 false，不建任何标签。
- **「显示一张 vault 图片」这件事本身已具备全部零件**：文档内图片引用今天就能显示，字节来自
  `fs_read_attachment`（invoke + base64，50MB 上限）→ `data:<mime>;base64,…`（
  `src/preview/attachments.ts:264` 的 `readDataUrl`）；放大查看已有遮罩（`src/lightbox.ts`，
  复用同一条 `data:` URL，不重读字节）。缺的只是「把它接到内容区，而不是一句提示」。

**为什么值得做**：Lumir 是本地文本工作台，图片是笔记的**一等附件**（截图、示意图、扫描件）；在
文档里能看到、在左栏点开却看不到，是同一种文件在同一个应用里的两种命运。这条缺口每天都在
dogfood 里出现（写明「暂不支持」的提示本身就是证据），而它**不引入新的字节通道**——只是把已有的
读取能力接在一个新的呈现面上。

**本提案不做的事**（先划清边界，也是拒绝面）：不做图片编辑 / 旋转 / 裁剪 / 导出；不做图集或缩略图
网格；不为不支持的格式做转码；不改 harness 输出里图片路径的可点性（那条 today 明确「图片保持纯文本」）。

## What Changes

逐条对应 spec 增量里的一个 requirement：

1. **图片文件的点击落点改为图片查看面**（file-tree，MODIFIED：点击打开文件与可编辑性裁决）。图片
   不再与二进制同档：点击后在内容区显示图片，不再出现「暂不支持预览」。md / code / text 的打开
   分类与可编辑性裁决逐字不变。
2. **独立查看 vault 图片文件**（attachment-display，ADDED：独立查看 vault 图片文件）。锁定查看面的
   形态（标签身份、适配显示且不放大、双击进既有放大遮罩、失败一律可见占位）、字节来源（既有
   `fs_read_attachment` + 既有 MIME 注册表，零新后端命令）、以及**结构性只读**（不产生未保存状态、
   ⌘S 无落点、搜索 / 大纲 / 阅读位置对它是空动作）。
3. **配套的既有面收口**（不新增 requirement，属实现任务，列在 tasks 里）：会话恢复的建壳闸门今天
   把图片与二进制一起挡掉（`src/main.ts:1635`），要放行图片；harness 路径链接的文件索引过滤
   （`src/main.ts:1037`）今天用「`openKind !== "binary"`」表达「只链接文本类」，分类变更后必须显式
   排除图片，否则会**静默**把图片路径变成可点——与本条 spec「图片保持纯文本」相悖。

## 起草期取值（已裁决之外，请评审时一并裁）

| # | 取值 | 倾向与理由 | 若你选另一侧 |
|---|---|---|---|
| D1 | 图片**作为一个文档标签**显示（可切换、⌘W 关闭、跨 pane 移动、重启后恢复） | 标签栏是唯一的「我在看什么」账本；图片与文档并列才能并排对比（分栏）、才有 ⌘W 与恢复；代价是会话模型要多一档「不可编辑会话」，改动面覆盖标签 / 恢复 / modeline（design §2 有逐点清单） | 「临时查看面」：点图片盖住当前 pane、点任一标签即恢复。实现小得多，但标签栏会显示上一个文档为「当前」，且图片不进会话恢复——形态上像「预览叠加层」而不是文档 |
| D2 | 显示**适配可视区且不放大**（与 lightbox 同口径） | 与既有放大查看共用一条口径（一处真源）；小图不糊、大图看得全 | 1:1 原尺寸 + 滚动：能看清像素级细节，但与 lightbox 口径分叉，且需要新的滚动容器与「居中 / 左上角」取舍 |
| D3 | 内存策略：**只保留当前激活图片的字节**，切走释放、切回重读一次 | 常驻内存合同 <200MB（ADR 0002 §6）；多张大图标签同时驻留会把这条打穿 | 全部保留：切标签瞬时（无加载态），代价是内存随打开过大图的张数线性增长 |
| D4 | 读取失败 / 超 50MB / 解码不出像素 → **占位 + 人话提示**（与文档内图片的可见回退同口径） | 一条口径覆盖两种承载面；不弹窗、不破图 | 回落到 D25 覆盖层：把「提示」换回整块覆盖，会盖住标签内容且语义上退回本提案要修掉的状态 |
| D5 | modeline 右段（原「语法 · 行数 · 编码」位）对图片显示**「图片 · 宽×高 · 文件大小」** | 这个位置本来就是「这份内容是什么」的读数；图片没有行数 / 语言 / 编码，空着像坏了 | 只显示「图片」两字，或整段留空 |

## Non-goals

- **不做图片编辑**：不写回源文件（ADR 0003 §3 铁律），不做旋转 / 裁剪 / 标注 / 导出。
- **不做图集 / 缩略图网格 / 幻灯片**：一次一张，走标签。
- **不为不支持的格式做转码**（heic / avif 等取决于系统渲染引擎）：渲染不出就按失败占位。
- **不做 1:1 滚动、缩放条、平移手势**（D2 的另一侧）。
- **不改 harness 输出里图片路径的可点性**：那条 spec 明确「图片 / 二进制保持纯文本」，本提案不动
  它（分类变更只要求**保持**该行为，见 What Changes 第 3 条）。
- **不新增后端命令**：字节走既有 `fs_read_attachment`，MIME 走既有注册表。
- **不改文档内图片引用的任何行为**（内联显示、路径解析、lightbox、可见回退全部逐条不变）。

## Impact

- **影响的 specs**：`file-tree`（MODIFIED：点击打开文件与可编辑性裁决）、`attachment-display`
  （ADDED：独立查看 vault 图片文件）。`multi-tabs` / `pane-layout` 的「会话即标签」语义被**引用**
  （图片标签是新的会话形态），本提案不改这两条的字面条款。
- **影响的代码 / 系统**：
  - 分类：`src/tree.ts` 的 `openKind` 增加图片分类（仍以 `src/preview/attachments.ts` 为唯一注册表）。
  - 会话模型：`src/editor.ts`（一类不可编辑会话）+ `src/main.ts`（打开分流、modeline、搜索 / 大纲 /
    阅读位置的空动作、会话恢复建壳、harness 路径索引过滤）+ `src/tabs.ts`（标题渲染，无逻辑分叉）。
  - 新模块：`src/image-viewer.ts`（查看面 DOM、字节装载、失败占位、双击进 lightbox）。
  - 后端：**零改动**（复用 `fs_read_attachment` 与既有 MIME 推导）。
- **关联约束**：
  - ADR 0002 §3：webview 不直接访问文件系统（走 invoke + base64）。
  - ADR 0002 §6：常驻内存 <200MB（D3 的内存策略就是为它设的）；打开 1MB Markdown 的时延口径不受
    影响（图片走独立标签，不进编辑器装载路径）。
  - ADR 0003 §3：不改写源文件。
  - 仓库信息卫生：视觉 / 验收 fixture 用合成小图（1×1 或小尺寸 PNG 的 base64 常量），不用真实截图。

## 观测闸三问

- **怎么知道用户用了它**：从树点开图片是显式动作；dogfood 即可感知；无埋点。
- **怎么知道它有效**：点开就看得到；大图完整适配、双击能放大；重启后图片标签还在；再也不会看到
  「Preview not supported」用在图片上。
- **出问题怎么发现**：机器面兜底——分类纯函数单测（image 不再落到 binary）、查看面的视觉场景
  （图片在场、适配、双击打开遮罩、失败占位）、会话恢复单测（图片标签建壳并恢复）、真机验收场景
  （点开、双击、⌘S 无写入、重启恢复）；`gate.sh quick` 与 `visual` 全绿。
