## Why

### 现场一：会话留存写失败只进 stderr，用户以为历史已保存

- `src-tauri/src/harness/jsonl.rs:250-281` 的 `record()` 返回 `()`：序列化失败、打开失败、
  首行写入失败、行写入失败全部只 `eprintln!` 后返回。生产路径 15 处调用点（`turn.rs` /
  `session.rs` / `title.rs` / `subagents.rs` / `harness.rs` / `run.rs`；子运行审计流水另用
  独立 writer）无一处处理返回值。
- `jsonl.rs:264-266` 另有一个同根缺陷：先 `self.pending_open.take()` 再写首行。首行写失败后
  这份挂起的 `session_open` 从内存消失，后续记录继续追加——产出一份首行不是 `session_open`
  的文件；`read_session_file` 判 `harness_session_invalid`（`jsonl.rs:411-416`），这份文件
  不能被恢复，也不会出现在历史列举里。
- `writeln!` 还可能**写入部分字节后返回错误**；`read_session_file` 对任一行非法 JSON 直接
  报错，因此部分写可能让整份文件不可读。保留挂起行只能修「内存遗忘」，不能保证文件仍合法。
- `harness.rs:905-915` 的 `list_sessions` 对不可读留存 `continue` + 一条 stderr——历史列表
  因此静默少一项。上述缺陷与这条跳过叠加，就是「不可恢复且不可见」。
- 后果：磁盘满、配置目录权限变化、配置目录被外部清理时，用户继续聊天、界面一切正常，
  但这段历史已经写不进去，且没有任何提示。

### 现场二：崩溃备份写失败被吞掉，文案已经备好却没有消费者

- `src/save-controller.ts:882-887` 的 `backupDirty()` 以
  `await recoveryBackup(...).catch(() => {})` 收尾；`save-controller.ts:324-328` 的
  `forgetBackup` 同样吞错；`checkRecovery()` 的读失败（`:898-907`）直接 `return`——
  有残留备份时用户永远不会被问要不要恢复。
- 文案面早已备好：`src/copy-data.ts:377` 的 `D198`「无法写入崩溃备份」映射到
  `recovery_write_failed`（`:2845`），`D201`「无法枚举恢复目录」映射到
  `recovery_list_failed`（`:2848`）——这两条**零消费者**：写失败的 reject 被
  `backupDirty` 吞掉，枚举失败的 reject 被 `checkRecovery` 吞掉。`D199` / `D200`
  （读 / 删失败）只在「恢复内容 / 丢弃备份」的动作失败分支里经 `errorText(e)` 消费，
  不在本次的静默面上（REVIEW.md「声明了却没有消费者」条针对的是前两条）。
- 后果：崩溃备份是「编辑器里唯一一份未保存内容」在崩溃时的唯一保险。保险失效时用户完全
  不知情，下一次崩溃就是永久丢失。
- 既有原则已经写明方向：`openspec/specs/fs-io/spec.md:423`「跳过是显式裁决，MUST NOT
  表现为『静默地什么都没有』」——写失败连「显式跳过」都不如。

### 一个被合并的事实：能写 ≠ 历史完整

初审版把两件事压进一个 `ok/degraded`：

1. 当前是否仍能写入；
2. 这段逻辑会话是否**已经**缺失历史记录。

`llm_request` / `llm_response` 一旦写失败，后续成功只证明写能力恢复，不会补回缺失记录；
压缩轮换后新文件首次成功也不能修复旧文件的洞。部分写还可能让 JSONL 直接损坏。因此本版把
健康拆成**当前写健康**与**历史缺口（`history_gap`）**两维：成功只清当前写失败，缺口在同一
逻辑会话内 latch，只有显式新会话 / 从历史恢复 / app 重启才停止展示。文案必须能说
「写入已恢复，但此前记录缺失」。

复审补充：**首行写失败会连带丢弃本次 `record(payload)` 的 payload**。即使首行干净失败、
没有写入任何字节，当前 `llm_request` / `llm_response` 也没有写出；不能因为「首行可重试」
就判无缺口。gap 必须按本次 payload 是否 recovery-critical 决定：history payload 一律置
gap，annotation payload 才按 annotation 规则不置。另加辅助事实 `history_written`（是否已
有至少一条 history 记录成功落盘），用于在「尚无任何历史落盘」时明确提示退出后无法恢复。

### 为什么两条告警面不合并

| | 文档崩溃备份 | Harness 会话留存 |
|---|---|---|
| 丢的是什么 | 内存里**唯一一份**未保存内容，崩溃即永久丢失 | 「以后能否恢复这段历史」；当前对话仍在内存，可继续 |
| 严重度 | 高 | 中 |
| 主载体 | 文档区 sticky 横幅，不自动消隐 | harness 面板 composer 上方常驻状态行 |
| 次载体 | 受影响标签的读屏名 / 悬停提示后缀 | 本逻辑会话首次进入 `history` 的一条 sticky 提示 |
| 动作 | 「全部保存」（复用既有 `saveAllDirty()`） | 无（修复磁盘不在 app 内） |
| 忽略 | 不提供 | 不提供；sticky 的点击关闭只关一次性提示，不等于静音（V3） |

合并成一套「通知中心」会把两种不同量级的风险压成同一种，也命中「不要扩成设置中心或通用
通知系统」的边界。

## What Changes

1. **新增 `harness` requirement「留存健康状态」**：维护**当前写健康**与**历史缺口**两维。
   当前写健康按任意写失败转 `degraded`、成功转 `ok`；历史缺口在 `llm_request` /
   `llm_response` 失败或任意可能部分写时 latch，成功 / 压缩轮换 / 切 vault 都不清除，只有
   新逻辑会话（显式新会话 / 从历史恢复 / app 重启）才重置。两维经 `harness_state` 快照的
   `persistence` 键与 `harness:event` 的同名事件呈现，同键同值；面板在 composer 上方持续
   显示状态行，缺口恢复后仍显示「写入已恢复但此前记录缺失」；`history_written=false` 且有
   告警时明确「本次会话的新记录尚未落盘，退出后无法恢复」；本逻辑会话首次进入 `history`
   （含 `annotation→history`）给一条 sticky。
2. **修改 `harness` requirement「会话本地留存」**：末句「写失败不阻断对话的既有纪律不变」
   改为「不阻断，但结果 SHALL 反映在**当前写健康与历史缺口**两维上」；其余留存语义一字不动。
3. **修改 `fs-io` requirement「崩溃备份与恢复入口」**：备份写失败与备份枚举失败 MUST 可见，
   且是横幅上两个**独立子条件**——写失败给「全部保存」，枚举失败给「重新检查」；保存成功
   只清对应路径的写失败子条件，MUST NOT 撤下枚举失败子条件。备份的触发、位置、生命周期、
   恢复语义一字不动。
4. **同批修 `pending_open` 的内存遗忘，并按 payload 判首行失败的 gap**：首行写失败后下一条
   记录 MUST 仍先重试写首行；MUST NOT 丢失挂起行。本次 payload 是 `llm_request` /
   `llm_response` 时，即使首行干净失败也 MUST 置 `history_gap`，后续成功不得补回或清缺口；
   annotation payload 才按 annotation 规则不置 gap。**不承诺部分写后的文件可恢复**：可能已
   写入字节时持续给 `history` 告警并写明边界；本 change 不做截断 / 回滚 / 原子发布。
5. **切 vault 不清健康**：切 vault 只切换展示哪份快照，后端会话仍按 vault 保留；切回显示
   同一会话自身仍 latch 的状态。
6. **诊断留痕**：每次留存写失败落一条结构化诊断日志（记录 kind + 错误分类 + 是否部分写，
   不含正文）。

## Non-goals

- 不新增设置项、不改设置面板、不做通知中心 / 历史总览 / 健康面板。
- 不提供「忽略 / 静音」出口（V3 默认）；sticky 的点击关闭只移除一次性提示，不撤状态行、
  不清缺口、不写配置、不构成对未来失败的静音。
- 不提供手动「重试」钮：两类写入都在下一次自然写入时自动重试；唯一的例外是备份枚举失败的
  「重新检查」（V5）。
- **不做 JSONL 原子发布 / 回滚 / 截断修复，不承诺部分写后的文件仍可读或可恢复**。若要绝对
  可恢复保证，另立 change 设计原子方案并补前缀写故障注入（V7）。
- 不为 annotation 另建一套历史 latch：annotation 干净失败只影响当前写健康；annotation
  部分写按「文件可能损坏」归入 `history` 缺口。
- 不覆盖 `fsync`、断电、文件被 `unlink` 后写到旧 inode、外部清空目录。
- 不把子运行审计流水（`subruns/`）、composer 草稿、附件纳入健康状态。
- 不追溯修复 / 提示本次之前已经产生的不可读留存文件。
- 不把健康状态持久化到配置或磁盘；app 重启后按新会话重新起算。`history_written` 只保存在
  后端内存，不跨 app 重启保留；webview 整页重载后由后端 Session 的 `harness_state` 快照重建。
- 不改会话留存与崩溃备份的既有触发、位置、生命周期与恢复语义；不改 vault 内文件格式
  （ADR 0003 第 3 条铁律）；不引入新的运行时依赖。
- 不改 cron 回执契约：隔离运行（无人值守）的健康只进日志，不向面板呈现。

枚举失败子条件独立保留，不随写失败清空撤下。理由见 `design.md` §5.6；若 Alex 希望保存后
仍保留，需要另给一个清空条件。

## 已知边界与验收可达性

| 场景 | 可达性 | 由谁承担 |
|---|---|---|
| 健康时不打扰（无横幅、无状态行、无后缀） | 真机可达（负向场景） | 真机验收 |
| 文档备份写失败可见 | 真机可达：`envWrite` 在 `<隔离配置>/lumir/recovery` 写一个**普通文件**，备份目录创建失败 | 真机验收 |
| 「全部保存」清写失败子条件；枚举失败仍保留 | 真机可达：`seed.envFiles` 预置 `recovery` 为普通文件 → 启动时枚举失败 → 编辑触发写失败 → 保存成功后横幅仍以枚举文案保留 | 真机验收 |
| 保存失败时横幅保留 | 真机可达（把 vault 内目标改成不可写或制造冲突） | 真机验收 |
| harness 写入失败正面注入 | **不可稳定真机注入**：会话目录与文件名由 app 生成；阻断父目录会变成「发送被拒」，不是记录失败 | Rust 单测 + 视觉桩；真机只验「健康时不打扰」 |
| 部分写导致坏 JSONL | **真机不可稳定注入** | Rust `LineSink` 故障注入（R7）；真机不验 |
| 首行干净失败 + history payload | **真机不可稳定注入** | Rust R6a：断言首行可重试但本条请求永久缺失、gap 保持；真机不验 |
| 首行干净失败 + annotation payload | **真机不可稳定注入** | Rust R6b：只丢 annotation、不置 gap；真机不验 |
| 尚无 history 落盘时的「退出后无法恢复」提示 | **harness 失败无法真机注入** | 前端 U13 + 视觉桩；真机不验 |
| 切 vault 保留健康 | **harness 失败无法真机注入** | Rust 单测 R4 + 前端 U10 |
| app 重启后文档失败重现 | 真机可达：重启后**再编辑一次**、等备份窗口到期才重现（失败态不持久化） | 真机验收 |

## 与既有纪律的关系

- 「写失败不阻断对话」不变：`record()` 仍不返回错误、不打断轮次；新增的是「必须可见」。
- 「变更默认直接切断」：不设兼容层；不保留「缺键当健康」之外的旧快照分支（缺键按
  `ok` / `present=false` 是为了不误报旧后端，属读取侧宽容，不是产品兼容层）。
- 「切 vault 不是会话替换」：后端会话按 vault 保留，健康不能随切换重置；这是本版对初审的
  修正。
- 「sticky 关闭不是静音」：一次性提示可关闭，常驻状态行与缺口不受影响。
- 仓库信息卫生：本 change 的所有 fixture / 截图 / 文档只用合成路径与人名；诊断日志不含
  正文、不含消息内容。
