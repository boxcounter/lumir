## Why

Alex 原话（2026-10-11）：「我使用时发现 harness composer 里先贴两张图之后，不能通过 CTRL+B 把光标挪到
两张图之间。但我有时候需要这样的能力——先截几张图贴进去，然后再写内容。这改进起来困难吗？」

**现状根因**（以下事实性断言全部对着本 worktree（基于 master `e4abfbf`）的源码逐行核实）：

1. composer 是混排编辑区，顶层只有两类块：**原子卡片**（引用 / 消息摘录 / 图片）与**问题段落**。光标位是模型值
   `ComposerCaret {block, offset}`，`offset` **只在段落文本内有意义**，卡片等非文本块上 offset 恒 0（= 该块
   前缘），「卡片后缘」用下一块的前缘表达（`src/harness-panel.ts:220-226`）。
2. 因此「两张相邻卡片之间」在**模型里其实是有表示的**：`{block: 后一张卡的下标, offset: 0}`。
3. 但 **DOM → 模型**这一侧读不出来：`caretFromDom` 对「选区锚在 composer 元素自身」的位置一律返回 `null`
   ——爬升循环 `while (blockEl.parentElement !== composer)` 走到 composer 之上就出循环，得到 `null` 并整体
   放弃（`src/harness-panel.ts:2622-2628`、`:2661`）。而「两张相邻块之间」在 DOM 里恰好就是这种位置
   （`Range(composer, N)`）。
4. 反方向（模型 → DOM）却是成立的：`setDomCaret` 把卡片前缘的光标写成 `range.setStart(composer, index)`
   （`src/harness-panel.ts:2672-2673`）。**写入可行、读回不可行**——这一处不对称就是根因。
5. 读回 `null` 之后，一切模型侧动作都退化成「无选区」兜底：退格 / 前删**直接不动**（`:5017-5018`）；⇧Enter、
   粘贴、拖入、插卡片一律退回 `{block: 末块, offset: 0}`（`:5007-5008`、`:5102`、`:5129`；插卡片路径见
   `:2479`/`:2503`）。用户看到的就是「按了 ⌃B，光标到不了两张图之间」。
6. 两条加重事实：
   - **即便读回成功，在该位置输入也是错的**：`insertPlainTextAtCaret` 在「光标落在卡片」这一档会用
     `blocks.slice(at + 1)` 跳过 `blocks[at]`（`:340`），即一边把它当作空段落处理、一边**把那张卡片删掉**，
     与它自己的注释（`:321`「光标在卡片前缘时视为在该处有一个空段落」）不符。
   - **这个空隙至今没被任何测试网住**：HC1 的落法虽已覆盖「卡片前缘」这一档
     （`insertSoftBreakAtCaret:366-372`），但它的属性生成器
     **不含任何两张卡片相邻的序列**（`tests/unit/harness-composer.test.ts:253-273` 只有 `[card, para]` /
     `[para, card]` / `[card]` / `[para]` 形态，没有 `[card, card]`）。
7. **「两张图相邻」不是特例**，是**本仓现有行为的自然产物**：在贴着卡片的位置再粘一张图，走的是
   `insertBlockAtCaret` 的「段落起始」档，产出 `[图片1, 图片2, 空段落]`（`src/harness-panel.ts:273-278`）——
   两张卡相邻、中间没有段落。这正是 Alex 现场贴两张图后得到的块序列。

**⌃B 走的是哪条路**（决定后备方案的必要性）：composer 的 keydown 处理器对所有修饰键直接 `return`
（`src/harness-panel.ts:5002`），而应用键位表里的 `Ctrl-b` / `Ctrl-f` 绑定作用域是 `editor`（判据「事件目标在
CodeMirror contentDOM 内」，`src/keys.ts:459-460`）——焦点在 composer 里时不命中。所以 ⌃B 走的是
**macOS 文本系统的原生 caret 移动**（同族先例与实测记录见 `src/editor.ts:385-395`：编辑器侧的 ⌃F/⌃B 正是因为
「原生 caret 进不了原子范围」才改由 CodeMirror 派发）。

**尚未实测、构成本提案唯一未知数的一条**：原生路径在两张卡片之间**究竟把光标落在哪、画不画得出光标、在那里
打字的字落到哪个节点**。上面的第 3–6 条是按源码推定的模型层缺口（已核实），但 WebKit 在 `Range(composer, N)`
这个「两个块级非编辑元素之间的零宽位置」上的具体表现没有本地证据。这是本 change 实现期的**第一件事**
（tasks §1 的探针），它的结论决定裁决点 2 走哪条路。

**外部信源**：本提案不需要对第三方文档的断言——全部锚点来自本仓源码与 Alex 的现场描述。

## What Changes

逐条对应 `specs/harness/spec.md` 增量里的一个 requirement：

1. **原子块边界光标位**（harness，ADDED）：composer 的模型层 SHALL 把「相邻两个原子块之间的位置」当作
   一等公民光标位——`{block: 后一块下标, offset: 0}` 这一表示 SHALL 能从 DOM 读回（`Range(composer, N)` 与
   「锚在某张卡片内部」两种 DOM 形态都归一到它）、能写回、能跨整面重渲与撤销 / 重做保持一致。**仅把光标
   移动到该位置 MUST NOT 改动块序列、MUST NOT 产生撤销步**（导航不是编辑）。
2. **边界光标位上的内容输入物化段落**（harness，ADDED）：光标停在边界位上时，到达**内容型输入**（键入字符、
   粘贴、拖入、⇧Enter、插入卡片）SHALL 在该位置物化一个段落块并让内容落进它；MUST NOT 把内容折进相邻的其它
   段落、MUST NOT 吞掉被该边界分隔的卡片。物化与该次输入 SHALL 合成**一个**撤销步（一次撤销回到「两张卡片
   相邻、光标在边界位」的前态）。
3. **混排对话输入区**（harness，MODIFIED）：把「光标可在任意卡片前后继续输入」这句写实——相邻卡片之间同样
   存在可编辑位置；并修掉今天「在卡片前缘输入会删掉那张卡片」的既存缺陷（`insertPlainTextAtCaret` 的卡片档）。
   > 归档对账注记：本 MODIFIED 基于**当前 living spec 文本**起草。`harness-composer-image-paste` 对同一条
   > requirement 也有一份在途 MODIFIED（它把「粘贴净化为纯文本」改成按剪贴板内容分派）。实现 / 归档时若它
   > 已先归档，本 MODIFIED 须在**它之后**的文本上重新落准（保留其图片分派句），避免互相覆盖。

|---|---|---|---|
| 1 | 「相邻卡片之间的可编辑空隙」怎么获得 | A. **边界光标位 + 输入时物化**（模型允许光标停在边界，输入到达时按需落一个段落块）；B. **相邻卡片之间恒保留空段落**（模型加不变量：两卡之间永远有一个空段落，边界光标位因此退化成普通的段落位）；C. **键位层接管水平移动**（composer 作用域自己实现 ⌃B/⌃F 的模型级移动，不依赖引擎原生路径），可与 A 叠加 | **倾向 A 为骨干，C 作为实测触发的后备**。A 与既有架构同向（数据层是唯一真源、DOM 只是渲染面），不改变「贴两张图」的既有观感，也不给每张卡片配一个删不掉的空行。B 把「卡片相邻」变成非法状态：任意两张相邻卡片之间恒多一行可见空行（空段落有 `min-height: 1em`）、这一行**删不掉**（删了就违反不变量），且会把空段落带进投递序列化。C 单独用不解决「输入落在哪」，只解决「光标到不到得了」，而 composer 的 Emacs 移动是**一整族**（⌃A/⌃E/⌃N/⌃P/⌥F/⌃D/⌃H…）都走原生路径，只接管 ⌃B/⌃F 会造成族内不一致——故仅在实测证明原生路径到不了边界时启用 |
| 2 | 原生 ⌃B 到不了边界时的后备（**实测闸**） | A. 先实测；实测证明「原生移动能落到边界、光标可见、打字落点可矫正」就只做方案 A；B. 实测不可达时**升级为 A+C**（接管 composer 的水平移动，物化仍按 A）；C. 实测不可达时改用方案 B（恒留空段落） | **倾向「A，不可达则自动升级为 A+C」，不回来二次裁决**——两条路都在本 change 的授权面内，探针判据写在 tasks §1（真机读数：光标落点 / 光标可见性 / 打字落点三组）。不倾向退到 B，理由同裁决点 1 |
| 3 | 物化的时机 | A. 只在**内容型输入**到达时物化（导航不成文档改动、不成撤销步）；B. 光标一落上去就物化（selectionchange 驱动）；C. 不物化，让输入走原生路径、靠 `normalize` 事后折进相邻段落 | **倾向 A**。B 会让「按 ⌃B 走一圈」产生一串空段落与撤销步，用户按撤销时会迷惑；C 正是今天的形态——内容是折进**相邻的其它段落**（位置错），也正是本次要消灭的缺陷 |
| 4 |「卡片前缘输入吞卡」这一既存缺陷（`insertPlainTextAtCaret:340`）是否同批修 | A. 本 change 内修（随 tasks 1.x）；B. 拆成独立缺陷修复先落地 | **倾向 A**——方案 A 下「边界光标位 + 输入」正是这条代码路径，不修则本 change 的功能不可能正确；两者共用同一处代码与同一批测试，拆开只会造成一次重复改动 |

## Non-goals

- **不做卡片的复制 / 剪切 / 拖拽重排**：本 change 只让「光标能停在卡片之间、并在那里输入」；卡片仍不可拖拽、
  不可复制。
- **不接管 composer 的其它 Emacs 键**：⌃A/⌃E/⌃N/⌃P/⌥F/⌥B/⌃D/⌃H/⌃K/⌃Y 等一律保持现状（走 macOS 文本系统
  原生路径）。若裁决点 2 触发 C，也只接管水平移动（⌃B/⌃F 及必要的扩选对称），不扩面到整族。
- **不改卡片的外观与堆叠间距**：选 A 意味着两张相邻卡片之间**不**凭空多出可见空行；`.lumir-hp-qcard` 的
  几何、间距、圆角一律不动。
- **不改投递序列化协议**：不改 `serializeDelivery` / `<quote>` / `<msg-quote>` 的形态。物化出来的空段落若不含
  内容、也不是光标所在，它是否进 wire 由既有序列化口径决定——实现期若发现空段落污染 wire，按「空文本段落不产
  part」，就地收口并在本 change 登记，不扩到协议面。
- **不做多张图片的批量粘贴**：一次粘贴仍只取第一张（既有口径）。
- **不给 composer 加新的可见提示**（如「此处可输入」的占位符 / hover hint）：本批不做，dogfood 后再看。
- **不承诺卡片与段落之间的上下移动（⌃N / ⌃P）跨卡片语义**：本 change 只承诺水平移动与输入落点。

## 观测闸三问（低成本口径）

- **怎么知道用户用了它**：产品零埋点，天然痕迹在**用户自己的输入结果**里——两张相邻卡片之间的新段落会出现在
  该轮消息的 wire 证据中（`input_text` 夹在两张卡片之间）。dogfood 期 Alex 贴两张图后试一次即可看到。
- **怎么知道它有效**：主判 Alex 手感——贴两张截图 → ⌃B → 打字，看三件事：字是否落在两图之间、光标是否看得到、
  撤销一次是否干净回到前态。辅判机器面（下面第三条）。
- **出问题怎么发现**：机器面兜底——模型层属性测试（边界光标位 × 各输入动词的物化不变量 + HC1 生成器含相邻卡片
  序列）＋真机验收场景（⌃B 落位 / 输入落点 / 撤销步数）。失败形态是「字落在别的段落」或「卡片被吞」，两者都有
  可判据的 DOM / 文本读数，不静默。
