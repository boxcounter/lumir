## 2. 候选方案与取舍

### 方案 A（起草倾向）：边界光标位 + 输入时物化

模型层接受「相邻原子块之间」为一等公民光标位（`{block: 后一块下标, offset: 0}`），导航可以停在那里而
**不动文档**；只有**内容型输入**到达时才在该位置物化一个段落块。

- 与既有架构同向：数据层是唯一真源、DOM 只是渲染面（`src/harness-panel.ts:203-217` 的分层纪律）。
- 不改「贴两张图」的既有观感（相邻卡片之间不会凭空多出可见空行）。
- 不引入新块到既有块序列（除用户真的在那里输入的那一刻）。
- 代价：边界光标位是**无文本宿主**的位置，全部输入动词都要定义物化行为（§3 的表），并且依赖引擎能把光标
  落在该边界上（§6 的实测闸）。

### 方案 B：相邻卡片之间恒保留空段落

模型加不变量：任意两张卡片之间至少有一个段落块（空段落允许）。边界光标位因此退化成**普通的段落位**，
`caretFromDom` / `setDomCaret` 一字不改，既有段落机制全部可用。

- 优点：完全不依赖引擎在「块级边界」上的 caret 行为；实现面最小。
- 代价（三处，按严重度排）：
  1. **可见空行**：空段落有 `min-height: 1em`，恒留一个 ⇒ 任意两张相邻卡片之间恒多一行空白。贴两张截图
     得到「图 / 空行 / 图」，与今天的「图 / 图」不同。
  2. **删不掉的空行**：用户删掉这一行就违反不变量、系统又得补回来 ⇒ 要么它不可删，要么删它必须连带删掉
     一张卡片（把两种语义绑在一起）。
  3. **进入投递面**：空段落是块序列的一部分，会走到序列化（`serializeDelivery`）与快照恢复面，需要额外的
     「空段落不产 part」口径；方案 A 只在真的输入后才有这个段落，且那时它不空。
- 结论：B 是用**数据结构去迎合渲染引擎的疑点**；在 §6 的实测结论出来之前不宜先付这三笔代价。列为裁决点 1
  的备选，但在起草倾向上被 A 压过。

### 方案 C（与 A 正交）：键位层接管 composer 的水平移动

把 ⌃B / ⌃F 从「引擎原生路径」收到应用的键位表（新增 composer 作用域绑定 + 一个模型级移动纯函数，
语义照 `insertSoftBreakAtCaret` 的模型层风格：原子卡片一步跨过）。同族先例：编辑器侧的 ⌃F / ⌃B 正是因为
「原生 caret 进不了原子范围」才改由 CodeMirror 派发（`src/editor.ts:385-395`）。

- 单独用**不解决**本需求（要的是「在那里输入」），只解决「光标到不到得了」。
- 代价：composer 的 Emacs 移动是**一整族**（⌃A/⌃E/⌃N/⌃P/⌥F/⌥B/⌃D/⌃H…，全部走原生路径）。只接管 ⌃B/⌃F
  而其余保持原生，会造成族内不一致（同一次按键序列里，一半由模型算、一半由引擎算），且扩选族
  （⌃⇧F/⌃⇧B）也得跟着走模型才自洽。
- 因此定位为**实测触发的后备**（裁决点 2）：只有当 §6 探针证明「原生路径到不了边界」时，才把水平移动
  接管进模型层；接管面限定为水平移动 + 其扩选对称，不扩到整族。

### 被排除的做法

**D. selectionchange 驱动的即时物化**（光标一落上去就 materialize）：导航本身会改文档 ⇒ 按 ⌃B 走一圈产生
一串空段落与撤销步，撤销语义被污染；且 selectionchange 与 `renderComposer` 形成回环风险。排除。
理由与裁决点 3 一致。

## 3. 方案 A 的机制

### 3.1 光标读回归一（DOM → 模型）

`caretFromDom` 增一档：选区锚在 **composer 元素自身**时（`anchorNode === composer`），把 `anchorOffset`
当作子块下标，归一到 `{block: anchorOffset, offset: 0}`——即「第 anchorOffset 块的前缘」。

| DOM 形态 | 今天的模型读回 | 归一到 |
|---|---|---|
| `Range(composer, N)`（两个相邻块之间的块级边界） | `null` | `{block: N, offset: 0}` |
| 锚在某张卡片元素内部 / 卡片元素本身 | `{block: 卡片下标, offset: 0}`（已可用，`:2630`） | 不变 |
| 锚在某段落内的文本节点 | `{block, offset}`（已可用，`:2631-2657`） | 不变 |

两种 DOM 形态归一到同一个模型值，正是 A 的要点：**不管引擎把光标画在哪一侧，模型只有一种表示**。
写回侧不用改——`setDomCaret` 已经在卡片前缘写 `Range(composer, index)`（`:2672-2673`），修好读回后
两者互为逆运算。

> 顺带修复（在 A 的范围内自然发生）：`removeBlockAt` 的兜底光标（`:315`，可指向卡片前缘）与撤销恢复出的
> 卡片前缘光标，今天写进 DOM 后读回是 `null`——下一拍输入会漂到末尾。读回修好后它们是稳定状态。

### 3.2 输入动词 × 边界光标位（物化规则表）

边界光标位 = `{block: N, offset: 0}` 且 `blocks[N]` 是卡片（N 可以是 0，即 composer 以卡片开头）。

| 输入动词 | 今天的行为 | 目标行为（物化后光标落新段落内） |
|---|---|---|
| 键入字符 | `beforeinput` 放行原生落字（`:5064-5071`），字落引擎自造节点，随 `normalize` 折进**相邻某个段落** | 拦下该拍并走模型：在边界物化空段落 + 把字符写进去（一次模型修改，一个撤销步） |
| IME 组合 | 组合期早退（`:5049-5062`），原生落字 | `compositionstart` 时若光标在边界位，先物化一个空段落（该处已有压前态，`:5074-5077`），组合内容落进它 |
| 粘贴纯文本 | 读回 `null` ⇒ 落 composer 末尾（`:5102`） | 落进边界处物化的段落 |
| 拖入纯文本 | 读回 `null` ⇒ 落 composer 末尾（`:5129`） | 同上 |
| 粘贴图片 | 读回 `null` ⇒ 落 composer 末尾（`:2501-2505`） | `insertBlockAtCaret` 的卡片档（`:267-270`）已保证「卡片 + 承接段落」；读回修好后即正确 |
| ⇧Enter | 读回 `null` ⇒ 落末尾（`:5007-5008`） | `insertSoftBreakAtCaret` 的卡片前缘档（`:366-372`）已实现（新空段落）；读回修好后即正确 |
| 插入卡片（摘录 / 消息摘录） | 读回 `null` ⇒ 落末尾（`:2479`） | `insertBlockAtCaret` 的卡片档已实现；读回修好后即正确 |
| 退格 / 前删 | `sel === null` 直接不动（`:5017-5018`） | 读回修好后走既有卡片语义：退格删**前**一张卡（`:465-476`）、前删删**后**一张卡（`:507-511`）；`at === 0` 时退格为无操作（`:468`） |
| 光标移动（⌃B/⌃F、方向键、点击） | 原生 | 不变（裁决点 2 未触发时不接管）；只要求读回正确 |

**结论**：`insertSoftBreakAtCaret`（⇧Enter）、`insertBlockAtCaret`（插卡片）**已经**实现了「在卡片前缘落新
段落」的语义，本 change 不需要改它们的落法——它们的今天是「读回 null 走不到」而非「落法错」。真正要动的只有
三处：读回归一（§3.1）、`insertPlainTextAtCaret` 的卡片档（修掉 `:340` 的吞卡）、以及键入 / IME 的分派
（把边界位上的内容型输入从原生路径挪到模型路径）。

### 3.3 `insertPlainTextAtCaret` 的卡片档（既存缺陷）

今天：`at` 指向卡片时，`current = ""`、`offset = 0`，随后 `[...blocks.slice(0, at), ...replacements,
...blocks.slice(at + 1)]`（`:340`）——`blocks.slice(at + 1)` **跳过 `blocks[at]`**，那张卡片被删掉。

修法（与函数自身注释一致）：卡片档视作「该处已有一个空段落」——即把
`slice(at, at + 1)` 换成保留原块（`slice(at)`），或等价地先在该处 splice 一个空段落再走段落分支。
产出：`[..., 段落(前缀+文本+后缀), ...原 at 起的块]`，卡片不丢。

**可达性注记**：这条缺陷今天已可从 DOM 侧到达——`caretFromDom` 对「锚在某张卡片内部」的选区会返回
`{block: 卡片下标, offset: 0}`（`:2630`），粘贴纯文本时若选区折叠在卡片上，就会走到这个档。**是否真能被用户
触发（WebKit 是否会把折叠光标放进 `contenteditable=false` 的卡片内部）未实测**；无论可达与否，方案 A 会让它
成为常用路径，必须修。

### 3.4 撤销栈口径

- **导航不成步**：把光标移到边界位（无论原生还是模型接管）MUST NOT 压栈、MUST NOT 改块序列。
- **物化 + 首次输入 = 一个撤销步**：物化与那一次输入在同一次模型修改里完成，前态快照在修改前压入（沿用
  `withModel` 的 `undoHistory.push(snapshot(), force)` 形状 `:2756-2765`）。一次撤销后回到「两张卡相邻、
  两者之间无段落、光标在边界位」。
- **连续键入的聚簇不变**：首次键入完成物化后，光标已是段落内的普通光标，后续键入走既有 `beforeinput`
  的 `force = false` 聚簇路径（`:5064-5071`），不在本 change 的改动面。

## 4. 与 HC1 / HC2 的相互影响

合同见 `docs/specs/harness-composer.md`（该文件不在本 change 的写入面，新增条款归实现期）。

- **HC1（一次 ⇧Enter 恰好多一行可见行，光标落可见行）**：
  - 「卡片前缘」这一档 HC1 已经实现且已测试（`insertSoftBreakAtCaret:366-372`，用例「composer 以卡片开头」）。
    本 change 不改落法，只让它变得**可达**。
  - 「对任意块序列」的承诺里，生成器目前缺 `[card, card]` 序列（§1 第 9 条）。本 change 要求把相邻卡片序列
    纳入生成器（`[card, card]`、`[card, card, card]`、`[para, card, card, para]`、`[card, para, card]`）。
  - 合同的 §适用范围一节已把「卡片前缘（含无前段落）」列为光标落点档；边界光标位与它是同一个模型值，无需新增
    落点档，只需把「相邻两张卡之间」写成显式一档（避免读者以为「卡片前缘」只指「卡片与段落之间」）。
- **HC2（断行 / 光标移动后光标行在视口内）**：
  - 边界光标位的 `Range` 包围盒可能**零高**（它落在两个块级元素的边界上，不是文本行）。`scrollCaretIntoView`
    已有零高回落（回落块元素矩形，`:2726-2740`）；边界档回落的是**后一张卡片**的矩形，「把卡片滚进视口」是
    「边界可见」的可用代理。这一条要在实现期核一次，若有偏差就在 HC2 条下补一句边界档的判据。
  - 原生移动（不经 `setDomCaret`）不适用 HC2 的显式滚动；WKWebView 自己会 reveal（合同 §HC2 的实测记录）。

## 5. 与「空段落归一化」和「原子块删除」的相互影响

- **归一化（`normalize`）**：方案 A 下「两张卡片相邻」是**合法状态**，`normalize` 保持现状——只收口裸块、
  只保证「至少一个段落」，MUST NOT 新增「在卡片之间补段落」的规则（那是方案 B）。
  顺带的鲁棒性收益：`normalize` 的收尾会把光标写回（`dirty && caret !== null` 时 `setDomCaret`，`:2611`），
  今天边界光标读回是 `null` ⇒ 归一整面后光标丢失；读回修好后边界光标能跨归一化存活。
- **原子块删除**：`backspaceAtCaret` / `deleteForwardAtCaret` 在卡片前缘的语义**已经定义**（删前 / 后整卡），
  今天因读回 `null` 而不可达。读回修好后它们是可达的正常行为，**不需要新语义**。
  需要核的一点：删掉两张相邻卡片中的一张后，剩下的单张卡片不产生新的非法状态（A 下相邻本就合法，无问题）。
- **投递序列化**：物化出来的段落当且仅当用户真的在其中输入后才存在，且那时它不空；空段落（例如 ⇧Enter 落下的
  那个）是否进 parts 由既有口径决定——本 change MUST NOT 改序列化面（proposal 的 Non-goals 已声明；实现期
  若发现真问题，就地收口并在 tasks 登记）。

## 6. 实测闸（裁决点 2 的判据）

**未知数**：原生 ⌃B 在「两张相邻卡片之间」这个零宽块级边界上的行为，本仓无实测。

**探针**（真机验收套件，mock provider，fixture 全合成）：composer 里放两张合成图片卡片（相邻），光标在它们
之后的段落里，注入 ⌃B，读三组读数——

| 读数 | 目标 | 判据 |
|---|---|---|
| 光标落点 | 模型读回的 `ComposerCaret` | `{block: 后一张卡片的下标, offset: 0}` = 边界位；若读到别的值，记下实际值 |
| 光标可见性 | 该 Range 的包围盒 + 截图 | 包围盒与被夹的两张卡片的位置关系（零宽 / 前一张的下沿 / 后一张的上沿）；截图人工过目 |
| 打字落点 | 注入一个字符后 composer 的子元素次序 + 文本读数 | 字符落进**新段落**且该段落位于两张卡片之间 |

**判定**：

- 三组读数都符合「目标」列 ⇒ **只做方案 A**（裁决点 2 选项 A）。
- 「光标落点」读不到边界位、或「打字落点」无法落在两卡之间 ⇒ **升级 A+C**（接管 composer 水平移动，
  物化仍按 A；裁决点 2 选项 B）。**这条升级不需要回来二次裁决**——proposal 已把两条路都写在授权面内。
- 探针结论（含截图与读数）登记进本 change 的 notes 与 `docs/backlog.md`（后续项）。

## 7. 视觉保真

本 change **无原型**（不新增界面形态）。方案 A 的预期是**零像素变化**：边界光标位不占位、不新增元素、
不改 `.lumir-hp-qcard` / `.lumir-hp-qpara` 的任何几何与间距。

核对口径（实现期）：

- `bash scripts/gate.sh visual` MUST 全绿且**既有基线零漂移**——有漂移即说明改动溢出到了样式面，回到本
  设计重新定位（不允许「顺手调一下」后直接 `--update`）。
- 真机侧：两张相邻图片卡片之间的截图与实现前逐像素同形（除光标本身）。
- 若裁决点 2 升级为方案 C，视觉面**仍**零变化（C 只改键位分发与模型移动，不碰样式）。

## 8. 验收面（机器判定锚点）
