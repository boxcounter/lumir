# Design: harness 输出预算与错误恢复的三项候选评估

- Change ID: `evaluate-harness-output-recovery`
- 日期: 2026-10-29
- 性质：实验设计（evaluation design）。本文件不含实现，也不含「哪一项该上线」的结论。

## 0. 范围、术语与硬约束

### 0.1 范围

本 change 只回答三个问题，且**分别**回答：

- 候选 A：给 `vault_search` 增加可选的上下文行，是否能在不增加成本的前提下减少「命中后再读文件」的追加调用？
- 候选 B：把 `cli_run` 的每流截断从「只留头」改成「头尾各半」，是否能让尾部承载的结论 / 错误进入模型可见范围，且不以丢掉中段信息为代价？
- 候选 C：给「只描述现状」的错误回执补上可行动的下一步，是否提高第二次调用的成功率？

### 0.2 术语

- **control**：当前实现（master 上的行为）。**treatment**：候选改动后的实现。两者只在候选定义的变量上不同。
- **离线判据**：不联网、不调用真实 provider、不起真实 app，只对工具函数 / mock provider 链路执行的确定性断言。
- **真实 provider 实验**：用 DeepSeek 或 Kimi 的真实模型跑预注册任务，产出行为数据。
- **留出真实任务**：任务素材来自真实使用形态、但在设计判据与描述文本时没有参与调参的任务。
- **A/B 交错（interleaving）**：同一个任务实例分别用 control 与 treatment 各跑一次，先后顺序由预生成随机序列决定。

### 0.3 硬约束（来自 mission 与仓库规则）

1. 本 mission 不写产品代码、不改工具 schema、不跑真实模型、不做真机验证。
2. 不读取、不复制、不打印真实 provider 凭据；不做环境变量转储。
3. 真实 vault 只读；需要写入的实验在 `.local/` 的副本上进行。
4. 仓库内制品不含真实 vault 内容；原始会话记录只落 `.local/`（git 外）。
5. 三项候选独立裁决；本提案不预设任何一项应上线。
6. **实现归属**：为跑实验所需的 control / treatment 代码放在**独立实验分支**
   （`exp/harness-output-recovery-*`，从当时 master 切出），**不合入 master、不进入本 change
   的合并面**；本 change 只提交 OpenSpec 制品。采纳后的产品实现由独立 change 在 master 上
   重新落地；实验分支只作测量与证据，可被参考，但不直接合并。

### 1.4 证据缺口（必须在报告里逐条写出的限制）

1. **原始超长未留存**：37 份截断结果的截断前内容不在会话记录里，无法事后分析「被丢掉的是
   什么」。任何关于尾部收益的结论只能来自合成 fixture 与前瞻性实验。
2. **采纳后的新行为样本很小**：`vault_list` 采纳后只有 5 个会话、7 条用户消息；本提案不依赖
   这段样本，但它提醒我们：任何「模型会怎么用新参数」的判断都缺基线。
3. **真实 patch 失败太少**：63 次里只有 3 次失败，无法支撑候选 C 的真实任务统计；候选 C 的
   主证据只能是合成注入 + 少量案例序列。
4. **`document_conflict` 在自动放行档基本不可达**：只有走批准闸（`read_only` 档）时才会把
   预览时刻的 revision 带到执行时刻；自动放行档在执行时取当前 revision。候选 C 的这一支
   只能做单元级验证，真实 provider 实验要等真机 + 批准窗脚本，且不得在无真机时宣称已验证。
5. **单用户、双 provider**：任何成功率差异的置信区间都会很宽；本设计不做确证性随机对照试验
   （randomized controlled trial，RCT），只做决策级实验（见 §6.5）。

## 3. 候选 A：`vault_search` 的可选上下文行

### 3.1 问题

现在一次搜索只返回「哪一行命中 + 该行前 200 字符」。要判断命中所在的段落、列表项、frontmatter
或代码块属于什么，模型只能追加 `vault_read`，并自己把命中行号换算成 `offset`。这是一次可以
省掉的往返，但省掉它的代价是搜索结果变大。

### 3.2 Treatment 定义

**参数**：`context`，整数，可选，缺省 0。

- 语义：对称前后行数（等价 `grep -C`）。有效值 = `clamp(context, 0, 5)`；负数按 0、超过 5 按 5。
- `context = 0`：结果与现状**逐字段一致**（`matches` + `truncated`），不新增字段。
- `context > 0`：结果改为块状，并回显有效 `context`：

```json
{
  "ok": true,
  "context": 2,
  "blocks": [
    {
      "path": "notes/a.md",
      "from_line": 10,
      "to_line": 16,
      "hits": [12, 14],
      "lines": [
        {"line": 10, "text": "…"},
        {"line": 11, "text": "…"},
        {"line": 12, "text": "…"}
      ]
    }
  ],
  "truncated": false
}
```

示例只展示部分行；实际的 `lines` 必须覆盖 `from_line..to_line` 的每一行（上例共 7 行）。

**窗口与合并规则**：

1. 命中检测与现状相同：`content.lines()` 逐行、大小写不敏感子串、忽略规则与 lazy 规则不变。
2. 每条命中的窗口 = `[line - context, line + context]`，裁剪到 `[1, 该文件行数]`。
3. 同一文件内按窗口起点排序；**相邻或重叠**（`下一段起点 ≤ 当前段终点 + 1`）的窗口合并。
   合并后的块**最多 60 行**：再加入下一段会超过 60 行时，在下一段的起点处切开，另起一块。
   这样每个块最多 `60 × 200 = 12,000` 字符，**单块永远放得进总字符预算**。
4. 合并后块内每行只出现一次。`lines` 含块内每一行的绝对行号与文本；`hits` 列出块内的命中
   行号（升序）；切块时命中行归属它落入的那一块。
5. 块按文件路径升序、块内按行号升序输出；与现状的扫描顺序同源。

**预算与截断**：

| 常量 | 值 | 说明 |
|---|---:|---|
| 命中上限 | 50 条 | 与现状相同；到达上限即 `truncated=true` |
| 每侧上下文上限 | 5 行 | 参数夹取上限 |
| 每行文本上限 | 200 字符（含省略号） | `context>0` 的 `lines[].text`：超长行取前 199 字符 + `…`，总长 ≤200；`context=0` 的 `matches[].snippet` 保持现状（200 字符 + `…`），因为缺省路径不改 |
| 单块行数上限 | 60 行 | 由「总字符预算 ÷ 每行上限」推导，保证单块必能放下 |
| 总行数预算 | 400 行 | 防御性上限（短行场景下先于字符预算生效） |
| 总字符预算 | 12,000 字符 | 只计 `text` 字符；与 `cli_run` 单流 10k 同量级 |

- **块是原子单位**：预算不足时整块不输出（不输出半块），`truncated=true`。由于单块最多 60 行、
  每行最多 200 字符，**第一块永远放得进预算**——不会出现「有命中却返回零块」的退化结果。
- 两种截断原因给不同的下一步文案（整条模板，机器可整串断言）：
  - 命中上限：`命中超过 50 条：收窄 query，或用 path_glob 限定范围。`
  - 预算上限：`结果达到输出预算：减小 context、用 path_glob 缩小范围，或用 vault_read 读取命中所在段落。`
  - 两者同时命中时，**命中上限文案优先**（先说明「还有更多命中」比「预算不够」更接近真实原因）。
- `truncated=false` 时不出现 hint 字段（缺席而不是空串，与 `vault_list` 的 `next_cursor` 同口径）。

**为什么是块状而不是「每条命中各带 before/after」**：重叠去重是任务要求；两条命中相隔两行时，
逐命中返回会把同一行发两次，既浪费预算又让行号出现两次。块状是 `grep -C` 的天然单位，也让
`hits` 与 `lines` 一一对应。代价是 `context` 的取值改变了结果形状——这是本候选最需要实验验证的
设计风险（见 §3.6）。

**工具描述（提案文本，整段替换现行描述）**：

> 在 vault 内做大小写不敏感子串搜索（query 不是正则）。尊重忽略规则表；只搜可见文本文件。
> 可选 `context`（0–5，缺省 0）为命中位置前后各取的行数：`context=0` 只返回命中行与 200 字符
> 片段；`context>0` 返回合并后的上下文块（每行带绝对行号，相邻 / 重叠窗口合并），适合判断命中
> 所在的段落、列表项、frontmatter 或代码块。只为计数或枚举命中时保持 0。结果受总预算限制；
> `truncated=true` 时按返回的提示缩小 context 或加 `path_glob`。

**何时用 / 何时不用（写进描述，也写进实验判据）**：

- 用：命中含义依赖相邻行（frontmatter 多行值、列表项归属、代码块上下文、定义句）。
- 不用：统计条数、收集链接、已知要读整篇（直接 `vault_read`）、结果本来就只有一两条（追加读
  一次更便宜）。
- 负向任务（枚举 / 计数）是实验的守门族：treatment 不得让这类任务变贵。

### 3.3 现状同一性（control 保护）

`context = 0` 时，结果 MUST 与 control 逐字段一致：同一组 `matches`、同一个 `truncated`、
不出现 `blocks` / `context` / `hint`。这是实验的 control 条件，也是低风险默认值的依据——不选
上下文就完全回到今天的行为。

实现阶段落在 `src-tauri/src/harness/tools.rs` 的单元测试（临时 vault）；fixture 全部合成，
不含真实内容。

**红绿分类（与 spec delta「离线机器判据」同一口径）**：

- **候选行为断言·收益侧**（A1–A3、A5–A11）：先在 control 上运行并证明会失败，再在 treatment
  上通过；红侧读数必须留存。
- **identity / 守门断言**（A4、A12）：在 control 与 treatment 上**均须绿**，不要求红侧证据；
  它们只证明没有退化，不能用来证明新能力。
- A6 与 A12 分开：A6 用 `context>0` 验证命中上限文案；A12 用 `context=0` 验证缺省路径仍是
  现状形状且**没有** hint——若给缺省路径加 hint，A12 直接红，control 合同被破坏。

### 3.5 真实 provider 任务族、指标与判据

| ID | 族 | 任务形态（表述不点名参数） | 验证器 |
|---|---|---|---|
| A-S1 | 语境依赖 | 合成 vault：frontmatter 多行值 + 小节标题；问「某字段属于哪一节 / 默认值是多少」 | 精确答案字符串 |
| A-S2 | 语境依赖 | 合成 vault：命中行是列表子项；问「这条属于哪个上级条目」 | 精确答案字符串 |
| A-S3 | 枚举（守门） | 「统计所有包含 X 的行数」 | 精确数字 |
| A-R1 | 留出真实 | 3 个由真实笔记结构改写的任务（本地副本，不入 git） | 预先写好的二元量规，盲评 |

**主指标（预先写死计算口径）**：每对任务先各算一个整数——「首次搜索之后对同一路径的
`vault_read` 次数」，记 control 为 `C_i`、treatment 为 `T_i`；主指标是**配对差**
`d_i = T_i − C_i`，**不是比值**。报告三项：`d` 的中位数、负 / 零 / 正配对计数、
以配对为单位重采样 10,000 次（固定种子）得到的 `d` 中位数 95% 区间。这样不存在 `0/0` 或
除零：两臂都为 0 的配对记为 `d=0`，照常进入样本；control 为 0 而 treatment 为正的配对记为
正值，不会被丢掉或放大成无穷。`C_i > 0` 的配对另报一个描述性比值（`T_i / C_i` 的中位数），
仅用于展示分布，不参与判据。

**机会规模预检**：若 control 侧 `vault_read` 次数的中位数为 0（多数任务不需要追加读），则
主指标没有可节省的空间，候选判 `undecided`（机会不足），MUST NOT 仅凭 token 或成功率采纳。

**守门指标**：成功率不劣；枚举族 token 比值不超过 1.10×。

**采纳阈值（提案值，节点 1 裁决）**：

1. 离线断言按各自口径通过：候选行为（A1–A3、A5–A11）红侧有读数、treatment 绿；identity /
   守门（A4、A12）在 control / treatment 两版上均绿；
2. 主指标：`median(d) ≤ −1`，负向配对 ≥ 2× 正向配对，且配对 bootstrap 95% 区间上界 < 0；
3. 成功率不劣：在 20 对里，「treatment 失败而 control 成功」的对数 ≤ 2，且没有任何一对的失败
   原因是「上下文块缺失 / 形状混淆」；
4. 枚举族：token 比值 ≤ 1.10×（比值口径见 §6.4），成功不劣于 control 超过 1 对；
5. 模型实际使用：语境依赖任务里 `context>0` 的比例 ≥ 50% 才可采纳；< 20% 判「死旋钮」——
   不采纳，可只改描述后重跑一轮（这一步不得与采纳同时发生）；20–50% 记为未达阈值；
6. DeepSeek 达到上述全部条件后，Kimi 只做方向确认：`median(d) ≤ −1`、负向配对 ≥ 正向配对、
   无成功反转。

### 3.6 风险与反例

- **形状分叉**：`context=0` 与 `>0` 两种结果形状，模型可能混淆。缓解：描述里写明两种形态；
  实验的 A4 断言锁死默认路径；若真实实验显示参数误用率高，候选直接判不采纳。
- **枚举任务被诱导**：模型可能对计数任务也开 context，导致预算被吃满。缓解：枚举族是守门族；
  描述明写「只为计数 / 枚举时保持 0」。
- **长行吃预算**：200 字符/行的上限让块的大小可预测；但一行 200 字符仍可能只覆盖句子的一部分。
  这是与现状 snippet 相同的限制，不新增。
- **合并语义的实现风险**：相邻窗口合并（`+1`）与「仅重叠合并」是两个可辩护的选择。本提案选
  相邻合并，因为 `grep -C` 在间隔为 0 时也把两组连成一段；若实验显示块过大，可把这条作为
  独立参数再裁决（不混入本次）。
- **`content.lines()` 与 `vault_read` 的行号口径**：两者对结尾换行与 CRLF 的处理不同；离线
  A9 断言锁死搜索侧行号，跨工具一致性不在本候选范围。

## 4. 候选 B：`cli_run` 每流的头尾保留

### 4.1 问题

现在每流超过 10,000 字符就只保留前 10,000 字符。CLI 的失败摘要、测试结论、`git log` 的最后
几条、错误堆栈的末端都在尾部；只留头会把这些直接丢掉，而 `truncated` 只告诉模型「有东西被
截了」，不告诉它「丢了什么、怎么继续」。

37 份历史截断结果**只能用于形状统计**（§7.2：哪一流触顶、退出码、是否结构化输出）——截断前
的原始内容没有留存，因此「头 / 中 / 尾各承载什么」的对比只能靠合成长输出 fixture（§4.4 的
B10a–B10c）与前瞻性真实模型实验（§4.5）。

### 4.2 Treatment 定义

**实现范围（单变量纪律）**：本候选**只改 `cli_run`**。中间截断逻辑可以抽成 helper 供
`cli_run` 使用，但 `task` 摘要的代码路径、预算、标记文案与输出 MUST 逐字节不变——`task`
不进本候选的改动面。理由是 control / treatment 只能有一个可见差异：任何 run 内只要出现
`task` 调用，`task` 文案变化就会污染归因。统一 `task` 的标记文案是另一个候选，另立判据，
不夹在 B 内。

**`cli_run` 规则**：

- 每流预算 `CLI_MAX_CHARS = 10_000` 不变；头 `5_000`、尾 `5_000`。
- 字符数 ≤ 10,000：原文返回，不出现标记，`truncated=false`（逐字节不变）。
- 字符数 > 10,000：`头 5,000 + …[省略 N 字符]… + 尾 5,000`，其中 `N = 总字符数 - 10,000`；
  `truncated=true`。
- 标记不计入 10,000 的内容预算（与现状的 `…[截断]` 同口径）。
- stdout 与 stderr **各自独立**计算；`truncated` 是两者的逻辑或。
- 计数单位是字符（与现状的 `chars().count()` 一致），不是字节。

**工具描述（提案文本，在现行描述上追加一句）**：

> stdout / stderr 各 10,000 字符：超出时保留头尾各 5,000 字符，中间标注 `…[省略 N 字符]…`
> （N 为省略的字符数）。需要被省略的中段或结构化输出时，用命令自身的过滤 / 分页参数缩小输出，
> 不要靠重跑碰运气。

### 4.3 损失剖面

设输出总长为 `N` 字符：

| 场景 | control 可见 | treatment 可见 | treatment 丢失 | 备注 |
|---|---|---|---|---|
| `N ≤ 10,000` | 全部 | 全部 | 无 | 逐字节不变 |
| `10,000 < N < 15,000` | `[0, 10k)` | `[0, 5k) ∪ (N-5k, N]` | `[5k, N-5k)` | 省略量 `N-10k`，小于 5k |
| `N ≥ 15,000` | `[0, 10k)` | `[0, 5k) ∪ (N-5k, N]` | `[5k, N-5k)` | 典型：`N=20k` 时丢 `[5k, 15k)` |

相对 control 的净变化：**得到** `(10k, N]` 的尾部；**失去** `[5k, 10k)` 的中段。离线 fixture
必须同时覆盖「尾部得到」与「中段失去」两侧，不能只测收益侧。

### 4.4 离线 fixture 与断言

| ID | fixture | 断言 | control 上应红？ |
|---|---|---|---|
| B1 | 9,999 字符 | 原文逐字节一致；无标记；`truncated=false` | 否（identity guard） |
| B2 | 10,000 字符 | 同上 | 否（identity guard） |
| B3 | 10,001 字符 | 头 5,000 + `…[省略 1 字符]…` + 尾 5,000；内容字符数 10,000 | 是 |
| B4 | 20,000 字符 | 头 / 尾各 5,000；标记精确为 `…[省略 10000 字符]…` | 是 |
| B5 | 边界处多字节字符 | 不 panic、无替换字符；字符计数精确 | 是（标记不同） |
| B6 | stdout 截断、stderr 短 | stdout 有标记；stderr 原文；`truncated=true` | 是 |
| B7 | stdout / stderr 都截断 | 两处标记、两个省略量各自正确 | 是 |
| B8 | 空流 | 无标记；`truncated=false` | 否（identity guard） |
| B9 | `task` 摘要 8,001 字符 | 与 control 的 golden 文本逐字节相等（仍为 `…[截断]…`）；预算 / 头尾不变 | 否（identity 守门，两版均绿） |
| B10a | 20k 输出，决定性词在 1k | control 与 treatment 均可见 | identity 守门 | 否（两版均绿） |
| B10b | 20k 输出，决定性词在 19k | treatment 可见、control 不可见 | 候选行为（收益侧） | 是 |
| B10c | 20k 输出，决定性词在 7k | **treatment 不可见、control 可见**；这是候选的代价侧断言，MUST NOT 当作 identity | 候选行为（代价侧） | 是（control 可见，故「不可见」断言在 control 上红） |
| B11 | 非法 UTF-8 字节 | 与 control 相同的 lossy 文本与省略量算法 | 否（identity guard） |

**红绿分类（与 spec delta「离线机器判据」同一口径）**：

- **候选行为断言·收益侧**（B3–B7、B10b）：先在 control 上红，再在 treatment 上绿；红侧读数
  必须留存。
- **候选行为断言·代价侧**（B10c）：断言的是「treatment 丢掉 7k 中段」这一预期代价，方向同样是
  control 红（7k 可见）→ treatment 绿（7k 不可见）。它不是 identity / 守门断言；若它在
  treatment 上变红（7k 反而可见），说明切片实现与设计不符，同样判 FAIL。
- **identity / 守门断言**（B1、B2、B8、B9、B10a、B11）：在 control 与 treatment 上**均须绿**，
  不要求红侧证据。B9 尤其锁死「`task` 未被本候选改动」——它若在 treatment 上变红，说明单变量
  纪律被破坏。

### 4.5 真实 provider 任务族、指标与判据

| ID | 族 | 任务形态 | 验证器 |
|---|---|---|---|
| B-S1 | 尾部决定性 | 20k 输出，最终结论 / 失败原因在最后 1k；问「最终结论 / 哪一步失败」 | 精确答案或关键词集合（预注册） |
| B-S2 | 头部决定性 | 20k 输出，答案在首 1k | 精确答案 |
| B-S3 | 中段决定性（守门） | 20k 输出，答案在 7k | 精确答案 |
| B-R1 | 留出真实 | 合成仓库上的 `git log` / `rg` 长输出；问尾部事实 | 精确答案 |

长输出由提交入库的合成 fixture 可执行文件产生（合成仓库、合成提交信息），不使用真实 vault
内容；权限模式在各臂保持一致，记录在实验元数据里。

**主指标（预先写死）**：每个有效配对（两臂都正常完成、无排除）的尾部任务二元结果记
`T_i` / `C_i`（1 = 成功，0 = 失败）；净增益 `G = Σ(T_i − C_i)`，同时报告
「treatment 成功 / control 失败」的对数与反向对数。**守门**：中段任务的净增益 `G_mid ≥ −1`；
token 比值 = `median(treatment tokens) / median(control tokens)`，比值口径见 §6.4（分母为 0
时按该节规则处理，不产生 NaN / ∞）。

**采纳阈值（提案值）**：

1. 离线断言按各自口径通过：候选行为断言（收益侧 B3–B7、B10b；代价侧 B10c）在 treatment 上
   绿且红侧有读数；identity / 守门断言（B1、B2、B8、B9、B10a、B11）两版均绿；
2. 尾部任务净增益 `G ≥ 3` 且反向对数 ≤ 1；离线可见率（treatment ≥ 80% 且 control ≤ 20%）
   只作辅助证据，**不能单独构成采纳**——那只是切片位置的算术结果，不是模型收益；
3. 中段任务：`G_mid ≥ −1`；
4. token 比值 ≤ 1.10×；
5. DeepSeek 达标后，Kimi 同方向（`G ≥ 1` 且 `G_mid ≥ 0`）。

### 4.6 风险与反例

- **中段丢失**：这是本候选唯一的结构性代价。B-S3（中段任务成功率）是它的守门断言；B10c
  在离线层面显式断言这个代价（7k 在 treatment 不可见、在 control 可见）。若中段任务出现明显
  退化，候选不采纳。
- **结构化输出**：JSON / CSV 被从中间截断后都不可解析；头尾保留不解决这个问题。描述里明确
  「用命令自身的过滤 / 分页参数缩小输出」，不承诺截断后仍可解析。
- **ANSI 颜色 / 进度条**：控制字符计入字符预算（现状如此）；本候选不改变这一口径，也不新增
  去色处理。
- **标记与内容边界**：`…[省略 N 字符]…` 可能被模型误读为文本内容。选择中文 + 方括号的显式
  标记，与现状 `…[截断]` 同族；离线断言锁死精确格式。
- **`task` 的边界**：本候选只改 `cli_run`，`task` 摘要的代码与输出逐字节不变。实现时若顺手
  统一 `task` 文案，control / treatment 就出现第二个可见差异，按协议违规处理（B9 会直接红）。
  若要统一 `task` 标记，另立候选与判据，不夹在 B 内。

## 5. 候选 C：错误回执带可行动的下一步

### 5.1 问题与范围

现行 `vault_patch` 失败只回「第 N 处编辑的 old_string 在 X 中命中 M 次（要求恰好 1 次）」；
`document_conflict` 只回「文件已被外部修改，请先协调冲突」；`vault_read` 越界只回总行数；
`vault_list` 非目录只回「不是目录」。这些回执描述了**现状**，但没有给**下一步**与执行下一步
所需的数据（命中在哪几行、文件共几行、目标路径是什么）。

**范围（5 类码）**：

| code | 现行消息的问题 | 回执应补的数据 |
|---|---|---|
| `patch_not_found` | 有路径、序号、0 次，但没有下一步 | 「先读再逐字复制 old_string，带前后 ≥3 行上下文重试」 |
| `patch_not_unique` | 有路径、序号、次数，但**没有命中行号**，也没有下一步 | 命中行号（前 20 处）+「扩大 old_string 使其唯一」 |
| `document_conflict` | **没有路径**，没有下一步 | 目标路径 +「先读当前内容，确认修改仍适用后重试」 |
| `read_out_of_range` | 有总行数，但没有可用的 offset 范围 | 「用 1–N 之间的 offset 重试」 |
| `list_not_a_directory` | 只有「不是目录」 | 「先列上级目录确认目标，或用 vault_read 读该路径」 |

**明确排除**：

- `list_path_absolute`：现行消息已经带下一步（「vault 根见 system 的工作区段」），本提案把它
  当作风格模板，不改。
- `patch_invalid`（空 `old_string` / 空 `edits`）：模型自己构造的空参数，下一步显然；加一句
  收益低、改动面反而扩大。
- 通用 `fs_*`（`fs_not_found` / `fs_read_failed` 等）：这些码由 `fs_io` 的共享解析层产出，
  editor 侧也在用；在 harness 层统一加下一步会改变非 harness 的回执。列入非目标。
- **分页边界本身**：`vault_list` 的 `cursor` 翻到末页返回空页是**成功**（`truncated=false`），
  不是错误回执；本候选覆盖的是分页之前的「目标不是目录」与读取越界，不把空页改成错误。

### 5.2 Treatment 定义

**信封不变**：仍是 `{ok:false, code, message}`，`code` 不变，不新增必填字段、不转发
`CommandError.params`。改动只在 `message` 文本。

**文案模板（机器整串断言）**：

- `patch_not_found`：
  `第 {index} 处编辑的 old_string 在 {rel} 中命中 0 次（要求恰好 1 次），已拒绝整组编辑。下一步：先用 vault_read 读取 {rel}，从返回内容里逐字复制 old_string，并带上前后至少 3 行上下文后重试。`
- `patch_not_unique`：
  `第 {index} 处编辑的 old_string 在 {rel} 中命中 {count} 次（要求恰好 1 次），已拒绝整组编辑。命中行：{lines}。下一步：把 old_string 扩大到能唯一覆盖目标位置的范围（含前后至少 3 行）后重试。`
  - `{lines}`：命中行号升序、中文顿号分隔（如 `12、47、88`）；超过 20 处时只列前 20 个，
    末尾加 `…（共 {count} 处）`。
- `document_conflict`：
  `文件 {rel} 在读取或批准后被外部修改，本次编辑未落盘。下一步：先用 vault_read 核对 {rel} 的当前内容，确认这条修改仍然适用后重试。`
- `read_out_of_range`：
  `offset {offset} 超出文件行数（{total} 行）。下一步：用 1–{total} 之间的 offset 重试；读末尾时用较大的 offset 配合 limit。`
- `list_not_a_directory`：
  `{rel} 不是目录。下一步：先用 vault_list 列出上级目录确认目标名称，或改用 vault_read 读取该路径。`

**风格约束**：中文；单段；每条 ≤ 400 字符；不回显文件正文；不编造「文件当前内容是什么」；
不承诺未验证的动作（例如「重试一定成功」）。

**为什么是 message 而不是结构化字段**：结构化字段（如 `next: {action, lines}`）机器更好判，
但会新增一个跨工具的回执协议，且前端、批准卡与恢复路径都要跟着消费；本候选先验证「有没有
下一步」是否影响模型行为，用最小改动面。若实验显示模型需要结构化指引，再立第二个候选。

### 5.3 「正确修复动作」的定义

对每个错误码预先定义「正确动作」与机器可判代理：

| code | 正确动作 | 机器代理（从会话记录可判） |
|---|---|---|
| `patch_not_found` | 先读同一路径，再以逐字存在的 old_string 重试 | 下一次调用是 `vault_read(path)`；其后的 `vault_patch(path)` 成功 |
| `patch_not_unique` | 先确认命中位置，再用更长的 old_string 重试 | 下一次是 `vault_read(path)` 或直接 `vault_patch`，且新 old_string 长度严格大于旧值、在文件内容中唯一 |
| `document_conflict` | 先读当前内容，确认后再改 | 下一次是 `vault_read(path)`；其后的 `vault_patch(path)` 成功 |
| `read_out_of_range` | 用范围内的 offset 重试 | 下一次 `vault_read` 的 offset 落在 `1..=total` |
| `list_not_a_directory` | 列上级或读该路径 | 下一次是 `vault_list(上级)` 或 `vault_read(path)` |

「第二次调用成功率」= 错误发生后 3 次工具调用内出现一次成功的同工具重试；超过 3 次记为失败。

**配对口径（预先写死）**：

- 一个配对只有在**两臂都出现目标错误**（C-S1 为 `patch_not_found`，C-S2 为
  `patch_not_unique`）时才进入第二次调用成功率的分母；分子是该臂在 3 次调用内恢复。
- 两臂都没有出现目标错误的配对：任务本身可能已成功，但**排除出本指标**，单独计数为
  `no-error pairs`。
- 只有一臂出现目标错误的配对：记为 `instance-not-triggered`，**两臂都不计入成功率**，
  单独计数；原因是该实例没有按设计同时暴露给两臂，比较不成立。
- 若某任务族中 `instance-not-triggered` 占该族配对 > 40%，该族判 `undecided`（实例设计不足），
  MUST NOT 事后改 fixture 再把数据合并；只能重开一轮新实验。
- 报告同时给出：每臂原始恢复次数、两臂都恢复 / 只 treatment 恢复 / 只 control 恢复 /
  都没恢复的四格计数。

### 5.4 离线 fixture 与断言

| ID | fixture | 断言 | control 上应红？ |
|---|---|---|---|
| C1 | 0 命中 | 整条 message 与模板完全相等（路径 / 序号 / 下一步） | 是 |
| C2 | 3 命中 | 整条 message 相等，命中行号精确为 `12、47、88` | 是 |
| C3 | 25 命中 | 只列前 20 个 + `…（共 25 处）`，总长 ≤ 400 | 是 |
| C4 | CAS 冲突（直接构造过期 revision） | 整条 message 相等，含路径与下一步 | 是 |
| C5 | `vault_read` offset 越界 | 整条 message 相等，含 `1–{total}` | 是 |
| C6 | `vault_list` 非目录 | 整条 message 相等 | 是 |
| C7 | 静态对账 | 「有下一步模板的 code 集合」==「工具实际产出的 code 集合」（双向）；新增 code 未登记即失败 | 静态对账元判据（两版同跑，不要求红绿方向） |
| C8 | 信封不变 | 失败结果恰好含 `ok` / `code` / `message` 三键，无新增必填字段 | 否（identity 守门，两版均绿） |
| C9 | 无正文回显 | message 不包含文件正文片段；长度 ≤ 400 | 否（identity 守门，两版均绿） |

**红绿分类（与 spec delta「离线机器判据」同一口径）**：

- **候选行为断言·收益侧**（C1–C6）：先在 control 上红（control 的 message 不含下一步与命中行号），
  再在 treatment 上绿；红侧读数必须留存。
- **identity / 守门断言**（C8、C9）：在 control 与 treatment 上**均须绿**，不要求红侧证据。
- **静态对账元判据**（C7）：两版以同一份模板表与实现集合运行，记录双向比对输出；失败即判实现
  不完整或表已过期，判据无效、实验不得开跑。它不针对单个实现版本，MUST NOT 要求红 / 绿方向，
  也 MUST NOT 被并入前两类。

### 5.5 真实 provider 任务族、指标与判据

| ID | 族 | 任务形态 | 验证器 |
|---|---|---|---|
| C-S1 | 零命中（自然） | 提问里引用一个「看起来一样」的字符串（全角 / 半角差异），模型若照抄就 0 命中 | 文件最终内容 |
| C-S2 | 多命中 | 文档里有 3 处相同的短串，任务只改其中一处、用上下文描述目标 | 文件最终内容 |
| C-S3 | 冲突 | **本轮只做离线单元**；真实实验需要 `read_only` 档 + 批准窗内外部改写 + 人工批准，归真机 runbook | 单元级 revision 断言 |
| C-R1 | 留出真实 | 真实笔记副本上的改写任务（可能不失败） | 案例序列，不做统计 |

**主指标（预先写死）**：在 §5.3 定义的**有效配对**（两臂都出现目标错误）上计算第二次调用
成功率的净增益 `G = Σ(T_i − C_i)`（`T_i` / `C_i` ∈ {0,1}），同时给出四格计数。`no-error`
与 `instance-not-triggered` 配对按 §5.3 排除并单列。**守门**：总调用数比值 ≤ 1.10×、
token 比值 ≤ 1.10×（比值口径见 §6.4）、人工介入次数不增加。

**采纳阈值（提案值）**：

1. 离线断言按各自口径通过：候选行为断言（C1–C6）红侧有读数、treatment 绿；identity / 守门
   （C8、C9）两版均绿；静态对账元判据（C7）两版同跑且比对通过；
2. 合成族在有效配对上的净增益 `G ≥ 2`（转成功 ≥ 4 次、反转 ≤ 2 次）；有效配对为空或
   某族 `instance-not-triggered` > 40% 时该族 `undecided`；
3. 总调用数比值 ≤ 1.10× 且 token 比值 ≤ 1.10×，人工介入次数不增加；
4. 结论记录必须写明「合成证据」；真实世界失败样本只有 3/63，不足以单独支撑采纳。**是否接受
   合成证据作为采纳依据，是节点 1 的裁决点**（见 §9 第 5 项）。

### 5.6 风险与反例

- **回执变长**：每条错误多几十到一百多字符。守门指标是总调用数与总 token（同一阈值 1.10×），
  单条上限 400 字符防止失控。
- **假设模型会读**：回执写了下一步，模型可能仍然直接重试。指标测「第二次调用成功率」而不是
  「模型是否照做」，避免把「听话」当成收益。
- **行号是失败时刻的快照**：文件可能在模型重试前再次变化；回执不承诺行号永久有效，只给
  「当时命中在哪」。
- **`document_conflict` 的可见性**：自动放行档基本不触发（见 §1.4 第 4 条）；不要用真实实验的
  零触发反推「冲突不存在」。
- **文案风格与 i18n**：这些 message 进模型上下文与工具行摘要，不进 UI 文案表；保持中文与现有
  工具错误一致。前端只显示摘要，不解析 message。

## 6. 预注册实验矩阵（三项共用协议）

### 6.1 任务族与素材

| 类别 | 来源 | 是否入库 | 用途 |
|---|---|---|---|
| 合成任务（S） | 提交入库的合成 vault / 合成长输出 fixture | 是（无真实内容） | 可重复、机器验证 |
| 留出真实任务（R） | 从真实笔记结构改写的任务，在 `.local/` 的副本上跑 | 否 | 检验合成结论的外部效度 |

合成任务与留出真实任务在判据里**分开报告**，不合并成一个成功率；留出真实任务不参与描述与
参数调优。

### 6.2 模型与 provider

| 项 | 值 |
|---|---|
| 主 provider | DeepSeek（现役 `deepseek/deepseek-flash`） |
| 确认 provider | Kimi（`kimi/k3.1-pro`；如实验期主模型别名变化，记录实际模型 id） |
| 每个 run | 全新会话（fresh session）；不继承历史、不共享批准缓存 |
| 模型配置 | 两臂完全相同；思考档位、温度类参数按当前配置固定，记录实际值 |
| 版本记录 | app commit、provider、模型 id、实验日期、OS |

### 6.3 A/B 交错与盲法

- 每个任务实例跑两次（control / treatment），顺序由预生成随机序列决定；同一实例的两臂不并行，
  避免机器负载与时间漂移混入。
- 合成任务由代码验证器判定；留出真实任务由盲评（评审者看不到臂标签）按预写量规判二元结果。
- 任务表述的生成有一道静态检查：不得出现被测参数名、取值、`context` / `头尾` / `省略` /
  `下一步` / `修复建议` 等提示词。
- 两臂的工具描述差异就是干预本身；除描述外，系统提示词、工具集、权限模式、`loop_max` 完全一致。

### 6.4 指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| 任务成功率 | 验证器 / 盲评的二元结果 | 守门与主判据（候选 B / C） |
| 总工具调用数 | 一次 run 内全部 `tool_calls` 计数 | 成本 |
| 总 token | 主回合内每次请求的 `input_tokens + output_tokens` 求和（`cached_tokens` 是 input 的子集，不重复加）；`usage` 缺失的请求记为缺失、不估算，缺失请求占比 > 10% 时该指标不参与判据 | 成本 |
| 截断后追加调用 | 首次出现 `truncated:true` 之后的工具调用数 | B / A 的直接成本 |
| 人工介入次数 | 首条用户消息之后的任何用户消息数；批准动作单列 | 可用性 |
| 错误码分布 | 各 `code` 频次 | 诊断 |
| 第二次调用成功率 | 错误后 3 次调用内同工具成功重试 | C 主判据 |
| `context` 使用率 | 语境依赖任务中 `context>0` 的 run 比例 | A 的诊断 / 死旋钮判据 |
| 尾部事实可见率 | 离线：决定性词是否落在可见切片内 | B 的离线判据 |

**计算口径（预先写死，避免事后解释）**：

- **配对单位**：同一任务实例的 control run 与 treatment run 构成一个配对；所有配对统计只在该
  配对集合上算，不把两臂拆成两个独立样本再比均值。
- **差值型指标**（候选 A 的追加读次数）：`d_i = T_i − C_i`；报告 `median(d)`、负 / 零 / 正配对
  计数与配对 bootstrap 95% 区间（重采样单位 = 配对，10,000 次，固定种子）。不使用比值，因此
  没有 `0/0` 或除零；两臂都为 0 的配对按 `d=0` 进入样本。
- **比值型指标**（token、总调用数）：`ratio = median(T) / median(C)`。分母 `median(C) = 0` 时
  MUST NOT 计算除法：若 `median(T) = 0` 记 `1.00`（不劣），若 `median(T) > 0` 判该守门不通过；
  禁止产生 `NaN` / `∞`，也禁止静默丢掉分母为 0 的配对。`median(C) > 0` 时按通常比值，并给
  配对 bootstrap 区间。
- **成功率**：每臂报告成功数 / 有效配对数与 Wilson 95% 区间；配对报告净增益与四格计数
  （都成功 / 只 T 成功 / 只 C 成功 / 都失败），MUST NOT 把四格压成单一成功率。
- **缺失与排除**：`usage` 缺失率 > 10% 时 token 不参与判据；provider 错误 / 超时 / 崩溃按
  §6.5 排除并记录；任何排除都不得只对一臂做。

### 6.5 样本量与序贯计划

单用户、双 provider 的现实下，本设计**不是确证性随机对照试验（randomized controlled trial，
RCT）**：N=20 的成功率区间仍会很宽，不能把「不显著」解释成「无效」。因此判据按「效应量 +
一致性」设计，并显式允许 `undecided`。

| 阶段 | 内容 | 规模 | 规则 |
|---|---|---|---|
| Tier 1（筛查） | 主任务族，DeepSeek | 8 对（每臂 8 run，共 16 run） | 只在「方向相反或无任何成本信号」时停止并记 `reject` 或 `undecided`；不得在 Tier 1 采纳 |
| Tier 2（确认） | 主任务族 + 守门族，DeepSeek | 主族 20 对（40 run）；守门族 10 对（20 run） | 按 §6.6 判据裁决 |
| Kimi 确认 | 主任务族 | 12 对（24 run） | 只在 DeepSeek 达到采纳阈值后跑；方向一致才采纳 |

- **只允许一次中期分析**（Tier 1 结束）；不得边跑边改判据。
- 实际有效配对少于计划值（协议偏离、provider 错误、崩溃）时，结论为 `undecided`，写明缺口。
- 排除规则预先声明：provider 错误 / 超时 / app 崩溃可排除并记录；同一 run 内出现协议未定义
  的人工介入，按 `intervention` 记录但不排除（它就是指标）。
- 报告：每臂成功率 + Wilson 95% 区间；配对不一致表（treatment 成功 / control 失败的对数 vs
  反向对数）；成本中位数 + bootstrap 95% 区间（10,000 次重采样，固定种子）。

### 6.6 三项判据（汇总）

| 候选 | 主判据 | 守门 / 反例 | 采纳条件 |
|---|---|---|---|
| A | 配对差 `median(d) ≤ −1`、负向对 ≥2× 正向对、配对 bootstrap 上界 <0 | 成功率不劣（20 对里失败差 ≤2 对）；枚举族 token 比值 ≤1.10×；`context` 使用率 ≥50%；机会不足（control 中位读数为 0）判 `undecided` | 离线按各自口径通过 + 主判据 + 守门 + DeepSeek 达标 + Kimi 方向一致（`median(d) ≤ −1`、负向 ≥ 正向） |
| B | 尾部任务净增益 `G ≥3` 且反向 ≤1（离线可见率只作辅助，不能单独采纳） | 中段 `G_mid ≥ −1`；token 比值 ≤1.10× | 离线按各自口径通过（B9/B10a 两版绿；B10b 收益侧红→绿；B10c 代价侧红→绿）+ 主判据 + 守门 + Kimi 方向一致（`G ≥1`、`G_mid ≥0`） |
| C | 有效配对的第二次调用成功率净增益 `G ≥2`（转成功 ≥4、反转 ≤2） | 总调用比值 ≤1.10× **且** token 比值 ≤1.10×；人工介入不增加；`instance-not-triggered` >40% 判 `undecided` | 离线按各自口径通过（C1–C6 红→绿；C8/C9 两版绿；C7 元判据两版同跑）+ 主判据 + 守门 + Alex 接受「合成证据」的限制 |

任一项未达阈值：记 `reject` 或 `undecided`（按原因），并写出可重启条件（例如「换更小的
context 上限后重跑」「换更窄的任务族后重跑」）。**不得用「趋势向好」替代达标。**

### 6.7 环境隔离与不可变项

- 独立 `XDG_CONFIG_HOME`（不碰用户真实配置）、合成 vault（`/tmp` 或 `.local/experiments/` 下）、
  独立端口（若起 app）；实验期间不做其他重负载工作。
- 需要写盘的合成任务使用 vault 工具（默认档自动放行）；CLI 长输出 fixture 尽量使用只读白名单
  命令；确需执行合成脚本时，两臂使用同一权限模式并记录。
- 不可变项：模型配置、系统提示词（除被测工具描述）、`loop_max`、工具集、权限模式、fixture
  内容、任务表述、验证器。改动任何一项 = 新实验，不能与旧数据合并。

### 6.8 不得按工具序列判定

成功率必须由验证器或盲评给出。工具序列只用于成本与诊断指标；「模型按预期顺序调用了工具」
不等于任务成功（REVIEW.md「断言等价于子串，没有区分度」的同族风险：把过程当结果）。

### 6.9 协议偏离

任何偏离（改了判据、补跑了失败的臂、换模型、换 fixture）都记入偏离清单，并在报告中单独列出；
偏离后的数据不得与未偏离数据合并成同一结论。若偏离影响到主判据，整个候选重跑。

## 7. 离线判据与「暂缓期能完成什么」

### 7.1 工作分层

| 工作 | 现在可做 | 需要实现 | 需要 provider | 需要真机 |
|---|---|---|---|---|
| 制品、判据、矩阵（本 change） | 是 | 否 | 否 | 否 |
| 回顾性聚合（§7.2） | 是（本地只读、只出聚合） | 否 | 否 | 否 |
| 单元级形状 fixture（A1–A12 / B1–B11 / C1–C9） | 否（要改测试与实现） | 是（实验分支） | 否 | 否 |
| mock provider 端到端链路 | 否 | 是（实验分支） | 否 | 否 |
| 真实 provider 的 A/B 实验 | 否 | 是（实验分支） | 是 | 否 |
| `document_conflict` 批准窗实验 | 否 | 是（实验分支） | 是 | 是 |
| 「原始超长里有什么」 | **永远不可做**（数据未留存） | — | — | — |

### 7.2 现在就能做的三项回顾性聚合（本地只读、只出计数）

这三项不构成收益证据，只用于估计机会规模；全部在 `.local/` 产出聚合读数，不复制正文：

1. **搜索后的追加读**：每次 `vault_search` 之后的下一次工具调用是否是同一路径的 `vault_read`？
   offset 与命中行的距离分布如何？（只记计数与行号差，不记内容）
2. **截断结果的形状**：37 份截断结果中，stdout / stderr 各自是否触顶？`exit_code` 是否为非零？
   文本是否以 `{` / `[` 开头（结构化输出被截断）？（只记形状）
3. **patch 失败案例序列**：3 次失败之后 3 次调用分别是什么、是否重试成功？（案例序列，不做统计）

这三项能回答「候选 A 的追加读有多常见」「候选 B 的尾部损失可能有多大面」「候选 C 的真实
失败有多稀有」，但不能回答「改动后会不会更好」。

### 7.3 暂缓期不得下的结论

- 不得说「头尾保留一定更好」——只能说合成 fixture 上尾部事实的可见性；模型收益未验证。
- 不得说「上下文能减少读文件」——只能说工具返回了上下文；追加读是否下降未验证。
- 不得说「错误回执能提高恢复率」——没有第二次调用数据前，只能说文案包含下一步。
- 不得用 37 份截断结果反推原始长度、被丢内容或尾部是否有错误。
- 不得把离线判据全绿写成「候选有效」；它只证明形状合同成立。
- 不得把三项的实验数据互相借用（A 的成本数据不能推断 C）。
