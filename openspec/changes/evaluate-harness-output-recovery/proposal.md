# Proposal: 评估 harness 输出预算与错误恢复的三项候选（离线判据 + 预注册实验）

- Change ID: `evaluate-harness-output-recovery`
- 日期: 2026-10-29
- 角色: Alex Lee（评审 / 裁决），AI agent（起草）

> **性质声明**：本 change 只产出实验提案、离线判据与预注册矩阵。它 MUST NOT 改产品代码、
> MUST NOT 发起真实 provider 请求、MUST NOT 做真机验证。三项候选各自独立裁决，本提案
> **不预设任何一项应上线**；三项全部被拒绝是一个合法且可接受的结果。

## Why

### 现场：真实会话里的三条浪费路径

2026-10-29 的会话聚合（只读、本地、聚合口径）给出三组读数：

| 事实 | 读数 | 含义 |
|---|---|---|
| `cli_run` 结果总量 | 230 份；中位 648 字符，193 份未截断，37 份截断 | 大多数输出很短；截断是少数但真实发生 |
| 截断后的原始超长 | **未留存**（截断发生在落盘之前） | 「被丢掉的是什么」无法事后反推——这是本提案最重要的一条限制 |
| `vault_search` | 70 次调用（占工具调用 12.2%），0 次失败；片段上限 200 字符、无上下文行 | 命中行之后的语境只能靠追加 `vault_read` 补 |
| `vault_patch` | 63 次调用，3 次失败（4.8%）；失败回执只报「第 N 处编辑命中 M 次」 | 内部已有的路径 / 序号 / 次数参数不随工具信封回送模型 |

这三组读数对应三条可验证的浪费路径：搜索缺语境 → 追加读；命令行输出只留头 → 尾部结论或
错误丢失；错误回执只描述现状 → 模型多走一步或猜错。三条都不是「工具不好用」的泛泛判断，
而是可以在同一组任务上量出差异的具体机制。

### 外部机制证据

同期完成的外部一手调研（Claude Code、OpenAI Codex CLI、Gemini CLI 三家的官方文档、第一方源码与
变更记录，2026-10-29 实际抓取；报告在 `.local/reports/harness-tool-principles-oct29/external-research.md`）
给出四条与本次三项候选对应的机制事实：

- 输出预算是显式合同，不是实现细节：三家都设上限、都显式标注截断，且都附「怎么继续读」的指引；
  没有一家静默截断。
- **中间截断是真实存在的另一种选择**：Claude Code 的 Bash 输出采用中间截断（保留头尾），而
  Lumir 的 `cli_run` 只留头部——CLI 的失败摘要、测试结论与错误堆栈常在尾部。
- **搜索上下文是常见旋钮**：Gemini 的 `grep_search` 提供 `context` / `after` / `before`
  （等价 `grep -C/-A/-B`），并给总条数与单文件条数两个独立上限。
- **错误回执要写「下一步」**：Anthropic 的官方工具设计文章要求错误消息本身承担引导职责，
  并给出「错误码 → 可执行下一步」的对照表；Gemini 把续读指令直接写进截断文本。

外部证据只支持「这些机制值得试」，不支持「照抄就对」。三家都是 coding harness，Lumir 是
个人知识库（Personal Knowledge Management，PKM）文本工作台，任务分布不同；能迁移的是机制与
判据，不是参数值。

### 为什么现在只做实验提案

- 真实 provider 与真机窗口当前不可用，且本阶段的硬约束就是不允许发起真实请求。
- 三项改动的收益都是**模型行为**问题：离线只能证明「结果形状的合同成立」，不能证明
  「模型因此少走了几步」。先锁定判据再跑数据，避免跑完再解释、也避免把方向性观察当成结论。
- 三项候选之间存在可能的交互（例如「截断处给下一步」同时出现在搜索与命令行两条路径上），
  只有把每项做成独立对照，才能分别归因。

## What Changes

1. **新增 capability `harness-tool-evaluation`**：把「候选独立裁决、离线判据、真实 provider
   预注册、证据与结论边界」写成方法论要求。本 change 不实现任何候选行为。
2. **候选 A —— `vault_search` 的可选上下文行**：新增可选参数 `context`（缺省 0，对称前后行，
   上限 5）。`context > 0` 时返回按文件合并的上下文块：每行带绝对行号，相邻或重叠的窗口合并
   去重；总预算 12,000 字符 / 400 行，超限显式标 `truncated` 并给下一步。`context = 0` 时输出
   与现状逐字段同形（同一组 `matches` 与 `truncated`，不新增字段）。
3. **候选 B —— `cli_run` 每流的头尾保留**：每流预算维持 10,000 字符，改为头 5,000 + 尾 5,000，
   中间以 `…[省略 N 字符]…` 标注（N 为精确省略量）；短输出逐字节不变；stdout 与 stderr 各自
   独立计算。
4. **候选 C —— 错误回执带可行动的下一步**：`vault_patch` / `vault_read` / `vault_list` 中
   当前「只描述现状」的 5 类错误码，回执补下一步与可执行数据（命中行号、总行数、目标路径）。
   `code` 与结果信封不变，不新增必填字段。
5. **预注册实验矩阵与判据**：合成任务 + 留出真实任务；DeepSeek 为主、Kimi 作确认；全新会话
   （fresh session）；A/B 交错（同一任务分别跑现状与改动，顺序随机）；任务表述不点名被测参数；
   指标含成功率、总调用数、总 token、截断后追加调用、人工介入次数。判据用「成本类主指标 +
   成功率守门」，不以工具序列或统计显著性单独判定。

### 三项候选一览（独立裁决单元）

| 候选 | 现状 | 候选改动 | 预期收益路径 | 可能的损失 |
|---|---|---|---|---|
| A 搜索上下文 | 只有命中行 + 200 字符片段 | `context` 0–5，块状结果、合并去重、总预算 | 少追加 `vault_read`；命中语境可直接判断 | 枚举型任务被诱导入大上下文，token 上升 |
| B 头尾保留 | 每流 10k 字符只留头 | 头 5k + 尾 5k + 精确省略量 | 保住尾部错误 / 结论；与 `task` 摘要的头尾口径一致 | 丢掉原先可见的中段（5k–10k） |
| C 错误下一步 | 只报「命中 N 次」等现状 | 回执补下一步 + 命中行号 / 总行数 | 第二次调用成功率上升；少一次试错 | 回执变长；可能鼓励模型照抄建议而不核对 |

三项互不依赖：可以只采纳 B、拒绝 A 与 C；也不存在「一起上线才成立」的组合。

## Non-goals

- 不实现任何候选：不改 `src-tauri/`、不改工具 schema、不改权限、不改截断预算。
- 不发起真实 provider 请求，不做真机验证，不读取或复制真实凭据。
- 不把 `vault_search` 改成正则、不改 50 条命中上限、不改 200 字符片段上限。
- 不为 `cli_run` 增加分页、会话续读、PTY 或结构化输出解析。
- 不改 `task` 的摘要预算（只在统一中间截断实现时同步标记文案，见 design §4.2；该子项可单独回退）。
- 不新增工具、不改 ADR 0007 的工具清单裁决、不重开 `vault_list` 的取舍。
- 不以本提案替代节点 2；本 change 的制品不进入 living spec 的 `harness` capability。

## 影响面

- **spec**：新增 `harness-tool-evaluation`（4 条 ADDED requirement）；不修改任何既有 capability 的
  requirement，因此没有 MODIFIED 整块替换的丢段风险。
- **代码**：本 change 无。实现阶段预计触及 `src-tauri/src/harness/tools.rs`（搜索、`cli_run`、
  错误回执、共享截断 helper）与 `src-tauri/src/fs_io.rs` 中 `fs_patch_file` 的错误文案；不触及
  前端、不改 ts-rs 导出面、不改视觉。
- **证据**：审阅包落主仓 `.local/reviews/harness-output-recovery-oct29/`（git 外）；后续实验
  原始记录落 `.local/experiments/harness-output-recovery-oct29/`；仓库内只留合成 fixture 与聚合读数。
- **验收**：本 change 的验收是制品层——`validate --all --strict`、`docs-check` 与审阅包可开；
  没有真机场景、没有门禁档位变化（不产生行为变更）。

## 需要 Alex 在节点 1 裁决的事项

以下是「取值本身就是产品判断」的参数与阈值。每一项都在 design 里给了提案值与理由；Alex 可以
只改数值、不重开方案结构。

| # | 事项 | 提案取值 | 为什么需要裁决 |
|---|---|---|---|
| 1 | 搜索上下文的参数上限 | 每侧 0–5 行 | 上限越大，块越大、token 越多；上限太小则语境不够 |
| 2 | 搜索上下文的总预算 | 12,000 字符 / 400 行 | 是「一次搜索能占多少上下文」的产品判断，与 `cli_run` 单流 10k 同量级 |
| 3 | 搜索结果在 `context > 0` 时的形状 | 块状（`blocks`）而非逐命中 | 为了重叠去重必须成块；是否接受两种形状由 `context` 取值切换 |
| 4 | `cli_run` 头尾切分 | 5,000 + 5,000，预算不变 | 切分比例决定「尾部保多少」与「中段丢多少」的平衡 |
| 5 | 候选 C 的采纳证据 | 接受「合成任务 + 3 例真实案例」 | 真实失败只有 3/63；不接受则可能长期无结论 |
| 6 | 错误回执的范围 | 5 类码、仅改 `message` | 决定改动面：是否只做 harness 侧、是否接受 prose 引导 |
| 7 | 命中行号枚举上限 | 前 20 处 | 影响回执长度与「多命中」场景的可操作性 |
| 8 | 实验样本量与阈值 | 见 design §6.5 / §6.6 | 决定实验成本与「多大算有效」；单用户场景下样本永远不构成确证性随机对照试验（randomized controlled trial，RCT） |
| 9 | 「三项全部拒绝」是否可接受 | 是 | 明确不预设成功；拒绝需记录可重启条件 |

## 结论口径（写给后续所有读者）

- 本提案成功与否，不看三项是否上线，而看**判据是否足以让「采纳 / 拒绝」都不靠事后解释**。
- 任一项的结论只有三种：`adopt`（达到预注册采纳阈值）、`reject`（达到拒绝阈值或方向相反）、
  `undecided`（样本不足 / 证据缺口）。第三种 MUST NOT 被写成前两种。
- 离线判据全绿只写「形状合同成立」；收益类断言一律等真实 provider 数据，未跑之前写「未验证」。
