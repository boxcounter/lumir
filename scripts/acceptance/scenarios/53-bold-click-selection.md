# 点击粗体不产生幻影选区（M259）

Alex 原话：「点击 markdown 文本中的粗体后，容易选中部份，如 Image 4（我猜测这是因为粗体会进入
编辑阶段，会瞬间出现额外的文字（出现额外星号 `*` 字符））。」截图现场：点击 **pnpm** 后字母 p 被选中。

## 这个场景验什么

**缺陷机理**（chromium 层已实证，见 `tests/visual/scenes/m259-bold-click-selection.spec.ts`）：显露一落地
就改变布局——被隐藏的 `**` 重新占宽（chromium ≈12px；WKWebView 真机同几何实测 **14 截图像素** = 1.82 个
字符宽，量法见下文「显露态点击为什么要多走一格」）。CM 的鼠标选区在**按下**时按渲染态布局算一次落点，
之后每次指针移动又按**当时的布局**重算一次（`basicMouseSelection.get` 比对 `start.pos` / `cur.pos`）；
两次之间布局位移，同一屏幕坐标便映射到靠前 1–2 个字符的位置，两个落点被当成一次拖拽 ⇒ 选中 1–2 个字符。
12px 位移下这不是偶发：指针抖动 1px 就足以跨过字符边界。

**修法**（M259）：按压期间把显露判定用的选区冻成「按下瞬间的快照」，布局因此从按下到抬起不动、
落点判定自始至终在同一份布局里做；抬起后解冻，显露照常跟随（只是推到 `mouseup` 落地）。实现见
`src/preview/reveal-gate.ts`。

**判据链条**（用「键入见证字符后读落盘文件」把「有没有选区」变成可读事实）。fixture 的粗体行是
20 个小写字母：见证字符 `0` 必须落在**点击坐标对应的那个位置**（`e` 与 `f` 之间），落盘形态因此是

| 情形 | 见证字符的后果 | 粗体行前缀 | 本场景的断言 |
|---|---|---|---|
| 无选区（正确） | 插入 | `**abcde0f…` | `/^\*\*abcde0/` 通过 |
| 原生抖动语义的 1 字符选区（正确） | 替换掉 `f` | `**abcde0…` | 同上（两种都算落点正确） |
| 布局位移把落点前移（缺陷） | 落在 `e` 上 | `**abcd0f…` | `/^\*\*abcd0/` 判红 |

**为什么判「落点位置」而不是「有没有选区」**：CM 的鼠标选区取「落点最近边界」语义——指针在按下与
抬起之间移动 1px，若跨过某个字符的中线就会选中那一个字符。这与布局位移无关，是点击抖动的原生后果
（同一支探针在**无强调范围的普通文本**上同样消费 1 个字符）。所以「零选区」在带抖动的通道上不是一个
可判的期望值；可判的是**落点**：布局不动时，见证字符必然落在点击坐标对应的位置；布局动了（缺陷），
同一坐标被映射到靠前 1 个字符的位置，见证字符就前移一格。

**修前修后实测**（同一场景、同一坐标，真机 WKWebView，1440 端口隔离）：

| src | 结果 | 落点读数 |
|---|---|---|
| master（修前） | **FAIL** | `**abcd0fghijklmnopqrst**` —— 前移 1 个字符 |
| 本分支（修后） | **PASS** | `**abcde0ghijklmnopqrst**` —— 点击坐标处 |

证据（git 外）：`test-results/m259/53-before-fix/`、`test-results/m259/53-after-fix/`（两轮的
ax/steps/shots 全量）与同目录两份 run.log。**第一版判据（字符位数）修前也 PASS——那是一条假绿**：
WKWebView 里 `**` 的显宽与粗体回退的净位移只相当于 1 个字符（chromium 上是 2 个），位数落不出
区分度；改用 1 个字符分辨率的落点判据才有区分度（REVIEW.md 第 1 条）。

## 判据走哪几条通道

| 要判的东西 | 通道 | 为什么不是别的 |
|---|---|---|
| 有没有选区 | **键入见证字符后读落盘文件**（长度形态） | 套件读不到选区（README「已知边界」：AX 读不到选区）。落盘文件是唯一能区分「插入」与「替换」的可读事实 |
| 落点是否进了粗体范围 | **编辑器的 AX 文本里出现 `**`** | 显露出源码是「光标落在范围内」的直接后果（M168）。没进范围这条会红——避免后面的断言在空转 |
| 按压是否改文档 | **文件 sha256 + mtime 双比** | 装饰层 MUST NOT 改写文档（ADR 0003 §3） |
| 布局是否真的动了 | 不在本场景（真机读不到坐标） | 归 chromium：`tests/visual/scenes/m259-bold-click-selection.spec.ts` 断言同坐标映射在按下前后逐值不变 |

## 为什么既有 `drag {dx: 1}` 也有 `clickEditor`

两条都在，缺一不可：

- **`drag {dx: 1}`**：缺陷**只在按压期间发生指针移动时**才出现（没有移动 ⇒ CM 不会重算落点 ⇒ 无幻影），
  而套件的 `click` / `clickEditor` 发不出「按住期间的 mousemove」。`drag` 是套件里唯一能在按住期间注入
  移动的动作（CGEvent `leftMouseDown → 插值 dragged ×N → leftMouseUp`，M228 起的通道）；`dx: 1` 是
  点击抖动量级（真机指针按下时的自然位移），不是拖拽。这一步是**缺陷的复现路径**。
- **`clickEditor`**：Alex 报告的是「点击」，不带抖动的单击是它的干净形态。这一步验**无位移 ⇒ 无选区**
  （`clickEditor` 不注入按压期间的移动）——它是缺陷的**用户形态**，也是「零选区」这条更窄的断言唯一能成立的地方。

## 落点的来历（锚在编辑器 bbox 上，不是窗口局部常数）

坐标的载体换了两次，两次都是为了**不把落点写成窗口局部常数**：

| 步 | 载体 | 为什么 |
|---|---|---|
| `drag`（复现路径） | `{role: AXTextArea, dx0: 0.1184, dy0: 0.097}` | 节点形态的落点 = **编辑器正文盒**（AXTextArea 的 bbox，即 `.cm-content` 的 border box）按比例取点。窗口变宽时正文列居中平移，落点跟着平移 ⇒ 第 3 行仍是第 3 行、同一字符位仍是同一字符位 |
| `clickEditor`（用户形态） | `dx: 110, dy: 60` | 同上口径的**像素**形态（`execute.mjs` 的 clickEditor = AXTextArea 的 bbox 左上角 + dx/dy，走 full 快照的截图像素空间）。改用它是为了修掉一条**坐标空间串味**：`click {x,y}` 的 x/y 是**截图像素**，而 `drag {x,y}` 的 x/y 是**窗口局部点**，同一组数字在两处指向不同物理点（截图是窗口按 768/窗高 等比缩放的，两个空间的换算系数随窗口高度变）。原来的 `click {x:430,y:200}` 因此和 `drag {x:430,y:200}` 从来不是「同一处」——2026-10-13 那轮它实际落在粗体行、drag 落在空白行，看起来像两条独立缺陷。**dx 与 drag 取「同一个像素」并不等于落在「同一个字符位」**，来历见下节 |

### 显露态点击为什么要多走一格（dx 80 → 110）

`drag` 与 `clickEditor` 取的是同一个像素，**不是同一个字符位**：drag 的落点在**渲染态**布局里算（按下那一刻
`**` 还没占宽），clickEditor 点下去时 `**` 已显露、整行文本右移——同一像素因此映射到**靠前约 1.8 个字符**的
位置。master tip 实测签名 `**abc9de0f…`（`9` 落在 c/d 之间）就是这条映射的产物。

位移量是量出来的，不是估的：把同一次运行里的 `02-渲染态起点` 与 `03-点击后` 两张截图在粗体行行带上做
互相关（同一窗口、同一几何），对齐偏移 = **14 截图像素**；同一把尺子量**逐字节未变**的普通文本行读到 0，
说明尺子本身没偏。粗体行墨迹宽 154px / 20 个字符 ⇒ 单字符宽 ≈ 7.7px，14px = 1.82 个字符宽。
（读数现场：`test-results/acceptance/2026-10-13-m495-bisect/53-bold-click-selection/shots/` 的
`02-渲染态起点.jpeg` 与 `03-点击后.jpeg`；Δ 与单字符宽都是**字体相对量**，换窗口缩放时按比例一起变，
所以这组比值可以跨轮次用。）

补足这 14px 只把落点**还原到 drag 那一格**——而那一格里已经躺着见证字符 `0`（drag 的落点插入的）。要让 `9` 落在
`0` **之后**，落点必须越过 `0` 那一格，并留半格余量、避开再次卡在边界上被判红。

**这一步的量靠实测锚点定，不靠模型外推。** M496 按「显露位移 14 + 一格 7.7 ≈ 22」把 dx 定为 102；但真机复跑
（2026-10-13，`test-results/acceptance/2026-10-13/53-bold-click-selection/`）末步仍红、落盘
`**abcde90fghijklmnopqrst**`——`9` 插在 `0` **之前**，落点仍卡在 `0` 那一格的左侧（e|0 边界），`/^\*\*abcde0/` 红。
即 102 欠的量「**不到一格**」（模型外推偏乐观：像素 → 字符位的换算里，drag 那格的实际落点比模型估的偏左）。
以这次实测落点为准向右再推、并留半格余量：

| 项 | 值（截图像素 / 字符宽） | 来历 |
|---|---|---|
| 单字符宽 | ≈7.7 | 粗体行墨迹 154px / 20 字符（字体相对量，随窗口缩放按比例变） |
| 显露位移 Δ | ≈14 | `02`/`03` 两图粗体行互相关 = 1.82 个字符宽 |
| dx=102 的实测落点 | 卡在 `0` 那格左侧（e\|0 边界） | 复跑签名 `**abcde90f…`，`9` 插到 `0` 前，欠不到一格 |
| 目标落点 | `0` 右缘 + 半格 | `0` 那一格被上一步插入的字符占住，须越过它；半格余量避免再卡边界 |
| bump | ≈ +1 格 ≈ +8px | 从实测落点向右推一格 |
| `dx` | 80 → **110** | 102 + 8 |

「同像素 ≠ 同字符位」这条纪律对 clickEditor 是**特有**的一步：drag 的落点是渲染态坐标、clickEditor 的落点是
显露态坐标，两者只在「布局没有位移」时才重合。代价是写死的像素值绑死了当轮的单字符宽——见下面的失效条件。

标定读数（2026-10-13 真机，窗口 1152×864，`test-results/acceptance/2026-10-13/53-bold-click-selection/`）：
编辑器正文盒 = `@314,151 760×688`（window-local 点，`ax/03-*` 的 mode=ax 快照）；
正文首行文字左缘 ≈ x=357.8（截图 `shots/02-渲染态起点.jpeg`，1024×768 = 0.889 缩放）；
单字符宽 ≈ 7.4–8.1（由「同一 x 落到的字符下标」反推：2026-10-08 那轮 x=430 落到第 6 个字符位、
2026-10-13 那轮 x=430 落到第 15 个字符位，两者的编辑器左缘差 23.5 = 窗口宽差的一半）。
于是：

- `dx0 = (404 − 314) / 760 = 0.1184`，x = 314 + 0.1184×760 = **404**（= 文字左缘 + 约 46 = 第 6 个
  字符位；判据要求落在 `e` 与 `f` 之间，即文字左缘 + 5.5..6.5 个字符宽 = 398..410，取中点附近）。
- `dy0 = 68 / 688 = 0.097`，y = 151 + 0.097×688 ≈ **218**（第 3 行行盒；第 3 行 = 正文盒顶 + 两行
  行高。行高在证据里只能夹在 25.5（M399 判决书的读数）与 29.25（截图里两行基线的间距）之间，
  y=218 同时落在两个行高模型算出的第 3 行里，取交集 [210, 227] 的中段）。

**这组数字什么时候失效**（判据链的生死线，不是措辞偏好）：

- **行几何一变即失效**（含空白行行高）：M399 让空段落占一条真行高；此后任何改动「第 3 行相对
  正文盒顶的偏移」的变更（行高、段距、空行规则、字号）都会让 dy0 指到别的行。dy0 是**正文盒高度的
  比例**，不是行号——窗口高度变化时它会跟着漂：编辑器高度 ∈ [566, 845]（窗高 742–1021）以内
  仍在第 3 行，出界就落到第 2/4 行。
- **正文字宽一变即失效**：dx0 的锚点是正文盒的左缘，前提是「文字从正文盒左缘内约 44px 处起排」
  且正文列宽为 760（默认 `content_width`，窗口宽 ≥ 约 1050 时成立）。列宽或左内边距一变，
  同一 dx0 落到别的字符位。
- **字体大小一变即失效**：字号改单字符宽，第 6 个字符位的像素位置随之变（drag 与 clickEditor 两条都吃这一条）。
- **clickEditor 的 `dx` 是截图像素常数，随窗口缩放失效**（drag 没有这一条——它锚的是 bbox 比例）：补偿量正比于
  **单字符宽**（dx 自 drag 像素 80 起算 ≈ 30px ≈ 3.9 个字符宽 = 显露位移 + 落点余量），而截图是窗口按 768/窗高
  等比缩放的，单字符宽随窗口变，同一个 110 的等效补偿量跟着变。110 的成立区是实测到的两档几何（1152×864 与
  1200×800，单字符宽 7.4–8.1）：窗口更小 ⇒ 等效补偿偏大，落点右移（`9` 插得更靠右，`**abcde0` 前缀照样过，
  只要没移出粗体范围）；窗口明显更大 ⇒ 偏小，落点退回 `0` 之前那一格（落盘成 `**abcde90…`）。要彻底去掉这条，
  得给 clickEditor 也换成 bbox 比例形态（`dx0`/`dy0`）——那是套件动作面（`execute.mjs`）的改动，不在本场景内。
- **drag 的落点一变即失效**：110 是从「dx=102 的实测落点 + 一格」折出来的，与 dx0 是配对的一组数；dx0 改到别的
  字符格，这一对就得一起重标。

这些失效都**当场判红、不会静默空转**：落点没进粗体范围时第一条断言（编辑器出现 `**`）就红；
进了范围但字符位错了，`/^\*\*abcde0/` 与 `/^\*\*abcd0/` 这一对把「偏 1 个字符」分辨出来
（前者过、后者不许过）——clickEditor 欠这一格时落点退回 `0` 之前，红的就是末步那条正向前缀
（`**abcde90f…` 的现场；M496 的 dx=102 就是这么红的）。

## 已知边界

- **0 与 9 两个见证字符会留在 fixture 里**（验收 vault 每次运行都从 fixtures/ 重置，且本场景的收尾断言按
  含 `0`/`9` 的形态写）。
- **不判手感**：点击后光标跳到哪一列、显露出源码的观感归 Alex，本场景只留截图证据。
- **`clickEditor` 那一步落在「已显露态」里**：`drag` 那一步之后光标已在粗体范围内，`**` 已经占宽——它验的是
  「已显露态下的无位移点击不消费字符」，与第一步（渲染态 → 按压 → 显露）互补。两条合起来覆盖
  「渲染态点击」与「显露态点击」两种起点；也正因为两条的起点布局不同，落点才不能共用一个像素
  （见正文「显露态点击为什么要多走一格」）。
- **`keys: ["0"]` / `["9"]` 走回读 + 有限重试**（README 的键盘注入纪律）：若丢键，`editor: {has: "0"}`
  那一条会红——按 REVIEW.md 第 11 条先复跑一次再判产品缺陷。
